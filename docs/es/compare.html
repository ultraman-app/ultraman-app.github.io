Comparar dos entornos #

Comparar ejecuta la misma pipeline en dos entornos y te dice, paso a paso, si responden igual: después de un despliegue, verifica que staging tenga la estructura y los datos replicados que tiene desarrollo. También puede verificar las respuestas de un entorno contra su tipo, un JSON Schema o la spec OpenAPI de la colección.

Qué responde #

Una comparación ejecuta toda la pipeline en el primer entorno y después en el segundo, cada ejecución con los valores, el login y los secretos de su propio entorno, y compara la respuesta de cada request. Una request con un bloque compare: se compara por su regla; una sin bloque, por Misma estructura, la opción por defecto: los mismos campos y tipos, los valores pueden diferir. Para cada request dice una de estas cosas:

  • igual: las dos respuestas coinciden (con body: shape, misma forma);
  • N rutas difieren: el estado, un header que nombraste o el cuerpo difieren, y dónde (el JSONPath de cada lugar);
  • no comparado, y por qué: un lado no ejecutó el paso, un lado lo falló, o la respuesta no se puede comparar.

Una request sin bloque se compara por estructura sin que se agregue nada a su archivo, y su fila lo dice ("same (by structure, the default)"). Un paso que no es una request (un extract, un assert, un wait) no tiene nada que comparar. Esto vale para una pipeline o colección que nombras; en la terminal, una selección con --all o --tag compara solo los bloques escritos (ver desde la terminal). Una request sin bloque que un lado nunca alcanzó (un if que solo un entorno toma) aparece como no comparada y por qué, pero no cambia el veredicto. Cada lado se guarda como una ejecución normal en ultraman/runs/. No se escribe nada más: ni archivo de diferencias ni línea base.

El bloque compare #

Un paso request de una pipeline, o una request de una colección, lleva el bloque junto a sus otros campos:

- request: get order
  method: GET
  path: /orders/{{order_id}}
  compare:
    body: value                      # value | shape | none; el estado siempre se compara
    only: [$.id, $.status, $.total, $.items]   # solo estos campos; sin esto, todo
    ignore: [$.updatedAt, $.meta.requestId]    # se dejan fuera, también dentro de una ruta de only
    lists:
      $.items: { match: sku }        # empareja los elementos por este campo
      $.tags: { order: any }         # los mismos elementos, en cualquier orden
    schema: files/order.schema.json  # el tipo de la respuesta, para --compare schema
    headers: [content-type]          # ninguno por defecto
    reuse: [order_id]                # ver "Pedir el mismo registro"

compare: {} compara el estado y todo el cuerpo por valor. Todas las claves son opcionales:

ClaveQué hace
bodyvalue: los datos deben ser los mismos. shape: los mismos campos con los mismos tipos, sin importar sus valores. none: solo el estado y los headers que nombres.
onlyJSONPaths. Solo se comparan estos campos; una ruta a un objeto o a una lista cubre lo que hay dentro.
shapeJSONPaths que se comparan solo por tipo, dentro de una comparación body: value: cada uno debe estar en ambos lados con el mismo tipo, y su valor puede diferir. El resto del cuerpo se compara por valor. Con only, una ruta de shape cuenta como incluida. Una ruta no puede estar a la vez en shape e ignore, y shape no va con body: shape ni none.
ignoreJSONPaths que se dejan fuera, en ambos modos, también dentro de una ruta de only. Una marca de tiempo o un id de request que cambia en cada llamada va aquí.
listsEn modo valor una lista se compara en orden, porque un orden distinto es una diferencia real. match: <campo> empareja los elementos por ese campo; order: any los compara como los mismos elementos en cualquier orden. Dos elementos con el mismo valor de match se emparejan en orden entre sí, y el resultado lo dice.
schemaUn archivo JSON Schema bajo ultraman/files/: el tipo del paso cuando comparas contra tipos.
headersNombres de headers que se comparan. authorization, cookie, set-cookie, proxy-authorization y www-authenticate se rechazan.
reuseNombres de variables que el segundo entorno toma del primero para este paso.

El caso clásico de shape es un id o una marca de tiempo: cada entorno genera la suya, así que los valores difieren, pero el campo debe estar y conservar su tipo:

compare:
  body: value
  shape: [$.id, $.createdAt]   # están en ambos lados, mismo tipo; los valores pueden diferir
  ignore: [$.meta.requestId]   # no se compara en absoluto

Un paso de pipeline vinculado a una request de una colección toma el bloque de esa request, como sus otros campos. El formato completo está en la referencia del formato.

Desde la terminal #

ultraman run "order compare" --compare local,staging
ultraman run "order compare" --env local --compare schema
ultraman run --tag smoke --compare dev,stg --junit reports/compare.xml

--compare a,b nombra dos entornos distintos del proyecto; el primero es la fuente de reuse. Funciona con una pipeline, --all, --tag o --collection. Una pipeline o colección que nombras compara cada request. --all y --tag se atienen a lo escrito: eligen solo las pipelines con un bloque compare: y comparan solo esos pasos, así que una pipeline que nadie nombró y que escribe sin bloque (un DELETE que borra datos) nunca se ejecuta porque una comparación la eligió. Las pipelines sin nada que comparar (contra un tipo, sin ninguna con tipo) se dejan fuera y se nombran. Una comparación imprime una tabla por pipeline cuando ambos lados terminaron:

order compare · local against staging
  login       POST /auth/login    200  200   same (by structure, the default)
  get order   GET  /orders/o-1    200  200   2 paths differ
      $.total       local 59.9 · staging 61.4
      $.items[1]    only in local
1 of 2 compared steps differs between local and staging.

Bajo una fila se listan como máximo 20 rutas, y luego "and N more". Los valores bajo una fila se ocultan y se recortan como cualquier cuerpo impreso. Los demás flags de ultraman run funcionan como siempre: --input va a ambos lados, --parallel ejecuta pipelines en paralelo (dentro de una, los dos entornos se ejecutan uno después del otro), --bail, --watch, --every y --contract. --env no va con --compare a,b (el par nombra ambos), y --load se rechaza: no se compara nada bajo carga. --json agrega side: 0 o 1 a cada evento y cierra cada pipeline con una línea compare que trae rutas y ningún valor.

Cuando la ventana tiene el proyecto abierto, la comparación se ejecuta en su motor y la ventana muestra ambas ejecuciones, como con un solo motor.

Pasos que escriben #

Una comparación envía cada paso dos veces, una a cada entorno. Un paso comparado que no es una lectura (un POST que crea un pedido) crearía datos en ambos, así que la terminal pregunta cada vez, nombrando el paso y los dos entornos, aunque el resto de la ejecución ya esté permitido. Una lectura es un GET, HEAD u OPTIONS, una query GraphQL (la operación que sale) y un recurso o un prompt MCP, cuando van al endpoint de su colección (la ruta que usan sus requests GraphQL, el servidor MCP del que vino); a cualquier otro lado, o desde un paso de pipeline sin colección, cuentan como escrituras. Una mutation o una subscription GraphQL, un documento que Ultraman no puede leer y una herramienta MCP cuentan como escrituras: el readOnlyHint de una herramienta es la palabra del servidor, nunca la de Ultraman. a (siempre) nunca cubre esta pregunta, y --yes tampoco. Sin terminal (CI), dilo por nombre: --allow-write dev,stg.

Una request sin bloque que escribe se ejecuta como en una ejecución normal de la misma pipeline: comparada por estructura, se rechaza solo en un entorno de producción y no pregunta nada en los demás. La pregunta es para los pasos que marcaste para comparar. La tarjeta de un agente igual nombra cada una ("it writes in both").

Un entorno con Esto es producción marcado (consulta entornos) es más estricto: cualquier paso que no sea una lectura, comparado o que solo alimenta la comparación, se rechaza antes de enviar nada, a menos que --allow-write nombre ese entorno:

Not run. "create order" is a POST and prod is a production environment:
comparing it would create an order in stg and another in prod.

Compare only the steps that read, or allow it by name: --allow-write prod

Un entorno sin marcar que apunta al host de un entorno de producción cuenta también como producción, en la terminal, en la ventana y para un agente: una copia de los valores de prod guardada con otro nombre, un entorno importado, o un host dado como input. El rechazo lo nombra ("qa apunta al host de prod, un entorno de producción"), y --allow-write qa lo permite por nombre. El host se compara entero, sea cual sea su ruta, así que un entorno que comparte el host de producción y solo difiere en la ruta cuenta como producción también. Solo deciden los hosts que leen tus pipelines y colecciones: un host que comparten todos los entornos y que solo nombra la ruta de un paso (un proveedor de login, una API de pagos) no los vuelve de producción.

Códigos de salida #

CódigoCuándo
0Todos los pasos comparados son iguales, y ambas ejecuciones pasaron.
1Un paso comparado difiere, o falló un check de una ejecución. Ambos se reportan.
2No se envió nada (un flag incorrecto, una escritura rechazada, un entorno desconocido), o un paso comparado no se pudo comparar y ninguno difiere ("1 of 3 compared steps couldn't be compared"): un paso que un lado no alcanzó, un cuerpo sobre su límite. La terminal dice entonces el motivo de cada uno de esos pasos. Una request sin bloque que un lado no alcanzó no cuenta, salvo que no se haya comparado nada más.

Una ruta que tenía un secreto queda "no comparado" (ver abajo), y nunca hace que un paso difiera por sí sola: una comparación cuyos únicos lugares abiertos eran secretos igual sale con 0 si todo lo demás es igual.

En CI: JUnit #

--junit FILE escribe una suite de pruebas por pipeline, llamada order compare · local against staging, con compare en sus propiedades y un caso de prueba por cada paso comparado:

<testcase classname="order compare · local against staging" name="get order" time="0.000">
  <failure message="2 paths differ: $.total, $.items[1]"></failure>
</testcase>

Una diferencia es un fallo cuyo mensaje trae la cuenta y hasta 20 JSONPaths. Un paso que falló en la ejecución de un lado es un fallo que nombra ese lado; "no comparado" se omite; cuando un paso no se pudo comparar y ninguno difiere, se agrega un caso de error, para que CI nunca lo lea como un éxito. El archivo no lleva ningún valor ni cuerpo. Consulta CI.

Contra un tipo #

--compare schema ejecuta un entorno (--env, o el único del proyecto) y verifica cada respuesta comparada contra su tipo: el archivo schema del bloque, o si no, la operación OpenAPI del contrato de la colección. Una respuesta que no es JSON (una página de error HTML) no coincide con el tipo de un archivo de schema.

order compare · local against each step's type
  login       POST /auth/login    200   not compared
  get order   GET  /orders/o-1    200   doesn't match the type Order at 2 paths
      $.currency    missing: the type requires it
      $.total       is a number, the type says string
      $.id          not named by the type (allowed)
1 of 1 compared step doesn't match its type in local.

El nombre del tipo es el title del schema, o si no, el nombre de su archivo. Los campos que la respuesta tiene y el tipo no nombra son una nota, nunca una diferencia, salvo que el schema diga additionalProperties: false: una API que agrega un campo no falla. Ultraman lee un subconjunto de JSON Schema; las palabras clave que no lee (patternProperties, prefixItems, if/then, un $ref a otro archivo…) aparecen como "not checked" en el paso, para que un éxito nunca afirme más de lo que se verificó. Con --compare schema, --contract off se rechaza: ahí el contrato es el tipo.

Pedir el mismo registro: reuse #

Por defecto cada entorno usa sus propios valores: su propio login, sus propios ids. Eso es lo correcto para la estructura. Para verificar que un registro se replicó, el segundo entorno tiene que pedir el registro del primero:

compare:
  reuse: [order_id]   # en el segundo entorno, este paso se envía con el order_id del primero

Solo ese paso toma el valor; la ejecución del segundo lado sigue con los suyos. --compare dev,stg le pide a stg el pedido de dev. Un valor hecho a partir de un secreto nunca se traslada, y un valor reutilizado no puede llevar la request a otro host: el paso falla antes de enviar. La pregunta de la terminal lo nombra ("in stg: send dev's order_id (reuse)").

El agente #

Un agente compara con run_compare, como una ejecución: una tarjeta para iniciarla y otra para entregarla (consulta agentes). Recibe el veredicto, los estados de cada paso y los JSONPaths que difieren con su clase y sus tipos JSON, nunca un valor: los valores los ves tú en la ventana o en la terminal. La tarjeta de inicio nombra el host de cada entorno, las escrituras comparadas, reuse y un entorno de producción ("prod is a production environment: this reads real data"). Una query GraphQL y un recurso o un prompt MCP son lecturas ahí, como un GET.

Un lado cuya propia comprobación falló se nombra con el paso que lo detuvo, no con el mensaje de la comprobación, que puede citar la respuesta. Un nombre de campo que ningún archivo del proyecto nombra (un email usado como clave, por ejemplo) llega al agente como su número en el resultado, $.balances[field 2], porque las claves de una respuesta pueden ser sus datos; la ventana y la terminal muestran el nombre.

La comparación de un agente nunca envía a un entorno de producción un paso que no sea una lectura, y nunca usa reuse con un entorno de producción como fuente: no hay manera de que permita ninguno de los dos, y una comparación así se rechaza antes de cualquier tarjeta, diciendo que la ejecutes desde la ventana o la terminal. Un entorno que no está marcado pero apunta al host de un entorno de producción (una copia de sus valores, la URL absoluta de un paso) cuenta aquí también como producción. Cuando un agente guarda un bloque compare:, su tarjeta dice lo que el bloque deja fuera ("compares only 2 fields", "ignores 3 fields: …").

En la ventana #

Comparar con… a la izquierda de Guardar envía el borrador del editor, como Enviar, y compara su respuesta:

  • Enviarla también a otro entorno: una request a cada entorno, cada una con sus propios valores.
  • Contra un tipo: el archivo de schema de la request, o la operación OpenAPI del contrato de su colección.
  • Mi último envío en un entorno: no se envía nada; compara tus dos últimos envíos ahí. El historial queda en cada computadora, así que un runner de CI nuevo no tiene ninguno: ahí compara dos entornos o contra el tipo.

El menú dice qué necesita cada entorno antes de que elijas, sin enviar nada: necesita login cuando una request de la colección hace el valor que le falta a la comparación, necesita order_id cuando nada lo hace, y nada cuando está listo. Va antes del resto de la línea (datos reales, pregunta antes de escribir).

El resultado se abre bajo la request: un encabezado con cada entorno y su color (uno de producción en ámbar), una frase ("The values differ at 2 paths."), y las rutas que difieren, leídas como migas de pan (items › 2 › qty, cada JSONPath en su tooltip; un paso dentro de un texto JSON se lee (JSON)). Abrir las diferencias muestra las dos respuestas Lado a lado o Unificada.

Pasa sobre un valor de una respuesta y abre Comparar… para Comparar este campo, Comparar solo su tipo o Ignorar este campo: cada uno agrega su ruta al bloque compare: de la request, y la request queda sin guardar como con cualquier edición. Elegir qué comparar pone la respuesta en un modo de selección: marca los campos y Listo escribe only. Sin una respuesta todavía, los campos salen del tipo; si no, envíala una vez antes. La pestaña Opciones de la request tiene una sección Comparar con las mismas reglas. Deja tres filas a la vista: Comparar del cuerpo (valores, forma o nada), Campos a comparar y Campos a ignorar. El resto está detrás de Más: los campos comparados solo por tipo, las reglas de listas, el tipo de la respuesta, los headers y reuse (solo aparece cuando el archivo lo tiene). Cerrado, Más dice lo que guarda en una línea de chips («1 regla de lista», «tipo order»), así que nada de lo que fijaste queda fuera de la vista; se abre solo mientras algo adentro no es válido.

Una pipeline (⋯ › Comparar en dos entornos… en su encabezado) o una colección (el mismo ítem en su ⋯ del árbol) se ejecuta en ambos entornos y muestra una fila por request: toda request se compara, por su propia regla o, si no tiene, por Misma estructura. Una fila termina con la regla que usó, como un chip, y con "por defecto" después cuando la request no tenía ninguna. En una colección, elegir otra regla en el chip de una fila abre esa request en una pestaña con la regla sin guardar (no se guarda nada ni se vuelve a enviar); el chip de una pipeline solo nombra la regla. Solo lo que difiere deja el resto plegado.

Antes de enviar nada, la ventana pregunta lo que pregunta la terminal: un secreto o un archivo que va por primera vez al host del segundo entorno, y un paso comparado que escribe, nombrado con ambos entornos y ambas URLs, con Comparar las últimas respuestas (no se envía nada) como primera respuesta. Un entorno de producción lo dice en la pregunta, y también uno que apunta al host de un entorno de producción («qa apunta al host de prod, un entorno de producción»); el menú Comparar lo marca además en ámbar. Contra un tipo, un paso que escribe en un entorno de producción no se envía desde la ventana: compáralo desde la terminal con --allow-write.

La primera comparación: Misma estructura, la opción por defecto #

Una request sin bloque compare: se compara por Misma estructura cuando eliges un entorno o Mi último envío en: los mismos campos y tipos, aunque los valores cambien, así que los ids y las fechas que hace cada entorno no se leen como una pared de diferencias. No se pregunta ni se escribe nada: la request no queda con cambios sin guardar.

La frase del resultado termina con la regla que usó: «local y staging responden lo mismo. Comparado por Misma estructura, la opción por defecto». La regla es un chip; haz clic para cambiarla:

  • Misma estructura: los mismos campos y tipos; los valores pueden cambiar. Para comprobar qué cambió un deploy. Escribe compare: { body: shape }.
  • Datos replicados: los mismos valores. Para comprobar que se copiaron los datos. Escribe compare: { body: value }.
  • Elegir qué comparar: marca lo que debe quedar igual sobre la respuesta que muestra la comparación; Listo escribe only.

Elegir una regla la escribe en la request (queda sin guardar, como con cualquier edición, y Guardar la conserva) y vuelve a comparar con ella. Una request con su propio bloque muestra su regla en el chip sin «la opción por defecto», y una que elige o ignora campos muestra Campos elegidos. Ignorar este campo en un resultado comparado por la opción por defecto mantiene Misma estructura para el resto. Las mismas dos reglas son tarjetas arriba en Opciones mientras la request no tiene bloque. Una comprobación contra un tipo no tiene chip: comprueba el tipo.

Campos que cambian solos #

Algunos campos cambian en cada llamada: una hora de creación, un id de request. Después de una comparación que difiere, la ventana los ofrece para ignore con un clic, en un aviso bajo la frase:

  • Después de Mi último envío en un entorno, ofrece todos los campos del cuerpo cuyo valor cambió entre esos dos envíos: «These 3 fields change by themselves: createdAt · requestId · meta › traceId.»
  • Después de una comparación entre dos entornos, ofrece solo las diferencias que también cambiaron entre dos envíos en el primer entorno, leídos de su historial (no se envía nada): «3 of the differences also change between two sends in dev: …». Una diferencia estable dentro de cada entorno es el hallazgo, así que no se ofrece.

Ignorar estos 3 campos agrega exactamente los campos que nombra el aviso a la lista ignore de la request (la request queda sin guardar) y vuelve a leer el resultado de las dos respuestas que el historial ya tiene. Los límites:

  • Solo un campo presente en ambos lados cuyo valor cambió. Nunca un campo que está de un solo lado, un tipo que cambió, un header, el status, el cuerpo entero ni un elemento de lista en sí (un campo dentro de los elementos vale para ese campo de todos, items › each › seenAt).
  • Nunca un lugar que tenía un secreto (quedan «no comparados») ni un campo que elegiste: uno de only o de shape, o un objeto que lo contiene.
  • Como máximo 8, todos nombrados. Con más, dice «and N more change too» y el clic no los agrega.
  • Nada con body: shape o none, cuando el status difiere, ni contra un tipo.

Entrar en el otro entorno #

Cada entorno usa sus propios valores: un token que hizo el login de un entorno nunca va al otro. Cuando a un entorno le falta un valor que la request necesita y una request de la colección lo hace, elegir ese entorno pregunta una vez: Para comparar, primero envía login en staging. Lista cada request que se enviará con su método (hasta tres, «POST login»), y cuando los dos lados necesitan una, van en la misma pregunta.

  • Cancelar (primero y con el foco) no envía nada.
  • Enviar login y comparar envía cada request listada a su propio entorno, con los valores de ese entorno, y luego compara. Lo que hacen queda solo en la sesión de ese entorno.
  • Escribir el valor en su lugar abre el diálogo de valores que faltan, cuyo título nombra el entorno cuando no es el actual: «Falta 1 valor para enviar get order en staging».

Un entorno de producción se nombra en una advertencia dentro de la pregunta («prod es un entorno de producción: esto envía POST login ahí.»). Si una request falla o no da el valor, no se envía nada más y su pestaña se abre con la respuesta. Con más de tres requests, o un valor que nada hace, aparece el diálogo de valores que faltan de siempre. Un secreto que va por primera vez a un servidor sigue pidiendo su propio sí.

Qué te mantiene a salvo #

  • Tú: los secretos de cada entorno van solo al host de ese entorno, con el consentimiento de siempre; el secreto de un entorno nunca llega al otro.
  • Tú: ambas respuestas se ocultan contra todos los secretos de la bóveda que usa el proyecto antes de compararse o mostrarse, y un lugar que tenía un secreto queda "no comparado", nunca "igual" ni "distinto" (ocultamiento). Los valores simples de ultraman/local/envs/ son variables normales y no se ocultan: guarda un valor sensible en la bóveda.
  • Tú: la pregunta antes de un login nombra cada request, su método y su entorno, producción incluida, y un sí cubre solo lo que listó. Cada entorno guarda su propia sesión, y el «necesita login» del menú se le pregunta a Ultraman sin enviar nada.
  • Tú: la sugerencia solo nombra campos de las respuestas que ya tienes, nunca el lugar de un secreto ni un campo que elegiste, y un clic agrega exactamente los nombres que muestra.
  • Tu equipo: una escritura comparada pregunta cada vez, y un entorno de producción rechaza toda escritura a menos que la nombres con --allow-write; la comparación de un agente no puede escribir ahí en absoluto (agentes).
  • CI: los resultados de una comparación, en JUnit y en la línea compare de --json, listan rutas, clases y tipos, no los valores. JUnit nombra un lado cuya comprobación falló solo por su paso; las líneas de --json conservan el mensaje de la comprobación, como en cualquier ejecución (en CI).
  • Límite: la casilla de producción vive en un archivo bajo git: protege de una escritura descuidada, no de alguien que pueda hacer push al repositorio (límites).
