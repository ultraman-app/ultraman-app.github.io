Requests #

El área de Requests es donde creas, envías y compruebas requests sueltas: colecciones con carpetas y requests que se abren en pestañas, como en Postman. La diferencia es que cada request lleva sus checks, y todo es un archivo de texto en ultraman/requests/ que tu equipo comparte por git.

Colecciones y carpetas #

Una colección tiene un host y, si quieres, auth, headers y variables (valores iniciales para {{nombre}}). Desde su menú puedes crear requests y carpetas, ejecutarlo todo, crear una pipeline o abrir sus ajustes. Las requests se pueden renombrar, mover, duplicar y agregar a una pipeline. Todo lugar que nombra una request (el árbol, las pestañas, el Historial, la apertura rápida, las filas de una ejecución de colección) muestra su clase donde va el método: el método en HTTP, y GQL, MCP, WS o SSE. Actualizar desde una spec OpenAPI… aparece en el menú solo en una colección que tiene una spec: un contrato OpenAPI, o requests que vienen de una operación.

Ejecutar una colección #

Ejecutar, en el menú de una colección o de una carpeta, envía todas las requests en orden, cada una con sus checks. Una request que falla no detiene a las demás: la ejecución sigue, y la franja sobre las filas dice cuántas pasaron y cuántas fallaron, y cuáles. Bajo una fila que falló están su error y los checks que no pasaron. Un check cuya request falló no se lee: dice «sin comprobar: la request falló». Una request que necesita un valor que otra anterior no produjo, como el token de un login que falló, no se envía: su fila dice «no enviada», y la franja dice por qué una sola vez. Detener termina la ejecución donde está: la request en curso dice «detenida» y las demás «sin ejecutar». La lista de Ejecuciones bajo las filas dice «7 pasaron», «1 de 7 falló» o «detenida». Una pipeline sigue deteniéndose en su primer fallo, porque sus pasos se alimentan entre sí. La terminal (`ultraman run --collection`), JUnit y el run_collection del agente informan una colección de la misma forma.

Enviar #

Enviar (Ctrl/Cmd+Enter) envía la request con el entorno elegido. La respuesta muestra el status, el tiempo, el tamaño, los headers y el body; Tiempos indica en qué se fue el tiempo (DNS, conexión, TLS, primer byte, total).

  • Las variables aparecen como chips: {{env.x}} viene del entorno, {{secrets.x}} de la bóveda y {{x}} de la sesión (lo que extrajo una request anterior) o de las variables de la colección. Ctrl+Space te las sugiere.
  • Si falta un valor, un diálogo te lo pide para esta sesión.
  • Si pegas un comando curl en el path, se convierte en la request.

El editor de requests #

Una request se abre en la primera pestaña que tenga contenido. Las pestañas son Params (parámetros de path, como :id, y de query), Headers, Body, Auth, Opciones, Checks y Notas. Si desactivas una fila, se queda en el archivo pero no se envía. Una request GET o HEAD no puede llevar body.

Body #

La pestaña Body tiene ocho modos. Cada uno pone el header Content-Type por ti, salvo que escribas uno en Headers (el editor te avisa de que el tuyo tiene prioridad y de que un header multipart escrito a mano pierde su boundary).

ModoQué se envíaContent-Type
Ningunonada de bodyninguno
JSONel JSON que escribas, con {{variables}} dentroapplication/json
Textoel texto tal cual (XML, CSV, lo que sea)text/plain
Formpares name=value codificados para URL; un nombre puede repetirseapplication/x-www-form-urlencoded
Multipartpartes de texto o de archivomultipart/form-data
Archivolos bytes de un archivose deduce de la extensión del archivo
GraphQLuna query, sus variables y el nombre de la operación, en JSON (ver GraphQL)application/json
MCPuna llamada a la herramienta, el recurso o el prompt de un servidor MCP, como JSON-RPC (ver Servidores MCP)application/json

Una request tiene un solo body a la vez. Los archivos se toman del proyecto: si eliges uno de otra ubicación, Ultraman te ofrece Copiarlo al proyecto (ultraman/files/, donde viaja con git) o Dejarlo fuera (solo en esta máquina). Un archivo que no está en ultraman/files/ pide tu sí la primera vez que se envía: consulta archivos.

Auth #

La pestaña Auth ofrece Heredada, Ninguno, Bearer, Basic y API key (en un header o en un parámetro de query, con el nombre que elijas). Una colección o una pipeline puede definir la auth una sola vez; cada request la hereda, define la suya o elige Ninguno. Los valores pueden ser variables, normalmente {{secrets.x}}, para que el token nunca quede en el archivo.

Esos son todos los tipos. Para una API con token, inicia sesión con una request, extrae el token y úsalo como bearer ({{token}}): así se cubren la mayoría de los flujos de login. No hay flujos OAuth 2, certificados de cliente ni firma de requests.

Desde una request #

En la ventana, la pestaña Auth de una request (o los ajustes de una colección) puede tomar un token bearer Desde una request: elige la request de login y la propiedad de su respuesta (de su última respuesta, o escrita como JSONPath). Ultraman escribe auth: { bearer: '{{token}}' } en la request o en la colección, y un check extract en el login. En una colección, el login recibe Ninguno como auth propia si no tenía, para que nunca envíe el bearer que él mismo genera. El archivo del login se escribe solo cuando su pestaña no tiene cambios sin guardar; si no, dice "Guarda primero el login".

Después, cuando envías y falta el token, o la respuesta es un 401, la ventana envía primero el login, en el mismo entorno, y luego tu request. Después de un 401 el token se renueva una sola vez: una request que solo lee (GET, HEAD, OPTIONS, una query GraphQL o un recurso o prompt MCP enviados al endpoint de su colección) se envía de nuevo sola, una que escribe espera a que la envíes otra vez ("Token renovado: envía de nuevo"), y un segundo 401 se muestra tal como llegó. Una ejecución de colección desde la ventana hace lo mismo con un token que falta, no con un 401 dentro de la ejecución. La primera vez para cada colección, entorno y login pregunta Enviar {login} y continuar, diciendo adónde va el login; en un entorno de producción pregunta siempre, con una advertencia.

Es solo bearer. Un agente que envía una request guardada o corre una colección también envía el login primero, bajo la tarjeta que apruebas (agentes); la CLI y las pipelines siguen usando un paso de login como antes.

Opciones de la request #

Opciones ajusta una sola request: timeout (en milisegundos; 30 000 por defecto, 0 para no tener límite), redirects (cuántas redirecciones seguir; 10 por defecto, 20 como máximo), tamaño máximo de la respuesta (50 MB), HTTP/2, HTTP plano (permite http: hacia un host que no sea localhost) y una CA propia (un archivo .pem del proyecto en el que se confía además de las CA habituales, para un servidor con su propio certificado). El HTTP plano y una CA propia reducen la protección de la conexión, así que la ventana te avisa cuando los activas.

Una opción vacía hereda su valor, y el editor indica en gris de dónde viene ("30000 ms, por defecto"). El orden es: las opciones de request del entorno, luego las de la pipeline o la colección y, por último, las de la request. Gana la más cercana.

Una request también puede marcarse como responde siempre lo mismo, algo que solo importa en una prueba de carga.

Copiar como cURL #

En una pipeline, el botón de terminal de la fila de una request la copia como comando curl, con los valores que tienes en la ventana. Los secretos nunca se escriben: se convierten en ${ULTRAMAN_SECRET_NAME}, así que el comando funciona en una shell donde definas esa variable y puedes pegarlo en un chat sin riesgo. También funciona al revés en el área de Requests: pega un comando curl en el path y se convierte en la request.

Redirects y Tiempos #

Una respuesta redirigida tiene una pestaña Redirects: cada salto con su status, la URL que respondió y sus headers (el location al que apuntaba, algún set-cookie por el camino). Tiempos indica en qué se fue el tiempo. Las redirecciones se siguen hasta el número que fija la opción redirects. Dos reglas te protegen: cuando una redirección va a otro origen, se descartan los headers authorization, cookie y proxy-authorization; y no se sigue un 307 o 308 que enviaría a otro origen un body con un secreto (la respuesta que ves es esa redirección, con su destino). Consulta redirecciones.

Checks #

Un check es un assert (algo que la request tiene que responder) o un extract (un valor que se guarda para después). Se ejecutan en cada envío, y la pestaña Checks de la respuesta muestra cuáles pasaron.

CheckPasa cuando
statusel status HTTP es el indicado
equals, notEqualsun valor es (o no es) el indicado
containsun valor o el body lo contiene
lessThan, greaterThanun número (o el tiempo en ms) está por debajo o por encima
exists, notExistsun path JSON o un header existe
matchesun texto coincide con una expresión regular
typeun valor JSON es string, número, array…
schemaun valor cumple un JSON Schema

La forma más rápida de agregar uno: en el body de la respuesta, pasa el mouse sobre un valor y usa su menú.

Generar checks #

Generar checks analiza la respuesta en pantalla y te propone checks:

  • que el status sea el que recibió;
  • para cada campo de primer nivel del JSON (o del primer elemento, si es una lista), que exista y su tipo.

Agrega 30 como máximo, omite los que la request ya tiene y no guarda nada hasta que hagas clic en Guardar: revísalos en la pestaña Checks y borra los que no quieras. Es un punto de partida para una prueba de contrato; los valores que cambian en cada llamada (ids, fechas, tokens) se comprueban por tipo, nunca por valor. En el área de Pipelines, el mismo botón los agrega como pasos justo después de la request.

En una llamada MCP los checks bajan un nivel: leen los campos del Resultado estructurado ($.structuredContent.total), no los bloques de texto de content. Una herramienta que respondió con un error recibe solo el check de status.

La sesión #

Hay una sesión por entorno. Lo que extrae un check (el token del login) queda disponible para la siguiente request (Authorization: Bearer {{token}}). Las variables de la colección son los valores iniciales.

Historial #

Cada envío queda en el Historial (junto a Colecciones): lo que se envió, la respuesta, el tiempo y los checks. Cada envío muestra el tiempo habitual de esa request ("212 ms · suele tardar 180 ms") y se marca cuando es más lento. Puedes reabrir una entrada tal como se envió o compararla lado a lado con otra. El historial es personal: nunca se sincroniza.

El historial tiene su propia pantalla: una tabla con lo más reciente primero, agrupada por día, en la que puedes buscar (un nombre, una URL o un status) y filtrar por método, status y entorno; la barra lateral la limita a una colección. El envío elegido se abre junto a la tabla, con lo que salió encima de lo que volvió (lado a lado en una pantalla ancha). Abrir como se envió lo devuelve a su pestaña; ⋯ borra el historial.

Deriva del contrato #

Después de un envío, si el envío anterior de la misma request también devolvió JSON, un aviso indica qué campos desaparecieron o cambiaron de tipo ($.id: string → number). Comparar abre los dos; Generar checks convierte la forma actual en checks. Un campo que la respuesta anterior no tenía no es un cambio: no muestra el aviso, y en la respuesta su línea dice nuevo desde el último envío.

Contrato OpenAPI #

Una colección puede indicar la spec OpenAPI que promete su API: Contrato en sus ajustes, o en collection.yaml:

contract:
  openapi: files/shop-openapi.yaml   # un archivo dentro de files/, o /openapi.json (una ruta en el host), o una URL entera
  mode: warn                         # warn (por defecto) o strict

A partir de ahí, cada respuesta de sus requests se comprueba contra su operación en la spec actual: en un envío, en una ejecución de la colección, en un paso de pipeline vinculado a una de sus requests, en la ejecución de un agente y en la CLI. La operación es la que la importación guardó en la request (operation:) o, si no hay ninguna, la que coincide con su método y su ruta. Lo que la spec no documenta aparece como aviso: status 500 isn't documented for GET /orders/{id}, $.total: expected number, got null, not in the spec: POST /orders/bulk. Un body que no es JSON, o una respuesta sin schema JSON, no tiene nada que comprobar.

  • Dónde se ve: junto al status (Contrato: 2 avisos), en la lista sobre el body, en la fila de la ejecución y en el historial. La terminal imprime una línea debajo del paso.
  • strict hace fallar el paso de una ejecución con el primer aviso (JUnit lo incluye). Un envío igualmente muestra los avisos: no tiene un paso que hacer fallar. En la CLI, --contract strict|warn|off tiene prioridad sobre el modo del archivo, así CI puede activarlo sin editar nada.
  • Un archivo se vuelve a leer cuando cambia. Una ruta o una URL se pide como una request más de la colección (con su host, auth, headers y secretos, y los mismos síes), una vez por ejecución; los envíos de la ventana la conservan hasta Releer la spec. Si no se puede leer, cuenta como un aviso, nunca como un paso fallido.
  • No bajo carga: una prueba de carga no comprueba el contrato.
  • Con contrato, Actualizar desde una spec OpenAPI no escribe checks de schema (el contrato ya los cubre) y, si el contrato es un archivo, escribe ahí la spec más nueva.

Copias vinculadas #

Agregar a una pipeline… pone una request al final de una pipeline como copia vinculada (recuerda de dónde vino). Cuando la cambias en un lugar, Ultraman te pregunta si quieres actualizar las demás copias. Una request WebSocket o SSE entra como su paso connect vinculado (solo el handshake: sus mensajes y la escucha se quedan en el área de Requests) y se mantiene vinculada de la misma manera.

Streams: WebSocket y SSE #

Abre un stream WebSocket o SSE en una pestaña, igual que una request: ve cada mensaje a medida que llega, envía uno desde un compositor, filtra y pausa la lista, y guarda toda la sesión en el Historial.

El menú de una colección tiene Nuevo WebSocket o SSE. Una request de stream es un archivo como cualquier otro (con websocket: live o sse: prices como primera clave) y se abre en una pestaña con la misma disposición que una request. La píldora del método es un selector WebSocket | SSE, el path va después del host de la colección (https pasa a wss y http a ws) y las pestañas son Params, Headers, Auth, Opciones (con las propias del stream: tamaño de mensaje, ping, inactividad), Mensajes, Checks y Notas.

Conectar (Ctrl/Cmd+Enter) abre el stream y se convierte en Desconectar mientras está abierto. Debajo, el panel del stream muestra una píldora de estado (connecting…, open 101, closed 1000), un reloj, cuántos mensajes fueron en cada sentido y dos pestañas:

  • Mensajes: una fila por mensaje, el más reciente abajo, con su dirección (↓ recibido, ↑ enviado), hora, tamaño y, en SSE, el nombre del event y el id. Haz clic en una fila para abrirla en el visor de body. Filtrar oculta filas por texto (o event:price en SSE), Pausar congela la lista mientras los mensajes se siguen contando y Limpiar la vacía.
  • Handshake: los headers del servidor (y el protocolo que eligió).

La pestaña Checks de la propia request guarda los checks de un stream. Leen el handshake (status, un header), no los mensajes: la pestaña lo dice cuando está vacía. Para comprobar un mensaje, pon el stream en una pipeline: la pestaña enlaza a la acción de abajo.

Esperar esto en una pipeline… está en la fila de un mensaje recibido (y en el mensaje next de una suscripción GraphQL). Propone una pipeline: el connect del stream (vinculado a esta request), los mensajes guardados que se envían antes, una espera de un mensaje como este con 5 segundos de límite, un check y el cierre. Una vista previa lista los pasos; puedes dejar uno fuera o moverlo, y no se guarda nada hasta Crear, que abre la nueva pipeline. El texto del mensaje se escribe como texto, nunca como variable.

En un WebSocket, el compositor que está debajo de la lista envía un mensaje (texto o JSON, Ctrl+Enter). Puede tomar uno de los mensajes guardados de la request, y Guardar como mensaje agrega a la request el texto del compositor. Un mensaje con {{secrets.x}} se envía con el valor y se muestra como [secret:x]. Cuando la bóveda se bloquea, también se cierra cualquier stream que haya usado un secreto.

El panel conserva los 500 mensajes más recientes, cada uno recortado a 64 KB. Cuando el stream termina (por ti, por el servidor o por un error), toda la sesión queda como una entrada en el Historial: su handshake, sus mensajes y cómo terminó.

En una ejecución de la colección, en ultraman run --collection y cuando la envía un agente, una request de stream se conecta, comprueba el handshake, envía sus mensajes guardados, escucha durante listen ms (2 segundos, salvo que el archivo indique otra cosa) y se cierra. Que un stream no reciba nada no es un fallo. Para esperar un mensaje concreto y comprobarlo, pon el stream en una pipeline.

Lo que no hay aquí: una request de stream no tiene mock, deriva ni reconexión (si el servidor te desconecta, vuelve a Conectar), y no se admiten Socket.IO ni los WebSocket comprimidos (deflate) (Si vienes de otra herramienta).

GraphQL #

Envía queries y mutations GraphQL con autocompletado a partir del schema de la API, y detecta los errores que un servidor devuelve con un 200.

El menú de una colección tiene Nueva request GraphQL, y el Body de cualquier request tiene un modo GraphQL (siempre POST). Ahí van la query, las Variables (JSON, con {{variables}} dentro de los strings, como en un body JSON), un selector de operación cuando la query define varias y Permitir errores.

El schema. Cargar schema le pide el schema al servidor enviando la propia request con la query de introspección: la misma URL, los mismos headers, auth y secretos, y las mismas preguntas que un envío. Con un schema, el editor autocompleta campos y argumentos, muestra la descripción de cada campo en la lista de sugerencias y marca lo que el schema no tiene. Guardar en el proyecto lo guarda como ultraman/files/<colección>.graphql y lo indica en collection.yaml: todas las requests GraphQL de esa colección lo usan y git lo comparte con tu equipo. Un schema que solo cargaste dura hasta que cierres la ventana. Sin schema, el editor igualmente resalta la query.

Errores. Un servidor GraphQL suele responder 200 con una lista errors. La respuesta muestra 1 error GraphQL (o N errores GraphQL) junto al status y, sobre el body, lista cada mensaje con su path. En una ejecución, en una ejecución de la colección y bajo carga, un paso cuya respuesta tiene errors falla con el primer mensaje, sea cual sea el status; bajo carga, cada uno cuenta como una request fallida. Una nota bajo la lista lo dice ("Una respuesta con errores falla la request. Permitir errores la deja pasar."). Permitir errores (allowErrors: true) es para una API que devuelve datos parciales a propósito.

La query se envía tal como está escrita: los {{...}} que contenga no se reemplazan, así que los valores van en las variables. La pestaña Enviado y el Historial muestran la query tal como la escribiste y las variables tal como salieron (un secreto, como [secret:x]).

Suscripciones. Cuando la operación es una subscription, la request muestra Suscribirse en lugar de Enviar. Ultraman abre un WebSocket que habla graphql-transport-ws en la URL de la request (https pasa a wss), o en el path graphql: { subscriptions: /graphql/ws } de la colección si el servidor sirve las suscripciones por separado, e inicia la suscripción. El panel del stream muestra cada next como una fila, en rojo si trae errores. Cancelar suscripción termina la suscripción y deja el socket abierto; Desconectar lo cierra. La sesión queda como una entrada en el Historial. En una ejecución de la colección y cuando la envía un agente, una suscripción escucha 2 segundos y se cierra, y sus checks leen su primer next. Para esperar eventos concretos y comprobarlos, usa pasos subscribe. Una suscripción no tiene Comparar con…, porque un stream no se compara; cámbiala a una query y el botón vuelve.

Todavía no hay: GraphQL sobre SSE (graphql-sse), el protocolo anterior subscriptions-transport-ws, requests GET ni persisted queries, batching ni subida de archivos.

Servidores MCP #

Llama a una herramienta, lee un recurso u obtén un prompt de un servidor MCP que habla MCP sobre HTTP, y revisa lo que vuelve como cualquier otra respuesta.

La request. El Body de una request tiene un modo MCP (siempre POST; el path es la dirección del servidor después del host de la colección, como /mcp). Elige Herramienta, Recurso o Prompt. El nombre se completa con la lista del servidor (la que guarda una colección importada del servidor), y los Argumentos son JSON, con {{variables}} dentro de los strings, como un body JSON. Permitir errores deja pasar el error propio de una herramienta (solo herramientas). Los argumentos de un prompt son texto.

Del servidor. Debajo de los argumentos, la tarjeta Del servidor muestra lo que dice el servidor del argumento donde está el cursor: sus palabras, su tipo, ejemplos y valor por defecto, y un clic escribe un valor. Fuera de un argumento, los lista todos. En el editor, la sugerencia trae las mismas palabras. Una request escrita a mano todavía no tiene lista: Cargar del servidor (↻ en la esquina de la tarjeta Del servidor, donde está todo lo que dice el servidor de la llamada) se la pide al servidor con la dirección y la auth de esta misma request. Es un envío, con las preguntas de un Send; lista el servidor y nunca llama a una herramienta. Guardar en el proyecto guarda la lista en la colección (files/<colección>.mcp.json), y Cargar de nuevo la vuelve a pedir.

La respuesta. La respuesta es el resultado de la herramienta: su contenido (texto, imágenes, recursos incrustados) y luego el Resultado estructurado (structuredContent), así que extraes y verificas sobre $.structuredContent… como en cualquier body JSON. Una herramienta que responde con un error lo muestra junto al status y hace fallar el paso, salvo que Permitir errores esté activado; un error JSON-RPC también lo hace fallar (MCP error -32602: …). El Historial los lista como MCP con el nombre de la herramienta, y su filtro de método tiene MCP. Una nota bajo el error de una herramienta dice que Permitir errores lo deja pasar. Enviado muestra el mensaje JSON-RPC que salió, nunca el id de sesión.

Bloques de texto. Un bloque de texto que trae JSON se muestra en el mismo visor que el resultado estructurado, así que pasar el mouse o Enter extrae o verifica un valor de adentro: el path lee dentro del texto ($.content[0].text.@json…, más abajo). Cuando dice lo mismo que el resultado estructurado, se pliega a una línea con Mostrar. Cualquier otro texto, también el de un recurso o un prompt, tiene un menú ⋯: Afirmar que contiene…, Extraer con una regex… (una regex lee toda la respuesta) y Copiar path. Generar checks lee structuredContent o, si una herramienta no lo manda, su primer texto JSON.

Una herramienta que responde JSON como texto. Muchas herramientas ponen su JSON en un string, en content[0].text. Añade .@json a la ruta y Ultraman lee dentro de ese texto: $.content[0].text.@json.customers[0].id, en un extract, un assert o el where de un stream. Puede repetirse y puede ir tras [*] (los elementos que no son JSON se saltan). Si el valor no es texto, el texto no es JSON o pasa de 1 MB, la ruta no encuentra nada y el fallo dice cuál (the text at … isn't JSON). Una clave que de verdad se llama @json se escribe ['@json']. Las rutas que eligen campos para dejar fuera en un compare no la aceptan.

Sesiones. Un Enviar abre su propia sesión, hace la llamada y la cierra. Una ejecución abre una sesión por servidor la primera vez que lo llama, la comparte entre bloques, repeticiones y ramas, y la cierra cuando termina (también con Stop). Copiar como cURL da el único POST, con un comentario de que el servidor puede necesitar un initialize antes.

Servidores que no siguen el estándar. Ultraman se comporta como el cliente más estricto de los habituales y dice por qué cuando hace algo distinto del estándar. Cuando solo existe una lectura posible de la respuesta y un cliente estándar funcionaría, se recupera y el paso queda en verde con una nota, en Enviado, en la ejecución, en la terminal y en JUnit, y en el resultado de un agente; una carga las cuenta por tipo. Se recupera de: una versión de protocolo anterior (2024-11-05) sobre este transporte, una sesión que el servidor olvidó (abre una nueva, una sola vez), un serverInfo o unas capabilities que faltan, una respuesta sin "jsonrpc", una con result y error a la vez, y un lote (lee el elemento que responde). Falla con palabras que nombran la falta cuando un paso en verde sería un resultado falso: un status HTTP sin respuesta MCP (un 401 dice que el servidor pide autorización), una redirección (dice a dónde; nunca se sigue: pon /mcp/ en la dirección si eso es lo que quiere el servidor), un 404 o 405 en la primera llamada (probablemente el transporte anterior HTTP+SSE, que no se admite), una respuesta a otro id, JSON-RPC con un content type equivocado, un error sin código numérico, un 400 donde el estándar responde 404, una petición del servidor a mitad del stream (sampling, roots, elicitation) o un stream que se cierra antes de la respuesta. Rechaza una redirección a otro origen, una versión de protocolo más nueva que la que habla (o ninguna) y un id de sesión que no sea ASCII visible.

El nombre de una herramienta o de un prompt es cualquier texto de hasta 128 caracteres sin caracteres de control ni {{, así que el ns/tool de un gateway funciona.

Qué te mantiene a salvo #

La promesa rige aquí como en todas partes. Esto es lo que agrega esta parte:

  • Tú y tu equipo: un body de archivo solo sale sin preguntar si está en ultraman/files/; cualquier otro archivo pregunta antes. Consulta archivos.
  • Tú: un valor leído con .@json es un valor de la respuesta: se oculta, y cuenta como el del secreto si un servidor lo devuelve tal cual o escrito con escapes, hasta seis niveles de profundidad (texto JSON dentro de texto JSON). Una verificación que lee un valor con ese eco se rechaza, y también un exists o notExists con .@json sobre una respuesta que devuelve uno.
  • Tú: una redirección a otro origen no se lleva tus credenciales. Consulta redirecciones.
  • Tu equipo: el historial es personal y nunca se sincroniza, así que las respuestas con datos reales se quedan en tu máquina. Consulta dónde se guarda cada cosa.
  • Tú: la URL de un contrato se pide igual que las requests de la colección: sus secretos piden el mismo sí, se rechaza en una carpeta que no marcaste como de confianza y los avisos citan la respuesta solo después de ocultar sus secretos. Un archivo de contrato solo se lee de ultraman/files/, nunca a través de un enlace. Consulta consentimiento.
  • Tú: las variables GraphQL son un body: un secreto en ellas pide el mismo sí que en cualquier otro lugar y se muestra como [secret:x], y Cargar schema es un envío, con las mismas preguntas. Consulta consentimiento.
  • Tú: Cargar del servidor es un envío: pregunta lo mismo que un Send, nunca sigue una redirección y nunca llama a una herramienta. Lo que dice el servidor se muestra como texto y llega al proyecto solo como texto literal: un {{ en él nunca es una variable viva. Consulta consentimiento.
  • Tu equipo: un schema solo se lee de ultraman/files/, nunca a través de un enlace, y sus descripciones y los mensajes de error de un servidor se muestran como texto plano. Consulta archivos.
  • Tú: las variables de una suscripción y el payload de connection_init son mensajes: un secreto en ellos pide el mismo sí que un header, se muestra como [secret:x] y, si un servidor lo devuelve, aparece oculto. Consulta consentimiento.
  • Tú: el único sí detrás de Enviar {login} y continuar se guarda en esta máquina (~/.ultraman/trust.json), nunca en el proyecto. Cualquier cambio en la request de login (su método, ruta, body, headers, extracts o lo que hereda de la colección), o en adónde va una vez completados los valores del entorno, vuelve a preguntar; un entorno de producción pregunta siempre, y ese sí no se guarda. El login va con los valores de su propia colección. Un token llega solo a la sesión de su propio entorno, y la ventana envía un login por ti solo para los nombres que lee una auth: cualquier otro valor que falte sigue preguntando.
  • Tú: un argumento MCP es un body: un secreto dentro pide el mismo sí que en cualquier parte y se muestra como [secret:x], y un resultado que lo repita se censura. El id de sesión del servidor nunca se muestra ni se guarda. Consulta consentimiento.
  • Tú: las palabras de un servidor (nombres de herramientas, descripciones, resultados, errores) se muestran como texto plano, sin caracteres de control, y se cortan antes de guardarse. Una redirección nunca se sigue, así que tu token y el id de sesión se quedan con la dirección que elegiste. Un servidor que se aparta del estándar se recupera solo cuando hay una lectura segura, y lo dice.
