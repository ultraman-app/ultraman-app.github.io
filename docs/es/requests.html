Requests #

El área de Requests es donde armás, enviás y chequeás requests sueltas: colecciones con carpetas y requests, abiertas en pestañas, como en Postman. Lo distinto es que cada request lleva sus checks, y todo es un archivo simple en ultraman/requests/ que tu equipo comparte por git.

Colecciones y carpetas #

Una colección tiene un host y, si querés, auth, headers y variables (valores iniciales para {{nombre}}). Su menú crea requests y carpetas, corre todo, crea una pipeline o abre su configuración. Las requests se pueden renombrar, mover, duplicar y agregar a una pipeline.

Enviar #

Enviar (Ctrl/Cmd+Enter) manda la request en el entorno elegido. La respuesta muestra su status, tiempo, tamaño, headers y body; Tiempos dice dónde se fue el tiempo (DNS, conexión, TLS, primer byte, total).

  • Las variables se ven como chips: {{env.x}} del entorno, {{secrets.x}} de la bóveda, {{x}} de la sesión (lo que extrajo una request anterior) o de las variables de la colección. Ctrl+Space las sugiere.
  • Si falta un valor, un diálogo lo pide para esta sesión.
  • Pegar un comando curl en el path lo convierte en la request.

El editor de requests #

Una request se abre en su primera pestaña con contenido. Las pestañas son Params (parámetros de path como :id, y el query), Headers, Body, Auth, Opciones, Checks y Notas. Una fila que apagás queda en el archivo pero no se envía. Una request GET o HEAD no puede tener body.

Body #

La pestaña Body tiene seis modos. Cada uno define por vos el header Content-Type, salvo que escribas uno en Headers (el editor avisa que el tuyo gana, y que un header multipart escrito a mano pierde su boundary).

ModoQué se envíaContent-Type
Ningunosin bodyninguno
JSONel JSON que escribís, con {{variables}} adentroapplication/json
Textoel texto tal como está escrito (XML, CSV, lo que sea)text/plain
Formpares name=value, codificados como URL; un nombre se puede repetirapplication/x-www-form-urlencoded
Multipartpartes que son texto o un archivomultipart/form-data
Archivolos bytes de un archivose deduce de la extensión del archivo

Una request tiene un solo body a la vez. Un archivo sale del proyecto: si elegís uno de otro lado, Ultraman ofrece Copiarlo al proyecto (ultraman/files/, donde viaja con git) o Dejarlo fuera (solo en esta máquina). Un archivo de fuera de ultraman/files/ pide tu sí la primera vez que se envía: mirá archivos.

Auth #

La pestaña Auth ofrece Heredada, Ninguno, Bearer, Basic y API key (un header o un parámetro de query, con el nombre que elijas). Una colección o una pipeline puede definir la auth una sola vez; una request la hereda, define la suya o dice Ninguno. Los valores pueden ser variables, normalmente {{secrets.x}}, así el token nunca queda en el archivo.

Esos son los tipos que hay. Para una API con token, iniciá sesión con una request, extraé el token y usalo como bearer ({{token}}): eso cubre la mayoría de los flujos de login. No hay flujos OAuth 2, certificados de cliente ni firma de requests.

Opciones de la request #

Opciones ajusta una request: timeout (milisegundos, 30 000 por defecto, 0 para ninguno), redirects (cuántas seguir, 10 por defecto, como máximo 20), tamaño máximo de la respuesta (50 MB), HTTP/2, HTTP plano (permitir http: hacia un host que no es localhost) y una CA propia (un archivo .pem del proyecto, en el que se confía además de las habituales, para un servidor con su propio certificado). HTTP plano y una CA propia bajan la protección de la conexión, así que la ventana avisa cuando los activás.

Una opción vacía hereda, y el editor dice de dónde, en gris ("30000 ms, por defecto"). El orden es: las opciones de request del entorno, después las de la pipeline o la colección, después las de la request. Gana la más cercana.

Una request también se puede marcar como responde siempre lo mismo: eso importa solo en un test de carga.

Copiar como cURL #

En una pipeline, el botón de terminal en la fila de una request la copia como un comando curl, con los valores que tenés en la ventana. Los secretos nunca se escriben: se vuelven ${ULTRAMAN_SECRET_NAME}, así que el comando funciona en una shell donde definas esa variable y es seguro pegarlo en un chat. La dirección contraria también funciona en el área de Requests: pegá un comando curl en el path y se vuelve la request.

Redirects y Tiempos #

Una respuesta que fue redirigida tiene una pestaña Redirects: cada salto con su status, la URL que respondió y sus headers (el location al que apuntaba, un set-cookie en el camino). Tiempos dice dónde se fue el tiempo. Las redirecciones se siguen hasta el límite de la opción redirects. Dos reglas te protegen: cuando una redirección va a otro origen, se descartan los headers authorization, cookie y proxy-authorization, y un 307 o 308 que enviaría a otro origen un body que contiene un secreto no se sigue (la respuesta que ves es esa redirección, con adónde apuntaba). Mirá redirecciones.

Checks #

Un check es un assert (la request tiene que responder algo) o un extract (guardar un valor para después). Corren en cada envío, y la pestaña Checks de la respuesta dice cuáles pasaron.

CheckPasa cuando
statusel status HTTP es el indicado
equals, notEqualsun valor es (o no es) el indicado
containsun valor o el body lo contiene
lessThan, greaterThanun número (o el tiempo en ms) está por debajo o por encima
exists, notExistsun path JSON o un header está
matchesun texto cumple una expresión regular
typeun valor JSON es string, número, array…
schemaun valor cumple un JSON Schema

La forma más rápida de agregar uno: en el body de la respuesta, pasá el mouse sobre un valor y usá su menú.

Generar checks #

Generar checks mira la respuesta que tenés en pantalla y te propone checks para ella:

  • que el status sea el que recibió;
  • por cada campo de primer nivel del JSON (o del primer elemento, si es una lista), que exista y su tipo.

Agrega como máximo 30, salta los que la request ya tiene y no guarda nada hasta que apretás Guardar: miralos en la pestaña Checks y borrá los que no quieras. Es un punto de partida para un test de contrato; los valores que cambian en cada llamada (ids, fechas, tokens) se chequean por tipo, nunca por valor. En el área de Pipelines, el mismo botón los agrega como pasos justo después de la request.

La sesión #

Hay una sesión por entorno. Lo que extrae un check (el token del login) queda disponible para la próxima request (Authorization: Bearer {{token}}). Las variables de la colección son los valores iniciales.

Historial #

Cada envío queda en el Historial (al lado de Colecciones): lo que se mandó, la respuesta, el tiempo y los checks. Cada envío muestra el tiempo habitual de esa request ("212 ms · suele tardar 180 ms") y se marca cuando es más lento. Una entrada se puede reabrir tal como se envió, o compararse con otra lado a lado. El historial es personal: nunca se sincroniza.

Deriva del contrato #

Después de un envío, si el envío anterior de la misma request también devolvió JSON, un cartel dice qué campos desaparecieron o cambiaron de tipo ($.id: string → number). Comparar abre los dos; Generar checks convierte la forma actual en checks.

Copias vinculadas #

Agregar a un pipeline… pone una request al final de una pipeline como una copia vinculada (recuerda de dónde vino). Cuando la cambiás en un lugar, Ultraman pregunta si querés actualizar las otras copias. Una request WebSocket o SSE va como su paso connect vinculado (solo el handshake: sus mensajes y la escucha quedan en el área de Requests) y la sigue de la misma manera.

Streams: WebSocket y SSE #

Abrí un stream WebSocket o SSE en una pestaña como una request: mirá cada mensaje a medida que llega, enviá uno desde un compositor, filtrá y pausá la lista, y guardá toda la sesión en el Historial.

El menú de una colección tiene Nuevo WebSocket o SSE. Una request de stream es un archivo como cualquier otro (websocket: live o sse: prices como primera clave), abierto en una pestaña con el mismo diseño que una request. La píldora del método es una elección WebSocket | SSE, el path va después del host de la colección (https pasa a ser wss, http pasa a ser ws), y las pestañas son Params, Headers, Auth, Opciones (incluidas las propias del stream: tamaño de mensaje, ping, inactividad), Mensajes, Checks y Notas.

Conectar (Ctrl/Cmd+Enter) abre el stream y pasa a ser Desconectar mientras está abierto. Debajo, el panel del stream muestra una píldora de estado (connecting…, open 101, closed 1000), un reloj, cuántos mensajes fueron en cada dirección y tres pestañas:

  • Mensajes: una fila por mensaje, el más nuevo abajo, con su dirección (↓ recibido, ↑ enviado), hora, tamaño y, en SSE, el nombre del event y el id. Hacé clic en una fila para abrirla en el visor de body. Filtrar oculta filas por texto (o event:price en SSE), Pausar detiene el movimiento de la lista mientras los mensajes siguen contando, Limpiar la vacía.
  • Handshake: los headers del servidor (y el protocolo que eligió).
  • Checks: los checks de la request corridos sobre el handshake (status, un header).

En un WebSocket, el compositor debajo de la lista envía un mensaje (texto o JSON, Ctrl+Enter). Puede elegir uno de los mensajes guardados de la request, y Guardar como mensaje agrega a la request el texto del compositor. Un mensaje con {{secrets.x}} se envía con el valor y se muestra como [secret:x]. Cuando la bóveda se bloquea, también se cierra un stream que usó un secreto.

El panel guarda los 500 mensajes más nuevos, cada uno cortado a 64 KB. Cuando el stream termina (vos, el servidor, un error), toda la sesión pasa a ser una entrada en el Historial: su handshake, sus mensajes y cómo terminó.

En una ejecución de colección, en ultraman run --collection y cuando la envía un agente, una request de stream conecta, chequea el handshake, envía sus mensajes guardados, escucha durante listen ms (2 segundos salvo que el archivo diga otra cosa) y cierra. Un stream callado no es un fallo. Para esperar un mensaje en particular y chequearlo, poné el stream en una pipeline.

Acá no hay: una request de stream no tiene mock, ni deriva, ni reconexión (si el servidor te corta, volvé a Conectar), y no se soportan Socket.IO ni los WebSocket comprimidos (deflate) (Si venís de otra herramienta).

Qué te mantiene a salvo #

La promesa vale acá como en todos lados. Lo que suma esta parte:

  • Vos y tu equipo: el body de un archivo sale sin preguntar solo desde ultraman/files/; cualquier otro archivo pregunta primero. Mirá archivos.
  • Vos: una redirección a otro origen no se lleva tus credenciales. Mirá redirecciones.
  • Tu equipo: el historial es personal y nunca se sincroniza, así que las respuestas con datos reales quedan en tu máquina. Mirá dónde se guarda cada cosa.
