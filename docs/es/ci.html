CI #

Ultraman corre en un pipeline de build con las mismas pipelines que usás en tu máquina, escribe un reporte JUnit y hace fallar el job cuando falla un paso o un umbral. Para GitHub Actions hay una action que además evita que los secretos vayan a algún lado que nadie aprobó. Para otros sistemas instalás el comando y lo llamás.

La GitHub Action #

ultraman-app/run-action@v1 instala solo el comando ultraman en el runner (Linux, macOS o Windows), corre tus pipelines o un test de carga y escribe el reporte JUnit. Sale igual que ultraman run: 1 cuando falla un paso o un umbral, 2 cuando no pudo correr (un input incorrecto, un valor que falta, un secreto que nadie permitió que vaya adonde lo manda una pipeline).

- uses: actions/checkout@v4
  with:
    persist-credentials: false
- uses: ultraman-app/run-action@v1
  env:
    ULTRAMAN_SECRET_API_KEY: ${{ secrets.API_KEY }}
  with:
    args: --tag smoke
    env: staging
    allow: api_key=https://staging.example.com

persist-credentials: false mantiene el token de GitHub del job fuera de la carpeta del proyecto; la action se niega a correr junto a él.

El reporte JUnit #

El reporte se escribe incluso cuando la corrida falla. Subilo para que las fallas se vean en el job:

- uses: ultraman-app/run-action@v1
  id: ultraman
  with:
    pipelines: create order
- uses: actions/upload-artifact@v4
  if: always()
  with:
    name: ultraman-junit
    path: ${{ steps.ultraman.outputs.junit }}
    retention-days: 7

Sin if: always() la subida se saltea justo cuando la necesitás.

Los inputs de la action #

InputQué hace
pipelinesPipelines a correr, una por línea. Dejalo vacío y usá args para --all, --tag X o --collection ID.
argsMás flags para ultraman run: --parallel 4, --bail... Se separan por espacios, así que un valor con espacio no puede ir acá.
loadUn test de carga a correr en su lugar; sus umbrales deciden el código de salida.
envEl entorno (ultraman/envs/<env>.yaml).
local-envLos valores solo de máquina del entorno. Ver valores locales.
allowQué secreto puede ir a qué origen. Ver allow.
yestrue pasa --yes. Por defecto false. Ver yes.
working-directoryLa carpeta que contiene ultraman/. Por defecto .
junitLa ruta del reporte dentro de ella. Por defecto ultraman-junit.xml.
versionLa versión de Ultraman a instalar, o latest (la de por defecto). Fijá una para corridas repetibles.

Salidas: junit (la ruta del reporte) y exit-code (0, 1 o 2).

Cada secreto que una pipeline usa como {{secrets.name}} viene de una variable ULTRAMAN_SECRET_<NAME> (ver la terminal): mapeá tus secrets de GitHub a ellas en el env: del paso, solo los que usan las pipelines. Ultraman escribe [secret:name] en todo lo que imprime y guarda, y GitHub también los enmascara en el log. La action siempre corre las pipelines en su propio proceso, nunca a través de un Ultraman que ya esté abierto en el runner.

Adónde puede ir un secreto: allow #

En tu máquina Ultraman pregunta antes de que un secreto vaya por primera vez a un origen. Un runner no tiene a quién preguntar, así que el workflow lo dice de antemano: allow lista, uno por línea, name=origin para cada secreto (un esquema, un host y un puerto si no es el de por defecto; sin path, sin barra final).

allow: |
  api_key=https://staging.example.com
  admin_token=https://admin.staging.example.com

Una pipeline que mandara un secreto a cualquier otro lado se rechaza antes de mandar nada (salida 2). Así, un pull request que cambia una pipeline o un entorno para apuntar un secreto a otro host no puede mandarlo ahí. Esto protege los secretos de tu equipo de un archivo cambiado; no puede protegerlos de un archivo de workflow cambiado, que corre lo que diga. GitHub no da secrets a los workflows de forks en pull_request; nunca hagas checkout del código de un pull request bajo pull_request_target o workflow_run con tus secretos a mano.

yes: la forma riesgosa #

yes: true deja que todo secreto vaya adonde digan las pipelines, sin preguntar nada. Cualquiera que pueda cambiar una pipeline o un entorno en la rama que se prueba puede entonces mandar tus secretos a un servidor suyo. Usalo solo para ramas a las que únicamente tu equipo puede hacer push, nunca para pull requests de forks, y preferí allow. Si querés la protección de allow, tampoco pongas --yes en args.

Archivos que manda una request #

Solo los archivos bajo ultraman/files/ salen sin un sí (la app de escritorio copia ahí los archivos que elegís). Un body, una parte multipart, un certificado o un mensaje de stream leído de cualquier otro lugar del repositorio necesita un sí la primera vez, y un runner no tiene a quién pedírselo: la corrida se detiene con salida 2 antes de mandar nada. Guardá en ultraman/files/ los archivos que mandan tus requests. Ver Seguridad y consentimiento.

Tests de carga en CI #

- uses: ultraman-app/run-action@v1
  with:
    load: checkout-peak
    env: staging
    allow: api_key=https://staging.example.com

Los umbrales del test deciden el código de salida: pasa cuando todos se cumplieron y el veredicto es aguanta, encola o limitado. Ver Carga para saber qué significan. Dos puntos para una máquina de build:

  • Cargá solo una API propia, y dimensioná el test para el runner: un runner compartido es una computadora chica, y un veredicto limitado dice que los números describen al runner, no al servidor.
  • --baseline last compara con el último reporte guardado en ultraman/loads/, y un runner nuevo no tiene ninguno, así que no imprime nada. Guardá el reporte con el que querés comparar (como artifact o en un cache), restauralo antes de la corrida y pasá su ruta: --baseline previous/load.json. --output load.json escribe el reporte a guardar.

Valores que viven en la máquina de una persona #

Algunos valores de entorno no están en git: en cada máquina viven en ultraman/local/envs/<env>.yaml. En un runner la action escribe ese archivo a partir de local-env, un name: value por línea, y primero enmascara cada valor en el log. Los valores son planos: sin comillas, comentarios, valores de varias líneas ni otro YAML; la action se detiene si encuentra alguno.

with:
  env: staging
  local-env: |
    tenant: acme
    user: ${{ vars.TEST_USER }}

Una credencial va mejor en una variable ULTRAMAN_SECRET_*: esas también se ocultan en los reportes, mientras que los valores de local-env se ocultan solo en el log.

Otros sistemas de CI #

Fuera de GitHub Actions no hay allow: --yes es todo o nada. Corrélo solo en ramas que controle tu equipo.

Todo lo que hace la action es el comando ultraman más algunas reglas. En GitLab, Jenkins, CircleCI o tu propio runner:

  1. Instalá solo el comando. En Linux y macOS: curl -fsSL https://ultraman-app.github.io/install.sh | sh -s -- --cli (agregá --version 0.6.2 para fijar una) y asegurate de que ~/.local/bin esté en el PATH. En Windows: $env:ULTRAMAN_CLI_ONLY = 1; irm https://ultraman-app.github.io/install.ps1 | iex. El instalador verifica los checksums firmados del release y trae su propio Node.
  2. Dale los secretos como variables enmascaradas llamadas ULTRAMAN_SECRET_<NAME>.
  3. Corrélo. El código de salida decide el job:
ultraman run --all --env ci --yes --junit reports/ultraman.xml
  1. Elegí `--yes` a conciencia. Un runner no tiene terminal, así que un secreto que va a un origen, un archivo de fuera de ultraman/files/ o una carpeta sin confianza necesitan --yes. La línea de comandos no tiene un equivalente de allow: --yes es todo o nada, con el mismo riesgo que yes: true de arriba. Agregá --local en un runner compartido.
  2. Valores solo de máquina (ultraman/local/envs/) no están en git: pasalos como variables de CI o escribí el archivo en un script.
  3. El reporte. Apuntá tu sistema al archivo. Ejemplos, que conviene que verifiques con la documentación de tu sistema:
# GitLab CI (.gitlab-ci.yml)
ultraman:
  script:
    - curl -fsSL https://ultraman-app.github.io/install.sh | sh -s -- --cli
    - export PATH="$HOME/.local/bin:$PATH"
    - ultraman run --all --env ci --yes --junit reports/ultraman.xml
  artifacts:
    reports:
      junit: reports/ultraman.xml

En Jenkins el paso junit lee el archivo (junit testResults: 'reports/ultraman.xml'), corrido en un bloque post { always { } } para que una corrida fallida igual se reporte.

Los tests de carga funcionan igual: ultraman run --load checkout-peak --env staging --yes --junit load.xml --output load.json.
