CI #

Ultraman se ejecuta en una pipeline de build con las mismas pipelines que usas en tu máquina, escribe un reporte JUnit y hace fallar el job cuando falla un paso o un umbral. Para GitHub Actions hay una action que, además, impide que los secretos vayan a cualquier lugar que nadie haya aprobado. En otros sistemas, instalas el comando y lo llamas.

La GitHub Action #

ultraman-app/run-action@v1 instala solo el comando ultraman en el runner (Linux, macOS o Windows), ejecuta tus pipelines o una prueba de carga y escribe el reporte JUnit. Termina igual que ultraman run: con 1 cuando falla un paso o un umbral, y con 2 cuando no pudo ejecutarse (un input incorrecto, un valor que falta, un secreto al que nadie le permitió ir adonde lo envía una pipeline).

- uses: actions/checkout@v4
  with:
    persist-credentials: false
- uses: ultraman-app/run-action@v1
  env:
    ULTRAMAN_SECRET_API_KEY: ${{ secrets.API_KEY }}
  with:
    args: --tag smoke
    env: staging
    allow: api_key=https://staging.example.com

persist-credentials: false deja el token de GitHub del job fuera de la carpeta del proyecto; la action se niega a ejecutarse si lo encuentra ahí.

El reporte JUnit #

El reporte se escribe aunque la ejecución falle. Súbelo para que los fallos aparezcan en el job:

- uses: ultraman-app/run-action@v1
  id: ultraman
  with:
    pipelines: create order
- uses: actions/upload-artifact@v4
  if: always()
  with:
    name: ultraman-junit
    path: ${{ steps.ultraman.outputs.junit }}
    retention-days: 7

Sin if: always(), la subida se omite justo cuando la necesitas.

Los inputs de la action #

InputQué hace
pipelinesLas pipelines que se ejecutan, una por línea. Déjalo vacío y usa args para --all, --tag X o --collection ID.
argsMás flags para ultraman run: --parallel 4, --bail... Se separan por espacios, así que aquí no cabe un valor que contenga un espacio.
loadUna prueba de carga que se ejecuta en su lugar; sus umbrales deciden el código de salida.
envEl entorno (ultraman/envs/<env>.yaml).
local-envLos valores del entorno que solo viven en cada máquina. Consulta valores locales.
allowQué secreto puede ir a qué origen. Consulta allow.
yestrue pasa --yes. Por defecto, false. Consulta yes.
working-directoryLa carpeta que contiene ultraman/. Por defecto, .
junitLa ruta del reporte dentro de esa carpeta. Por defecto, ultraman-junit.xml.
versionLa versión de Ultraman que se instala, o latest (por defecto). Fija una para que las ejecuciones sean repetibles.

Salidas: junit (la ruta del reporte) y exit-code (0, 1 o 2).

Cada secreto que una pipeline usa como {{secrets.name}} sale de una variable ULTRAMAN_SECRET_<NAME> (consulta la terminal): asigna tus secrets de GitHub a esas variables en el env: del paso, solo los que usan las pipelines. Ultraman escribe [secret:name] en todo lo que muestra y guarda, y GitHub también los enmascara en el log. La action siempre ejecuta las pipelines en su propio proceso, nunca a través de un Ultraman que ya esté abierto en el runner.

Adónde puede ir un secreto: allow #

En tu máquina, Ultraman pregunta antes de que un secreto vaya por primera vez a un origen. En un runner no hay nadie a quien preguntar, así que el workflow lo indica de antemano: allow enumera, uno por línea, name=origin para cada secreto (un esquema, un host y un puerto si no es el de por defecto; sin path ni barra final).

allow: |
  api_key=https://staging.example.com
  admin_token=https://admin.staging.example.com

Una pipeline que enviaría un secreto a cualquier otro lugar se rechaza antes de enviar nada (salida 2). Así, un pull request que modifica una pipeline o un entorno para dirigir un secreto a otro host no puede enviarlo allí. Esto protege los secretos de tu equipo frente a un archivo modificado; no los protege frente a un archivo de workflow modificado, que ejecuta lo que diga. GitHub no da secrets a los workflows de forks en pull_request; nunca hagas checkout del código de un pull request en pull_request_target o workflow_run con tus secretos a su alcance.

yes: la opción arriesgada #

yes: true deja que cada secreto vaya adonde indiquen las pipelines, sin preguntar nada. Cualquiera que pueda modificar una pipeline o un entorno en la rama que se prueba puede entonces enviar tus secretos a un servidor propio. Úsalo solo en ramas a las que únicamente tu equipo puede hacer push, nunca en pull requests de forks, y prefiere allow. Si quieres la protección de allow, tampoco pongas --yes en args.

Archivos que envía una request #

Solo los archivos que están en ultraman/files/ salen sin un sí (la app de escritorio copia ahí los archivos que eliges). Un body, una parte multipart, un certificado o un mensaje de stream que se lea de cualquier otro lugar del repositorio necesita un sí la primera vez, y en un runner no hay nadie que pueda darlo: la ejecución se detiene con salida 2 antes de enviar nada. Guarda en ultraman/files/ los archivos que envían tus requests. Consulta Seguridad y consentimiento.

Pruebas de carga en CI #

- uses: ultraman-app/run-action@v1
  with:
    load: checkout-peak
    env: staging
    allow: api_key=https://staging.example.com

Los umbrales de la prueba deciden el código de salida: pasa cuando se cumplieron todos y el veredicto es aguanta, encola o limitado. En Carga se explica qué significan. Dos cosas a tener en cuenta en una máquina de build:

  • Carga solo una API propia y dimensiona la prueba para el runner: un runner compartido es una computadora pequeña, y un veredicto limitado indica que los números describen al runner, no al servidor.
  • --baseline last compara con el último reporte guardado en ultraman/loads/, y un runner recién creado no tiene ninguno, así que no muestra nada. Conserva el reporte con el que quieres comparar (como artifact o en una caché), restáuralo antes de la ejecución y pasa su ruta: --baseline previous/load.json. --output load.json escribe el reporte que vas a conservar.

Valores que viven en la máquina de cada desarrollador #

Algunos valores de entorno no están en git: en cada máquina viven en ultraman/local/envs/<env>.yaml. En un runner, la action escribe ese archivo a partir de local-env, un name: value por línea, y antes enmascara cada valor en el log. Los valores son simples: sin comillas, comentarios, valores de varias líneas ni ningún otro YAML; si encuentra alguno, la action se detiene.

with:
  env: staging
  local-env: |
    tenant: acme
    user: ${{ vars.TEST_USER }}

Una credencial debe ir en una variable ULTRAMAN_SECRET_*: esas también se ocultan en los reportes, mientras que los valores de local-env solo se ocultan en el log.

Otros sistemas de CI #

Fuera de GitHub Actions no existe allow: --yes es todo o nada. Ejecútalo solo en ramas que controle tu equipo.

Todo lo que hace la action se reduce al comando ultraman más unas cuantas reglas. En GitLab, Jenkins, CircleCI o tu propio runner:

  1. Instala solo el comando. En Linux y macOS: curl -fsSL https://ultraman-app.github.io/install.sh | sh -s -- --cli (agrega --version 0.6.2 para fijar una) y asegúrate de que ~/.local/bin esté en el PATH. En Windows: $env:ULTRAMAN_CLI_ONLY = 1; irm https://ultraman-app.github.io/install.ps1 | iex. El instalador verifica los checksums firmados del release y trae su propio Node.
  2. Pásale los secretos como variables enmascaradas llamadas ULTRAMAN_SECRET_<NAME>.
  3. Ejecútalo. El código de salida decide si el job pasa:
ultraman run --all --env ci --yes --junit reports/ultraman.xml
  1. Usa `--yes` sabiendo lo que implica. Un runner no tiene terminal, así que un secreto que va a un origen, un archivo de fuera de ultraman/files/ o una carpeta sin confianza necesitan --yes. La línea de comandos no tiene un equivalente a allow: --yes es todo o nada, con el mismo riesgo que yes: true más arriba. En un runner compartido, agrega --local.
  2. Los valores que solo viven en cada máquina (ultraman/local/envs/) no están en git: pásalos como variables de CI o escribe el archivo con un script.
  3. El reporte. Indica a tu sistema dónde está el archivo. Estos son ejemplos; compruébalos con la documentación de tu sistema:
# GitLab CI (.gitlab-ci.yml)
ultraman:
  script:
    - curl -fsSL https://ultraman-app.github.io/install.sh | sh -s -- --cli
    - export PATH="$HOME/.local/bin:$PATH"
    - ultraman run --all --env ci --yes --junit reports/ultraman.xml
  artifacts:
    reports:
      junit: reports/ultraman.xml

En Jenkins, el paso junit lee el archivo (junit testResults: 'reports/ultraman.xml'); ejecútalo dentro de un bloque post { always { } } para que también se reporte una ejecución fallida.

Las pruebas de carga funcionan igual: ultraman run --load checkout-peak --env staging --yes --junit load.xml --output load.json.
