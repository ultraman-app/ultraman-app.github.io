Pipelines #

Una pipeline es un flujo de requests y checks que se lee de arriba hacia abajo, guardado en ultraman/pipelines/<nombre>.yaml y que se corre desde la ventana o desde la terminal. Tiene un host, auth y headers opcionales para todas sus requests, inputs (valores que la corrida pide) y pasos. Nada queda escondido: lo que hace un paso es lo que dice su fila.

Los pasos #

PasoQué hace
requestmanda una request HTTP; los demás se refieren a ella como $nombre
extracttoma un valor de una respuesta (path JSON, header o regex) y lo guarda en {{nombre}}
assertchequea algo de una respuesta (ver Checks)
waitespera unos milisegundos
repeatcorre sus pasos N veces, o una vez por elemento de una lista
ifcorre sus pasos solo si se cumple una condición
usecorre un bloque (una pipeline reutilizable) con sus inputs
parallelcorre ramas al mismo tiempo; el paso siguiente espera a todas
websocket, sseabre un stream; los demás se refieren a él como $nombre (el handshake)
sendescribe un mensaje en un WebSocket
receiveespera el próximo mensaje de un stream que cumple un filtro; los demás se refieren a él como $nombre
closecierra un stream (uno que queda abierto se cierra al terminar la corrida)

Agregar paso explica cada uno. El + entre dos pasos inserta uno justo ahí. Desde una colección… agrega una request de una colección, con sus checks, como copia vinculada.

Streams en una pipeline #

Un stream WebSocket o SSE son cuatro tipos de paso que se ven, en orden: abrirlo, enviar, esperar un mensaje, cerrarlo. El host de la pipeline también sirve al stream (https pasa a wss).

steps:
  - websocket: live
    path: /live

  - send: live
    json: { subscribe: orders }

  - receive: update
    from: $live
    where: { path: $.type, equals: order.updated }
    timeout: 5000

  - assert: equals
    of: $update
    path: $.status
    equals: shipped

  - close: live
    code: 1000
    reason: done

$live es el handshake, así que assert: status of: $live equals: 101 funciona. Un mensaje recibido es una respuesta como cualquier otra: su texto es el body, y extract y assert lo leen con un path JSON. En SSE, el event y el id del evento se leen como headers (header: event).

receive toma el próximo mensaje que cumple su where. Los anteriores se pasan por alto y se cuentan, y un segundo receive empieza después del mensaje que cumplió el primero. Sin where, cualquier mensaje cumple. Si nada cumple en timeout ms (el options.timeout del stream si el paso no tiene uno), el paso falla y muestra los últimos tres mensajes que pasó por alto.

wherecumple cuando
{ path: $.type, equals: order.created }el body JSON tiene ese valor en el path
{ path: $.id, exists: true }el path encuentra algo
{ contains: shipped }el texto lo contiene
{ matches: /^ord_/ }el texto cumple una regex
{ event: price }solo SSE: el nombre del evento; puede ir junto con uno de los anteriores

repeat: 10 alrededor de un receive junta diez mensajes. En una corrida, el pliegue Mensajes bajo la fila websocket o sse lista todo lo que llevó el stream, en los dos sentidos, así que se ve lo que llegó entre un paso y otro. Una request de stream del área Requests también se puede agregar a una pipeline (Desde una colección…).

Un token en el subprotocolo. Algunos servidores (Kubernetes exec, algunos gateways de GraphQL sobre WebSocket) aceptan el token solo en Sec-WebSocket-Protocol. Para esos casos protocols acepta un secreto, protocols: [v4.channel.k8s.io, "{{secrets.kube_token}}"], con el mismo sí que un header, y se muestra como [secret:kube_token] en todos lados. Preferí un header Authorization cuando el servidor lo acepta: los proxies suelen registrar los subprotocolos. Los detalles están en la referencia del formato.

Inputs #

inputs: [user] declara valores que la pipeline necesita y no tiene. Correr los pide en un diálogo; en la terminal los pasás con --input user=ana (ver la terminal), y un bloque los recibe de use … with. Una corrida a la que le falta un input no arranca. Dentro de la pipeline un input es una variable, {{user}}.

Headers para todas las requests #

headers: en una pipeline (o en un bloque, o en una colección) lo mandan todas sus requests. Un paso que define el mismo header, con cualquier combinación de mayúsculas, conserva el suyo. Los headers de un bloque son solo del bloque: la pipeline que lo llama no pasa sus headers a las requests del bloque. Un secreto en un header compartido pide el sí de su host igual que uno en un paso.

name: orders
host: "{{env.api}}"
headers: { x-tenant: acme }
steps:
  - request: list
    method: GET
    path: /orders

Al mismo tiempo #

parallel corre dos o más ramas a la vez y el paso siguiente espera a todas. Que una rama falle no frena a las otras: el parallel falla cuando todas terminaron. Dos ramas no pueden extraer la misma variable.

- parallel: dashboard
  branches:
    - - request: me
        method: GET
        path: /me
    - - request: orders
        method: GET
        path: /orders

Encontrar lo que buscás #

Dale etiquetas a una pipeline en Auth y opciones (Enter o una coma agrega una) y aparecen como chips debajo de su nombre; un clic en un chip filtra por ella. Cada barra lateral tiene una caja Filtrar… (un nombre, o #etiqueta). Ctrl+P (Cmd+P en macOS) abre una sola caja sobre pipelines, bloques y requests: escribí unas letras del nombre, o #etiqueta, y Enter la abre.

Lista y diagrama #

La Lista muestra cada paso en una línea, tal como los demás se refieren a él. El Diagrama dibuja los mismos pasos con una flecha desde la request que produce un valor hasta la que lo lee, así que el flujo de datos se ve de un vistazo.

Correr #

Correr corre la pipeline de arriba hacia abajo contra el entorno elegido. Cada paso muestra su estado y su tiempo; un check que falla muestra la respuesta que lo hizo fallar. Vigilar la vuelve a correr cuando algo cambia, o con un temporizador. Las corridas anteriores quedan listadas bajo la pipeline.

Bloques #

Un bloque es una pipeline pensada para reutilizarse: un login, una preparación. Declara inputs y exports. Una pipeline lo corre con use: login, y recibe sus exports como variables.

Ayudas #

  • Funciones dentro de {{ }}: random.uuid, random.email, random.int(1, 100), now.iso, counter, base64(x), hmac.sha256(secrets.key, body) y más (ver la referencia del formato).
  • Extract con regex: regex: name="csrf" value="([^"]+)" toma el grupo 1.
  • Extract opcional: cuando no se encuentra nada, la variable queda sin definir en vez de fallar.
  • `if`: corre sus pasos solo cuando se cumple una condición. No hay else.

Juntas cubren los casos de siempre, "el token está en la página, el cupón quizá":

- extract: csrf
  from: $page
  regex: 'name="csrf" value="([^"]+)"'

- extract: coupon
  from: $cart
  path: $.coupon
  optional: true

- if: { exists: coupon }
  steps:
    - request: apply
      method: POST
      path: /cart/coupon
      json: { code: "{{coupon}}" }

No hay scripts a propósito: lo que hace un paso siempre se ve, y quien revisa puede leer una pipeline en un pull request.

Qué te mantiene a salvo #

La promesa rige acá como en todos lados. Lo que suma esta parte:

  • Vos: una condición, un check o una regex nunca lee el contenido de un secreto, ni de un valor hecho a partir de uno: una pipeline que lo hiciera se rechaza en vez de correr, así que una rama que tomes no puede revelar un secreto. Ver la redacción.
  • Tu equipo: una pipeline de una carpeta en la que no confiaste no manda nada desde la ventana. Ver carpetas de confianza.
