Pipelines #

Una pipeline es un flujo de requests y checks que se lee de arriba abajo. Se guarda en ultraman/pipelines/<nombre>.yaml y se ejecuta desde la ventana o desde la terminal. Tiene un host, auth y headers opcionales para todas sus requests, inputs (valores que la ejecución pide) y pasos. No hay nada oculto: lo que hace un paso es lo que dice su fila.

Los pasos #

PasoQué hace
requestenvía una request HTTP; los demás pasos la nombran como $nombre
extracttoma un valor de una respuesta (path JSON, header o regex) y lo guarda en {{nombre}}
assertcomprueba algo de una respuesta (ver Checks)
waitespera unos milisegundos
repeatejecuta sus pasos N veces, o una vez por cada elemento de una lista
ifejecuta sus pasos solo si se cumple una condición
useejecuta un bloque (una pipeline reutilizable) con sus inputs
parallelejecuta ramas al mismo tiempo; el paso siguiente espera a que terminen todas
websocket, sseabre un stream; los demás pasos lo nombran como $nombre (el handshake)
sendescribe un mensaje en un WebSocket
receiveespera el siguiente mensaje de un stream que cumpla un filtro; los demás pasos lo nombran como $nombre
closecierra un stream (si alguno queda abierto, se cierra al terminar la ejecución)

Agregar paso explica cada uno. El + entre dos pasos inserta uno justo ahí. Desde una colección… agrega una request de una colección, con sus checks, como copia vinculada.

GraphQL. Un paso request puede llevar un body GraphQL, que se edita igual que en el área de Requests (ver GraphQL); si está vinculado, usa el schema de su colección. La lista muestra el nombre de su operación (POST /graphql · Order), y una respuesta con errors hace fallar el paso, aunque llegue con un 200.

Streams en una pipeline #

Un stream WebSocket o SSE se compone de cuatro tipos de paso visibles, en orden: abrirlo, enviar, esperar un mensaje y cerrarlo. El host de la pipeline también sirve el stream (https pasa a wss).

steps:
  - websocket: live
    path: /live

  - send: live
    json: { subscribe: orders }

  - receive: update
    from: $live
    where: { path: $.type, equals: order.updated }
    timeout: 5000

  - assert: equals
    of: $update
    path: $.status
    equals: shipped

  - close: live
    code: 1000
    reason: done

$live es el handshake, así que assert: status of: $live equals: 101 funciona. Un mensaje recibido es una respuesta como cualquier otra: su texto es el body, y extract y assert lo leen con un path JSON. En SSE, el event y el id del evento se leen como headers (header: event).

receive toma el siguiente mensaje que cumpla su where. Los mensajes anteriores se saltan y se cuentan, y un segundo receive empieza después del mensaje que encontró el primero. Sin where, cualquier mensaje sirve. Si ninguno cumple en timeout ms (el options.timeout del stream si el paso no tiene uno), el paso falla y muestra los tres últimos mensajes que saltó. Un timeout de 0 espera sin límite, hasta que un mensaje cumpla, el stream termine o detengas la ejecución.

wherecumple cuando
{ path: $.type, equals: order.created }el body JSON tiene ese valor en el path
{ path: $.id, exists: true }el path encuentra algo
{ contains: shipped }el texto lo contiene
{ matches: /^ord_/ }el texto coincide con una regex
{ event: price }solo en SSE: el nombre del evento; se puede combinar con uno de los anteriores

repeat: 10 alrededor de un receive recoge diez mensajes. En una ejecución, la sección plegable Mensajes bajo la fila websocket o sse lista todo lo que pasó por el stream, en ambos sentidos, así que se ve lo que llegó entre un paso y otro. Una request de stream del área de Requests también se puede agregar a una pipeline (Desde una colección…).

Un token en el subprotocolo. Algunos servidores (Kubernetes exec, algunos gateways de GraphQL sobre WebSocket) solo aceptan el token en Sec-WebSocket-Protocol. Para ellos, protocols acepta un secreto, protocols: [v4.channel.k8s.io, "{{secrets.kube_token}}"], con el mismo sí que un header, y se muestra como [secret:kube_token] en todas partes. Si el servidor acepta un header Authorization, úsalo en su lugar: los proxies suelen registrar los subprotocolos en sus logs. Tienes los detalles en la referencia del formato.

Suscripciones GraphQL #

Una suscripción GraphQL es un WebSocket con graphql: y pasos subscribe visibles sobre él; sus eventos se reciben como mensajes.

steps:
  - websocket: live
    path: /graphql
    graphql:
      init: { authorization: "Bearer {{secrets.token}}" }

  - subscribe: orders
    on: $live
    graphql:
      query: |
        subscription { orderCreated { id total } }

  - receive: order
    from: $orders
    where: { path: $.data.orderCreated.total, exists: true }
    timeout: 5000

  - close: orders

  - close: live

graphql: en un paso websocket lo convierte en un socket GraphQL: Ultraman configura el subprotocolo (graphql-transport-ws), envía connection_init con init como payload y espera la confirmación del servidor (ackTimeout ms; si no lo defines, el timeout del paso). Cada subscribe inicia una suscripción sobre él (puedes abrir varias en el mismo socket si las necesitas), cada una con su propio $nombre. Un receive de una suscripción toma su siguiente evento que cumpla el filtro: el body es el payload del evento ({ data, errors }), así que $.data.orderCreated.id lo lee. Un evento con errors hace fallar el receive, salvo que la suscripción tenga allowErrors: true. close: orders termina una suscripción; close: live las termina todas y cierra el socket, igual que el final de la ejecución.

Los mensajes propios del protocolo los gestiona Ultraman: un socket GraphQL no acepta send, y un receive nombra una suscripción, no el socket. El demo incluye esta pipeline como live orders (graphql).

Inputs #

inputs: [user] declara valores que la pipeline necesita y no tiene. Ejecutar te los pide en un diálogo; en la terminal se pasan con --input user=ana (ver la terminal), y un bloque los recibe de use … with. Si falta un input, la ejecución no empieza. Dentro de la pipeline, un input es una variable: {{user}}.

Headers para todas las requests #

Todas las requests de una pipeline (o de un bloque, o de una colección) envían los headers: que esta defina. Un paso que define el mismo header, aunque lo escriba con otras mayúsculas y minúsculas, conserva el suyo. Los headers de un bloque son solo suyos: la pipeline que lo llama no pasa sus headers a las requests del bloque. Un secreto en un header compartido pide el sí de su host igual que uno en un paso.

name: orders
host: "{{env.api}}"
headers: { x-tenant: acme }
steps:
  - request: list
    method: GET
    path: /orders

Al mismo tiempo #

parallel ejecuta dos o más ramas a la vez, y el paso siguiente espera a que terminen todas. Si una rama falla, las demás siguen: el parallel falla cuando todas han terminado. Dos ramas no pueden extraer la misma variable.

- parallel: dashboard
  branches:
    - - request: me
        method: GET
        path: /me
    - - request: orders
        method: GET
        path: /orders

Encuentra lo que buscas #

Ponle etiquetas a una pipeline en Auth y opciones (Enter o una coma agregan una) y aparecerán como chips bajo su nombre; al hacer clic en un chip, se filtra por esa etiqueta. Cada barra lateral tiene un cuadro Filtrar… (un nombre, o #etiqueta). Ctrl+P (Cmd+P en macOS) abre un solo cuadro de búsqueda sobre pipelines, bloques y requests: escribe algunas letras del nombre, o #etiqueta, y pulsa Enter para abrirlo.

Lista y diagrama #

La Lista muestra cada paso en una línea, tal como lo nombran los demás. El Diagrama dibuja los mismos pasos con una flecha desde la request que produce un valor hasta la que lo lee, para que el flujo de datos se vea de un vistazo.

Ejecutar #

Ejecutar recorre la pipeline de arriba abajo con el entorno elegido. Cada paso muestra su estado y su tiempo; un check que falla muestra la respuesta que lo hizo fallar. Vigilar la vuelve a ejecutar cuando algo cambia, o cada cierto tiempo. Las ejecuciones anteriores quedan listadas bajo la pipeline.

Bloques #

Un bloque es una pipeline pensada para reutilizarse: un login, una preparación. Declara inputs y exports. Una pipeline lo ejecuta con use: login y recibe sus exports como variables.

Ayudas #

  • Funciones dentro de {{ }}: random.uuid, random.email, random.int(1, 100), now.iso, counter, base64(x), hmac.sha256(secrets.key, body) y más (ver la referencia del formato).
  • Extract con regex: regex: name="csrf" value="([^"]+)" toma el grupo 1.
  • Extract opcional: si no encuentra nada, la variable queda sin definir en lugar de fallar.
  • `if`: ejecuta sus pasos solo si se cumple una condición. No hay else.

Juntas cubren los casos típicos de "el token está en la página y quizá haya un cupón":

- extract: csrf
  from: $page
  regex: 'name="csrf" value="([^"]+)"'

- extract: coupon
  from: $cart
  path: $.coupon
  optional: true

- if: { exists: coupon }
  steps:
    - request: apply
      method: POST
      path: /cart/coupon
      json: { code: "{{coupon}}" }

No hay scripts, y es a propósito: lo que hace un paso siempre está a la vista, y quien revisa puede leer una pipeline en un pull request.

Qué te mantiene a salvo #

La promesa rige aquí como en todas partes. Esto es lo que agrega esta parte:

  • Tú: una condición, un check o una regex nunca leen el contenido de un secreto, ni el de un valor creado a partir de uno: una pipeline que lo hiciera se rechaza en lugar de ejecutarse, así que la rama que se tome no puede revelar un secreto. Consulta cómo se ocultan los secretos.
  • Tu equipo: una pipeline de una carpeta que no marcaste como de confianza no envía nada desde la ventana. Consulta carpetas de confianza.
