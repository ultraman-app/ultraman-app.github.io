Preguntas #

Respuestas breves a lo que suelen preguntar los equipos antes de adoptar Ultraman, incluidos los "no" honestos. Cada respuesta enlaza a la página donde se explica con más detalle.

Confianza y seguridad #

¿Podría enviar mi token a donde no debe? #

Un secreto solo va a un origen (esquema, host y puerto) al que le diste un sí; la primera vez que iría a un lugar nuevo, Ultraman pregunta, y también lo hace en una terminal. Cuando una redirección lleva a otro origen, las credenciales se descartan. En una carpeta en la que no has confiado, la ventana no envía nada ni ejecuta git. Consulta Seguridad y consentimiento.

¿Un agente de IA puede ver mis secretos? #

No. Un agente conectado por MCP puede usar {{secrets.x}}, pero el valor nunca le llega, y cada llamada muestra en la ventana una tarjeta que tú apruebas o rechazas. No puede desbloquear la bóveda, dar un sí a un host nuevo, confiar en una carpeta, sincronizar con git ni borrar nada. Un token que un paso extrae de una respuesta es un dato, no un secreto: la tarjeta que entrega un resultado resalta los tokens antes de que lo apruebes. Consulta Agentes.

¿Envía algún dato sobre mí? #

No hay telemetría ni cuenta. Mientras la ventana está abierta, Ultraman le pregunta a GitHub, como mucho una vez al día, si hay una versión más reciente, y no envía nada sobre ti ni sobre tus proyectos; ULTRAMAN_NO_UPDATE_CHECK=1 lo desactiva. No se descarga nada hasta que eliges Actualizar y reiniciar. Consulta Qué sale de tu máquina.

¿En qué sistemas funciona? #

Windows (x64), macOS (Apple silicon e Intel) y Linux (x64, como AppImage). Los instaladores no están firmados por Microsoft ni por Apple, así que la primera vez que lo abres aparece una advertencia; las actualizaciones y los checksums de los scripts de instalación sí están firmados. Consulta La advertencia del primer arranque.

¿Cómo comparto secretos con mi equipo? #

No se comparten. Cada persona guarda sus propios valores en su propia bóveda, con los nombres que usa el entorno (staging.token); CI recibe los suyos a través de ULTRAMAN_SECRET_*. El repo solo contiene {{secrets.x}}. Consulta Secretos.

Qué hace y qué no hace #

¿Puedo escribir scripts? #

No, a propósito: lo que hace un paso siempre está a la vista, y quien revisa lo lee en un diff sin ejecutar nada. En su lugar hay asserts, extracts (por path JSON, header o regex), pasos if y repeat, bloques reutilizables y funciones dentro de {{ }} como random.uuid, now.iso, base64(x) y hmac.sha256(secrets.key, body). Al importar, los test scripts habituales de Postman se convierten en checks; los demás scripts aparecen en una lista para ti y nunca se ejecutan. Consulta Ayudas.

¿Qué protocolos soporta? #

HTTP y HTTPS (GraphQL incluido), WebSocket y Server-Sent Events (SSE). Los streams funcionan como requests en el área Requests, como pasos de una pipeline y bajo carga. No se admiten: Socket.IO, WebSockets comprimidos, reconexiones automáticas (vuelve a conectar o escribe el reintento como pasos) ni un mock para streams. Consulta Streams.

¿Soporta gRPC? #

No. Ultraman prueba APIs HTTP, incluidos los streams WebSocket y SSE; para gRPC, elige una herramienta que lo soporte (consulta Cuándo elegir otra herramienta).

¿Soporta GraphQL? #

Sí: una request puede llevar un body GraphQL, con autocompletado a partir del schema de la API (cargado desde el servidor o guardado en el proyecto), y una respuesta con errors hace fallar el paso aunque el status sea 200, también bajo carga. Las suscripciones funcionan sobre graphql-transport-ws, en el área Requests y como pasos de una pipeline. Todavía no: GraphQL sobre SSE, GET y persisted queries, batching ni subida de archivos. Consulta GraphQL.

¿Qué tipos de autenticación admite? #

Bearer token, basic auth y API key (en un header o en la query string), definidos en una request, una colección o una pipeline. ca confía en la autoridad certificadora propia de tu servidor. No hay certificados de cliente (mTLS), flujos OAuth2, AWS SigV4 ni NTLM. Para una API que emite tokens, un paso de login, un extract del token y una auth bearer que lo use cubren el caso habitual. Consulta Pipelines.

¿Puedo traer el trabajo que ya tengo? #

Sí: colecciones y entornos de Postman, documentos OpenAPI 3, planes .jmx de JMeter, scripts de Artillery y tráfico grabado en tu navegador como archivo HAR. Los secretos de un entorno de Postman van a la bóveda. Lo que no se puede traducir aparece en una lista, no se pierde, y una importación nunca envía una request ni ejecuta un script. Consulta Importar.

¿Necesita tener Node, Java u otra cosa instalada? #

No. El instalador trae todo, Node incluido, a tu carpeta de usuario, sin permisos de administrador. Consulta Instalar.

¿Puedo usarlo sin la app de escritorio? #

Sí: instala solo el comando (--cli) en una máquina de build o un servidor. La ventana es donde respondes las preguntas de consentimiento y apruebas las tarjetas de los agentes; el comando, en cambio, pregunta en la terminal. Consulta La terminal.

Equipos y CI #

¿Quién puede ver y modificar nuestras pruebas? #

Quien pueda leer o escribir en tu repo git: Ultraman no tiene cuentas, roles ni workspaces propios. Los cambios en las pruebas llegan al equipo con Sincronizar y se revisan como pull requests. Los secretos nunca se sincronizan: cada persona guarda los suyos en su propia bóveda. Consulta Trabajar en equipo.

¿Qué pasa si dos personas cambiamos la misma pipeline? #

Sincronizar muestra las dos versiones lado a lado, como pasos o como YAML, y eliges Quedarme con la mía, Usar la del remoto o Guardar la mía como copia. Esc cancela sin cambiar nada. Consulta Conflictos.

¿Funciona en CI? #

Sí. ultraman run ejecuta pipelines, colecciones o pruebas de carga, escribe un reporte JUnit y termina con 0 (pasó), 1 (falló un check o un umbral) o 2 (no pudo ejecutarse). En GitHub, la action ultraman-app/run-action@v1 lo instala y lo ejecuta; en otros sistemas, instala solo la CLI. Un runner no tiene bóveda: los secretos llegan por variables de entorno ULTRAMAN_SECRET_<NAME>. Consulta CI.

Carga #

¿Una prueba de carga puede ejecutarse en varias máquinas? #

No. Una carga se ejecuta en una sola computadora, con un hilo por defecto y hasta 8 con --workers. Si necesitas generar carga desde muchas máquinas o desde la nube, elige una herramienta pensada para eso (consulta Cuándo elegir otra herramienta).

¿Cuánta carga puede generar? #

Toda la que pueda enviar tu computadora: depende de la máquina, de la red y de lo pesada que sea cada request. Durante la ejecución, la franja Esta computadora vigila tu máquina, y cuando ella fue el cuello de botella el veredicto dice limited en lugar de culpar a la API. Consulta Más de un hilo.
