Carga #

Carga (al lado de Correr) te dice cuántos usuarios, o cuánto tráfico, aguanta tu API antes de ponerse lenta o fallar. Abre la pantalla de carga de la pipeline que tenés en pantalla: cada usuario virtual corre la pipeline entera en loop, y si un paso falla, esa vuelta cuenta como error y el usuario arranca otra.

Mandá carga solo a una API tuya, o una que tengas permiso de probar. La pantalla de carga muestra el destino antes de empezar y dice lo mismo.

Un test de carga es un archivo #

Su configuración vive en ultraman/load-tests/<nombre>.yaml, compartida por git, así el mismo test corre igual para todos. La primera vez, Carga crea uno con 10 usuarios durante 30 segundos.

La forma de la carga #

Los presets dibujan los usuarios previstos mientras escribís:

PresetForma
Constantelos mismos usuarios todo el tiempo
Subida y sostenidocrece, se sostiene, baja (el thread group de JMeter)
Rampacrece de 0 a los usuarios
Picouna base y un pico repentino
Tasa de arriboN iteraciones nuevas por segundo, tarde lo que tarde la API (el arrivalRate de Artillery)
A medidatus propias etapas

Usuarios (un modelo cerrado) responde "¿aguanta esta cantidad de gente?". Tasa de arribo (un modelo abierto) responde "¿aguanta este tráfico?": si la API se pone lenta, los arribos siguen llegando, como en producción.

Con tasa de arribo, cada arribo es un usuario nuevo que corre una iteración. Máximo de usuarios (maxUsers, 100 si el test no dice otra cosa, 1000 como máximo) es cuántos pueden estar vivos a la vez. Un arribo que los encuentra a todos ocupados se descarta, nunca se pone en cola, y el reporte lo cuenta. Si se descarta más del 1% de los arribos, el veredicto dice que no se llegó a la tasa. Entonces el reporte tiene dos latencias: el tiempo de servicio (desde que se manda hasta que llega la respuesta) y el tiempo de respuesta, contado desde que el arribo debía ocurrir, así que un arranque lento de esta computadora se nota en él.

Por usuario #

En Más:

  • Bloque de preparación: corre una vez por usuario antes de su primera vuelta (loguearse una vez por usuario).
  • Antes y después: un bloque una vez por test (cargar datos, limpiar).
  • Cookies: cada usuario tiene su propio frasco de cookies.
  • Archivo de datos: un CSV o JSON dentro del proyecto; cada fila son los valores de un usuario (o de una vuelta).
  • Pausa (think time) y ritmo (pacing): pausas entre vueltas, y un tiempo mínimo por vuelta.
  • Respuestas: por defecto solo se guardan los bodies que lee un check o un extract, para ahorrar memoria.

Mientras corre #

Fichas y gráficos en vivo muestran requests por segundo, latencia, errores y usuarios. −N, +N, Mantener y Retomar cambian la carga sin pararla. La franja Esta computadora vigila tu propia máquina: si el generador es el cuello de botella, el veredicto dice limited en vez de culpar a la API.

El veredicto #

El reporte empieza con un veredicto en palabras. Son:

VeredictoEn palabras simplesMás o menos cuándo
Aguantala API pudo con la cargafalló menos del 1% de las iteraciones y la latencia no subió al crecer los usuarios
Encolala API se puso más lenta en vez de fallarel p95 del último quinto del test es más de cinco veces el del primer quinto y al menos 50 ms más, y las requests por segundo dejaron de crecer con los usuarios; en un test de tasa de arribo, también cuando se descartó más del 1% de los arribos
Rechazala API contestó erroresfalló más del 1% de las iteraciones; dice cuándo empezaron los errores y con cuántos usuarios
Rotael problema es la pipeline o la dirección, no la cargafallaron todas las primeras 20 iteraciones; "El destino rechaza conexiones" cuando el servidor no es alcanzable
Muy pocas iteracionesno alcanza para concluircorrieron menos de 20 iteraciones; subí el tiempo o los usuarios
Limitadoesta computadora fue el límite, así que los números dicen poco de la APIel hilo, la memoria o las conexiones de Ultraman estaban en su límite
ProtegidoUltraman frenó el test para proteger esta computadorase estaba acabando la memoria; lo que midió hasta ahí está en el reporte

Una carga nunca dice "aguanta" en una computadora que estaba en su límite: dice Limitado. La franja Esta computadora muestra por qué.

El reporte #

Al final, un veredicto en palabras (aguantó, se encoló, se rompió…), las latencias (p50, p95, p99, máx), el throughput, los errores por paso con una request fallida guardada para cada uno, dónde se fue el tiempo y APDEX si el test lo pide.

  • Los umbrales (p95: 500ms, errors: 1%) aprueban o reprueban la corrida; los niveles warn solo avisan.
  • Comparar con pone un reporte contra uno anterior; Tendencia muestra las últimas corridas del test.
  • Exportar escribe una página HTML autocontenida o archivos CSV.

Respuestas que no deben cambiar #

En las Opciones de una request, responde siempre lo mismo marca una request que debería dar la misma respuesta cada vez (una página de producto, una consulta). Bajo carga cada respuesta, status y body, se compara con la primera de esa misma request. Una distinta hace fallar esa iteración, y el reporte muestra cuántas veces y las dos respuestas. Ignorar campos ($.timestamp, $.meta.requestId) deja afuera lo que cambia a propósito. En YAML es idempotent: true o idempotent: { ignore: [$.timestamp] }. Cuando un test descarta los bodies de las respuestas, no hay nada para comparar, y el reporte dice "not compared".

Streams bajo carga #

Una pipeline con pasos websocket o sse es un escenario de carga como cualquier otro: cada iteración abre su propia conexión, corre send y receive sobre ella y la cierra (o lo hace el motor al final de la iteración). Diez usuarios que sostienen un socket veinte segundos cada uno esperando tres actualizaciones es un repeat alrededor de un receive; el demo tiene ese test como live orders.

Con streams en el test, el reporte suma una franja Streams debajo de las fichas: conexiones abiertas, cuántas estuvieron abiertas a la vez y cuántas siguen abiertas al final (debería ser 0), mensajes recibidos y enviados, mensajes por segundo, cuántos streams cerró el servidor (con el código de cierre más común) y cuántos mensajes dejó afuera un tope de tamaño. El gráfico de Usuarios dibuja las conexiones abiertas como una línea punteada. Una fila receive en la tabla de pasos informa el tiempo hasta el mensaje, la latencia del stream, con su propio p95 y tasa de error.

  • streamErrors: 0% es un umbral sobre las conexiones que el servidor cerró a mitad de la corrida y los mensajes que descartó; steps: { update: { p95: 3s } } acota un receive por su nombre.
  • Cada stream guarda como máximo 1 MB en buffer bajo carga, y el lector espera cuando ese buffer se llena.
  • Exportar y --csv agregan -streams.csv con los números de la franja.
  • El veredicto limited aplica acá también: un conteo de conexiones es un límite de la máquina como cualquier otro.

Varios escenarios #

Un test puede mezclar pipelines: tres personas mirando por cada una que compra. Cada escenario tiene sus propias etapas, o comparten las del test repartidas por peso. El reporte tiene una fila y un veredicto por escenario.

Más de un hilo #

Por defecto una carga corre en un hilo. Cuando la franja Esta computadora muestra el hilo en su límite y el veredicto dice limited, repartí los usuarios en más hilos: --workers N (de 1 a 8) en ultraman run --load, o la variable de entorno ULTRAMAN_LOAD_WORKERS; los reportes se juntan en uno. Un test con un bloque before o after corre en un solo hilo.

Qué te mantiene a salvo #

La promesa rige acá como en todos lados. Lo que suma esta parte:

  • Quien es dueño de la API: el destino se muestra antes de que empiece el test, con un recordatorio de probar solo una API propia.
  • Vos: los frenos mantienen o paran usuarios cuando tu computadora está sobrecargada o con poca memoria, en vez de colgarla.
  • Tu equipo: un test de carga nunca guarda un secreto; sus inputs no pueden llevar valores secrets. ni env.. Los reportes en ultraman/loads/ quedan en tu máquina. Ver dónde se guarda cada cosa.
