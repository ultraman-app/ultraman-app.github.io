Documentación de Ultraman

Cómo funciona Ultraman, qué te da cada función y qué protege a tu equipo y a ti.

  1. Lo que te da Ultraman

    Ultraman prueba APIs HTTP, incluidos WebSocket y SSE: una sola app en tu computadora para requests sueltas, pruebas de varios pasos, carga y CI, todo guardado como archivos simples en tu propio repo de git. Ultraman nunca envía nada de forma insegura sin tu consentimiento explícito: un secreto solo va a un host que aprobaste, y una carpeta que no marcaste como de confianza no envía nada.

  2. Por qué Ultraman

    Ultraman reúne requests de API, flujos de prueba, pruebas de carga y checks de CI en una sola app local, guardados como archivos simples en tu propio repo de git. Esta página explica en qué se diferencia de herramientas que quizá ya usas, y cuándo alguna de ellas es mejor opción.

  3. Primeros pasos

    De la instalación de Ultraman a tu primera request y tu primera pipeline, y también cómo se actualiza, por qué tu sistema puede mostrar una advertencia y cómo desinstalarlo.

  4. Seguridad y consentimiento

    Qué te pregunta Ultraman antes de enviar algo, cómo mantiene tus secretos fuera de la vista y qué deja en tus manos: promesas que puedes comprobar, para ti, para tu equipo y para tu CI. No hay telemetría, ni analíticas, ni reportes de fallos, ni cuenta.

  5. Requests

    El área de Requests es donde creas, envías y compruebas requests sueltas: colecciones con carpetas y requests que se abren en pestañas, como en Postman. La diferencia es que cada request lleva sus checks, y todo es un archivo de texto en ultraman/requests/ que tu equipo comparte por git.

  6. Pipelines

    Una pipeline es un flujo de requests y checks que se lee de arriba abajo. Se guarda en ultraman/pipelines/<nombre>.yaml y se ejecuta desde la ventana o desde la terminal. Tiene un host, auth y headers opcionales para todas sus requests, inputs (valores que la ejecución pide) y pasos. No hay nada oculto: lo que hace un paso es lo que dice su fila.

  7. Carga

    Carga (junto a Ejecutar) te dice cuántos usuarios, o cuánto tráfico, aguanta tu API antes de volverse lenta o empezar a fallar. Abre la pantalla de carga de la pipeline que tienes en pantalla: cada usuario virtual ejecuta la pipeline completa en bucle, y si un paso falla, esa iteración cuenta como error y el usuario empieza otra.

  8. Entornos y secretos

    Con los entornos, las mismas requests se ejecutan contra local, staging o producción; con los secretos, los tokens y las contraseñas se quedan en tu computadora, cifrados, fuera de git y fuera de cualquier log.

  9. Importar

    El menú Importar junto a Nueva colección (área de Requests) trae lo que ya tienes: una exportación de Postman, una spec OpenAPI, un plan de JMeter o un script de Artillery; el que está junto a Nueva pipeline (área de Pipelines) trae una grabación del navegador. Así no empiezas desde cero. No se sobrescribe nada del proyecto: si un nombre ya existe, se le agrega -2. Al final, un resumen indica qué entró, qué se adaptó, qué hay que terminar a mano y qué archivos se omitieron.

  10. Servidor mock

    El servidor mock responde las requests a tu API con respuestas que ya grabaste. Así, un front end (o un test) puede seguir trabajando aunque la API real esté caída, vaya lenta o todavía no exista. Se ejecuta en tu computadora y nadie más puede acceder a él, salvo que tú lo decidas.

  11. La terminal

    El comando ultraman ejecuta tus pipelines y pruebas de carga desde una terminal, sirve el proyecto a otras herramientas y guarda secretos en la bóveda. Ejecútalo desde la carpeta del proyecto (o desde cualquier carpeta dentro de ella). Para usarlo en una máquina de build, consulta CI.

  12. CI

    Ultraman se ejecuta en una pipeline de build con las mismas pipelines que usas en tu máquina, escribe un reporte JUnit y hace fallar el job cuando falla un paso o un umbral. Para GitHub Actions hay una action que, además, impide que los secretos vayan a cualquier lugar que nadie haya aprobado. En otros sistemas, instalas el comando y lo llamas.

  13. Trabajar en equipo

    Todo lo que comparte un equipo es un archivo dentro de ultraman/. Así, tus pruebas viajan con tu código, y un cambio en una prueba aparece en un pull request como cualquier otro cambio.

  14. Agentes (MCP)

    Un agente de IA (Claude Code o cualquier otro cliente MCP) puede usar Ultraman a través de ultraman mcp. Puede hacer lo mismo que tú en la ventana: leer y escribir requests, pipelines y pruebas de carga, enviarlas y ejecutarlas, importar, iniciar el servidor mock, leer reportes y compararlos. Tú apruebas cada llamada.

  15. Si vienes de otra herramienta

    Algunas ideas se llaman igual aquí, otras tienen otro nombre y unas pocas no existen a propósito.

  16. Preguntas

    Respuestas breves a lo que suelen preguntar los equipos antes de adoptar Ultraman, incluidos los "no" honestos. Cada respuesta enlaza a la página donde se explica con más detalle.

  17. Format reference (YAML)

    Everything lives as YAML under ultraman/ in the user's project. Unknown keys are errors: write only what's listed. Variables: {{env.x}} (the environment), {{secrets.x}} (a secret: usable, never visible), {{x}} (an input, an extract or a collection variable).
