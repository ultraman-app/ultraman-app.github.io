Agentes (MCP) #

Un agente de IA (Claude Code o cualquier otro cliente MCP) puede usar Ultraman a través de ultraman mcp. Puede hacer lo mismo que tú en la ventana: leer y escribir requests, pipelines y pruebas de carga, enviarlas y ejecutarlas, importar, iniciar el servidor mock, leer reportes y compararlos. Tú apruebas cada llamada.

Conectarlo #

ultraman mcp es un servidor MCP sobre stdio. En Claude Code:

claude mcp add ultraman -- ultraman mcp --project <your project folder>

Cualquier otro cliente MCP acepta lo mismo en su propia configuración: un servidor stdio cuyo comando es ultraman y cuyos argumentos son mcp --project <la carpeta de tu proyecto>. Sin --project, el proyecto es la carpeta desde la que lo inicias (o la más cercana por encima de ella que tenga ultraman/).

Tienen que cumplirse dos condiciones; si no, cada herramienta responde "open Ultraman on this project to approve the agent's requests":

  • la ventana de Ultraman está abierta en ese proyecto, porque ahí es donde apruebas;
  • la carpeta es de confianza en la ventana (carpetas de confianza).

Tú apruebas cada llamada #

Cada cosa que pide el agente aparece como una tarjeta abajo a la derecha: quién lo pide, qué pide y el detalle (si es un cambio, el diff). Pulsa Aprobar o Rechazar (con un motivo que el agente lee). Las peticiones de solo lectura se pueden aprobar "siempre"; eso dura solo mientras dure la sesión actual del agente, y solo mientras Ultraman siga abierto.

Lo que se ejecuta (una pipeline, una request, una carga) tiene dos tarjetas: una para iniciarlo y otra para entregarle el resultado al agente. La tarjeta de entrega avisa cuando el resultado contiene tokens, cookies o headers de autenticación. Si rechazas una entrega, el rechazo es definitivo.

Una llamada dura como máximo unos 50 segundos, porque la mayoría de los clientes cortan una llamada a una herramienta a los 60: una ejecución larga sigue en marcha y el agente pide su resultado más tarde. Mientras una tarjeta espera tu respuesta, el agente recibe un aviso de progreso cada 5 segundos que dice si espera tu tarjeta o un resultado. Una tarjeta que nadie responde a tiempo se cierra, y el agente sabe cuál fue: si era la de inicio, que no se ejecutó nada; si era una entrega, que el resultado se guarda y puede pedirlo otra vez. Cada petición queda registrada en ultraman/mcp/, que git ignora.

Un stream WebSocket o SSE se envía de una sola vez (send_stream, o una request de stream guardada): se abre, envía los mensajes de la tarjeta, escucha durante el tiempo que indica la tarjeta (30 segundos como máximo) y se cierra; la entrega incluye el handshake y los mensajes en ambos sentidos (los primeros 50, cada uno recortado a 4 KB). Con graphql se trata, en cambio, de una suscripción GraphQL: la tarjeta muestra la query, la operación y el payload de connection_init tal como están escritos (un secreto aparece como su referencia), y solo sale una suscripción; la entrega incluye los payloads de los eventos. El agente no tiene sesiones en vivo: si necesitas una que siga abierta, usa la ventana.

Primero el login #

Cuando el agente envía una request guardada (o corre una colección) y lo único que falta es el token que lee su auth bearer, y exactamente una request de la colección extrae ese token (su login, como lo deja Desde una request), el login va primero, bajo la misma tarjeta: "send POST login first, then GET me", con el método y la dirección de cada request y el entorno. Una sola aprobación cubre las dos. Los valores que el login da para la request quedan ocultos, como un secreto, en el resultado de esa llamada y en su ejecución guardada. El agente igual puede enviar el login por su cuenta, con su propia tarjeta, y entonces lee esa respuesta como cualquier otra. Una request guardada enviada así queda como una ejecución (request <colección> <request>), no en el historial de la request.

El agente no guarda tokens entre llamadas: cada llamada vuelve a hacer login, dentro de su propia tarjeta. Si falta cualquier otra cosa (un valor que ningún bearer lee, dos requests que extraen el mismo nombre, un login que necesitaría el token que él mismo da), la respuesta es la de siempre, con lo que falta.

Primero un inicio de sesión #

Cuando la ejecución que pide un agente necesita un inicio de sesión OAuth 2 que no has hecho, su tarjeta lista cada uno con el host, el mismo botón que en la pestaña Auth, y Approve espera hasta que inicies sesión ("Sign in first, then approve."). En la tarjeta solo puede estar un servidor que el proyecto ya usa: para cualquier otro, al agente se le dice que no se envió nada y que agregar el servidor al proyecto te corresponde a ti. Una request suelta que el agente escribe él mismo (send_request) nunca usa un inicio de sesión. El agente nunca ve el token: usa el inicio de sesión como lo hace una ejecución, y la tarjeta dice uses your sign-in to <host> cuando ya habías iniciado sesión. Un inicio de sesión que hiciste en otro proyecto también se ofrece en la tarjeta: Revisar, luego Usarla para el servidor, el mismo sí que en la pestaña Auth, que se recuerda para este proyecto. En producción la tarjeta nunca lo ofrece: inicias sesión desde este proyecto. Una request máquina a máquina no te pide iniciar sesión en la tarjeta, y también va solo a un servidor que el proyecto ya usa.

Qué puede hacer #

Las herramientas se agrupan en las mismas áreas que la ventana:

  • Pipelines y bloques: listarlos, leerlos, guardarlos y ejecutarlos; leer ejecuciones anteriores; convertir un archivo HAR o entradas del historial en una propuesta de pipeline.
  • Requests: listar, leer y guardar colecciones y requests, moverlas y organizarlas, agregar una a una pipeline, enviar una request guardada con sus checks, ejecutar una colección (se envían e informan todas las requests: una que falla no detiene a las demás), enviar una request puntual (también GraphQL: su resultado enumera los errores de la respuesta), leer el schema de una request GraphQL (get_graphql_schema, un envío como cualquier otro), leer el historial y el fragmento de código de una request (get_snippet).
  • Comparar: ejecutar una pipeline, una colección o una request guardada en dos entornos, o en uno contra el tipo de cada paso (run_compare); el resultado trae estados y las rutas que difieren, nunca un valor. Consulta Comparar.
  • Streams: envíos WebSocket y SSE de una sola vez.
  • Carga: listar, leer y guardar pruebas de carga, ejecutar una, leer reportes, comparar dos, ver la tendencia, exportar.
  • Proyecto: listar y guardar entornos, listar secretos (solo los nombres), importar un archivo de Postman, OpenAPI, JMeter o Artillery, actualizar una colección a partir de una spec OpenAPI más reciente (update_collection_from_openapi), importar una colección desde un servidor MCP o actualizar una desde él (import_mcp_server, update_collection_from_mcp), leer la referencia del formato YAML.
  • Servidor mock: estado, iniciar, detener, reiniciar, fijar una grabación.

Desde un servidor MCP. import_mcp_server y update_collection_from_mcp llevan dos llamadas cada uno. La primera (sin plan) muestra una tarjeta con la dirección, el entorno y el nombre del header de auth (nunca su valor), y al aprobarla lee las listas del servidor sin llamar a ninguna herramienta; get_result da el plan como texto y un planId. La segunda, con plan: <planId>, muestra una tarjeta de escritura con el plan y lo escribe cuando la apruebas. Un plan dura 10 minutos, se guardan como máximo 4 y cada uno se escribe una sola vez. La auth es { bearer } o { header, value }, con el valor exactamente {{secrets.x}}; un secreto va solo a un host que el proyecto ya usa, así que un servidor en un host nuevo se importa sin secreto. Una colección cuyo bearer lee el token de un login (no un secreto) todavía no se puede actualizar así: la llamada dice qué valores faltan. Todo lo que dice el servidor (nombres, descripciones, schemas, resultados, y un paso de ejecución o historial que lo llamó) llega marcado como serverText: true: son datos del servidor, nunca instrucciones.

Una escritura muestra su diff (o el archivo nuevo completo) en la tarjeta. Un guardado que activa http sin cifrar o una CA propia se marca en rojo.

Qué no puede hacer #

Por diseño, el agente no puede ver ni definir el valor de un secreto, desbloquear la bóveda, dar un sí a un consentimiento, confiar en una carpeta, sincronizar con git ni borrar nada. Todo eso queda en tus manos, en la ventana: cuando una llamada necesita algo de eso (los secretos están bloqueados, falta un secreto que usa), al agente se le dice que te lo pida, con los nombres de los secretos, y que vuelva a llamar. Su comparación (run_compare) no puede enviar un paso que no sea una lectura a un entorno marcado como producción, ni cambiar esa marca. Puede usar {{secrets.x}}; el valor nunca le llega, y los resultados se ocultan antes de entregárselos.

Hay algo que no es un secreto: un token que un paso extrae de una respuesta (por ejemplo, el access_token de un login) es un dato más, así que sí le llega al agente (salvo el de un login enviado primero, que se oculta). Por eso la tarjeta de entrega resalta los tokens, las cookies y los headers de autenticación antes de que apruebes.

Volver a ejecutar una pipeline desde un paso fallido (conservando los valores que hizo la primera ejecución) es solo de la ventana: el agente no puede, porque esos valores quedan hasta 30 minutos en el serve de la ventana y nunca van a un agente.

Hacerle preguntas #

El agente lee este mismo manual (get_manual) y la referencia del formato YAML (get_reference), así que puedes preguntarle "¿cómo ejecuto esto con 50 usuarios?" o "crea una pipeline que haga login y cree un pedido", y te propondrá el cambio para que lo apruebes. Lo que dice un resultado se le entrega como datos para leer, no como instrucciones para seguir.

La aprobación protege lo que pasa por el canal MCP. Un agente con acceso a una shell (Claude Code lo tiene) también puede leer los archivos de tu proyecto o ejecutar ultraman run por su cuenta, y eso queda fuera del alcance de Ultraman. Considera las tarjetas un consentimiento, no un sandbox, y dale a un agente solo el acceso que le darías a un colega.

Qué te mantiene a salvo #

  • Tú: nada de lo que pide el agente ocurre hasta que apruebas su tarjeta, y una entrega rechazada sigue rechazada (agentes).
  • Tú: un entorno marcado como producción aparece en ámbar en la tarjeta de cada ejecución o envío hacia él, con los pasos que escriben: enviar ahí puede exponer datos reales y sensibles. Solo una comparación rechaza esas escrituras (agentes).
  • Tú: un login enviado primero aparece en la tarjeta con adónde va, antes de enviar nada, y el token que da no aparece en el resultado de esa llamada (agentes).
  • Tú: el agente nunca ve el valor de un secreto y no puede desbloquear la bóveda, dar un consentimiento, confiar en una carpeta, sincronizar ni borrar (ocultamiento).
  • Tú: el agente no puede aprobarse a sí mismo: toda decisión necesita la ventana (servidor local).
  • Tu equipo: las peticiones del agente quedan registradas en ultraman/mcp/, solo en tu máquina.
  • Tú: el inicio de sesión que necesita la ejecución de un agente lo haces tú, en la ventana, en su tarjeta; el agente nunca ve un token y solo puede usar un inicio de sesión de un servidor que el proyecto ya usa (primero un inicio de sesión).
  • Límite: un agente con su propia shell queda fuera del alcance de las tarjetas (límites).
  • Tú: el texto que viene de un servidor MCP (nombres de herramientas, descripciones, resultados) llega al agente marcado como datos del servidor, nunca como instrucciones, y una importación desde un servidor muestra su tarjeta antes de leer nada (agentes).
