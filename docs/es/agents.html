Agentes (MCP) #

Un agente de IA (Claude Code, o cualquier otro cliente MCP) puede usar Ultraman a través de ultraman mcp. Puede hacer lo que hacés vos en la ventana: leer y escribir requests, pipelines y tests de carga, mandarlos y correrlos, importar, iniciar el servidor mock, leer reportes y compararlos. Vos aprobás cada llamada.

Conectarlo #

ultraman mcp es un servidor MCP sobre stdio. En Claude Code:

claude mcp add ultraman -- ultraman mcp --project <your project folder>

Cualquier otro cliente MCP toma lo mismo en su propia configuración: un servidor stdio cuyo comando es ultraman y cuyos argumentos son mcp --project <la carpeta de tu proyecto>. Sin --project, el proyecto es la carpeta desde donde lo iniciás (o la más cercana hacia arriba que tenga ultraman/).

Dos cosas tienen que cumplirse, o cada herramienta responde "open Ultraman on this project to approve the agent's requests":

  • la ventana de Ultraman está abierta en ese proyecto, porque ahí es donde aprobás;
  • la carpeta es de confianza en la ventana (carpetas de confianza).

Vos aprobás cada llamada #

Cada cosa que pide el agente aparece como una tarjeta abajo a la derecha: quién pide, qué, y el detalle (para un cambio, el diff). Aprobar o Rechazar (con un motivo que el agente lee). Las requests de solo lectura se pueden aprobar "siempre"; eso dura solo lo que dure la sesión actual del agente, y solo mientras Ultraman siga abierto.

Lo que corre (una pipeline, una request, una carga) tiene dos tarjetas: una para iniciarlo, y otra para entregarle el resultado al agente. La tarjeta de entrega avisa cuando el resultado lleva tokens, cookies o headers de autenticación. Si rechazás una entrega, es definitivo.

Una llamada dura como mucho unos 50 segundos, porque la mayoría de los clientes cortan una llamada a una herramienta a los 60: una corrida larga sigue andando y el agente pide su resultado más tarde. Mientras una tarjeta espera por vos, el agente recibe un aviso de progreso cada 5 segundos. Cada request queda registrada en ultraman/mcp/, que git ignora.

Un stream WebSocket o SSE se manda una sola vez (send_stream, o una request de stream guardada): se abre, manda los mensajes de la tarjeta, escucha durante el tiempo de la tarjeta (30 segundos como máximo), se cierra, y la entrega lleva el handshake y los mensajes en los dos sentidos (los primeros 50, cada uno cortado a 4 KB). El agente no tiene una sesión en vivo: para una que quede abierta, usá la ventana.

Qué puede hacer #

Las herramientas vienen en áreas que coinciden con la ventana:

  • Pipelines y bloques: listarlos, leerlos, guardarlos y correrlos; leer corridas anteriores; convertir un archivo HAR o entradas del historial en una propuesta de pipeline.
  • Requests: listar, leer y guardar colecciones y requests, moverlas y organizarlas, agregar una a una pipeline, mandar una request guardada con sus checks, correr una colección, mandar una request ad hoc, leer el historial.
  • Streams: envíos WebSocket y SSE de una sola vez.
  • Carga: listar, leer y guardar tests de carga, correr uno, leer reportes, comparar dos, tendencia, exportar.
  • Proyecto: listar y guardar entornos, listar secretos (solo los nombres), importar un archivo de Postman, OpenAPI, JMeter o Artillery, leer la referencia del formato YAML.
  • Servidor mock: estado, iniciar, parar, reiniciar, fijar una grabación.

Una escritura muestra su diff (o el archivo nuevo entero) en la tarjeta. Un guardado que activa http plano o una CA propia se marca en rojo.

Qué no puede hacer #

A propósito, el agente no puede ver ni definir el valor de un secreto, abrir la bóveda, decir que sí a un consentimiento, confiar en una carpeta, sincronizar con git ni borrar nada. Eso queda en tus manos, en la ventana. Puede usar {{secrets.x}}; el valor nunca le llega, y los resultados se redactan antes de entregárselos.

Una cosa no es un secreto: un token que un paso extrae de una respuesta (por ejemplo el access_token de un login) es solo un dato, así que vuelve al agente. Por eso la tarjeta de entrega resalta tokens, cookies y headers de autenticación antes de que apruebes.

Preguntarle cosas #

El agente lee este mismo manual (get_manual) y la referencia del formato YAML (get_reference), así que le podés preguntar "¿cómo corro esto con 50 usuarios?" o "armá una pipeline que haga login y cree una orden" y te va a proponer el cambio para que lo apruebes. Lo que dice un resultado se le entrega como dato para leer, no como instrucciones para seguir.

La aprobación protege lo que pasa por el canal MCP. Un agente con una shell (Claude Code tiene una) también puede leer los archivos de tu proyecto o correr ultraman run por su cuenta: eso queda fuera del alcance de Ultraman. Tomá las tarjetas como consentimiento, no como un sandbox, y dale a un agente solo el acceso que le darías a un colega.

Qué te mantiene a salvo #

  • Vos: nada de lo que pide el agente ocurre hasta que aprobás su tarjeta, y una entrega rechazada sigue rechazada (agentes).
  • Vos: el agente nunca ve el valor de un secreto y no puede abrir la bóveda, dar un consentimiento, confiar en una carpeta, sincronizar ni borrar (redacción).
  • Vos: el agente no puede aprobarse a sí mismo: una decisión necesita la ventana (servidor local).
  • Tu equipo: las requests del agente quedan registradas en ultraman/mcp/, solo en tu máquina.
  • Límite: un agente con su propia shell queda fuera de las tarjetas (límites).
