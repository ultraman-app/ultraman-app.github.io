La terminal #

El comando ultraman corre tus pipelines y tests de carga desde una terminal, sirve el proyecto a otras herramientas y guarda secretos en la bóveda. Corrélo desde la carpeta del proyecto (o cualquier carpeta dentro). Para usarlo en una máquina de build, mirá CI.

Los comandos #

ComandoQué hace
ultraman run <pipeline>Corre una pipeline, buscada por nombre y después por id.
ultraman run --all, --tag X, --collection IDCorre varias pipelines a la vez.
ultraman run --load <test>Reproduce un test de carga; ultraman run <pipeline> --load usa el test por defecto de esa pipeline.
ultraman serve [--port 4100]Inicia el servidor local del proyecto (con el que hablan la ventana y los otros comandos).
ultraman secret set <name>, list, rm <name>, passwordManeja la bóveda.
ultraman mock [--port 4300]Sirve tu historial grabado como una API mock. Ver Servidor mock.
ultraman mcp [--project <folder>]El puente al que se conecta un agente de IA. Ver Agentes.
ultraman --versionImprime la versión.

Un comando sin argumentos, o uno desconocido, imprime el uso y sale con 2.

Correr pipelines #

ultraman run "create order" --env local --input user=ana
ultraman run --all --env ci --yes
ultraman run --tag smoke --env ci --parallel 4
ultraman run --collection shop --env staging

Indicá exactamente una de estas: una pipeline, --all, --tag o --collection; cualquier otra cosa sale con 2. Todo se verifica para todas las pipelines elegidas antes de que salga la primera request.

FlagQué hace
--allTodas las pipelines del proyecto.
--tag XLas pipelines con esa etiqueta. Repetilo y una pipeline necesita todas las etiquetas dadas.
--collection IDCorre una colección; shop/orders corre solo esa carpeta.
--env XEl entorno. Con un solo entorno en el proyecto se usa solo; con varios tenés que pasar --env.
--input k=vUn valor para un input; repetilo para más. Un valor que empieza con [ o { se lee como JSON cuando es válido; cualquier otra cosa queda como texto (id=00123 queda 00123). Los nombres env.* y secrets.* están reservados.
--parallel NCorre hasta N pipelines al mismo tiempo (de 1 a 16). Cada una se imprime entera cuando termina.
--bailDeja de iniciar pipelines nuevas después de la primera que falla. Las que están corriendo terminan; el resto aparece como salteado.
--watchCorre de nuevo cada vez que cambia un archivo bajo ultraman/.
--every DCorre de nuevo con un temporizador: 30s, 5m, 1h o un número pelado de segundos, de 5 segundos como mínimo. Cuenta desde el final de la corrida anterior y se combina con --watch.
--no-notifyCon --watch o --every, sin notificación de escritorio cuando una corrida falla y cuando vuelve a pasar.
--jsonUn evento JSON por línea en la salida estándar, para otras herramientas. Sin colores.
--junit FILEEscribe un reporte JUnit XML. Ver JUnit.
--localCorre en este proceso aunque la ventana tenga el proyecto abierto. Ver Un solo motor.
--yesResponde que sí a toda pregunta. Leé antes Consentimiento en la terminal.

Cada corrida se guarda en ultraman/runs/. Los colores aparecen solo en una terminal; NO_COLOR los apaga. Ctrl+C cancela el paso en curso, guarda la corrida y sale con 1.

Códigos de salida: 0 todo pasó, 1 un paso falló (o apretaste Ctrl+C), 2 no llegó a correr: un flag incorrecto, una pipeline, input, entorno o secreto que falta, una pipeline inválida, o no se mandó nada porque nadie dijo que sí.

Consentimiento en la terminal #

Ultraman pregunta antes de mandar algo que no aprobaste. En una terminal pregunta cuando:

  • la carpeta todavía no es de confianza;
  • un secreto iría a un origen al que nunca fue;
  • se mandaría un archivo de fuera de ultraman/files/.

La pregunta lista qué iría adónde, y respondés y (esta vez), a (siempre, para este proyecto) o N (la opción por defecto: no se manda nada). "Siempre" se guarda en ~/.ultraman/trust.json en tu máquina, nunca en el proyecto, así que el checkout de un compañero no puede llevarlo. El modelo completo está en la página Seguridad y consentimiento.

Sin terminal y sin --yes no hay a quién preguntar: Ultraman lista lo que mandaría y sale con 2, sin haber mandado nada.

`--yes` se saltea todas las preguntas. Todo lo que digan las pipelines y los entornos va entonces adonde digan, incluidos tus secretos, y también va un valor tomado de una respuesta que lleva un secreto. Usalo donde solo tu equipo pueda cambiar esos archivos; nunca con código de forks o de gente que no conocés. CI explica la forma más segura para GitHub Actions.

Correr un test de carga #

ultraman run --load checkout-peak --env staging --junit load.xml --html report.html --baseline last

El test es ultraman/load-tests/<nombre>.yaml, dado por nombre o por id. Además de --env, --input, --junit, --json, --local y --yes (que funcionan como arriba), una carga acepta:

FlagQué hace
--target URLManda todo a otro origen en esta corrida (https://staging.example.com, con un path base opcional, sin usuario, contraseña, ? ni #).
--overrides JSONReemplaza claves de primer nivel del test en esta corrida, escritas como en el YAML.
--workers NReproduce la carga con N hilos (de 1 a 8). Por defecto uno, o ULTRAMAN_LOAD_WORKERS.
--output FILEEscribe el reporte final como JSON.
--html FILEEscribe el reporte como una página autocontenida.
--csv DIREscribe las series y los pasos como archivos CSV en esa carpeta.
--baseline last o un archivoImprime cómo se compara esta corrida con un reporte anterior: el último guardado para este test, o un archivo JSON.

--all, --tag, --collection, --bail, --parallel, --watch y --every no aplican a una carga.

Códigos de salida: 0 todos los umbrales se cumplieron y el veredicto es aguanta, encola o limitado; 1 falló un umbral, la API rechazó o se rompió, salieron muy pocas requests, o se frenó (Ctrl+C o los frenos del propio generador); 2 no se mandó nada. Los umbrales y los veredictos se explican en Carga; para compuertas en una pipeline mirá CI.

JUnit para CI #

--junit FILE escribe un reporte JUnit XML después de las corridas, también tras Ctrl+C con lo que corrió: un test suite por pipeline y un test case por paso de primer nivel, con lo que se mandó y se recibió en los que fallaron. Los secretos están ocultos ahí como en todos lados. Las carpetas que falten se crean.

ultraman run --all --env ci --yes --junit reports/ultraman.xml

Secretos #

En tu máquina, ultraman secret set api-key guarda uno en la bóveda: pide la contraseña maestra y el valor, los dos sin eco. Un valor que viene por pipe (echo "$VALUE" | ultraman secret set api-key) se lee de la entrada estándar; la contraseña maestra igual necesita una terminal. Los nombres usan letras, dígitos, _, . y -. secret list muestra los nombres, secret rm <name> borra uno (sale con 1 si no está) y secret password cambia la contraseña maestra. Ver la bóveda.

En una máquina de build no hay bóveda. Pasá un secreto como variable de entorno llamada ULTRAMAN_SECRET_ más su nombre en mayúsculas, con cada carácter que no sea letra ni dígito convertido en _: api-key es ULTRAMAN_SECRET_API_KEY. Gana sobre la bóveda y no necesita contraseña. Sin --yes, un secreto igual va solo adonde fue aprobado.

Variables de entorno #

VariableQué hace
ULTRAMAN_SECRET_<NAME>El valor de un secreto para este comando.
ULTRAMAN_HOMEReemplaza ~/.ultraman, donde viven la bóveda, la lista de confianza y las claves del servidor.
ULTRAMAN_LOAD_WORKERSLa cantidad de hilos por defecto para una carga (--workers gana).
ULTRAMAN_NO_UPDATE_CHECK1 apaga la consulta diaria de una versión más nueva.
ULTRAMAN_PROJECTLa carpeta de proyecto con la que abre la ventana de escritorio.
NO_COLORSin colores en la salida.
ULTRAMAN_VERSION, ULTRAMAN_CLI_ONLYPara los instaladores: la versión a instalar, y solo el comando, sin la ventana. Ver Instalar.

La ventana y la terminal juntas #

Si la ventana está abierta en el proyecto, ultraman run le pasa la corrida: la ves en vivo en la ventana, y la terminal imprime lo mismo de siempre. --local la corre en la terminal, que es lo que querés en una máquina de build compartida. Las corridas de CI siempre lo usan.
