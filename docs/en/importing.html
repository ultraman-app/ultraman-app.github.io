Importing #

The Import menu next to New collection (Requests area) brings in what you already have: a Postman export, an OpenAPI spec, a JMeter plan or an Artillery script; the one next to New pipeline (Pipelines area), a browser recording. So you don't start from zero. Nothing in the project is overwritten: a name that's taken gets -2. At the end, a summary says what came in, what was adapted, what needs a hand, and which files were skipped.

From Postman #

Import › Postman takes collections (v2.0, v2.1), environments and globals exported from Postman. Folders, requests, bodies (GraphQL ones with their query and variables), auth (bearer, basic, API key), variables and descriptions come in as they were. Environment secrets go to the vault, never to a file. Common test scripts (status, equals, includes, response time, pm.environment.set) become checks; the rest stays in the request's Notes.

From OpenAPI #

Import › OpenAPI takes an OpenAPI 3 document (JSON or YAML) and makes a collection: a request per operation, with example bodies and contract checks (status and response shape).

Update from a newer spec #

When the API's spec changes (a team that generates it from the code regenerates it often), don't import it again: open the collection's menu › Update from the spec… and pick the newer document. A preview says what changes (2 new · 5 updated · 1 gone · 0 need a hand), each request unfolds into its changes, and nothing is written until you Apply.

Each operation keeps its request file, so the request keeps its history, the drift baseline and the mock's answers. Ultraman finds the request by the operation the import stored in it (operation: in the file), then by its operationId (a path that moved is followed), then by method and path. Two requests that claim one operation are listed for you to sort out, never guessed.

  • The spec changes: the checks it wrote (marked source: openapi), the description, the path when the operationId moved, and new parameters (with their example values).
  • You keep: the name, body, headers, auth, options, your own checks, notes and the values you gave parameters.
  • New operations come in as the import writes them. Operations gone from the spec stay, with a line in their notes and a mark in the tree; delete them yourself if you want.

A collection imported before this existed is matched by method and path; the schema checks that import copied are listed, and the preview offers to remove them.

From JMeter #

Import › JMeter (.jmx) takes a .jmx plan: a pipeline per Thread Group, a setup block from a Once Only Controller, an environment from the User Defined Variables, and a load test with a scenario per group. What doesn't translate (scripts, some controllers) is listed as "needs a hand" with its text.

From Artillery #

Import › Artillery takes an Artillery script (.yml or .json): pipelines, before/after blocks, environments and a load test with its phases as stages and weights. Processors and hooks are listed, not run.

From recorded traffic #

Import › From a HAR file… (Pipelines area) turns a browser recording into a pipeline. In Chrome or Firefox: DevTools › Network › right click › Save all as HAR. Ultraman keeps the API calls, finds the values one response gives the next (an id, a token) and makes them visible extracts, so the pipeline works again instead of replaying old values.

A recording can contain passwords and tokens: Ultraman replaces the ones it knows from your vault with {{secrets.x}}, but read the proposal before saving.

What an import never does #

An import only reads the file you chose and writes files into your project. It never sends a request, never reads any other file on your disk, never fetches an address named inside the file (an OpenAPI $ref to a URL is noted, not followed), never expands XML entities in a .jmx and never runs a script: Postman test scripts, JMeter processors and Artillery hooks are listed under "needs a hand" with their text, and only the common, plain cases become checks.

A file from someone else can contain anything, but importing it is as safe as opening it as text. Review what came in before you run it: the first run is what sends.

What keeps you safe #

  • You: importing sends nothing and runs nothing; the first request goes out only when you send or run it, with the usual yes for any secret. See consent.
  • You and your team: secret values in a Postman environment go to the vault, never to a file in the project. In a HAR, values that match your vault become {{secrets.x}}; read the proposal before saving, since a recording can hold passwords you never stored. See the vault.
  • You: Update from the spec writes only inside that collection's folder and never deletes a request or its history; an open request with unsaved changes is named before you apply.
  • You: a pipeline that came from outside still can't read a secret into a check, or send a file from outside ultraman/files/ unasked. See files.
