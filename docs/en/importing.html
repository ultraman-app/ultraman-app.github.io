Importing #

The Import menu next to New collection (Requests area) brings in what you already have: a Postman export, an OpenAPI spec, a JMeter plan, an Artillery script or an MCP server; the one next to New pipeline (Pipelines area), a browser recording. So you don't start from zero. Nothing in the project is overwritten: a name that's taken gets -2. At the end, a summary says what came in, what was adapted, what needs a hand, and which files were skipped.

From Postman #

Import › Postman takes collections (v2.0, v2.1), environments and globals exported from Postman. Folders, requests, bodies (GraphQL ones with their query and variables), auth (bearer, basic, API key), variables and descriptions come in as they were. Environment secrets go to the vault, never to a file. Common test scripts (status, equals, includes, response time, pm.environment.set) become checks; the rest stays in the request's Notes.

From OpenAPI #

Import › OpenAPI takes an OpenAPI 3 document (JSON or YAML) and makes a collection: a request per operation, with example bodies and contract checks (status and response shape).

Update from a newer spec #

When the API's spec changes (a team that generates it from the code regenerates it often), don't import it again: open the collection's menu › Update from an OpenAPI spec… and pick the newer document. A preview says what changes (2 new · 5 updated · 1 gone · 0 need a hand), each request unfolds into its changes, and nothing is written until you Apply.

Each operation keeps its request file, so the request keeps its history, the drift baseline and the mock's answers. Ultraman finds the request by the operation the import stored in it (operation: in the file), then by its operationId (a path that moved is followed), then by method and path. Two requests that claim one operation are listed for you to sort out, never guessed.

  • The spec changes: the checks it wrote (marked source: openapi), the description, the path when the operationId moved, and new parameters (with their example values).
  • You keep: the name, body, headers, auth, options, your own checks, notes and the values you gave parameters.
  • New operations come in as the import writes them. Operations gone from the spec stay, with a line in their notes and a mark in the tree; delete them yourself if you want.

A collection imported before this existed is matched by method and path; the schema checks that import copied are listed, and the preview offers to remove them.

From an MCP server #

Import › From an MCP server… (Requests area) turns what an MCP server offers into a collection. It asks for the server's address (https://…/mcp), the environment and how to sign in (a secret from your vault, sent as a bearer or as a header you name). Ultraman opens a session, reads the server's lists (tools, resources, resource templates and prompts, as many pages as it takes, within limits), ends the session, and shows the plan before it writes anything: the server's name and version, each item, and which tools change data (from the server's own hints). Create collection writes it. If the server answers 401 or 403, a hint under Auth says it wants authorization: choose Bearer or API key header, and a secret.

  • A request per tool, in a tools/ folder, with example arguments built from its input schema (required ones; the optional ones are listed in the notes), its description, a schema check on structuredContent when the tool declares an output schema (marked source: mcp) and the tool's hints in the notes.
  • A request per resource in resources/ (named by its name, or its address). A template such as users://{id}/profile keeps its {id} as plain text, with a note to replace it: the server's words never read a variable of yours, so write the real address (users://42/profile) before sending. Update from the server still finds that request: an address that fits the template is its request, and it keeps your address.
  • A request per prompt in prompts/, its required arguments filled with their own names as the example text.
  • The collection records the server's path and keeps the lists in ultraman/files/ so the name completion and From the server work on any machine.
  • Adapted lists what the plan changed to make it fit: a gateway's ns/tool names kept as they are, a server that says it has no capabilities but answers anyway, a templates list it refuses, a list that stopped at an odd page. What needs your hand is listed apart.

The import is a send: in a folder you haven't trusted it refuses, and a secret going to a new address asks your yes first. It reads at most 2 000 items in all, tools first, and the plan says where it stopped. The server's text is shown as data, never run.

Update from the server #

A collection made this way has Update from the server… in its menu, with the environment to ask. A preview says what changes, and nothing is written until you Apply. It never asks for the secret again: it sends with the collection's own auth.

  • The server changes: the description, the source: mcp checks, and new required arguments (with an example).
  • You keep: the name, argument values you set, headers, options, your own checks and notes. Arguments the schema no longer has are listed, not removed.
  • New tools, resources and prompts come in as the import writes them; gone ones stay, with a line in their notes and a mark in the tree.

Each request is found by its mark (the tool, resource or prompt it calls), so a renamed request is followed. An agent can do the same: see the agent's tools.

From JMeter #

Import › JMeter (.jmx) takes a .jmx plan: a pipeline per Thread Group, a setup block from a Once Only Controller, an environment from the User Defined Variables, and a load test with a scenario per group. What doesn't translate (scripts, some controllers) is listed as "needs a hand" with its text.

From Artillery #

Import › Artillery takes an Artillery script (.yml or .json): pipelines, before/after blocks, environments and a load test with its phases as stages and weights. Processors and hooks are listed, not run.

From recorded traffic #

Import › From a HAR file… (Pipelines area) turns a browser recording into a pipeline. In Chrome or Firefox: DevTools › Network › right click › Save all as HAR. Ultraman keeps the API calls, finds the values one response gives the next (an id, a token) and makes them visible extracts, so the pipeline works again instead of replaying old values.

A recording can contain passwords and tokens: Ultraman replaces the ones it knows from your vault with {{secrets.x}}, but read the proposal before saving.

What an import never does #

An import only reads the file you chose and writes files into your project. It never sends a request, never reads any other file on your disk, never fetches an address named inside the file (an OpenAPI $ref to a URL is noted, not followed), never expands XML entities in a .jmx and never runs a script: Postman test scripts, JMeter processors and Artillery hooks are listed under "needs a hand" with their text, and only the common, plain cases become checks.

A file from someone else can contain anything, but importing it is as safe as opening it as text. Review what came in before you run it: the first run is what sends.

What keeps you safe #

  • You: importing sends nothing and runs nothing; the first request goes out only when you send or run it, with the usual yes for any secret. See consent.
  • You and your team: secret values in a Postman environment go to the vault, never to a file in the project. In a HAR, values that match your vault become {{secrets.x}}; read the proposal before saving, since a recording can hold passwords you never stored. See the vault.
  • You: Update from an OpenAPI spec writes only inside that collection's folder and never deletes a request or its history; an open request with unsaved changes is named before you apply.
  • You: a pipeline that came from outside still can't read a secret into a check, or send a file from outside ultraman/files/ unasked. See files.
  • You: importing from an MCP server sends only what it needs to read the lists, never calls a tool, and the plan shows which tools change data before you create anything. A tool's description is text, not an instruction. See consent.
  • You and your team: a secret goes to the server only as the vault value you chose, is never written to a file (only {{secrets.x}} is), and a server that echoes it back gets it redacted. The session id is never saved.
  • You: Update from the server writes only inside that collection's folder and never deletes a request or its history.
