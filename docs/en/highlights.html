What Ultraman gives you #

Ultraman tests HTTP APIs, WebSocket and SSE included: one app on your computer for single requests, multi-step tests, load and CI, all saved as plain files in your own git repo. Ultraman never sends anything in an unsafe way without your explicit consent: a secret goes only to a host you approved, and a folder you haven't trusted sends nothing.

Each part below says what it does for you and where to read more. If you'd rather start from your role, jump to Where to start.

Pipelines you can see #

A pipeline is a test written as a list of steps: log in, take the token from the response, create an order, check that it shows up. You get a test you can read like a sentence: every step is a row ("token ← $login $.token"), and the same pipeline shows as a diagram, with an arrow from the request that produces a value to the one that uses it. It's saved as YAML in your repo, so a change to a test is reviewed in a pull request like any other code. → Pipelines

Requests like in Postman, with memory #

When you just want to try a call: collections, folders, tabs, Send. Each request keeps its own checks, and every send lands in the history with its timing, so you can see what an endpoint answered yesterday. When a response changes shape compared with the previous one, Ultraman tells you. WebSocket and SSE streams open in a tab of their own. → Requests

Load testing for real #

The pipeline you already have, run by many virtual users or at a fixed arrival rate: you learn how your API behaves under load without writing a second test. Ramps, holds, think time, per-user data and cookies, several scenarios mixed by weight, up to 8 threads on one machine. The report gives a verdict in words (it held, it queued, it rejected requests…) and says so when your own computer, not the API, was the limit. → Load

Bring what you already have #

You don't start from zero: Postman collections and environments, OpenAPI documents, JMeter plans, Artillery scripts and traffic recorded in your browser become collections, pipelines, environments and load tests. What can't be translated is listed, not lost. An import reads only the file you pick, and sends nothing. → Importing

Your secrets go only where you said #

Ultraman never sends anything in an unsafe way without your explicit consent. A secret, written {{secrets.token}}, lives in an encrypted vault on your computer, never in the repo. The first time a request would send it to a server you haven't approved for it, Ultraman asks; so does a file from outside the project's ultraman/files/ folder. Where a secret's value would show (a response, the history, a run report, an export), you see [secret:token] instead. A folder you don't trust yet opens in restricted mode: it sends nothing and runs no git. That is what lets you open a pipeline a colleague wrote, or one from the internet, without it quietly sending your token somewhere else. What this can't cover is said plainly in the limits. → Security and consent, Environments and secrets

A team that shares through git #

Your team shares tests the way it shares code, with no account and no server in between: pipelines, collections, environments, load tests and the files requests send are all files under ultraman/. Sync commits and pushes only those, and shows conflicts side by side. Secrets, this machine's values and your history stay on your computer. → Working as a team

The same tests in CI #

The tests you run in the window can gate your build. ultraman run runs pipelines, a collection or a load test from a terminal, writes a JUnit report and exits with an error when a check or a threshold fails. In GitHub Actions, ultraman-app/run-action installs and runs it; you say which server each secret may go to. → CI, The terminal

Your agent can drive it #

An AI agent that speaks MCP (Claude Code, for one) can create requests, write pipelines, run them, start a load and read the reports, while you stay in charge: every call shows a card in the window and nothing happens until you approve it (read-only calls can be let through for the rest of a session). The agent can use your secrets by name but never sees their values. → Agents (MCP)

A fake API from what you already sent #

When the real API is down, slow or not built yet, the mock server answers with the responses you already recorded, so a front end or a test can keep working. It answers only on your computer unless you start it from the terminal and choose otherwise. → Mock server
