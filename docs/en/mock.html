Mock server #

The mock server answers your API's requests with responses you already recorded, so a front end (or a test) can work while the real API is down, slow or not built yet. It runs on your computer and nobody else can reach it unless you choose.

Where it gets its answers #

From the History: every request you sent is a recording. In History, open Mock server: it lists the routes it can answer (method and path, with path parameters) for the chosen environment.

Start it #

Choose a port and Start (4300 by default). It answers only on this machine, and only starts in a trusted folder (the terminal asks).

  • Recorded delay answers as slowly as the real API did.
  • Forward the rest to sends what it has no recording for to a real host.
  • A route with several recordings answers with the newest; pin a specific one, or In order to go through them one by one (Reset sequences starts again).

Which recording answers #

A request is matched in this order, and the first match wins:

  1. the same method, path and query (the order of the query parameters doesn't matter);
  2. the same method and path, any query;
  3. the request's path template: /users/:userId/orders answers /users/u_bob/orders with the recording of u_ana.

With no match, the mock answers 404 with the known routes. If a route has several recordings, the newest answers, unless you pin one or choose In order. Only the chosen environment's recordings are served, and a new send is picked up without restarting. Each answer carries x-ultraman-mock headers that say which recording it was, and a response too big or binary is cut or empty, with a header that says so. Cookies and tokens that the real API set are served as recorded.

From the terminal #

ultraman mock --env local --port 4300 starts the same server without the window; --proxy <url> forwards the rest.

To let other computers on your network reach it, the terminal has --expose. It is not in the window and an agent can't turn it on. Ultraman warns that anyone on your network can read the responses, which may hold real data, and waits for Enter (or --yes). With --proxy too, it warns that anyone on your network, and any web page open there, could call that API through this machine with this machine's access. The safe choice is to leave --expose out.

What keeps you safe #

  • You: the mock listens on 127.0.0.1 only and answers only requests that name this machine. A web page from another site gets a refusal, so a site you visit can't read your recordings or reach an API through --proxy.
  • You: --proxy forwards only to the address you give, and adds no credentials of its own.
  • Your team: recordings come from your personal history, which is never synced. Secrets in it are already hidden as [secret:x]. See where things are stored and the local server.
  • You: --expose is a deliberate, warned choice in the terminal. See the limits.
