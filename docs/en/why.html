Why Ultraman #

Ultraman puts API requests, test flows, load tests and CI checks in one local app, saved as plain files in your own git repo. This page says how that differs from tools you may already use, and when one of them is the better choice.

The idea in short #

Ultraman fits a team that keeps its API tests next to its code, reviews them in pull requests, and wants one file to serve as the manual test, the CI check and the load scenario.

  • One file, three uses. A pipeline, a list of visible steps, is a test you run in the window, a check in CI and a scenario in a load test.
  • Nothing hidden in code. Steps are requests, extracts, checks, waits, repeats and branches you can read. What a step does is always on screen and in the diff.
  • Your git repo is the shared place. No account and no workspace: Sync commits only Ultraman's folders, and a change to a test reviews like any change to code.
  • Secrets stay yours. A secret lives in an encrypted vault on your computer and goes only to hosts you said yes to.

The comparisons below are about approach and were checked against each tool's own documentation in November 2026. Tools change: their documentation says what they do today.

Postman #

Postman is a broad API platform built around team workspaces. Ultraman covers the part of it that sends and tests HTTP requests, and adds flows, load and CI that live in your repo.

  • Where tests live. Collections, pipelines, environments and load tests are YAML files under ultraman/, and git is the only way they are shared. A pull request shows exactly what changed. See Working as a team.
  • Checks without scripts. Postman runs JavaScript before and after a request. In Ultraman a check is a step you read ("status is 201", "$.id exists"), and a value goes from one response to the next request through a visible extract. See Checks.
  • Flows you can see. A pipeline shows as a list and as a diagram, with an arrow from the step that produces a value to the step that uses it. See Pipelines.
  • Load from the same file. Postman can also run a collection with many virtual users. In Ultraman a load test is a file in the repo, with stages, per-user data and cookies, an arrival-rate model, controls while it runs, and a verdict that says when your own computer was the limit. See Load.

Where Postman is the better choice: many more protocols (gRPC, Socket.IO, MQTT and others); scripts for any logic you can write in JavaScript; and hosted collaboration, where a whole company shares and discusses work in workspaces.

Bruno, Insomnia and Hoppscotch #

These are request clients: you build, organize and send requests, and run them from a command line too. Bruno shares Ultraman's starting point, collections as plain-text files you keep in git.

  • A flow above the request. In Ultraman, passing a value from one response to the next request is a step you can read, not a script, and the whole flow draws as a diagram. See Pipelines.
  • Load in the same app. The pipeline you send by hand also runs under load, with a verdict in words. There is no second tool and no second format to keep in step. See Load.
  • Secrets with consent. Secrets come from an encrypted vault, show as [secret:name] in every response, history entry and export, and the first send to a new host asks you. See Security and consent.
  • Changes of shape. Ultraman warns when a response's shape changes compared with the last time you sent it. See Contract drift.

Where they are the better choice: gRPC requests (Bruno and Insomnia), Socket.IO and MQTT (Hoppscotch); JavaScript scripts in all three; Hoppscotch runs in a browser with nothing to install, and can be hosted on your own servers; Insomnia has plugins.

k6 #

k6 is a load testing tool where a test is a JavaScript or TypeScript program. Both tools offer closed models (a number of virtual users) and open models (an arrival rate), and thresholds that fail a CI build.

  • No code. In Ultraman a load test is a short YAML file that names a pipeline and its stages. You build the pipeline in a window and try it one step at a time before you put load on it. See The shape of the load.
  • One file for every use. The pipeline you load is the one you send by hand and run in CI, so a change reaches all three at once.
  • A verdict in words. The report says whether the API held, queued, rejected or broke, and says limited when your own computer was the bottleneck, instead of blaming the API. See The report.
  • Steer it while it runs. Add or remove users, hold and resume without stopping; then compare the report with an earlier one or see the trend of the last runs. See While it runs.

Where k6 is the better choice: logic of any kind, written as code; gRPC, and more protocols through extensions; performance tests through a real browser; and load spread over many machines (in Kubernetes, or in Grafana Cloud).

JMeter #

JMeter is a Java load testing tool with a desktop editor for test plans and a command-line mode to run them.

  • Readable files. An Ultraman load test is a few lines of YAML that review in a pull request. A JMeter plan is a .jmx file; Ultraman imports one and lists what it can't translate. See From JMeter.
  • The same flow for functional tests and load. The pipeline under load is the one your CI runs on every change.
  • A report that explains itself. A verdict in words, where the time went, errors per step with one failed request kept for each, thresholds that pass or fail the run. See The report.
  • Secrets out of the files. A secret lives in an encrypted vault and is never written into the files you commit. See The vault.

Where JMeter is the better choice: many more protocols (databases over JDBC, JMS, LDAP, FTP, mail, TCP); scripts in Groovy and other JVM languages; distributed tests, where one controller drives many remote machines; and plugins.

Artillery #

Artillery describes tests in YAML, with custom logic in JavaScript. It is the closest to Ultraman's format: an Artillery script imports, phases become stages, capture becomes an extract and ensure becomes thresholds. See Coming from Artillery.

  • A window around the YAML. The diagram, Send for one step, Generate checks, the history, a Requests area for exploring the API and a local mock server, all on the same files. See List and diagram.
  • Reports stay with you. Each load report is kept on your machine; compare it with an earlier one, see the trend, or export it as HTML or CSV, with no service to sign up for. See The report.
  • Secrets with consent. Secrets come from an encrypted vault and need your yes for each new host. See Security and consent.
  • One file, three uses. The scenario you load is a pipeline you also run by hand and in CI.

Where Artillery is the better choice: custom logic in JavaScript with any npm package; Socket.IO; load through real browsers with Playwright; tests spread over cloud services (AWS Lambda, AWS Fargate, Azure Container Instances); a hosted dashboard for teams; and plugins.

When to pick something else #

Ultraman is not the right tool if you need:

  • logic written in code: Ultraman has no scripts, on purpose (see Why no scripts);
  • gRPC, Socket.IO, MQTT, databases or other protocols: Ultraman speaks HTTP (GraphQL included), WebSocket and SSE (see Which protocols);
  • load from several machines or from the cloud: Ultraman generates load from one computer, on up to 8 threads (see More than one thread);
  • load through real browsers;
  • accounts, roles and permissions in a hosted workspace: Ultraman's access control is your git repo (see Permissions);
  • OAuth2 flows, client certificates, AWS SigV4 or NTLM (see Authentication);
  • a tool in the browser with nothing to install.
