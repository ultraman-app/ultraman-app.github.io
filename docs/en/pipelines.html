Pipelines #

A pipeline is a flow of requests and checks you can read from top to bottom, saved in ultraman/pipelines/<name>.yaml and run from the window or the terminal. It has a host, optional auth and headers for all its requests, inputs (values the run asks for) and steps. Nothing in it is hidden: what a step does is what its row says.

The steps #

StepWhat it does
requestsends an HTTP request; others refer to it as $name
extracttakes a value from a response (JSON path, header or regex) into {{name}}
assertchecks something about a response (see Checks)
waitpauses some milliseconds
repeatruns its steps N times, or once per item of a list
ifruns its steps only when a condition holds
useruns a block (a reusable pipeline) with its inputs
parallelruns branches at the same time; the next step waits for all
websocket, sseopens a stream; others refer to it as $name (the handshake)
sendwrites one message on a WebSocket
receivewaits for the next message on a stream that matches a filter; others refer to it as $name
closeends a stream (one left open is closed when the run ends)

Add step explains each one. The + between two steps inserts one right there. From a collection… adds a collection request, with its checks, as a linked copy.

GraphQL. A request step can carry a GraphQL body, edited the same way as in the Requests area (see GraphQL); a linked one uses its collection's schema. The list names its operation (POST /graphql · Order), and an answer with errors fails the step, even with a 200.

Streams in a pipeline #

A WebSocket or an SSE stream is four kinds of step you can see, in order: open it, send, wait for a message, close it. The pipeline's host serves the stream too (https becomes wss).

steps:
  - websocket: live
    path: /live

  - send: live
    json: { subscribe: orders }

  - receive: update
    from: $live
    where: { path: $.type, equals: order.updated }
    timeout: 5000

  - assert: equals
    of: $update
    path: $.status
    equals: shipped

  - close: live
    code: 1000
    reason: done

$live is the handshake, so assert: status of: $live equals: 101 works. A received message is a response like any other: its text is the body, and extract and assert read it with a JSON path. On SSE, the event's event and id are read like headers (header: event).

receive takes the next message that matches its where. The ones before it are passed over and counted, and a second receive starts after the first one's match. Without where, any message matches. If nothing matches in timeout ms (the stream's options.timeout if the step has none), the step fails and shows the last three messages it passed over. A timeout of 0 waits with no limit, until a message matches, the stream ends or you stop the run.

wherematches
{ path: $.type, equals: order.created }the JSON body has that value at the path
{ path: $.id, exists: true }the path finds something
{ contains: shipped }the text contains it
{ matches: /^ord_/ }the text matches a regex
{ event: price }SSE only: the event's name; it can go with one of the above

repeat: 10 around a receive collects ten messages. In a run, the Messages fold under the websocket or sse row lists everything the stream carried, both ways, so what arrived between steps is visible. A stream request from the Requests area can be added to a pipeline too (From a collection…).

A token in the subprotocol. Some servers (Kubernetes exec, some GraphQL-over-WebSocket gateways) take the token only in Sec-WebSocket-Protocol. For them protocols accepts a secret, protocols: [v4.channel.k8s.io, "{{secrets.kube_token}}"], with the same yes as a header, and it shows as [secret:kube_token] everywhere. Prefer an Authorization header when the server takes one: proxies often log subprotocols. Details in the format reference.

GraphQL subscriptions #

A GraphQL subscription is a WebSocket with graphql: and visible subscribe steps on it; its events are received like messages.

steps:
  - websocket: live
    path: /graphql
    graphql:
      init: { authorization: "Bearer {{secrets.token}}" }

  - subscribe: orders
    on: $live
    graphql:
      query: |
        subscription { orderCreated { id total } }

  - receive: order
    from: $orders
    where: { path: $.data.orderCreated.total, exists: true }
    timeout: 5000

  - close: orders

  - close: live

graphql: on a websocket step makes it a GraphQL socket: Ultraman sets the subprotocol (graphql-transport-ws), sends connection_init with init as its payload and waits for the server's acknowledgement (ackTimeout ms, the step's timeout unless you set one). Each subscribe starts a subscription on it, several on one socket if you need them, each with its own $name. A receive from a subscription takes its next event that matches: the body is the event's payload ({ data, errors }), so $.data.orderCreated.id reads it. An event with errors fails the receive unless the subscription has allowErrors: true. close: orders ends one subscription; close: live ends them all and closes the socket, and the end of the run does the same.

The protocol's own messages are Ultraman's: a GraphQL socket takes no send, and a receive names a subscription, not the socket. The demo has this pipeline as live orders (graphql).

Inputs #

inputs: [user] declares values the pipeline needs and doesn't have. Run asks for them in a dialog; in the terminal you pass them with --input user=ana (see the terminal), and a block gets them from use … with. A run with an input missing doesn't start. Inside the pipeline an input is a variable, {{user}}.

Headers for every request #

headers: on a pipeline (or on a block, or on a collection) is sent by all its requests. A step that sets the same header, in any casing, keeps its own. A block's headers are its own: the pipeline that calls it doesn't pass its headers into the block's requests. A secret in a shared header asks for its host's yes like one in a step.

name: orders
host: "{{env.api}}"
headers: { x-tenant: acme }
steps:
  - request: list
    method: GET
    path: /orders

At the same time #

parallel runs two or more branches at once and the next step waits for all of them. One branch failing doesn't stop the others: the parallel fails when they are all done. Two branches can't extract the same variable.

- parallel: dashboard
  branches:
    - - request: me
        method: GET
        path: /me
    - - request: orders
        method: GET
        path: /orders

Find your way around #

Give a pipeline tags in Auth and options (Enter or a comma adds one) and they show as chips under its name; a click on a chip filters by it. Every sidebar has a Filter… box (a name, or #tag). Ctrl+P (Cmd+P on macOS) opens one box over pipelines, blocks and requests: type some letters of the name, or #tag, and Enter opens it.

List and diagram #

The List shows each step as one line, the way others refer to it. The Diagram draws the same steps with an arrow from the request that produces a value to the one that reads it, so the data flow is visible at a glance.

Running #

Run runs the pipeline top to bottom against the selected environment. Each step shows its status and time; a failed check shows the response that failed it. Watch reruns it when something changes, or on a timer. Past runs stay listed under the pipeline.

Blocks #

A block is a pipeline meant to be reused: a login, a setup. It declares inputs and exports. A pipeline runs it with use: login, and gets its exports as variables.

Helpers #

  • Functions inside {{ }}: random.uuid, random.email, random.int(1, 100), now.iso, counter, base64(x), hmac.sha256(secrets.key, body) and more (see the format reference).
  • Regex extract: regex: name="csrf" value="([^"]+)" takes group 1.
  • Optional extract: when nothing is found, the variable stays unset instead of failing.
  • `if`: runs its steps only when a condition holds. There is no else.

Together they cover the usual "token on the page, coupon maybe" cases:

- extract: csrf
  from: $page
  regex: 'name="csrf" value="([^"]+)"'

- extract: coupon
  from: $cart
  path: $.coupon
  optional: true

- if: { exists: coupon }
  steps:
    - request: apply
      method: POST
      path: /cart/coupon
      json: { code: "{{coupon}}" }

There are no scripts on purpose: what a step does is always visible, and a reviewer can read a pipeline in a pull request.

What keeps you safe #

The promise applies here as everywhere. What this part adds:

  • You: a condition, a check or a regex never reads the content of a secret, or of a value made from one: a pipeline that would is refused instead of run, so a branch you take can't reveal a secret. See redaction.
  • Your team: a pipeline from a folder you haven't trusted doesn't send anything from the window. See trusted folders.
