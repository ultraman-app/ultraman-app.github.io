Environments and secrets #

Environments let the same requests run against local, staging or production, and secrets keep tokens and passwords on your computer, encrypted, out of git and out of every log.

Environments #

An environment (local, staging, production) is a set of values: api: https://staging.example.com. Requests read them as {{env.api}}. Choose one with the selector at the top; Environments… at the bottom of that selector edits them: the environments on the left (New environment, Rename, Duplicate, Delete), the chosen one's variables on the right.

Each value has two halves:

  • the shared value, in ultraman/envs/<name>.yaml, synced through git;
  • this machine's value, in ultraman/local/envs/<name>.yaml, never synced. Use it for what only applies to you.

An empty machine value means "same as shared". One with a value wins over the shared one everywhere: the window, the CLI and the agent. If an environment file doesn't parse, the panel shows the error and lets you fix it as text.

Import a .env file #

Import .env… reads a .env file (KEY=value, export, quotes, comments) into this machine's values. Nothing reaches the shared file, and so nothing reaches git, until you move it there yourself. A variable that is a secret keeps the value it has in the vault.

See where a value comes from #

The eye next to the environment selector opens a quick look at the chosen environment. Each variable says where its value comes from: shared, local, vault or session. A secret always shows as ●●●●.

Below, the session lists each value that steps extracted (or that you typed in a dialog), which step made it and which steps use it. The pencil edits this machine's value (empty goes back to the shared one). A session row, or the whole session, can be cleared; it comes back when the step that makes it runs again. The session is not saved: closing the window drops it.

When a request needs a value the environment doesn't have, a dialog asks for it. A plain value can be kept for this session only, saved in the environment's shared file (it goes to git) or saved on this machine. A secret has a Save on this machine checkbox: checked, it goes to the vault and never to a file.

Request options #

An environment can also carry request options: timeouts, redirects, HTTP/2, plain http for an internal service without TLS, or a custom CA for a server with its own certificate. They live under options: in the environment file, shared or this machine's only, and never as a variable:

# ultraman/envs/internal.yaml
api: http://billing.internal:8080
options:
  plainHttp: true

A request's own options win over its pipeline's (or collection's), which win over the environment's; the Options tab says where an inherited value comes from. Plain http and a custom CA both lower the protection of TLS: the window warns you when you turn them on. A CA file outside the project asks before its first use, like any file.

Secrets #

A secret is a value that must not leave your computer: a token, a password, an API key. Requests use it as {{secrets.token}}, and its value:

  • lives in a vault in your user folder, encrypted with your master password, never in the repo;
  • shows as [secret:token] in responses, history, runs, exports and logs;
  • goes only to hosts you said yes to: the first time a secret would go to a new host, Ultraman asks (see Security and consent).

An environment value can point to a secret (token: "{{secrets.token}}"), so each environment can use its own. In the Environments panel, turn a variable into a secret and its value moves to the vault after a warning; the YAML keeps only the reference. The vault name defaults to <environment>.<variable> (for example staging.token) and you can change it. Your teammates set their own values in their own vaults. Rename moves the vault names that follow the environment's name when the vault is open.

The first time a run needs a secret, the window asks for the master password: to create it, or to unlock the vault. The vault locks again after 30 idle minutes; the lock at the top locks it now, changes the password or forgets it. How it is encrypted and what it does and doesn't protect: the vault.

If you forget the master password, the secrets can't be recovered. Forgot it? deletes every saved secret after you type the confirmation; set them again afterwards.

Remember on this machine #

Remember on this machine is off by default and only exists in the desktop window. It keeps the vault's key in your system keychain so the vault opens without asking. It trades safety for convenience: on Windows and Linux other apps you run can read the keychain entry; on macOS the Keychain asks you first. The checkbox says so. The terminal never uses this key: the CLI asks for the master password itself.

In CI #

A runner has no vault: pass each secret as an environment variable, ULTRAMAN_SECRET_TOKEN for token (uppercase, anything that isn't a letter or digit becomes _). See The terminal and CI for values that only exist on one machine.

What keeps you safe #

The promise applies here as everywhere. What this part adds:

  • Your team: the shared half of an environment is in git; this machine's values and the vault are not (what is stored).
  • CI: secrets come from ULTRAMAN_SECRET_* variables, so nothing sensitive lives in the repo (CI).
