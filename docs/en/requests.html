Requests #

The Requests area is where you build, send and check single requests: collections with folders and requests, opened in tabs, like Postman. What's different is that each request carries its checks, and everything is a plain file in ultraman/requests/ that your team shares through git.

Collections and folders #

A collection has a host, and optionally auth, headers and variables (starting values for {{name}}). Its menu creates requests and folders, runs everything, creates a pipeline, or opens its settings. Requests can be renamed, moved, duplicated and added to a pipeline.

Sending #

Send (Ctrl/Cmd+Enter) sends the request in the selected environment. The response shows its status, time, size, headers and body; Timings says where the time went (DNS, connection, TLS, first byte, total).

  • Variables show as chips: {{env.x}} from the environment, {{secrets.x}} from the vault, {{x}} from the session (what a previous request extracted) or the collection's variables. Ctrl+Space suggests them.
  • If a value is missing, a dialog asks for it for this session.
  • Pasting a curl command into the path turns it into the request.

The request editor #

A request opens on its first tab with content. The tabs are Params (path parameters such as :id, and the query), Headers, Body, Auth, Options, Checks and Notes. A row you switch off stays in the file but isn't sent. A GET or HEAD request can't have a body.

Body #

The Body tab has seven modes. Each sets the Content-Type header for you, unless you write one in Headers (the editor warns that yours wins, and that a hand-written multipart header loses its boundary).

ModeWhat is sentContent-Type
Noneno bodynone
JSONthe JSON you write, with {{variables}} insideapplication/json
Textthe text as written (XML, CSV, anything)text/plain
Formname=value pairs, URL-encoded; a name can repeatapplication/x-www-form-urlencoded
Multipartparts that are text or a filemultipart/form-data

GraphQLa query, its variables and operation name, as JSON (see GraphQL)application/json

A request has one body at a time. A file comes from the project: if you pick one from somewhere else, Ultraman offers to copy it into the project (ultraman/files/, where it travels with git) or to keep it outside (only on this machine). A file outside ultraman/files/ asks your yes the first time it is sent: see files.

Auth #

The Auth tab offers Inherited, None, Bearer, Basic and API key (a header or a query parameter, with the name you choose). A collection or a pipeline can set auth once; a request inherits it, sets its own, or says None. Values can be variables, usually {{secrets.x}}, so the token never sits in the file.

Those are the types there are. For a token API, log in with one request, extract the token and use it as a bearer ({{token}}): that covers most login flows. There are no OAuth 2 flows, client certificates or request signing.

Request options #

Options tune one request: timeout (milliseconds, 30 000 by default, 0 for none), redirects (how many to follow, 10 by default, at most 20), max size of the response (50 MB), HTTP/2, plain HTTP (allow http: to a host that isn't localhost) and a custom CA (a .pem file in the project, trusted on top of the usual ones, for a server with its own certificate). Plain HTTP and a custom CA lower the protection of the connection, so the window warns when you turn them on.

An empty option inherits, and the editor says from where in gray ("30000 ms, by default"). The order is: the environment's request options, then the pipeline's or the collection's, then the request's. The closest one wins.

A request can also be marked always answers the same: that matters only in a load test.

Copy as cURL #

In a pipeline, the terminal button on a request's row copies it as a curl command, with the values you have in the window. Secrets are never written out: they become ${ULTRAMAN_SECRET_NAME}, so the command works in a shell where you set that variable and is safe to paste in a chat. The other direction works in the Requests area too: paste a curl command into the path and it becomes the request.

Redirects and Timings #

A response that was redirected gets a Redirects tab: each hop with its status, the URL that answered, and its headers (the location it pointed to, a set-cookie on the way). Timings says where the time went. Redirects are followed up to the redirects option. Two rules protect you: when a redirect goes to another origin, the authorization, cookie and proxy-authorization headers are dropped, and a 307 or 308 that would send a body holding a secret to another origin isn't followed (the response shown is that redirect, with where it pointed). See redirects.

Checks #

A check is an assert (the request must answer something) or an extract (take a value for later). They run on every Send, and the response's Checks tab says which passed.

CheckPasses when
statusthe HTTP status is the one given
equals, notEqualsa value is (or isn't) the one given
containsa value or the body contains it
lessThan, greaterThana number (or the time in ms) is below or above
exists, notExistsa JSON path or a header is there
matchesa text matches a regular expression
typea JSON value is a string, number, array…
schemaa value follows a JSON Schema

The quickest way to add one: in the response body, hover a value and use its menu.

Generate checks #

Generate checks looks at the response on screen and proposes checks for it:

  • that the status is the one it got;
  • for each top-level field of the JSON (or of the first item, for a list), that it exists and its type.

It adds at most 30, skips the ones the request already has, and saves nothing until you Save: look at them in the Checks tab and delete the ones you don't want. It's a starting point for a contract test; values that change on every call (ids, dates, tokens) are checked by type, never by value. In the Pipelines area, the same button adds them as steps right after the request.

The session #

There's one session per environment. What a check extracts (the login's token) is there for the next request (Authorization: Bearer {{token}}). The collection's variables are the starting values.

History #

Every send lands in History (next to Collections): what was sent, the response, the time and the checks. Each send shows the usual time for that request ("212 ms · usually 180 ms") and is marked when it's slower. An entry can be reopened as sent, or compared with another one side by side. The history is personal: never synced.

History is a screen of its own: a table, newest first and by day, that you can search (a name, a URL or a status) and filter by method, status and environment; the sidebar narrows it to one collection. The chosen send opens beside the table, what went out over what came back (side by side on a wide screen). Open as sent puts it back in its tab; ⋯ clears the history.

Contract drift #

After a send, if the previous send of the same request returned JSON too, a banner says which fields disappeared or changed type ($.id: string → number). Compare opens both; Generate checks turns the current shape into checks.

OpenAPI contract #

A collection can name the OpenAPI spec its API promises: Contract in its settings, or in collection.yaml:

contract:
  openapi: files/shop-openapi.yaml   # a file under files/, or /openapi.json (a path on the host), or a whole URL
  mode: warn                         # warn (the default) or strict

Then every answer of its requests is checked against its operation in the current spec: a Send, a collection run, a pipeline step linked to one of its requests, an agent's run and the CLI. The operation is the one the import stored in the request (operation:), or else the one its method and path match. What the spec doesn't document shows as a warning: status 500 isn't documented for GET /orders/{id}, $.total: expected number, got null, not in the spec: POST /orders/bulk. A body that isn't JSON, or an answer with no JSON schema, has nothing to check.

  • Where it shows: beside the status (Contract: 2 warnings), the list above the body, on the run's row and in the history. The terminal prints a line under the step.
  • strict fails a run's step with the first warning (JUnit carries it). A Send still shows the warnings: it has no step to fail. --contract strict|warn|off in the CLI goes over the file's mode, so CI can turn it on without an edit.
  • A file is read again when it changes. A path or a URL is fetched like one of the collection's requests (its host, auth, headers and secrets, with the same yeses), once per run; the window's sends keep it until Reload spec. If it can't be read, that is one warning, never a failed step.
  • Not under load: a load test doesn't check the contract.
  • With a contract, Update from the spec writes no schema checks (the contract covers them) and, when the contract is a file, writes the newer spec there.

Linked copies #

Add to pipeline… puts a request at the end of a pipeline as a linked copy (it remembers where it came from). When you change it in one place, Ultraman asks whether to update the other copies. A WebSocket or SSE request goes as its linked connect step (the handshake only: its messages and listening stay in the Requests area) and follows it the same way.

Streams: WebSocket and SSE #

Open a WebSocket or SSE stream in a tab like a request: see every message as it arrives, send one from a composer, filter and pause the list, and keep the whole session in History.

A collection's menu has New WebSocket or SSE. A stream request is a file like any other (websocket: live or sse: prices as its first key), opened in a tab with the same layout as a request. The method pill is a WebSocket | SSE choice, the path goes after the collection's host (https becomes wss, http becomes ws), and the tabs are Params, Headers, Auth, Options (including the stream's own: message size, ping, idle), Messages, Checks and Notes.

Connect (Ctrl/Cmd+Enter) opens the stream and becomes Disconnect while it's open. Below, the stream panel shows a status pill (connecting…, open 101, closed 1000), a clock, how many messages went each way, and three tabs:

  • Messages: one row per message, newest at the bottom, with its direction (↓ received, ↑ sent), time, size and, on SSE, the event name and id. Click a row to open it in the body viewer. Filter hides rows by text (or event:price on SSE), Pause stops the list moving while messages keep counting, Clear empties it.
  • Handshake: the server's headers (and the protocol it chose).
  • Checks: the request's checks run on the handshake (status, a header).

On a WebSocket, the composer under the list sends a message (text or JSON, Ctrl+Enter). It can pick one of the request's saved messages, and Save as message adds the composer's text to the request. A message with {{secrets.x}} is sent with the value and shown as [secret:x]. When the vault locks, a stream that used a secret closes too.

The panel keeps the newest 500 messages, each cut at 64 KB. When the stream ends (you, the server, an error), the whole session becomes one entry in History: its handshake, its messages and how it ended.

In a collection run, in ultraman run --collection and when an agent sends it, a stream request connects, checks the handshake, sends its saved messages, listens for listen ms (2 seconds unless the file says otherwise) and closes. A quiet stream isn't a failure. To wait for a particular message and check it, put the stream in a pipeline.

Not here: a stream request has no mock, no drift and no reconnect (if the server drops you, Connect again), and Socket.IO and compressed (deflate) WebSockets aren't supported (Coming from another tool).

GraphQL #

Send GraphQL queries and mutations with completion from the API's schema, and catch the errors a server returns with a 200.

A collection's menu has New GraphQL request, and any request's Body has a GraphQL mode (always POST). It holds the query, the Variables (JSON, with {{variables}} inside strings, like a JSON body), an operation picker when the query defines several, and An answer with errors passes.

The schema. Load schema asks the server for its schema by sending the request itself with the introspection query: the same URL, headers, auth and secrets, and the same questions as a Send. With a schema, the editor completes fields and arguments, shows a field's description in the completion list, and marks what the schema doesn't have. Save to project keeps it as ultraman/files/<collection>.graphql and names it in collection.yaml: every GraphQL request of that collection uses it, and git shares it with your team. A schema you only loaded lasts until you close the window. Without a schema, the editor still highlights the query.

Errors. A GraphQL server often answers 200 with an errors list. The response shows 1 GraphQL error (or N GraphQL errors) next to the status and lists each message, with its path, above the body. In a run, a collection run and under load, a step whose answer has errors fails with the first message, whatever the status; under load each one counts as a failed request. An answer with errors passes (allowErrors: true) is for an API that answers partial data on purpose.

The query is sent as written: {{...}} in it isn't replaced, so values go in the variables. The Sent tab and History show the query as you wrote it and the variables as they went out (a secret as [secret:x]).

Subscriptions. When the operation is a subscription, the request shows Subscribe instead of Send. Ultraman opens a WebSocket that speaks graphql-transport-ws on the request's URL (https becomes wss), or on the collection's graphql: { subscriptions: /graphql/ws } path when the server serves subscriptions apart, and starts the subscription. The stream panel lists each next as a row, red when it carries errors. Unsubscribe ends the subscription and keeps the socket open; Disconnect closes it. The session becomes one entry in History. In a collection run and when an agent sends it, a subscription listens for 2 seconds and closes, and its checks read its first next. To wait for particular events and check them, use subscribe steps.

Not here yet: GraphQL over SSE (graphql-sse), the older subscriptions-transport-ws protocol, GET requests and persisted queries, batching and file uploads.

What keeps you safe #

The promise applies here as everywhere. What this part adds:

  • You and your team: a file body goes unasked only from ultraman/files/; any other file asks first. See files.
  • You: a redirect to another origin doesn't carry your credentials along. See redirects.
  • Your team: the history is personal and never synced, so responses with real data stay on your machine. See where things are stored.
  • You: a contract URL is fetched like the collection's own requests: its secrets ask the same yes, it's refused in a folder you haven't trusted, and the warnings quote the answer only after its secrets are hidden. A contract file is read only from ultraman/files/, never through a link. See consent.
  • You: GraphQL variables are a body: a secret in them asks the same yes as anywhere and shows as [secret:x], and Load schema is a send, with the same questions. See consent.
  • Your team: a schema is read only from ultraman/files/, never through a link, and its descriptions and a server's error messages show as plain text. See files.
  • You: a subscription's variables and connection_init payload are messages: a secret in them asks the same yes as a header, shows as [secret:x], and a server that echoes it back gets it redacted. See consent.
