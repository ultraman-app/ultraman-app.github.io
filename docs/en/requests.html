Requests #

The Requests area is where you build, send and check single requests: collections with folders and requests, opened in tabs, like Postman. What's different is that each request carries its checks, and everything is a plain file in ultraman/requests/ that your team shares through git.

Collections and folders #

A collection has a host, and optionally auth, headers and variables (starting values for {{name}}). Its menu creates requests and folders, runs everything, creates a pipeline, or opens its settings. Requests can be renamed, moved, duplicated and added to a pipeline. Every place that names a request (the tree, the tabs, History, quick open, a collection run's rows) shows its kind where the method goes: the method for HTTP, and GQL, MCP, WS or SSE. Update from an OpenAPI spec… is in the menu only for a collection that has a spec: an OpenAPI contract, or requests that came from an operation.

Running a collection #

Run, in a collection's or a folder's menu, sends every request in order, each with its checks. A request that fails doesn't stop the others: the run goes on, and the strip above the rows says how many passed and failed, and which ones. Under a failed row are its error and the checks that didn't pass. A check whose request failed isn't read: it says "not checked: the request failed". A request that needs a value an earlier one didn't make, like the token of a login that failed, isn't sent: its row says "not sent", and the strip says why once. Stop ends the run where it is: the request in flight says "stopped" and the rest "not run". The Runs list under the rows says "7 passed", "1 of 7 failed" or "stopped". A pipeline still stops at its first failure, because its steps feed each other. The terminal (`ultraman run --collection`), JUnit and the agent's run_collection report a collection the same way.

Sending #

Send (Ctrl/Cmd+Enter) sends the request in the selected environment. The response shows its status, time, size, headers and body; Timings says where the time went (DNS, connection, TLS, first byte, total).

  • Variables show as chips: {{env.x}} from the environment, {{secrets.x}} from the vault, {{x}} from the session (what a previous request extracted) or the collection's variables. Ctrl+Space suggests them.
  • If a value is missing, a dialog asks for it for this session.
  • Pasting a curl command into the path turns it into the request.

The request editor #

A request opens on its first tab with content. The tabs are Params (path parameters such as :id, and the query), Headers, Body, Auth, Options, Checks and Notes. A row you switch off stays in the file but isn't sent. A GET or HEAD request can't have a body.

The kind. The first cell of the URL box is the request's kind: HTTP, GraphQL, MCP, WebSocket or SSE. For HTTP the method follows it; GraphQL and MCP are always sent as POST. A collection's menu has one New request: it opens on HTTP with the kind's cell focused, or on MCP when the collection declares its MCP server's path. Changing the kind keeps the name, path, headers, auth and options. When the new kind has no place for something (a JSON body going to GraphQL, a query going to a stream), a question lists what is removed before anything changes, and until you close the tab, changing back brings it back. A stream that is open can't change kind. In a pipeline's request step the kind is HTTP, GraphQL or MCP, and a linked step's kind is changed in its collection.

Body #

The Body tab has six modes. Each sets the Content-Type header for you, unless you write one in Headers (the editor warns that yours wins, and that a hand-written multipart header loses its boundary).

ModeWhat is sentContent-Type
Noneno bodynone
JSONthe JSON you write, with {{variables}} insideapplication/json
Textthe text as written (XML, CSV, anything)text/plain
Formname=value pairs, URL-encoded; a name can repeatapplication/x-www-form-urlencoded
Multipartparts that are text or a filemultipart/form-data
Filethe bytes of one fileguessed from the file's extension

A request has one body at a time. A GraphQL query and an MCP call have a tab of their own in Body's place, Query and Call (see GraphQL and MCP servers). A file comes from the project: if you pick one from somewhere else, Ultraman offers to copy it into the project (ultraman/files/, where it travels with git) or to keep it outside (only on this machine). A file outside ultraman/files/ asks your yes the first time it is sent: see files.

Auth #

The Auth tab offers Inherited, None, Bearer, Basic and API key (a header or a query parameter, with the name you choose). A collection or a pipeline can set auth once; a request inherits it, sets its own, or says None. Values can be variables, usually {{secrets.x}}, so the token never sits in the file.

Those are the types there are, plus OAuth 2 for MCP servers (below). For a token API, log in with one request, extract the token and use it as a bearer ({{token}}): that covers most login flows. There are no client certificates or request signing.

From a request #

In the window, a request's Auth tab (or a collection's settings) can take a bearer token From a request: pick the login request and the property of its answer (from its last answer, or typed as a JSONPath). Ultraman writes auth: { bearer: '{{token}}' } on the request or the collection, and an extract check on the login. On a collection the login gets None as its own auth when it had none, so it never sends the bearer it makes. The login's file is written only when its tab has no unsaved edits; otherwise it says "Save login first".

After that, when you Send and the token is missing, or the answer is a 401, the window sends the login first, in the same environment, and then your request. After a 401 the token is renewed once: a request that only reads (GET, HEAD, OPTIONS, a GraphQL query or an MCP resource or prompt sent to its collection's endpoint) goes again by itself, a write waits for you to send it again ("Token renewed: send again"), and a second 401 is shown as it came. A collection run from the window does the same for a missing token, not for a 401 inside a run. The first time for each collection, environment and login it asks Send {login} and continue, naming where the login goes; in a production environment it asks every time, with a warning.

This is bearer only. An agent's saved request and collection run send the login first too, under the card you approve (agents); the CLI and pipelines keep using a login step as before.

OAuth 2 sign-in #

For an MCP server that asks you to sign in, pick OAuth 2 in the Auth tab. It has three optional fields: Issuer URL, Client ID and Scopes. They can hold an environment value, {{env.x}}, so each environment signs in to its own server (the values are filled in before anything else reads them, and an environment value is never a secret: a {{secrets.x}} here is refused). A server that follows the MCP standard needs none of them. A collection's or a pipeline's auth can be OAuth 2 and its requests inherit it; WebSocket and SSE steps don't offer it.

At the top of the OAuth 2 body a button shows where the sign-in stands, and the same mark sits on the Auth tab's label (hover it for the state in words): an amber ring means you have to sign in or can't yet (its centre breathes while the browser is open), a green circle means you are signed in, and a red square means the sign-in failed. The button's menu says the state, with the host to check in bold, and offers one action: Sign in, Open browser, Cancel, Sign out, Sign in again or, when the state needs it, Review, Use OAuth 2 sign-in, Open Secrets, Trust this folder or Open the collection's auth. Opening the menu sends nothing. Sign in looks up where to sign in and shows the host before Open browser; the system browser then opens at the sign-in server.

When you Send with no sign-in, Ultraman asks: Cancel, Send without signing in or Open browser. If the server can't identify Ultraman or doesn't say where to sign in, the question asks for the client id or the issuer URL; for a Send, what you type becomes an unsaved change in the request's Auth. A run, Load from the server or a compare asks the same question without Send without signing in.

In a production environment Ultraman asks before every browser opening, and never remembers that yes. A sign-in made in another project is used here only after a yes in this project (Review, then Use it for the server). That yes is for that one sign-in: after a sign-out or a sign-in as someone else, this project is asked again. In production it is never remembered: it covers your next send or run here only, and a yes you gave while in another environment doesn't count there. Sign out asks first: Ultraman asks the server to end the sign-in and forgets it on this computer, so other projects that use it have to sign in again.

Machine to machine #

For a service or a CI job there is no person to sign in. In the OAuth 2 body, set Flow to Client credentials (machine to machine). It has four fields: Issuer URL, Client ID, Client secret and Scopes, plus an optional Token URL for an issuer that doesn't publish where its token endpoint is. The client secret is a secret reference, {{secrets.x}}, never the value. Ultraman asks the issuer for a token by itself and sends it as a bearer.

The token goes to any path on the API's own origin (scheme, host and port) and to no other origin, and it lives in memory only: it is never saved in the project, the vault or git, and a new run asks again when it has expired. A Token URL must be on the issuer's own origin. A request that uses a machine token needs no sign-in and no unlocked vault; on a build machine the secret comes from ULTRAMAN_SECRET_<NAME> (the terminal). WebSocket and SSE steps can't use OAuth 2 and say so. A load test shares one token per environment among all its users and renews it for them.

Two yeses come first, each asked once per project: the client secret going to the issuer's origin, and the token going to the API's origin when it isn't the issuer's. They are separate: allowing the token at an origin never lets the secret itself go there. In CI, allow says both beforehand (OAuth 2 in CI).

In Copy as cURL and in the Code tab, an OAuth 2 request's token is written as ${ULTRAMAN_OAUTH_TOKEN}: set that variable where the code runs.

Request options #

Options tune one request: timeout (milliseconds, 30 000 by default, 0 for none), redirects (how many to follow, 10 by default, at most 20), max size of the response (50 MB), HTTP/2, plain HTTP (allow http: to a host that isn't localhost) and a custom CA (a .pem file in the project, trusted on top of the usual ones, for a server with its own certificate). Plain HTTP and a custom CA lower the protection of the connection, so the window warns when you turn them on.

An empty option inherits, and the editor says from where in gray ("30000 ms, by default"). The order is: the environment's request options, then the pipeline's or the collection's, then the request's. The closest one wins.

A request can also be marked always answers the same: that matters only in a load test.

Copy as cURL #

A request's code, cURL included, now lives in the Code tab: see Code snippets. The </> button (copy as code) on a pipeline request's row opens that tab in the inspector, in the last language you used. Secrets are never written out: they become ${ULTRAMAN_SECRET_NAME}, so the command works in a shell where you set that variable and is safe to paste in a chat. The other direction works in the Requests area too: paste a curl command into the path and it becomes the request.

Code snippets #

A request's Code tab (after Notes) shows the request as code you can copy. Pick the language: cURL (bash), cURL (PowerShell), JavaScript fetch, Python requests, HTTPie (bash), HTTPie (PowerShell), Go net/http, C# HttpClient, or HTTP, a display of the raw request (not a .http file to run). The bash flavours are for bash or zsh; the PowerShell ones call curl.exe and read secrets from $env:. They run only in PowerShell 7.3 or later (HTTPie only as http.exe): Windows PowerShell 5.1 can split a value into other options when it hands it to a program, so there the snippet stops with an error instead of running. Never paste a cURL or HTTPie snippet into the Windows Command Prompt (cmd.exe): it reads &, |, > and ^ inside the quotes as commands, so a value could run a program or write a file. A header, form field or basic auth that can't go safely on a command line is left out with a # comment; if the URL or the body can't, or HTTPie can't send the method, the snippet is only that comment. Long lines wrap, Copy puts the code on the clipboard, and the tab remembers the last language you used (the first time it is cURL, on Windows its PowerShell flavour).

The environment's values are written in. Each secret is read from an environment variable named ULTRAMAN_SECRET_<NAME> in that language (process.env, os.environ, os.Getenv, $ULTRAMAN_SECRET_NAME, and so on), so you set the variable where the code runs and the snippet is safe to paste. In a pipeline, the </> button on a request's row opens the inspector on the Code tab. An MCP request's snippet starts with a comment saying the call needs a session or server/discover first. A WebSocket or SSE request has no code to show: a live connection has no code to copy, and the tab says so. Agents have get_snippet, which gives the same text.

Redirects and Timings #

A response that was redirected gets a Redirects tab: each hop with its status, the URL that answered, and its headers (the location it pointed to, a set-cookie on the way). Timings says where the time went. Redirects are followed up to the redirects option. Two rules protect you: when a redirect goes to another origin, the authorization, cookie and proxy-authorization headers are dropped, and a 307 or 308 that would send a body to another origin isn't followed (the response shown is that redirect, with where it pointed). See redirects.

Checks #

A check is an assert (the request must answer something) or an extract (take a value for later). They run on every Send, and the response's Checks tab says which passed.

CheckPasses when
statusthe HTTP status is the one given
equals, notEqualsa value is (or isn't) the one given
containsa value or the body contains it
lessThan, greaterThana number (or the time in ms) is below or above
exists, notExistsa JSON path or a header is there
matchesa text matches a regular expression
typea JSON value is a string, number, array…
schemaa value follows a JSON Schema

The quickest way to add one: in the response body, hover a value and use its menu.

Generate checks #

Generate checks looks at the response on screen and proposes checks for it:

  • that the status is the one it got;
  • for each top-level field of the JSON (or of the first item, for a list), that it exists and its type.

It adds at most 30, skips the ones the request already has, and saves nothing until you Save: look at them in the Checks tab and delete the ones you don't want. It's a starting point for a contract test; values that change on every call (ids, dates, tokens) are checked by type, never by value. In the Pipelines area, the same button adds them as steps right after the request.

For an MCP call the checks go one level in: they read the fields of the Structured result ($.structuredContent.total), not the blocks of text in content. A tool that answered with an error gets only its status check.

The session #

There's one session per environment. What a check extracts (the login's token) is there for the next request (Authorization: Bearer {{token}}). The collection's variables are the starting values.

History #

Every send lands in History (next to Collections): what was sent, the response, the time and the checks. Each send shows the usual time for that request ("212 ms · usually 180 ms") and is marked when it's slower. An entry can be reopened as sent, or compared with another one side by side. The history is personal: never synced.

History is a screen of its own: a table, newest first and by day, that you can search (a name, a URL or a status) and filter by method, status and environment; the sidebar narrows it to one collection. The chosen send opens beside the table, what went out over what came back (side by side on a wide screen). Open as sent puts it back in its tab; ⋯ clears the history.

Contract drift #

After a send, if the previous send of the same request returned JSON too, a banner says which fields disappeared or changed type ($.id: string → number). Compare opens both; Generate checks turns the current shape into checks. A field the previous answer didn't have is no change: it raises no banner, and in the response its line is marked new since the last send.

OpenAPI contract #

A collection can name the OpenAPI spec its API promises: Contract in its settings, or in collection.yaml:

contract:
  openapi: files/shop-openapi.yaml   # a file under files/, or /openapi.json (a path on the host), or a whole URL
  mode: warn                         # warn (the default) or strict

Then every answer of its requests is checked against its operation in the current spec: a Send, a collection run, a pipeline step linked to one of its requests, an agent's run and the CLI. The operation is the one the import stored in the request (operation:), or else the one its method and path match. What the spec doesn't document shows as a warning: status 500 isn't documented for GET /orders/{id}, $.total: expected number, got null, not in the spec: POST /orders/bulk. A body that isn't JSON, or an answer with no JSON schema, has nothing to check.

  • Where it shows: beside the status (Contract: 2 warnings), the list above the body, on the run's row and in the history. The terminal prints a line under the step.
  • strict fails a run's step with the first warning (JUnit carries it). A Send still shows the warnings: it has no step to fail. --contract strict|warn|off in the CLI goes over the file's mode, so CI can turn it on without an edit.
  • A file is read again when it changes. A path or a URL is fetched like one of the collection's requests (its host, auth, headers and secrets, with the same yeses), once per run; the window's sends keep it until Reload spec. If it can't be read, that is one warning, never a failed step.
  • Not under load: a load test doesn't check the contract.
  • With a contract, Update from an OpenAPI spec writes no schema checks (the contract covers them) and, when the contract is a file, writes the newer spec there.

Linked copies #

Add to pipeline… puts a request at the end of a pipeline as a linked copy (it remembers where it came from). When you change it in one place, Ultraman asks whether to update the other copies. A WebSocket or SSE request goes as its linked connect step (the handshake only: its messages and listening stay in the Requests area) and follows it the same way.

Streams: WebSocket and SSE #

Open a WebSocket or SSE stream in a tab like a request: see every message as it arrives, send one from a composer, filter and pause the list, and keep the whole session in History.

Pick WebSocket or SSE in the request's kind cell. A stream request is a file like any other (websocket: live or sse: prices as its first key), opened in a tab with the same layout as a request. The kind cell says which one (it takes the method's place), the path goes after the collection's host (https becomes wss, http becomes ws), and the tabs are Params, Headers, Auth, Options (including the stream's own: message size, ping, idle), Messages, Checks and Notes.

Connect (Ctrl/Cmd+Enter) opens the stream and becomes Disconnect while it's open. Below, the stream panel shows a status pill (connecting…, open 101, closed 1000), a clock, how many messages went each way, and two tabs:

  • Messages: one row per message, newest at the bottom, with its direction (↓ received, ↑ sent), time, size and, on SSE, the event name and id. Click a row to open it in the body viewer. Filter hides rows by text (or event:price on SSE), Pause stops the list moving while messages keep counting, Clear empties it.
  • Handshake: the server's headers (and the protocol it chose).

The request's own Checks tab holds the checks of a stream request. They read the handshake (status, a header), not the messages: the tab says so when it is empty. To check a message, put the stream in a pipeline: the tab links to the action below.

Wait for this in a pipeline… is on a received message's row (and on a GraphQL subscription's next message). It proposes a pipeline: the stream's connect (linked to this request), the saved messages sent before it, a wait for a message like this one with a 5 second timeout, a check, and close. A preview lists the steps; leave one out or move it, and nothing is saved until Create, which opens the new pipeline. The message's text is written as text, never as a variable.

On a WebSocket, the composer under the list sends a message (text or JSON, Ctrl+Enter). It can pick one of the request's saved messages, and Save as message adds the composer's text to the request. A message with {{secrets.x}} is sent with the value and shown as [secret:x]. When the vault locks, a stream that used a secret closes too.

The panel keeps the newest 500 messages, each cut at 64 KB. When the stream ends (you, the server, an error), the whole session becomes one entry in History: its handshake, its messages and how it ended.

In a collection run, in ultraman run --collection and when an agent sends it, a stream request connects, checks the handshake, sends its saved messages, listens for listen ms (2 seconds unless the file says otherwise) and closes. A quiet stream isn't a failure. To wait for a particular message and check it, put the stream in a pipeline.

Not here: a stream request has no mock, no drift and no reconnect (if the server drops you, Connect again), and Socket.IO and compressed (deflate) WebSockets aren't supported (Coming from another tool).

GraphQL #

Send GraphQL queries and mutations with completion from the API's schema, and catch the errors a server returns with a 200.

Pick GraphQL in the request's kind cell (always POST). Its Query tab holds the query, the Variables (JSON, with {{variables}} inside strings, like a JSON body), an operation picker when the query defines several, and Allow errors.

The schema. Load schema asks the server for its schema by sending the request itself with the introspection query: the same URL, headers, auth and secrets, and the same questions as a Send. With a schema, the editor completes fields and arguments, shows a field's description in the completion list, and marks what the schema doesn't have. Save to project keeps it as ultraman/files/<collection>.graphql and names it in collection.yaml: every GraphQL request of that collection uses it, and git shares it with your team. A schema you only loaded lasts until you close the window. Without a schema, the editor still highlights the query.

Errors. A GraphQL server often answers 200 with an errors list. The response shows 1 GraphQL error (or N GraphQL errors) next to the status and lists each message, with its path, above the body. In a run, a collection run and under load, a step whose answer has errors fails with the first message, whatever the status; under load each one counts as a failed request. A hint under the list says so ("An answer with errors fails the request. Allow errors lets it pass."). Allow errors (allowErrors: true) is for an API that answers partial data on purpose.

The query is sent as written: {{...}} in it isn't replaced, so values go in the variables. The Sent tab and History show the query as you wrote it and the variables as they went out (a secret as [secret:x]).

Subscriptions. When the operation is a subscription, the request shows Subscribe instead of Send. Ultraman opens a WebSocket that speaks graphql-transport-ws on the request's URL (https becomes wss), or on the collection's graphql: { subscriptions: /graphql/ws } path when the server serves subscriptions apart, and starts the subscription. The stream panel lists each next as a row, red when it carries errors. Unsubscribe ends the subscription and keeps the socket open; Disconnect closes it. The session becomes one entry in History. In a collection run and when an agent sends it, a subscription listens for 2 seconds and closes, and its checks read its first next. To wait for particular events and check them, use subscribe steps. A subscription has no Compare with…, since a stream isn't compared; edit it into a query and the button is back.

Not here yet: GraphQL over SSE (graphql-sse), the older subscriptions-transport-ws protocol, GET requests and persisted queries, batching and file uploads.

MCP servers #

Call a tool, read a resource or get a prompt on an MCP server that speaks MCP over HTTP, and check what comes back like any other answer.

The request. Pick MCP in the request's kind cell (always POST; its Call tab; the path is the server's address after the collection's host, such as /mcp). Pick Tool, Resource or Prompt. The name is completed from the server's list (the one a collection imported from the server keeps), and Arguments are JSON, with {{variables}} inside strings, like a JSON body. Allow errors lets a tool's own error pass (tools only). A hint under a tool's error says so. A prompt's arguments are text.

From the server. Under the arguments, the From the server card shows what the server says about the argument at the cursor: its words, type, examples and default, and a click writes a value. Outside an argument it lists all of them. In the editor, the completion carries the same words. A request written by hand has no list yet: Load from the server (↻ in the corner of the From the server card, where everything the server says about the call is) asks the server for it with this request's own address and auth. It is a send, with the questions a Send asks; it lists the server and never calls a tool. Save to project then keeps the list in the collection (files/<collection>.mcp.json), and Load again asks once more.

The answer. The response is the tool's result: its content (text, images, embedded resources), then Structured result (structuredContent), so you extract and assert on $.structuredContent… as on any JSON body. A tool that answers with an error shows it beside the status and fails the step, unless Allow errors is on; a JSON-RPC error fails it too (MCP error -32602: …). History lists these as MCP with the tool's name, and its Method filter has MCP. Sent shows the JSON-RPC message that went out, never the session id.

Text blocks. A text block that holds JSON shows in the same viewer as the structured result, so hover and Enter extract or assert a value inside it: the path reads into the text ($.content[0].text.@json…, below). When it says the same as the structured result, it folds to one line with Show. Any other text, a resource's or a prompt's too, has a ⋯ menu: Assert that it contains…, Extract with a regex… (a regex reads the whole answer) and Copy path. Generate checks reads structuredContent, or, when a tool sends none, its first JSON text.

A tool that answers JSON as text. Many tools put their JSON in a string, in content[0].text. Add .@json to the path and Ultraman reads inside that text: $.content[0].text.@json.customers[0].id, in an extract, an assert or a stream's where. It can repeat and can follow [*] (items that aren't JSON are skipped). If the value isn't text, the text isn't JSON or it is over 1 MB, the path finds nothing and the failure says which (the text at … isn't JSON). A key really named @json is written ['@json']. Paths that choose fields to leave out in a compare don't take it.

Protocol versions. Ultraman speaks MCP over HTTP (the Streamable HTTP transport) in four versions: 2026-07-28, which has no initialize and no session (each call stands alone), and 2025-11-25, 2025-06-18 and 2025-03-26, which open a session with initialize. By default the protocol is Automatic: the first time it meets a server, Ultraman asks it server/discover; a server that answers in 2026-07-28 is spoken to that way, and one that doesn't gets the earlier handshake, asking for the newest version first. It remembers what it found while the app stays open, so a load test doesn't ask again for every user. A server that changes era in the middle of a run fails that call, and the next one asks again.

Pinning the protocol. Add protocol: to a request's mcp: (or to the collection's) with auto or one of the four versions, and Ultraman speaks only that one and never asks the server which it speaks. A request's own value wins over its collection's, auto included. In the window, the request's Call tab has a Protocol picker beside Allow errors (a resource has it on a line of its own), and the collection's MCP server section holds the collection's choice, which each request uses unless it picks its own; the picker says when a value comes from the collection. A server that doesn't speak the pinned version fails the step.

What the session line says. Under the answer, a server of the earlier versions reads "Session: shop 1.2 · MCP 2025-11-25 · opened for this Send and ended after it", and one of 2026-07-28 reads "Server: shop 1.2 · MCP 2026-07-28 · no session: each call stands alone". A run's step and a pipeline's result name the version the same way, and the terminal prints it under the step whose first call opened it. In a load test the report has a row per server and method for what opens a session (server/discover and initialize apart), and their time stays out of the verdict's p95.

A tool left out of a listing. In 2026-07-28 a tool may mark an argument to travel as a header (x-mcp-header). When a tool's schema does that in a way Ultraman can't send safely (a name that isn't a valid header, two arguments with the same header, or an argument that isn't a string, integer or boolean), the tool is left out of the listing and the import says why, instead of the whole listing failing. Update from the server keeps that tool's request as it was, and the saved lists say "left out", never "gone".

Sessions. With 2025-11-25 and the earlier versions, a Send opens its own session, makes the call and ends it. A run opens one session per server the first time it calls it, shares it between blocks, repeats and branches, and ends it when the run ends (Stop too). The Code tab gives the one POST, with a comment that the server may need a session or server/discover first.

Servers that don't follow the standard. Ultraman behaves like the strictest mainstream client and says why when it does something other than the standard. When exactly one reading of the answer exists and a standard client would work, it recovers and the step stays green with a note, in Sent, in the run, in the terminal and JUnit, and in an agent's result; a load counts them by kind. It recovers from: an older protocol version (2024-11-05) over this transport, a session the server forgot (it opens a new one, once), a missing serverInfo or capabilities, an answer without "jsonrpc", one with both result and error, and a batch (it reads the item that answers). It fails in words that name the fault when a green step would be a false result: an HTTP status with no MCP answer (a 401 says the server wants authorization), a redirect (it says where to; it is never followed: put /mcp/ in the address if that is what the server wants), a 404 or 405 to the first call (probably the older HTTP+SSE transport, which isn't supported), an answer to a different id, JSON-RPC under the wrong content type, an error with no numeric code, a 400 where the standard answers 404, a request the server makes mid-stream (sampling, roots, elicitation), or a stream that closes before the answer. It refuses a redirect to another origin, a newer protocol version than it speaks (or none), and a session id that isn't visible ASCII.

A tool or prompt name is any text of at most 128 characters without control characters or {{, so a gateway's ns/tool works.

What keeps you safe #

The promise applies here as everywhere. What this part adds:

  • You and your team: a file body goes unasked only from ultraman/files/; any other file asks first. See files.
  • You: a value read through .@json is a value of the answer: it is redacted, and it counts as the secret's when a server echoes one as it is or written with escapes, up to six levels deep (JSON text inside JSON text). A check that reads a value holding the echo is refused, and so is an exists or notExists through .@json on an answer that echoes one.
  • You: an OAuth 2 token stays in this computer's secret store, never in the project and never in git, is kept by the server's address and goes only to that server. Check the host the menu shows before you open the browser; a production environment asks before every opening, and a sign-in from another project is used here only after your yes. An untrusted folder never signs in, and with no secret store the window sends you to Secrets. See where things are stored.
  • You: the client secret of a machine-to-machine sign-in goes only to its issuer's token endpoint and asks first, like any secret going to a new host. A machine token is never saved, never shown (it is hidden like a secret) and goes only to its API's origin, which asks first too, once per origin. An environment value in OAuth 2's fields is never a secret.
  • You: a redirect to another origin doesn't carry your credentials along. See redirects.
  • You: in 2026-07-28, an argument a tool asks to send as a header (Mcp-Param-…) goes to the same server that already gets that value in the body; what you see of it (Sent, history, an error that quotes the header back) is built from the hidden value, so a secret never shows there, even encoded as text. The server's tool schema chooses which arguments travel as headers, and gateways and access logs often record headers: don't put a secret in a header-marked argument of a server you don't trust with it.
  • Your team: the history is personal and never synced, so responses with real data stay on your machine. See where things are stored.
  • You: a contract URL is fetched like the collection's own requests: its secrets ask the same yes, it's refused in a folder you haven't trusted, and the warnings quote the answer only after its secrets are hidden. A contract file is read only from ultraman/files/, never through a link. See consent.
  • You: GraphQL variables are a body: a secret in them asks the same yes as anywhere and shows as [secret:x], and Load schema is a send, with the same questions. See consent.
  • You: Load from the server is a send: it asks what a Send asks, never follows a redirect and never calls a tool. What the server says shows as plain text and reaches the project only as literal text: a {{ in it is never a live variable. See consent.
  • Your team: a schema is read only from ultraman/files/, never through a link, and its descriptions and a server's error messages show as plain text. See files.
  • You: a subscription's variables and connection_init payload are messages: a secret in them asks the same yes as a header, shows as [secret:x], and a server that echoes it back gets it redacted. See consent.
  • You: the one yes behind Send {login} and continue is stored on this machine (~/.ultraman/trust.json), never in the project. Any change to the login request (its method, path, body, headers, extracts or what it inherits from the collection), or to where it goes once the environment's values are filled in, asks again; a production environment always asks, and that yes isn't kept. The login goes with its own collection's values. A token lands only in its own environment's session, and the window sends a login for you only for the names an auth reads: any other missing value still asks.
  • You: an MCP argument is a body: a secret in it asks the same yes as anywhere and shows as [secret:x], and a result that echoes one is redacted. The server's session id is never shown or saved. See consent.
  • You: a server's words (tool names, descriptions, results, errors) show as plain text, with control characters removed, and are cut before they are kept. A redirect is never followed, so your token and session id stay with the address you chose. A server that bends the standard is recovered only when one reading is safe, and says so.
  • You: a snippet never holds a secret's value: each secret is a reference to an environment variable named ULTRAMAN_SECRET_<NAME>, and every other value is written as data in the language you picked, escaped for it (for cURL and HTTPie, as bash, zsh or PowerShell read it; a secret inside a JSON string is JSON-escaped first), so one can't break out of its string there. What a language can't write safely is left out, and a comment says so. Generating a snippet sends nothing. See consent.
