CI #

Ultraman runs in a build pipeline with the same pipelines you use on your machine, writes a JUnit report and fails the job when a step or a threshold fails. For GitHub Actions there is an action that also keeps secrets from going anywhere nobody approved. For other systems you install the command and call it.

The GitHub Action #

ultraman-app/run-action@v1 installs only the ultraman command on the runner (Linux, macOS or Windows), runs your pipelines or a load test and writes the JUnit report. It exits like ultraman run: 1 when a step or threshold fails, 2 when it couldn't run (a bad input, a missing value, a secret nobody allowed to go where a pipeline sends it).

- uses: actions/checkout@v4
  with:
    persist-credentials: false
- uses: ultraman-app/run-action@v1
  env:
    ULTRAMAN_SECRET_API_KEY: ${{ secrets.API_KEY }}
  with:
    args: --tag smoke
    env: staging
    allow: api_key=https://staging.example.com

persist-credentials: false keeps the job's GitHub token out of the project folder; the action refuses to run next to it.

The JUnit report #

The report is written even when the run fails. Upload it so the failures show on the job:

- uses: ultraman-app/run-action@v1
  id: ultraman
  with:
    pipelines: create order
- uses: actions/upload-artifact@v4
  if: always()
  with:
    name: ultraman-junit
    path: ${{ steps.ultraman.outputs.junit }}
    retention-days: 7

Without if: always() the upload is skipped exactly when you need it.

The action's inputs #

InputWhat it does
pipelinesPipelines to run, one per line. Leave it empty and use args for --all, --tag X or --collection ID.
argsMore flags for ultraman run: --parallel 4, --bail... They are split on spaces, so a value with a space can't go here.
loadA load test to run instead; its thresholds decide the exit code.
envThe environment (ultraman/envs/<env>.yaml).
local-envThe environment's machine-only values. See local values.
allowWhich secret may go to which origin. See allow.
yestrue passes --yes. Default false. See yes.
working-directoryThe folder that holds ultraman/. Default .
junitThe report's path inside it. Default ultraman-junit.xml.
versionThe Ultraman version to install, or latest (the default). Pin one for repeatable runs.

Outputs: junit (the report's path) and exit-code (0, 1 or 2).

Each secret a pipeline uses as {{secrets.name}} comes from an ULTRAMAN_SECRET_<NAME> variable (see the terminal): map your GitHub secrets onto them in the step's env:, only the ones the pipelines use. Ultraman writes [secret:name] in everything it prints and saves, and GitHub masks them in the log too. The action always runs the pipelines in its own process, never through an Ultraman already open on the runner.

Where a secret may go: allow #

On your machine Ultraman asks before a secret goes to an origin for the first time. A runner has nobody to ask, so the workflow says it beforehand: allow lists, one per line, name=origin for each secret (a scheme, a host and a port if it isn't the default; no path, no trailing slash).

allow: |
  api_key=https://staging.example.com
  admin_token=https://admin.staging.example.com

A pipeline that would send a secret anywhere else is refused before anything is sent (exit 2). So a pull request that changes a pipeline or an environment to point a secret at another host can't send it there. This protects your team's secrets from a changed file; it can't protect them from a changed workflow file, which runs whatever it says. GitHub gives no secrets to workflows from forks on pull_request; never check out a pull request's code under pull_request_target or workflow_run with your secrets around.

yes: the risky way #

yes: true lets every secret go wherever the pipelines say, with nothing asked. Anyone who can change a pipeline or an environment in the branch being tested can then send your secrets to a server of theirs. Use it only for branches that only your team can push to, never for pull requests from forks, and prefer allow. If you want allow's protection, don't put --yes in args either.

Files a request sends #

Only files under ultraman/files/ go out without a yes (the desktop app copies the files you pick there). A body, multipart part, certificate or stream message read from anywhere else in the repository needs a yes the first time, and a runner has nobody to give it: the run stops with exit 2 before anything is sent. Keep the files your requests send in ultraman/files/. See Security and consent.

Load tests in CI #

- uses: ultraman-app/run-action@v1
  with:
    load: checkout-peak
    env: staging
    allow: api_key=https://staging.example.com

The test's thresholds decide the exit code: it passes when they all held and the verdict is holds, queues or limited. See Load for what they mean. Two points for a build machine:

  • Load only an API of your own, and size the test for the runner: a shared runner is a small computer, and a verdict of limited says the numbers describe the runner, not the server.
  • --baseline last compares with the last report saved in ultraman/loads/, and a fresh runner has none, so it prints nothing. Keep the report you want to compare with (as an artifact or in a cache), restore it before the run and pass its path: --baseline previous/load.json. --output load.json writes the report to keep.

Values that live on a developer's machine #

Some environment values aren't in git: on each machine they live in ultraman/local/envs/<env>.yaml. On a runner the action writes that file from local-env, one name: value per line, and masks each value in the log first. Values are plain: no quotes, comments, multi-line values or other YAML; the action stops on one.

with:
  env: staging
  local-env: |
    tenant: acme
    user: ${{ vars.TEST_USER }}

A credential belongs in an ULTRAMAN_SECRET_* variable instead: those are hidden in the reports too, while local-env values are hidden only in the log.

Other CI systems #

Outside GitHub Actions there is no allow: --yes is everything or nothing. Run it only on branches your team controls.

Everything the action does is the ultraman command plus a few rules. On GitLab, Jenkins, CircleCI or your own runner:

  1. Install only the command. On Linux and macOS: curl -fsSL https://ultraman-app.github.io/install.sh | sh -s -- --cli (add --version 0.6.2 to pin one) and make sure ~/.local/bin is on the PATH. On Windows: $env:ULTRAMAN_CLI_ONLY = 1; irm https://ultraman-app.github.io/install.ps1 | iex. The installer checks the release's signed checksums and carries its own Node.
  2. Give it the secrets as masked variables named ULTRAMAN_SECRET_<NAME>.
  3. Run it. The exit code gates the job:
ultraman run --all --env ci --yes --junit reports/ultraman.xml
  1. Choose `--yes` knowingly. A runner has no terminal, so a secret going to an origin, a file from outside ultraman/files/ or an untrusted folder all need --yes. The command line has no equivalent of allow: --yes is everything or nothing, with the same risk as yes: true above. Add --local on a shared runner.
  2. Machine-only values (ultraman/local/envs/) aren't in git: provide them as CI variables or write the file in a script.
  3. The report. Point your system at the file. Examples, which you should check against your system's documentation:
# GitLab CI (.gitlab-ci.yml)
ultraman:
  script:
    - curl -fsSL https://ultraman-app.github.io/install.sh | sh -s -- --cli
    - export PATH="$HOME/.local/bin:$PATH"
    - ultraman run --all --env ci --yes --junit reports/ultraman.xml
  artifacts:
    reports:
      junit: reports/ultraman.xml

In Jenkins the junit step reads the file (junit testResults: 'reports/ultraman.xml'), run in a post { always { } } block so a failed run is still reported.

Load tests work the same way: ultraman run --load checkout-peak --env staging --yes --junit load.xml --output load.json.
