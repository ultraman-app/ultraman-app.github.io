Security history #

How Ultraman's security has been reviewed so far, in numbers: what each review looked at, what it found and what happened to it.

These are internal reviews, done as part of building Ultraman. No outside party has audited it (Honest limits). This page gives totals only, never the details of a single problem.

How a review works #

A review reads the code from an attacker's side: what a project folder from someone else, a hostile server, a web page or another program on the same computer could make Ultraman do. Large features are reviewed as they are built, and a release is reviewed before it goes out.

  • Each finding is written down with a severity: the reviewer's judgment of how much harm it could do, and how easily.
  • Most fixes come with a test that fails before the fix and passes after it, so the problem can't come back unnoticed.
  • When a review finds something serious, the fixes get a second review.

How to read these numbers #

  • They show that reviews happen and that nearly everything they found is fixed. They don't show that nothing is left to find.
  • More findings don't mean a weaker area: an area reviewed more often, or more deeply, records more.
  • None of this is an outside audit or a certification.
  • To report a problem, see the security policy: reports go privately, through GitHub.
