Questions #

Short answers to what teams ask before they adopt Ultraman, the honest "no"s included. Each answer links to the page that goes deeper.

Trust and safety #

Could it send my token to the wrong place? #

A secret goes only to an origin (scheme, host and port) you said yes to; the first time it would go somewhere new, Ultraman asks, and in a terminal it asks too. When a redirect leads to another origin, credentials are dropped. In a folder you haven't trusted, the window sends nothing and runs no git. See Security and consent.

Can an AI agent see my secrets? #

No. An agent connected over MCP can use {{secrets.x}}, but the value never reaches it, and every call shows a card in the window that you approve or reject. It can't unlock the vault, say yes to a new host, trust a folder, sync with git or delete anything. A token that a step extracts from a response is data, not a secret: the card that delivers a result highlights tokens before you approve it. See Agents.

Does it send anything about me? #

No telemetry and no account. While the window is open, Ultraman asks GitHub at most once a day whether a newer version exists, and sends nothing about you or your projects; ULTRAMAN_NO_UPDATE_CHECK=1 turns that off. Nothing downloads until you choose Update and restart. See What leaves your machine.

Which systems does it run on? #

Windows (x64), macOS (Apple silicon and Intel) and Linux (x64, as an AppImage). The installers aren't signed by Microsoft or Apple, so the first launch shows a warning; updates and the install scripts' checksums are signed. See The first-launch warning.

How do I share secrets with my team? #

You don't. Each person sets their own values in their own vault, under the names the environment uses (staging.token); CI gets its own through ULTRAMAN_SECRET_*. The repo carries only {{secrets.x}}. See Secrets.

What it does and doesn't do #

Can I write scripts? #

No, on purpose: what a step does is always on screen, and a reviewer reads it in a diff without running anything. Instead there are asserts, extracts (by JSON path, header or regex), if and repeat steps, reusable blocks, and functions inside {{ }} such as random.uuid, now.iso, base64(x) and hmac.sha256(secrets.key, body). When you import, common Postman test scripts become checks; other scripts are listed for you, never run. See Helpers.

Which protocols does it speak? #

HTTP and HTTPS (GraphQL included), WebSocket and Server-Sent Events (SSE). Streams work as requests in the Requests area, as pipeline steps and under load. Not supported: Socket.IO, compressed WebSockets, automatic reconnects (connect again, or write the retry as steps) and a mock for streams. See Streams.

Does it do gRPC? #

No. Ultraman tests HTTP APIs, including WebSocket and SSE streams; for gRPC, pick a tool that supports it (see When to pick something else).

Does it do GraphQL? #

Yes: a request can carry a GraphQL body, with completion from the API's schema (loaded from the server or saved in the project), and an answer with errors fails the step even when the status is 200, under load too. Subscriptions work over graphql-transport-ws, in the Requests area and as pipeline steps. Not yet: GraphQL over SSE, GET and persisted queries, batching and file uploads. See GraphQL.

Which kinds of authentication? #

Bearer token, basic auth and API key (in a header or in the query string), set on a request, a collection or a pipeline. ca trusts your own server certificate authority. There are no client certificates (mTLS), OAuth2 flows, AWS SigV4 or NTLM. For an API that hands out tokens, a login step, an extract of the token and a bearer auth that uses it cover the usual case. See Pipelines.

Can I bring my existing work? #

Yes: Postman collections and environments, OpenAPI 3 documents, JMeter .jmx plans, Artillery scripts, and traffic recorded in your browser as a HAR file. Secrets from a Postman environment go to the vault. What can't be translated is listed, not lost, and an import never sends a request or runs a script. See Importing.

Does it need Node, Java or anything installed? #

No. The installer brings everything, Node included, into your user folder, with no admin rights. See Install.

Can I use it without the desktop app? #

Yes: install only the command (--cli) for a build machine or a server. The window is where you answer consent questions and approve agent cards; the command asks in the terminal instead. See The terminal.

Teams and CI #

Who can see and change our tests? #

Whoever can read or write your git repo: Ultraman has no accounts, roles or workspaces of its own. Changes to tests reach the team through Sync and review as pull requests. Secrets are never synced: each person keeps their own in their own vault. See Working as a team.

What happens when two of us change the same pipeline? #

Sync shows both versions side by side, as steps or as YAML, and you choose Keep mine, Use the remote's or Save mine as a copy. Esc cancels and changes nothing. See Conflicts.

Does it work in CI? #

Yes. ultraman run runs pipelines, collections or load tests, writes a JUnit report, and exits with 0 (passed), 1 (a check or threshold failed) or 2 (it couldn't run). On GitHub, the action ultraman-app/run-action@v1 installs and runs it; on other systems, install the CLI alone. A runner has no vault: secrets come from ULTRAMAN_SECRET_<NAME> environment variables. See CI.

Load #

Can a load test run on several machines? #

No. A load runs on one computer, on one thread by default and up to 8 with --workers. If you need load from many machines or from the cloud, pick a tool built for that (see When to pick something else).

How much load can it make? #

As much as your computer can send: it depends on the machine, the network and how heavy each request is. The strip This computer watches your machine during the run, and when it was the bottleneck the verdict says limited instead of blaming the API. See More than one thread.
