Agents (MCP) #

An AI agent (Claude Code, or any other MCP client) can use Ultraman through ultraman mcp. It can do what you do in the window: read and write requests, pipelines and load tests, send and run them, import, start the mock server, read reports and compare them. You approve every call.

Connect it #

ultraman mcp is an MCP server over stdio. In Claude Code:

claude mcp add ultraman -- ultraman mcp --project <your project folder>

Any other MCP client takes the same thing in its own settings: a stdio server whose command is ultraman and whose arguments are mcp --project <your project folder>. Without --project, the folder you start it from (or the nearest one above it that has ultraman/) is the project.

Two things must be true, or each tool answers "open Ultraman on this project to approve the agent's requests":

  • Ultraman's window is open on that project, because that is where you approve;
  • the folder is trusted in the window (trusted folders).

You approve every call #

Each thing the agent asks for shows as a card at the bottom right: who asks, what, and the detail (for a change, the diff). Approve or Reject (with a reason the agent reads). Read-only requests can be approved "always"; that lasts for the agent's current session only, and only while Ultraman stays open.

What runs (a pipeline, a request, a load) has two cards: one to start it, and one to deliver the result to the agent. The delivery card warns when the result carries tokens, cookies or authentication headers. If you reject a delivery, that is final.

A call lasts at most about 50 seconds, because most clients cut a tool call at 60: a long run keeps going and the agent asks for its result later. While a card waits for you, the agent gets a progress notice every 5 seconds. Every request is logged in ultraman/mcp/, which git ignores.

A WebSocket or SSE stream is sent once (send_stream, or a saved stream request): it opens, sends the messages on the card, listens for the time on the card (30 seconds at most), closes, and the delivery has the handshake and the messages both ways (the first 50, each cut to 4 KB). The agent has no live session: for one that stays open, use the window.

What it can do #

The tools come in areas that match the window:

  • Pipelines and blocks: list, read, save and run them; read past runs; turn a HAR file or history entries into a proposed pipeline.
  • Requests: list, read and save collections and requests, move and organize them, add one to a pipeline, send a saved request with its checks, run a collection, send an ad-hoc request, read the history.
  • Streams: one-shot WebSocket and SSE sends.
  • Load: list, read and save load tests, run one, read reports, compare two, trend, export.
  • Project: list and save environments, list secrets (names only), import a Postman, OpenAPI, JMeter or Artillery file, read the YAML format reference.
  • Mock server: status, start, stop, reset, pin a recording.

A write shows its diff (or the whole new file) on the card. A save that turns on plain http or a custom CA is flagged in red.

What it can't do #

On purpose, the agent can't see or set a secret's value, unlock the vault, say yes to a consent, trust a folder, sync with git, or delete anything. Those stay with you, in the window. It can use {{secrets.x}}; the value never reaches it, and results are redacted before they are handed over.

One thing is not a secret: a token that a step extracts from a response (for example a login's access_token) is just data, so it comes back to the agent. That is why the delivery card highlights tokens, cookies and authentication headers before you approve.

Asking it things #

The agent reads this same manual (get_manual) and the YAML format reference (get_reference), so you can ask it "how do I run this with 50 users?" or "make a pipeline that logs in and creates an order" and it will propose the change for you to approve. What a result says is handed to it as data to read, not as instructions to follow.

The approval protects what goes through the MCP channel. An agent with a shell (Claude Code has one) can also read your project's files or run ultraman run on its own: that is outside Ultraman's reach. Treat the cards as consent, not as a sandbox, and give an agent only the access you would give a colleague.

What keeps you safe #

  • You: nothing the agent asks for happens until you approve its card, and a rejected delivery stays rejected (agents).
  • You: the agent never sees a secret's value and can't unlock the vault, give a consent, trust a folder, sync or delete (redaction).
  • You: the agent can't approve itself: a decision needs the window (local server).
  • Your team: the agent's requests are logged in ultraman/mcp/, on your machine only.
  • Limit: an agent with its own shell is outside the cards (limits).
