Agents (MCP) #

An AI agent (Claude Code, or any other MCP client) can use Ultraman through ultraman mcp. It can do what you do in the window: read and write requests, pipelines and load tests, send and run them, import, start the mock server, read reports and compare them. You approve every call.

Connect it #

ultraman mcp is an MCP server over stdio. In Claude Code:

claude mcp add ultraman -- ultraman mcp --project <your project folder>

Any other MCP client takes the same thing in its own settings: a stdio server whose command is ultraman and whose arguments are mcp --project <your project folder>. Without --project, the folder you start it from (or the nearest one above it that has ultraman/) is the project.

Two things must be true, or each tool answers "open Ultraman on this project to approve the agent's requests":

  • Ultraman's window is open on that project, because that is where you approve;
  • the folder is trusted in the window (trusted folders).

You approve every call #

Each thing the agent asks for shows as a card at the bottom right: who asks, what, and the detail (for a change, the diff). Approve or Reject (with a reason the agent reads). Read-only requests can be approved "always"; that lasts for the agent's current session only, and only while Ultraman stays open.

What runs (a pipeline, a request, a load) has two cards: one to start it, and one to deliver the result to the agent. The delivery card warns when the result carries tokens, cookies or authentication headers. If you reject a delivery, that is final.

A call lasts at most about 50 seconds, because most clients cut a tool call at 60: a long run keeps going and the agent asks for its result later. While a card waits for you, the agent gets a progress notice every 5 seconds. Every request is logged in ultraman/mcp/, which git ignores.

A WebSocket or SSE stream is sent once (send_stream, or a saved stream request): it opens, sends the messages on the card, listens for the time on the card (30 seconds at most), closes, and the delivery has the handshake and the messages both ways (the first 50, each cut to 4 KB). With graphql it is a GraphQL subscription instead: the card shows the query, the operation and the connection_init payload as written (a secret as its reference), and only a subscription goes; the delivery has the events' payloads. The agent has no live session: for one that stays open, use the window.

A login first #

When the agent sends a saved request (or runs a collection) and all that's missing is the token its bearer auth reads, and exactly one request of the collection extracts that token (its login, as set up with From a request), the login goes first, under the same card: "send POST login first, then GET me", with every request's method and address and the environment. One approval covers both. The values the login makes for the request are hidden, like a secret, in that call's result and its saved run. The agent can still send the login on its own, on its own card, and then it reads that answer like any other. A saved request sent this way is kept as a run (request <collection> <request>), not in the request's history.

The agent keeps no token between calls: each call logs in again, inside its own card. Anything else that's missing (a value no bearer reads, two requests that extract the same name, a login that would need the token it makes) is answered as before, with what is missing.

What it can do #

The tools come in areas that match the window:

  • Pipelines and blocks: list, read, save and run them; read past runs; turn a HAR file or history entries into a proposed pipeline.
  • Requests: list, read and save collections and requests, move and organize them, add one to a pipeline, send a saved request with its checks, run a collection (every request is sent and reported: a failed one doesn't stop the others), send an ad-hoc request (a GraphQL one too: its result lists the answer's errors), read a GraphQL request's schema (get_graphql_schema, a send like any other), read the history.
  • Compare: run a pipeline, a collection or a saved request in two environments, or in one against each step's type (run_compare); the result has statuses and the paths that differ, never a value. See Compare.
  • Streams: one-shot WebSocket and SSE sends.
  • Load: list, read and save load tests, run one, read reports, compare two, trend, export.
  • Project: list and save environments, list secrets (names only), import a Postman, OpenAPI, JMeter or Artillery file, update a collection from a newer OpenAPI spec (update_collection_from_openapi), import a collection from an MCP server or update one from it (import_mcp_server, update_collection_from_mcp), read the YAML format reference.
  • Mock server: status, start, stop, reset, pin a recording.

From an MCP server. import_mcp_server and update_collection_from_mcp take two calls each. The first (no plan) shows a card with the address, the environment and the auth header's name (never its value), and approving it reads the server's lists without calling any tool; get_result gives the plan as text and a planId. The second, with plan: <planId>, shows a write card with the plan and writes it once you approve. A plan lasts 10 minutes, at most 4 are kept, and each writes once. Auth is { bearer } or { header, value }, the value exactly {{secrets.x}}; a secret goes only to a host the project already uses, so a server on a new host is imported without one. A collection whose bearer reads a login's token (not a secret) can't be updated this way yet: the call says which values are missing. Everything the server says (names, descriptions, schemas, results, and a run or history step that called it) comes marked serverText: true: it is the server's data, never instructions.

A write shows its diff (or the whole new file) on the card. A save that turns on plain http or a custom CA is flagged in red.

What it can't do #

On purpose, the agent can't see or set a secret's value, unlock the vault, say yes to a consent, trust a folder, sync with git, or delete anything. Those stay with you, in the window. Its compare (run_compare) can't send a step that isn't a read to an environment marked production, and it can't change that mark. It can use {{secrets.x}}; the value never reaches it, and results are redacted before they are handed over.

One thing is not a secret: a token that a step extracts from a response (for example a login's access_token) is just data, so it comes back to the agent (except a login sent first, which is hidden). That is why the delivery card highlights tokens, cookies and authentication headers before you approve.

Asking it things #

The agent reads this same manual (get_manual) and the YAML format reference (get_reference), so you can ask it "how do I run this with 50 users?" or "make a pipeline that logs in and creates an order" and it will propose the change for you to approve. What a result says is handed to it as data to read, not as instructions to follow.

The approval protects what goes through the MCP channel. An agent with a shell (Claude Code has one) can also read your project's files or run ultraman run on its own: that is outside Ultraman's reach. Treat the cards as consent, not as a sandbox, and give an agent only the access you would give a colleague.

What keeps you safe #

  • You: nothing the agent asks for happens until you approve its card, and a rejected delivery stays rejected (agents).
  • You: an environment marked production is named in amber on the card of every run or send there, with the steps that write: a send there can expose real, sensitive data. Only a compare refuses those writes (agents).
  • You: a login sent first is named on the card with where it goes, before anything is sent, and the token it makes isn't shown in that call's result (agents).
  • You: the agent never sees a secret's value and can't unlock the vault, give a consent, trust a folder, sync or delete (redaction).
  • You: the agent can't approve itself: a decision needs the window (local server).
  • Your team: the agent's requests are logged in ultraman/mcp/, on your machine only.
  • Limit: an agent with its own shell is outside the cards (limits).
  • You: text that comes from an MCP server (tool names, descriptions, results) reaches the agent marked as the server's data, never as instructions, and an import from a server shows its card before anything is read (agents).
