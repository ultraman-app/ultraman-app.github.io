Security and consent #

What Ultraman asks before it sends anything, how it keeps your secrets out of sight, and what it leaves to you: the promises you can check, for you, your team and your CI. There is no telemetry, no analytics, no crash reporting and no account.

The promise #

Ultraman never sends anything in an unsafe way without your explicit consent. In practice:

  • a secret goes only to an origin (scheme, host and port) you said yes to for that secret;
  • a file goes out without asking only from ultraman/files/, the folder your project shares on purpose; any other file needs a yes;
  • a folder you haven't trusted sends nothing and runs no git;
  • a secret's value doesn't show: everywhere you can read it, it says [secret:name].

A yes is yours. It is stored on your computer, never in the project, so whoever wrote a pipeline can't say yes for you. When Ultraman can't ask (a terminal with nobody at it, a CI runner), it stops instead of sending. The only way around the questions is one you choose yourself: --yes in a terminal or yes: true in CI, meant for branches only your team can change.

See it for yourself, in your own project:

  • Point a request that uses {{secrets.x}} at a host you haven't allowed for that secret and press Send: the question appears before anything leaves. Press Esc and nothing is sent.
  • Open ultraman/.gitignore: runs/, loads/, mcp/, history/, .serve, local/ and mock/ stay out of git. Search the project for secrets.: you find only references like {{secrets.token}}, never a value Ultraman stored.
  • Look in ~/.ultraman: secret values are stored only encrypted, in secrets.enc (with vault.json); the same folder also holds plain-text files such as trust.json and the update check. None of it is in the project.

The rest of this page says how each part works, who it protects, and what it doesn't cover.

When Ultraman asks #

Ultraman asks before it sends a secret to an origin you haven't allowed for that secret in this project, and before it sends a file from outside ultraman/files/. The question names what goes where. The safe choice comes first and has the focus; Cancel (or Esc) sends nothing.

A secret to a new origin. The window asks "Send the secret token to https://api.example.com?" and reminds you that if someone else wrote the request, you should check the host is yours. The value itself is never shown.

A yes covers one secret and one origin: the same secret to another host or port asks again, and so does another secret to the same host. When a request sets its own host header, the origin that header names is asked for too.

A file from outside `ultraman/files/`. The window asks "Send a file from outside ultraman/files?", with the path and where it goes, and says that whoever wrote the path picked the file. Choose the file (desktop window) lets you pick it yourself, in the project or copied into it; Send it, and remember this file lets it go from now on in this project; Cancel sends nothing.

In the terminal. ultraman run lists what the run would send that you haven't said yes to, names the file to look at, and asks:

  y  yes, just this once
  a  always: allow these for this project
  N  no, send nothing (default)

Enter, Ctrl+C or Ctrl+D is a no. In a folder you haven't trusted, a also trusts it. With no terminal to ask in, the run stops with exit code 2 before sending anything. --yes says yes to everything for that one run and remembers nothing; in CI, list what may go where instead (In CI).

Who it protects: you, when you run a request someone else wrote; your team, because a teammate's change can't point your secret at a new host without you seeing it; CI, which refuses instead of sending.

Trusted folders and restricted mode #

The first time you open a folder, Ultraman asks "Do you trust this folder?": its pipelines and requests can send your secrets and files to any server, and its git settings can run commands on your computer.

  • Open in restricted mode (the default): browse and edit it. Ultraman sends nothing from it, runs nothing (no requests, pipelines, load tests, streams or mock server) and runs no git, so there is no sync. A Restricted mode lock in the top bar asks again when you're ready.
  • Trust this folder: only if you know where it came from. You decide once per folder, on this computer.

An agent can't save, send or run anything in a folder you haven't trusted. Your trusted folders are kept in your Ultraman folder (~/.ultraman/trust.json), never in the project.

Trust isn't a blank check: in a trusted folder, a secret still asks before it goes to a new origin, and a file from outside ultraman/files/ still asks before it goes out.

Who it protects: you, when you open a repository someone else wrote. Git runs what a repository's own settings say, so Ultraman doesn't run it there until you trust the folder.

The vault #

Secret values live in a vault on your computer: vault.json and secrets.enc in ~/.ultraman/ (or the folder ULTRAMAN_HOME names). They are never in the project, so git never carries them: a project holds only references like {{secrets.token}}.

  • Encryption. A random key encrypts the secrets (AES-256-GCM). That key is stored only wrapped by a key derived from your master password (scrypt). The password needs at least 8 characters; a long phrase is better.
  • Locking. The window asks for the password the first time a run needs a secret. The vault locks again after 30 idle minutes. The lock at the top (Secrets: lock, password) locks it now or changes the password. Locking also ends the WebSocket and SSE sessions that read a secret from the vault.
  • No recovery. Nobody can open the vault without the password, Ultraman included. If you forget it, Forgot it? deletes every saved secret so you can start again.
  • Remember on this machine (desktop window only, off by default) keeps the vault's key in your system keychain so the vault opens without asking. On Windows and Linux other apps you run can read that entry; on macOS the Keychain asks first. The terminal never uses it: the CLI always asks for the password, or takes ULTRAMAN_SECRET_<NAME> variables instead (Secrets).

Who it protects: you, because a copy of your Ultraman folder, a backup or a stolen disk doesn't open your secrets without the password; your team, because secrets never travel through the repository.

Redaction #

A secret's value doesn't appear where you can read it: responses, history, runs, load reports, exports (cURL, HTML, CSV), errors, terminal output and what an agent receives. It shows as [secret:name].

  • Values made from a secret count too: a basic-auth header built from it, the secret URL-encoded or in base64, a value the server echoes back, and values passed on through variables, blocks, exports and extracts. Ultraman keeps up to 256 such values for each pipeline and block in a run; past that, it treats the whole variable as a secret.
  • Hidden before it's cut. A long body is cut to fit only after secrets are hidden, so it never shows half of one.
  • Checks can't read a secret. An assert, an if, a stream's where, or a regex extract over a response that echoes a secret is refused with an error instead of run: whether it passed would tell something about the value. Compare a value the response gives instead.

Files a request sends #

Only files in ultraman/files/ go out without asking. That is the folder your project shares on purpose: when you pick a file from elsewhere in the window, Ultraman offers Copy it into the project, and git sync shares it with your team.

Any other file a request reads (a body, a multipart part, a stream message, a custom CA) asks once (When Ultraman asks) and isn't used until you say yes. That includes files elsewhere in the repository, hidden files and folders like .env, .npmrc or .git (even inside ultraman/files/), and this computer's own folders under ultraman/ (local values, history, runs, reports).

Ultraman also doesn't follow symbolic links (or Windows junctions) inside ultraman/. If a file there is a link, a dialog says where it points and nothing is saved through it; Save as a regular file here replaces the link instead.

Who it protects: you, your team and CI: a shared pipeline or a pull request can't make a request send your SSH keys, a .env file or a checkout's credentials without someone saying yes.

Redirects #

When a server redirects a request to another origin, Ultraman drops the authorization, cookie and proxy-authorization headers. If the request carries a secret in another header, its custom headers stay behind too. A 307 or 308 that would resend a body containing a secret to another origin isn't followed: you get the redirect itself as the response. A redirect from https to http is refused, and a WebSocket or SSE handshake never follows a redirect.

Who it protects: you: the yes you gave for one host doesn't follow a redirect to another.

The local server #

The window, the ultraman command and the agent bridge talk to one local server per project (ultraman serve). It listens only on 127.0.0.1, and:

  • answers only requests addressed to 127.0.0.1 or localhost, so a web page can't reach it by pointing its own domain name at your computer;
  • refuses changes from any web page but the window's own, and takes only JSON;
  • needs the window's session token and origin for every decision: answering a consent question, trusting a folder, opening the vault, approving an agent's card, opening a stream;
  • asks any other caller to prove it is Ultraman's CLI, with a key kept in your Ultraman folder; the CLI checks the server the same way before handing it a run.

The window's page loads only its own files and connects only to this computer.

The mock server listens on 127.0.0.1 too and answers only pages and programs on this computer. ultraman mock --expose opens it to your network, after a warning you confirm; the window and the agent can't do that.

Who it protects: you: a web page open in your browser is refused by the local server, so it can't make Ultraman send your secrets or read your project.

Agents #

An AI agent connected through ultraman mcp works with your approval, card by card (Agents):

  • every call shows a card in the window; running something takes two, one to start and one to hand the result to the agent; only read-only calls can be approved "always", and only for that session;
  • the agent can use {{secrets.x}} but never sees or sets a value; what it receives is redacted, and the delivery card warns when a result carries tokens, cookies or authentication headers;
  • it can send a secret only to a host the project already names (an environment value or a pipeline's host), and the start card lists each secret and origin you haven't allowed yet: approving the card lets them go that one time;
  • it can't unlock the vault, answer a consent question, trust a folder, sync with git or delete anything.

Who it protects: you, when something the agent reads tries to steer it: nothing runs or leaves without your click.

In CI #

A runner has no vault and nobody to ask. Secrets come from ULTRAMAN_SECRET_<NAME> variables (In CI) and are hidden like any other. With the GitHub Action, the allow input lists which secret may go to which origin; anything else is refused before it is sent. yes: true (or --yes) turns the questions off: use it only for branches only your team can push to. Only ultraman/files/ goes out without a yes here too, and the action refuses to run next to the job's checkout token. The details are in CI.

Who it protects: CI and your team: a pull request that points a secret at a new host fails instead of sending it.

What leaves your computer #

Your requests, to the hosts they name, under the rules above. Besides those:

  • The update check. When the window opens, the local server asks GitHub for Ultraman's latest release, at most once a day. GitHub sees your IP address; nothing about you or your projects is sent. Only if a newer version exists does the desktop window read the update's details from GitHub. Nothing is downloaded until you click Update and restart, and an update installs only if it carries Ultraman's signature. Set ULTRAMAN_NO_UPDATE_CHECK=1 in the environment you start Ultraman from to turn both off.
  • Git sync, to your own remote, when you sync (trusted folders only).
  • The mock server's `--proxy`, to the URL you give it.

There is no telemetry, no analytics, no crash reporting and no account.

Honest limits #

What Ultraman doesn't protect, and what to do about it:

  • A trusted folder is trusted. Trusting lets its requests run and its git settings apply. Trust a folder only when you would also run its code.
  • Your computer is out of scope. A program running as you can read an unlocked vault from memory or record the password you type. With Remember on this machine on Windows or Linux, other apps you run can read the key: keep it off on shared or unmanaged computers.
  • A forgotten master password loses the secrets. By design, there is no recovery.
  • Only secrets are hidden. A token typed into a header or an environment value is plain text: it shows, it is saved in history, and it is synced if it's in a shared file. Values in ultraman/local/ stay off git but aren't hidden. Make every credential a secret.
  • Redaction works by value. Ultraman recognizes a secret in the spellings it can predict (as is, URL-encoded, base64, echoed back); a server that transforms it some other way returns something Ultraman can't tell apart. Very short secrets are recognized in fewer ways: use long ones. And it hides values, not names: a secret a server sends back as the name of a header shows as it is.
  • CI runs what the workflow says. A pull request that changes the workflow file itself is outside what Ultraman can check, and yes: true or --yes turns the questions off. Keep your secrets away from pull requests from forks (CI).
  • An agent with a shell can also run commands on its own: the approval cards cover only what goes through Ultraman.
  • The installers aren't signed by Microsoft or Apple, so your system warns the first time you open Ultraman. What is signed: updates (checked against a key built into the app) and the release checksums the install scripts verify before installing. The one-line install command runs a script fetched from Ultraman's site, so it trusts the site for that script.
  • No independent audit. Ultraman's security reviews are done by the people who build it, before each release; no outside party has audited it. If your policy needs one before you store credentials in a tool, that is the honest answer today.
