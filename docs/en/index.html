Ultraman docs

How Ultraman works, what each feature gives you and what keeps you and your team safe.

  1. What Ultraman gives you

    Ultraman tests HTTP APIs, WebSocket and SSE included: one app on your computer for single requests, multi-step tests, load and CI, all saved as plain files in your own git repo. Ultraman never sends anything in an unsafe way without your explicit consent: a secret goes only to a host you approved, and a folder you haven't trusted sends nothing.

  2. Why Ultraman

    Ultraman puts API requests, test flows, load tests and CI checks in one local app, saved as plain files in your own git repo. This page says how that differs from tools you may already use, and when one of them is the better choice.

  3. Getting started

    From installing Ultraman to your first request and your first pipeline, plus how it updates, why your system may warn about it, and how to remove it.

  4. Security and consent

    What Ultraman asks before it sends anything, how it keeps your secrets out of sight, and what it leaves to you: the promises you can check, for you, your team and your CI. There is no telemetry, no analytics, no crash reporting and no account.

  5. Requests

    The Requests area is where you build, send and check single requests: collections with folders and requests, opened in tabs, like Postman. What's different is that each request carries its checks, and everything is a plain file in ultraman/requests/ that your team shares through git.

  6. Pipelines

    A pipeline is a flow of requests and checks you can read from top to bottom, saved in ultraman/pipelines/<name>.yaml and run from the window or the terminal. It has a host, optional auth and headers for all its requests, inputs (values the run asks for) and steps. Nothing in it is hidden: what a step does is what its row says.

  7. Load

    Load (next to Run) tells you how many users, or how much traffic, your API can take before it slows down or fails. It opens the load screen of the pipeline on screen: each virtual user runs the whole pipeline in a loop, and if a step fails, that iteration counts as an error and the user starts another one.

  8. Environments and secrets

    Environments let the same requests run against local, staging or production, and secrets keep tokens and passwords on your computer, encrypted, out of git and out of every log.

  9. Importing

    The Import menu next to New collection (Requests area) brings in what you already have: a Postman export, an OpenAPI spec, a JMeter plan or an Artillery script; the one next to New pipeline (Pipelines area), a browser recording. So you don't start from zero. Nothing in the project is overwritten: a name that's taken gets -2. At the end, a summary says what came in, what was adapted, what needs a hand, and which files were skipped.

  10. Mock server

    The mock server answers your API's requests with responses you already recorded, so a front end (or a test) can work while the real API is down, slow or not built yet. It runs on your computer and nobody else can reach it unless you choose.

  11. The terminal

    The ultraman command runs your pipelines and load tests from a terminal, serves the project to other tools and keeps secrets in the vault. Run it from the project's folder (or any folder inside it). To use it on a build machine, see CI.

  12. CI

    Ultraman runs in a build pipeline with the same pipelines you use on your machine, writes a JUnit report and fails the job when a step or a threshold fails. For GitHub Actions there is an action that also keeps secrets from going anywhere nobody approved. For other systems you install the command and call it.

  13. Working as a team

    Everything a team shares is a file under ultraman/, so your tests travel with your code and a change to a test shows up in a pull request like any other change.

  14. Agents (MCP)

    An AI agent (Claude Code, or any other MCP client) can use Ultraman through ultraman mcp. It can do what you do in the window: read and write requests, pipelines and load tests, send and run them, import, start the mock server, read reports and compare them. You approve every call.

  15. Coming from another tool

    Some ideas have the same name here, some have another, and a few don't exist on purpose.

  16. Questions

    Short answers to what teams ask before they adopt Ultraman, the honest "no"s included. Each answer links to the page that goes deeper.

  17. Format reference (YAML)

    Everything lives as YAML under ultraman/ in the user's project. Unknown keys are errors: write only what's listed. Variables: {{env.x}} (the environment), {{secrets.x}} (a secret: usable, never visible), {{x}} (an input, an extract or a collection variable).
