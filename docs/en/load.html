Load #

Load (next to Run) tells you how many users, or how much traffic, your API can take before it slows down or fails. It opens the load screen of the pipeline on screen: each virtual user runs the whole pipeline in a loop, and if a step fails, that iteration counts as an error and the user starts another one.

Send load only to an API of your own, or one you have permission to test. The load screen shows the target before you start and says the same.

A load test is a file #

Its settings live in ultraman/load-tests/<name>.yaml, shared through git, so the same test runs the same way for everyone. The first time, Load creates one with 10 users for 30 seconds.

The shape of the load #

The presets draw the planned users as you type:

PresetShape
Steadythe same users all along
Ramp-up and holdgrow, hold, come down (JMeter's thread group)
Rampgrow from 0 to the users
Spikea base and a sudden peak
Arrival rateN new iterations per second, whatever the API takes (Artillery's arrivalRate)
Customyour own stages

Users (a closed model) answers "does it hold this many people?". Arrival rate (an open model) answers "does it hold this traffic?": if the API slows down, arrivals keep coming, like in production.

With arrival rate, each arrival is a new user that runs one iteration. Max users (maxUsers, 100 unless the test says, at most 1000) is how many may be alive at once. An arrival that finds them all busy is dropped, never queued, and the report counts it. If more than 1% of the arrivals are dropped, the verdict says the rate wasn't reached. The report then has two latencies: the service time (from sending to the answer) and the response time, counted from when the arrival was due, so a slow start on this computer shows in it.

Per user #

Under More:

  • Setup block: runs once per user before its first iteration (log in once per user).
  • Before and after: a block once per test (seed data, clean up).
  • Cookies: each user has its own cookie jar.
  • Data file: a CSV or JSON inside the project; each row is one user's (or one iteration's) values.
  • Think time and pacing: pauses between iterations, and a minimum time per iteration.
  • Responses: by default only the bodies a check or extract reads are kept, to save memory.

While it runs #

Live tiles and charts show requests per second, latency, errors and users. −N, +N, Hold and Resume change the load without stopping it. The strip This computer watches your own machine: if the generator is the bottleneck, the verdict says limited instead of blaming the API.

The verdict #

The report starts with a verdict in words. They are:

VerdictIn plain wordsRoughly when
Holdsthe API kept upunder 1% of the iterations failed and the latency didn't climb as users grew
Queuesthe API got slower instead of failingthe p95 of the last fifth of the test is over five times the first fifth's and at least 50 ms more, and the requests per second stopped growing with the users; in an arrival-rate test, also when more than 1% of the arrivals were dropped
Rejectsthe API answered errorsmore than 1% of the iterations failed; it says when the errors started and with how many users
Brokenthe problem is the pipeline or the address, not the loadthe first 20 iterations all failed; "The target refuses connections" when the server isn't reachable
Too few iterationsnot enough to concludefewer than 20 iterations ran; raise the time or the users
Limitedthis computer was the limit, so the numbers say little about the APIUltraman's own thread, memory or connections were at their limit
ProtectedUltraman stopped the test to protect this computermemory was running out; what it measured up to then is in the report

A load never says "holds" on a computer that was at its limit: it says Limited. The This computer strip shows why.

The report #

At the end, a verdict in words (it held, it queued, it broke…), the latencies (p50, p95, p99, max), throughput, errors per step with one failed request kept for each, where the time went, and APDEX if the test asks for it.

  • Thresholds (p95: 500ms, errors: 1%) pass or fail the run; warn levels only warn.
  • Compare with puts a report against an earlier one; Trend shows the last runs of the test.
  • Export writes a self-contained HTML page or CSV files.

Responses that must not change #

In a request's Options, always answers the same marks a request that should give the same answer every time (a product page, a lookup). Under load each answer, status and body, is compared with the first one for the same request. A different one fails that iteration, and the report shows how many times and the two answers. Ignore fields ($.timestamp, $.meta.requestId) leaves out what changes on purpose. In YAML it is idempotent: true or idempotent: { ignore: [$.timestamp] }. When a test discards response bodies, there is nothing to compare, and the report says "not compared".

Streams under load #

A pipeline with websocket or sse steps is a load scenario like any other: each iteration opens its own connection, runs send and receive on it, and closes it (or the engine does at the iteration's end). Ten users who hold a socket for twenty seconds each waiting for three updates is a repeat around a receive; the demo has that test as live orders.

With streams in the test, the report gains a Streams strip under the tiles: connections opened, how many were open at once and still open at the end (should be 0), messages received and sent, messages per second, how many streams the server closed (with the most common close code) and how many messages a size cap left out. The Users chart draws the open connections as a dotted line. A receive row in the steps table reports the time to the message, the stream's latency, with its own p95 and error rate.

  • streamErrors: 0% is a threshold on the connections the server closed mid-run and the messages it dropped; steps: { update: { p95: 3s } } bounds one receive by its name.
  • Each stream buffers at most 1 MB under load, and the reader waits when that's full.
  • Export and --csv add -streams.csv with the strip's numbers.
  • The limited verdict applies here too: a connection count is a machine limit like any other.

Several scenarios #

A test can mix pipelines: three people browsing for each one checking out. Each scenario has its own stages, or they share the test's stages split by weight. The report has a row and a verdict per scenario.

More than one thread #

By default a load runs on one thread. When the This computer strip shows the thread at its limit and the verdict says limited, spread the users over more threads: --workers N (1 to 8) in ultraman run --load, or the ULTRAMAN_LOAD_WORKERS environment variable; the reports merge into one. A test with a before or after block runs on one thread.

What keeps you safe #

The promise applies here as everywhere. What this part adds:

  • Whoever owns the API: the target is shown before the test starts, with a reminder to test only an API of your own.
  • You: brakes hold or stop users when your own computer is overloaded or low on memory, instead of freezing it.
  • Your team: a load test never holds a secret; its inputs can't carry secrets. or env. values. The reports in ultraman/loads/ stay on your machine. See where things are stored.
