The terminal #

The ultraman command runs your pipelines and load tests from a terminal, serves the project to other tools and keeps secrets in the vault. Run it from the project's folder (or any folder inside it). To use it on a build machine, see CI.

The commands #

CommandWhat it does
ultraman run <pipeline>Runs a pipeline, found by name and then by id.
ultraman run --all, --tag X, --collection IDRuns several pipelines at once.
ultraman run --load <test>Plays a load test; ultraman run <pipeline> --load uses that pipeline's default test.
ultraman serve [--port 4100]Starts the project's local server (the window and the other commands talk to it).
ultraman secret set <name>, list, rm <name>, passwordManages the vault.
ultraman mock [--port 4300]Serves your recorded history as a mock API. See Mock server.
ultraman mcp [--project <folder>]The bridge an AI agent connects to. See Agents.
ultraman sampleResets the sample project in Ultraman's own folder and prints its path. See the sample project.
ultraman --versionPrints the version.

A command with no arguments, or an unknown one, prints the usage and exits with 2.

Run pipelines #

ultraman run "create order" --env local --input user=ana
ultraman run --all --env ci --yes
ultraman run --tag smoke --env ci --parallel 4
ultraman run --collection shop --env staging

Give exactly one of: a pipeline, --all, --tag or --collection; anything else is exit 2. Everything is checked for all the selected pipelines before the first request goes out.

FlagWhat it does
--allEvery pipeline in the project.
--tag XThe pipelines with that tag. Repeat it and a pipeline needs every tag given.
--collection IDRuns a collection; shop/orders runs only that folder.
--env XThe environment. With a single environment in the project it is used on its own; with several you must pass --env.
--input k=vA value for an input; repeat it for more. A value that starts with [ or { is read as JSON when it is valid; anything else stays text (id=00123 stays 00123). The names env.* and secrets.* are reserved.
--parallel NRuns up to N pipelines at the same time (1 to 16). Each one prints whole when it ends.
--bailStops starting new pipelines after the first one that fails. The ones running finish; the rest show as skipped.
--watchRuns again whenever a file under ultraman/ changes.
--every DRuns again on a timer: 30s, 5m, 1h or a bare number of seconds, at least 5 seconds. It counts from the end of the previous run and combines with --watch.
--no-notifyWith --watch or --every, no desktop notification when a run fails and when it passes again.
--jsonOne JSON event per line on standard output, for other tools. No colors.
--junit FILEWrites a JUnit XML report. See JUnit.
--contract Mstrict, warn or off: over each collection's contract mode, so CI fails on what the spec doesn't document. See the contract.
--localRuns in this process even when the window has the project open. See One engine.
--yesAnswers yes to every question. Read Consent in the terminal first.

Each run is saved in ultraman/runs/. Colors appear only in a terminal; NO_COLOR turns them off. Ctrl+C cancels the running step, saves the run and exits with 1.

Exit codes: 0 everything passed, 1 a step failed (or you pressed Ctrl+C), 2 it never ran: a bad flag, a missing pipeline, input, environment or secret, an invalid pipeline, or nothing was sent because nobody said yes.

Consent in the terminal #

Ultraman asks before it sends anything you haven't approved. In a terminal it asks when:

  • the folder isn't trusted yet;
  • a secret would go to an origin it has never gone to;
  • a file from outside ultraman/files/ would be sent.

The question lists what would go where, and you answer y (this time), a (always, for this project) or N (the default: nothing is sent). "Always" is kept in ~/.ultraman/trust.json on your machine, never in the project, so a teammate's checkout can't carry it. The whole model is on the Security and consent page.

Without a terminal and without --yes there is nobody to ask: Ultraman lists what it would send and exits with 2, having sent nothing.

`--yes` skips every question. Anything the pipelines and environments say then goes wherever they say, including your secrets, and a value taken from a response that carries a secret goes too. Use it where only your team can change those files; never on code from forks or people you don't know. CI explains the safer way for GitHub Actions.

Run a load test #

ultraman run --load checkout-peak --env staging --junit load.xml --html report.html --baseline last

The test is ultraman/load-tests/<name>.yaml, given by name or id. Besides --env, --input, --junit, --json, --local and --yes (which work as above), a load takes:

FlagWhat it does
--target URLSends everything to another origin for this run (https://staging.example.com, with an optional base path, without user, password, ? or #).
--overrides JSONReplaces top-level keys of the test for this run, written as in the YAML.
--workers NPlays the load with N threads (1 to 8). The default is one, or ULTRAMAN_LOAD_WORKERS.
--output FILEWrites the final report as JSON.
--html FILEWrites the report as one self-contained page.
--csv DIRWrites the series and the steps as CSV files into that folder.
--baseline last or a filePrints how this run compares with an earlier report: the last one saved for this test, or a JSON file.

--all, --tag, --collection, --bail, --parallel, --watch and --every don't apply to a load.

Exit codes: 0 every threshold held and the verdict is holds, queues or limited; 1 a threshold failed, the API rejected or broke, too few requests went out, or it was stopped (Ctrl+C or the generator's own brakes); 2 nothing was sent. The thresholds and verdicts are explained in Load; for gates in a pipeline see CI.

JUnit for CI #

--junit FILE writes a JUnit XML report after the runs, also after Ctrl+C with what ran: a test suite per pipeline and a test case per top-level step, with what was sent and received for the ones that failed. Secrets are hidden in it like everywhere else. Missing folders are created.

ultraman run --all --env ci --yes --junit reports/ultraman.xml

Secrets #

On your machine, ultraman secret set api-key saves one in the vault: it asks for the master password and the value, both without echo. A value piped in (echo "$VALUE" | ultraman secret set api-key) is read from standard input; the master password still needs a terminal. Names use letters, digits, _, . and -. secret list shows the names, secret rm <name> removes one (exit 1 if it isn't there) and secret password changes the master password. See the vault.

On a build machine there is no vault. Pass a secret as an environment variable named ULTRAMAN_SECRET_ plus its name in upper case, with every character that isn't a letter or a digit turned into _: api-key is ULTRAMAN_SECRET_API_KEY. It wins over the vault and needs no password. Without --yes, a secret still goes only where it has been approved.

Environment variables #

VariableWhat it does
ULTRAMAN_SECRET_<NAME>The value of a secret for this command.
ULTRAMAN_HOMEReplaces ~/.ultraman, where the vault, the trust list and the server's keys live.
ULTRAMAN_LOAD_WORKERSThe default number of threads for a load (--workers wins).
ULTRAMAN_NO_UPDATE_CHECK1 turns off the daily check for a newer version.
ULTRAMAN_PROJECTThe project folder the desktop window opens with.
NO_COLORNo colors in the output.
ULTRAMAN_VERSION, ULTRAMAN_CLI_ONLYFor the installers: the version to install, and only the command, without the window. See Install.

The window and the terminal together #

If the window is open on the project, ultraman run hands the run to it: you see it live in the window, and the terminal prints the same as always. --local runs it in the terminal instead, which is what you want on a shared build machine. CI runs always use it.
