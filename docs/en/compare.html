Compare two environments #

Compare runs the same pipeline in two environments and tells you, step by step, whether they answer the same: after a deploy, check that staging has the structure and the replicated data that development has. It can also check one environment's answers against their type, a JSON Schema or the collection's OpenAPI spec.

What it answers #

A compare runs the whole pipeline in the first environment, then in the second, each run with its own environment's values, its own login and its own secrets, and compares the answer of every request. A request with a compare: block is compared by its rule; one with none is compared by Same structure, the default: the same fields and types, the values may differ. For every request it says one of:

  • same: the two answers match (with body: shape, same shape);
  • N paths differ: the status, a header you named or the body differ, and where (the JSONPath of each place);
  • not compared, and why: one side didn't run the step, a side failed it, or the answer can't be compared.

A request with no block is compared by structure without anything being added to its file, and its row says so ("same (by structure, the default)"). A step that isn't a request (an extract, an assert, a wait) has nothing to compare. This is for a pipeline or collection you name; a terminal selection by --all or --tag compares only the blocks written (see from the terminal). A request with no block that one side never reached (an if only one environment takes) shows as not compared and why, but doesn't change the verdict. Each side is saved as an ordinary run in ultraman/runs/. Nothing else is written: no diff file, no baseline.

The compare block #

A request step in a pipeline, or a request of a collection, carries the block beside its other fields:

- request: get order
  method: GET
  path: /orders/{{order_id}}
  compare:
    body: value                      # value | shape | none; the status is always compared
    only: [$.id, $.status, $.total, $.items]   # just these fields; without it, everything
    ignore: [$.updatedAt, $.meta.requestId]    # left out, also inside an only path
    lists:
      $.items: { match: sku }        # pair the items by this field
      $.tags: { order: any }         # the same items, in any order
    schema: files/order.schema.json  # the answer's type, for --compare schema
    headers: [content-type]          # none by default
    reuse: [order_id]                # see "Asking for the same record"

compare: {} compares the status and the whole body by value. Every key is optional:

KeyWhat it does
bodyvalue: the data must be the same. shape: the same fields with the same types, whatever their values. none: only the status and the headers you name.
onlyJSONPaths. Only these fields are compared; a path to an object or a list covers what is inside it.
shapeJSONPaths compared by type only, inside a body: value compare: each must be there on both sides with the same type, and its value may differ. The rest of the body is compared by value. With only, a shape path counts as included. A path can't be in both shape and ignore, and shape doesn't go with body: shape or none.
ignoreJSONPaths left out, in both modes, also inside an only path. A timestamp or a request id that changes on every call goes here.
listsIn value mode a list is compared in order, because a changed order is a real difference. match: <field> pairs items by that field; order: any compares them as the same items in any order. Two items with the same match value pair in order among themselves, and the result says so.
schemaA JSON Schema file under ultraman/files/: the step's type when you compare against types.
headersHeader names to compare. authorization, cookie, set-cookie, proxy-authorization and www-authenticate are refused.
reuseVariable names the second environment takes from the first for this step.

The classic case for shape is an id or a timestamp: each environment makes its own, so the values differ, but the field must be there and keep its type:

compare:
  body: value
  shape: [$.id, $.createdAt]   # there on both sides, same type; the values may differ
  ignore: [$.meta.requestId]   # not compared at all

A pipeline step linked to a collection's request takes that request's block, like its other fields. The full format is in the format reference.

From the terminal #

ultraman run "order compare" --compare local,staging
ultraman run "order compare" --env local --compare schema
ultraman run --tag smoke --compare dev,stg --junit reports/compare.xml

--compare a,b names two different environments of the project; the first is the source for reuse. It works with a pipeline, --all, --tag or --collection. A pipeline or collection you name compares every request. --all and --tag keep to what was written: they pick only the pipelines with a compare: block and compare only those steps, so a pipeline nobody named that writes with no block (a DELETE that resets data) never runs because a compare picked it. Pipelines with nothing to compare (against a type, none with a type) are left out and named. A compare prints a table per pipeline once both sides have finished:

order compare · local against staging
  login       POST /auth/login    200  200   same (by structure, the default)
  get order   GET  /orders/o-1    200  200   2 paths differ
      $.total       local 59.9 · staging 61.4
      $.items[1]    only in local
1 of 2 compared steps differs between local and staging.

At most 20 paths are listed under a row, then "and N more". Values under a row are hidden and cut like any printed body. The other flags of ultraman run work as usual: --input goes to both sides, --parallel runs pipelines side by side (inside one, the two environments run one after the other), --bail, --watch, --every and --contract. --env doesn't go with --compare a,b (the pair names both), and --load is refused: nothing is compared under load. --json adds side: 0 or 1 to each event and ends each pipeline with a compare line that has paths and no values.

When the window has the project open, the compare runs in its engine and the window shows both runs, as with one engine.

Steps that write #

A compare sends every step twice, once to each environment. A compared step that isn't a read (a POST that creates an order) would create data in both, so the terminal asks every time, naming the step and both environments, even when the rest of the run is already allowed. A read is a GET, HEAD or OPTIONS, a GraphQL query (the operation that goes out) and an MCP resource or prompt, when they go to their collection's endpoint (the path its GraphQL requests use, the MCP server it came from); anywhere else, or from a pipeline step of no collection, they count as writes. A GraphQL mutation or subscription, a document Ultraman can't parse, and an MCP tool count as writes: a tool's own readOnlyHint is the server's word, never Ultraman's. a (always) never covers this question, and neither does --yes. Without a terminal (CI), say it by name: --allow-write dev,stg.

A request with no block that writes runs as it does in an ordinary run of the same pipeline: compared by structure, it is refused only in a production environment and asks nothing elsewhere. The question is for the steps you marked to compare. An agent's card still names each one ("it writes in both").

An environment with This is production ticked (see environments) is stricter: any step that isn't a read, compared or only feeding the compare, is refused before anything is sent, unless --allow-write names that environment:

Not run. "create order" is a POST and prod is a production environment:
comparing it would create an order in stg and another in prod.

Compare only the steps that read, or allow it by name: --allow-write prod

An environment that isn't ticked but points at a production environment's host counts as production too, in the terminal, the window and for an agent: a copy of prod's values saved under another name, an imported environment, or a host given as an input. The refusal names it ("qa points at prod's host, a production environment"), and --allow-write qa allows it by name. The host is compared whole, whatever its path, so an environment that shares production's host and differs only by its path counts as production as well. Only the hosts your pipelines and collections read decide it: a host every environment shares that only a step's path names (a login provider, a payment API) doesn't make them production.

Exit codes #

CodeWhen
0Every compared step is the same, and both runs passed.
1A compared step differs, or a run's own check failed. Both are reported.
2Nothing was sent (a bad flag, a refused write, an unknown environment), or a compared step couldn't be compared and none differs ("1 of 3 compared steps couldn't be compared"): a step a side didn't reach, a body over its limit. The terminal then says each such step's reason. A request with no block that a side didn't reach doesn't count, unless nothing else was compared.

A path that held a secret is "not compared" (see below), and it never makes a step differ on its own: a compare whose only open places were secrets still exits 0 when everything else is the same.

In CI: JUnit #

--junit FILE writes one test suite per pipeline, named order compare · local against staging, with compare in its properties and a test case per compared step:

<testcase classname="order compare · local against staging" name="get order" time="0.000">
  <failure message="2 paths differ: $.total, $.items[1]"></failure>
</testcase>

A difference is a failure whose message has the count and up to 20 JSONPaths. A step a side's run failed is a failure that names the side; "not compared" is skipped; when a step couldn't be compared and none differs, an error case is added, so CI never reads it as a pass. The file carries no value and no body. See CI.

Against a type #

--compare schema runs one environment (--env, or the project's only one) and checks each compared answer against its type: the block's schema file, or else the OpenAPI operation of the collection's contract. An answer that isn't JSON (an HTML error page) doesn't match a schema file's type.

order compare · local against each step's type
  login       POST /auth/login    200   not compared
  get order   GET  /orders/o-1    200   doesn't match the type Order at 2 paths
      $.currency    missing: the type requires it
      $.total       is a number, the type says string
      $.id          not named by the type (allowed)
1 of 1 compared step doesn't match its type in local.

The type's name is the schema's title, or else its file name. Fields the answer has and the type doesn't name are a note, never a difference, unless the schema says additionalProperties: false: an API that adds a field doesn't fail. Ultraman reads a subset of JSON Schema; the keywords it doesn't read (patternProperties, prefixItems, if/then, a $ref to another file…) are listed as "not checked" on the step, so a pass never claims more than was checked. With --compare schema, --contract off is refused: there the contract is the type.

Asking for the same record: reuse #

By default each environment uses its own values: its own login, its own ids. That is right for structure. To check that a record was replicated, the second environment has to ask for the first one's record:

compare:
  reuse: [order_id]   # in the second environment, this step is sent with the first one's order_id

Only that step takes the value; the second side's run goes on with its own. --compare dev,stg asks stg for dev's order. A value made from a secret is never carried, and a reused value can't move the request to another host: the step fails before it sends. The terminal's question names it ("in stg: send dev's order_id (reuse)").

The agent #

An agent compares with run_compare, like a run: a card to start it and a card to deliver it (see agents). It gets the verdict, each step's statuses and the JSONPaths that differ with their kind and JSON types, never a value: you see the values in the window or the terminal. The start card names each environment's host, the compared writes, reuse and a production environment ("prod is a production environment: this reads real data"). A GraphQL query and an MCP resource or prompt are reads there, like a GET.

A side whose own check failed is named with the step that stopped it, not with the check's message, which can quote the answer. A field name that no file of the project names (an email used as a key, say) reaches the agent as its number in the result, $.balances[field 2], since an answer's keys can be its data; the window and the terminal show the name.

An agent's compare never sends a step that isn't a read to a production environment, and never uses reuse with a production environment as its source: there is no way for it to allow either, and such a compare is refused before any card, saying to run it from the window or the terminal. An environment that isn't marked but points at a production environment's host (a copy of its values, a step's absolute URL) counts as production here too. When an agent saves a compare: block, its card says what the block leaves out ("compares only 2 fields", "ignores 3 fields: …").

In the window #

Compare with… to the left of Save sends the editor's draft, as Send does, and compares its answer:

  • Send it to another environment too: one request to each environment, each with its own values.
  • Against a type: the request's schema file, or the OpenAPI operation of its collection's contract.
  • My last send in an environment: nothing is sent; it compares your two latest sends there. The history stays on each computer, so a fresh CI runner has none: there, compare two environments or against the type.

The menu says what each environment needs before you pick it, without sending anything: needs login when a request of the collection makes the value the compare is missing, needs order_id when nothing makes it, and nothing when it is ready. It comes before the rest of the line (real data, asks before it writes).

The result opens under the request: a head with each environment and its colour (a production one in amber), a sentence ("The values differ at 2 paths."), and the paths that differ, read as breadcrumbs (items › 2 › qty, each JSONPath in its tooltip; a step inside a JSON text reads (JSON)). Open the diff shows the two answers Side by side or Unified.

Hover a value in an answer and open Compare… for Compare this field, Compare only its type or Ignore this field: each adds its path to the request's compare: block, and the request turns unsaved like any edit. Choose what to compare puts the answer in a pick mode: tick the fields, and Done writes only. With no answer yet, the fields come from the type; otherwise send it once first. The request's Options tab has a Compare section with the same rules. It keeps three rows in sight: Compare the body's (values, shape or nothing), Fields to compare and Fields to ignore. The rest is behind More: the fields compared by type only, list rules, the answer's type, headers and reuse (shown only when the file has it). Closed, More says what it holds in a line of chips ("1 list rule", "type order"), so nothing you set is out of sight; it opens by itself while something inside is invalid.

A pipeline (⋯ › Compare in two environments… in its header) or a collection (the same item in its ⋯ in the tree) runs in both environments and shows a row per request: every request is compared, by its own rule or, if it has none, by Same structure. A row ends with the rule it used, as a chip, and "the default" after it when the request had none. In a collection, picking another rule on a row's chip opens that request in a tab with the rule unsaved (nothing is saved and nothing is sent again); a pipeline's chip only names the rule. Only what differs keeps the rest folded.

Before anything is sent, the window asks what the terminal asks: a secret or a file going to the second environment's host for the first time, and a compared step that writes, named with both environments and both URLs, with Compare the last answers instead (nothing is sent) as the first answer. A production environment says so in the question, and so does one that points at a production environment's host ("qa points at prod's host, a production environment"); the Compare menu marks it in amber too. Against a type, a step that writes in a production environment isn't sent from the window: compare it from the terminal with --allow-write.

The first compare: Same structure, the default #

A request with no compare: block is compared by Same structure when you pick an environment or My last send in: the same fields and types, while the values may differ, so the ids and dates each environment makes don't read as a wall of differences. Nothing is asked and nothing is written: the request has no unsaved changes afterwards.

The result's sentence ends with the rule it used: "local and staging answer the same. Compared by Same structure, the default". The rule is a chip; click it to change it:

  • Same structure: the same fields and types; the values may differ. For checking what a deploy changed. It writes compare: { body: shape }.
  • Replicated data: the same values. For checking that data was copied. It writes compare: { body: value }.
  • Choose what to compare: tick what must stay the same on the answer the compare shows; Done writes only.

Picking a rule writes it into the request (it turns unsaved, like any edit, and Save keeps it) and compares again by it. A request with its own block shows its rule in the chip without "the default", and one that picks or ignores fields shows Chosen fields. Ignore this field on a result compared by the default keeps Same structure for the rest. The same two rules are cards at the top of Options while the request has no block. A check against a type has no chip: it checks the type.

Fields that change by themselves #

Some fields change on every call: a creation time, a request id. After a compare that differs, the window offers them for ignore in one click, in a banner under the sentence:

  • After My last send in an environment, it offers every body field whose value changed between those two sends: "These 3 fields change by themselves: createdAt · requestId · meta › traceId."
  • After a compare between two environments, it offers only the differences that also changed between two sends in the first environment, read from that environment's history (nothing is sent): "3 of the differences also change between two sends in dev: …". A difference that is stable inside each environment is the finding, so it isn't offered.

Ignore these 3 fields adds exactly the fields the banner names to the request's ignore list (the request turns unsaved) and reads the result again from the two answers the history already holds. The limits:

  • Only a field present on both sides whose value changed. Never a field on one side only, a changed type, a header, the status, the whole body or a list item itself (a field inside the items stands for that field of every item, items › each › seenAt).
  • Never a place that held a secret (those are "not compared"), and never a field you chose: one in only or shape, or an object above it.
  • At most 8, all named. With more, it says "and N more change too", and the click doesn't add those.
  • Nothing with body: shape or none, when the status differs, or against a type.

Logging in for the other environment #

Each environment uses its own values: a token one environment's login made never goes to the other. When an environment is missing a value the request needs, and a request of the collection makes it, picking that environment asks once: To compare, first send login in staging. It lists each request that will be sent with its method (up to three, "POST login"), and when both sides need one they are in the same question.

  • Cancel (first, and focused) sends nothing.
  • Send login and compare sends each listed request to its own environment, with that environment's values, then compares. What they make stays in that environment's session.
  • Type the value instead opens the missing-values dialog, whose title names the environment when it isn't the current one: "1 value is missing to send get order in staging".

A production environment is named in a warning inside the question ("prod is a production environment: this sends POST login there."). If a request fails or doesn't give the value, nothing else is sent and its tab opens with the answer. With more than three requests, or a value nothing makes, you get the missing-values dialog as before. A secret going to a server for the first time still asks its own yes.

What keeps you safe #

  • You: each environment's secrets go only to that environment's host, with the usual consent; one environment's secret never reaches the other.
  • You: both answers are hidden against every vault secret the project uses before they are compared or shown, and a place that held a secret is "not compared", never "same" or "different" (redaction). Plain values in ultraman/local/envs/ are ordinary variables and aren't hidden: keep a sensitive value in the vault.
  • You: the question before a login names every request, its method and its environment, production included, and a yes covers only what it listed. Each environment keeps its own session, and the menu's "needs login" is asked of Ultraman without sending anything.
  • You: the suggestion only names fields of the answers you already have, never a secret's place or a field you chose, and one click adds exactly the names it shows.
  • Your team: a compared write asks every time, and a production environment refuses every write unless you name it with --allow-write; an agent's compare can't write there at all (agents).
  • CI: a compare's results, in JUnit and in --json's compare line, list paths, kinds and types, not the values there. JUnit names a side whose check failed by its step only; the --json lines keep the check's message, as in any run (in CI).
  • Limit: the production box lives in a file under git: it guards against a careless write, not against someone who can push to the repository (limits).
