Perguntas #

Respostas curtas ao que os times perguntam antes de adotar o Ultraman, os "nãos" honestos incluídos. Cada resposta leva à página que aprofunda.

Confiança e segurança #

Ele poderia enviar meu token ao lugar errado? #

Um segredo vai só para uma origem (esquema, host e porta) à qual você disse sim; na primeira vez que ele iria para um lugar novo, o Ultraman pergunta, e num terminal também pergunta. Quando um redirecionamento leva a outra origem, as credenciais são descartadas. Numa pasta em que você não confiou, a janela não envia nada e não executa git. Veja Segurança e consentimento.

Um agente de IA pode ver meus segredos? #

Não. Um agente conectado por MCP pode usar {{secrets.x}}, mas o valor nunca chega a ele, e toda chamada mostra um cartão na janela que você aprova ou rejeita. Ele não pode desbloquear o cofre, dar sim a um host novo, confiar numa pasta, sincronizar com o git nem apagar nada. Um token que um passo extrai de uma resposta é dado, não segredo: o cartão que entrega um resultado destaca os tokens antes de você aprová-lo. Veja Agentes.

Ele envia alguma coisa sobre mim? #

Sem telemetria e sem conta. Enquanto a janela está aberta, o Ultraman pergunta ao GitHub no máximo uma vez por dia se existe uma versão mais nova, e não envia nada sobre você nem sobre seus projetos; ULTRAMAN_NO_UPDATE_CHECK=1 desliga isso. Nada é baixado até você escolher Atualizar e reiniciar. Veja O que sai da sua máquina.

Em quais sistemas ele roda? #

Windows (x64), macOS (Apple silicon e Intel) e Linux (x64, como AppImage). Os instaladores não são assinados pela Microsoft nem pela Apple, então a primeira abertura mostra um aviso; as atualizações e os checksums dos scripts de instalação são assinados. Veja O aviso da primeira abertura.

Como compartilho segredos com meu time? #

Não compartilha. Cada pessoa define os próprios valores no próprio cofre, com os nomes que o ambiente usa (staging.token); o CI recebe os dele por ULTRAMAN_SECRET_*. O repositório leva só {{secrets.x}}. Veja Segredos.

O que ele faz e não faz #

Posso escrever scripts? #

Não, de propósito: o que um passo faz está sempre na tela, e quem revisa o lê num diff sem executar nada. Em vez disso há asserts, extracts (por path JSON, header ou regex), passos if e repeat, blocos reutilizáveis e funções dentro de {{ }} como random.uuid, now.iso, base64(x) e hmac.sha256(secrets.key, body). Quando você importa, scripts de teste comuns do Postman viram checks; os outros scripts são listados para você, nunca executados. Veja Ajudantes.

Quais protocolos ele fala? #

HTTP e HTTPS, WebSocket e Server-Sent Events (SSE). Os streams funcionam como requests na área de Requests, como passos de pipeline e sob carga. Sem suporte: Socket.IO, WebSockets comprimidos, reconexões automáticas (conecte de novo, ou escreva a nova tentativa como passos) e um mock para streams. Veja Streams.

Ele faz gRPC? #

Não. O Ultraman testa APIs HTTP, incluindo streams WebSocket e SSE; para gRPC, escolha uma ferramenta que o suporte (veja Quando escolher outra coisa).

Ele faz GraphQL? #

Não há suporte dedicado a GraphQL: sem schema, sem editor de queries. Uma query GraphQL é um POST HTTP com um body JSON, então você pode enviá-la como qualquer request e checar o resultado. Um servidor GraphQL muitas vezes responde 200 mesmo quando a query falhou, então acrescente um assert de que $.errors não existe. Veja Checks.

Quais tipos de autenticação? #

Bearer token, basic auth e API key (num header ou na query string), definidos numa request, numa coleção ou numa pipeline. ca confia na autoridade certificadora do seu próprio servidor. Não há certificados de cliente (mTLS), fluxos OAuth2, AWS SigV4 nem NTLM. Para uma API que distribui tokens, um passo de login, um extract do token e uma auth bearer que o usa cobrem o caso comum. Veja Pipelines.

Posso trazer meu trabalho existente? #

Sim: coleções e ambientes do Postman, documentos OpenAPI 3, planos .jmx do JMeter, scripts do Artillery e tráfego gravado no seu navegador como um arquivo HAR. Os segredos de um ambiente do Postman vão para o cofre. O que não pode ser traduzido é listado, não perdido, e uma importação nunca envia uma request nem executa um script. Veja Importar.

Ele precisa de Node, Java ou algo instalado? #

Não. O instalador traz tudo, Node incluído, para a sua pasta de usuário, sem direitos de administrador. Veja Instalar.

Posso usá-lo sem o app desktop? #

Sim: instale só o comando (--cli) para uma máquina de build ou um servidor. A janela é onde você responde às perguntas de consentimento e aprova os cartões do agente; o comando pergunta no terminal em vez disso. Veja O terminal.

Times e CI #

Quem pode ver e mudar nossos testes? #

Quem pode ler ou escrever no seu repositório git: o Ultraman não tem contas, papéis nem workspaces próprios. As mudanças nos testes chegam ao time por Sincronizar e são revisadas como pull requests. Os segredos nunca são sincronizados: cada pessoa guarda os seus no próprio cofre. Veja Trabalhando em time.

O que acontece quando duas pessoas mudam a mesma pipeline? #

Sincronizar mostra as duas versões lado a lado, como passos ou como YAML, e você escolhe Ficar com a minha, Usar a do remoto ou Salvar a minha como cópia. Esc cancela e não muda nada. Veja Conflitos.

Funciona no CI? #

Sim. ultraman run executa pipelines, coleções ou testes de carga, escreve um relatório JUnit e sai com 0 (passou), 1 (um check ou limiar falhou) ou 2 (não conseguiu executar). No GitHub, a action ultraman-app/run-action@v1 instala e executa; em outros sistemas, instale só a CLI. Um runner não tem cofre: os segredos vêm de variáveis de ambiente ULTRAMAN_SECRET_<NAME>. Veja CI.

Carga #

Um teste de carga pode rodar em várias máquinas? #

Não. Uma carga roda num computador, numa thread por padrão e até 8 com --workers. Se você precisa de carga vinda de muitas máquinas ou da nuvem, escolha uma ferramenta feita para isso (veja Quando escolher outra coisa).

Quanta carga ele consegue gerar? #

Tanto quanto o seu computador conseguir enviar: depende da máquina, da rede e do peso de cada request. A faixa Este computador vigia a sua máquina durante a execução, e quando ela foi o gargalo o veredito diz limited em vez de culpar a API. Veja Mais de uma thread.
