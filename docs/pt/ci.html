CI #

O Ultraman roda num pipeline de build com as mesmas pipelines que você usa na sua máquina, escreve um relatório JUnit e faz o job falhar quando um passo ou um limiar falha. Para o GitHub Actions existe uma action que também impede os segredos de irem a qualquer lugar que ninguém aprovou. Para outros sistemas você instala o comando e o chama.

A GitHub Action #

ultraman-app/run-action@v1 instala só o comando ultraman no runner (Linux, macOS ou Windows), executa suas pipelines ou um teste de carga e escreve o relatório JUnit. Ela sai como ultraman run: 1 quando um passo ou limiar falha, 2 quando não conseguiu executar (um input errado, um valor faltando, um segredo que ninguém permitiu ir aonde uma pipeline o envia).

- uses: actions/checkout@v4
  with:
    persist-credentials: false
- uses: ultraman-app/run-action@v1
  env:
    ULTRAMAN_SECRET_API_KEY: ${{ secrets.API_KEY }}
  with:
    args: --tag smoke
    env: staging
    allow: api_key=https://staging.example.com

persist-credentials: false mantém o token do GitHub do job fora da pasta do projeto; a action se recusa a executar ao lado dele.

O relatório JUnit #

O relatório é escrito mesmo quando a execução falha. Envie-o para que as falhas apareçam no job:

- uses: ultraman-app/run-action@v1
  id: ultraman
  with:
    pipelines: create order
- uses: actions/upload-artifact@v4
  if: always()
  with:
    name: ultraman-junit
    path: ${{ steps.ultraman.outputs.junit }}
    retention-days: 7

Sem if: always() o envio é pulado exatamente quando você mais precisa dele.

Os inputs da action #

InputO que faz
pipelinesPipelines a executar, uma por linha. Deixe vazio e use args para --all, --tag X ou --collection ID.
argsMais flags para ultraman run: --parallel 4, --bail... São separadas por espaços, então um valor com espaço não pode ir aqui.
loadUm teste de carga para executar no lugar; os limiares dele decidem o código de saída.
envO ambiente (ultraman/envs/<env>.yaml).
local-envOs valores do ambiente que são só da máquina. Veja valores locais.
allowQual segredo pode ir para qual origem. Veja allow.
yestrue passa --yes. Padrão false. Veja yes.
working-directoryA pasta que contém ultraman/. Padrão .
junitO caminho do relatório dentro dela. Padrão ultraman-junit.xml.
versionA versão do Ultraman a instalar, ou latest (o padrão). Fixe uma para execuções repetíveis.

Saídas: junit (o caminho do relatório) e exit-code (0, 1 ou 2).

Cada segredo que uma pipeline usa como {{secrets.name}} vem de uma variável ULTRAMAN_SECRET_<NAME> (veja o terminal): mapeie os seus segredos do GitHub nelas no env: do passo, só os que as pipelines usam. O Ultraman escreve [secret:name] em tudo o que imprime e salva, e o GitHub também os mascara no log. A action sempre executa as pipelines no próprio processo, nunca por um Ultraman que já esteja aberto no runner.

Aonde um segredo pode ir: allow #

Na sua máquina o Ultraman pergunta antes de um segredo ir a uma origem pela primeira vez. Um runner não tem ninguém para perguntar, então o workflow diz de antemão: allow lista, um por linha, name=origin para cada segredo (um esquema, um host e uma porta se não for a padrão; sem path, sem barra no fim).

allow: |
  api_key=https://staging.example.com
  admin_token=https://admin.staging.example.com

Uma pipeline que enviaria um segredo a qualquer outro lugar é recusada antes de qualquer envio (saída 2). Assim, um pull request que muda uma pipeline ou um ambiente para apontar um segredo a outro host não consegue enviá-lo para lá. Isso protege os segredos do seu time de um arquivo alterado; não os protege de um arquivo de workflow alterado, que executa o que ele disser. O GitHub não dá segredos a workflows de forks em pull_request; nunca faça checkout do código de um pull request sob pull_request_target ou workflow_run com os seus segredos por perto.

yes: o jeito arriscado #

yes: true deixa todo segredo ir para onde as pipelines disserem, sem perguntar nada. Qualquer pessoa que possa mudar uma pipeline ou um ambiente na branch testada pode então enviar os seus segredos a um servidor dela. Use só em branches nas quais apenas o seu time consegue fazer push, nunca em pull requests de forks, e prefira allow. Se você quer a proteção do allow, também não ponha --yes em args.

Arquivos que uma request envia #

Só os arquivos sob ultraman/files/ saem sem um sim (o app desktop copia para lá os arquivos que você escolhe). Um body, parte multipart, certificado ou mensagem de stream lido de qualquer outro lugar do repositório precisa de um sim na primeira vez, e um runner não tem quem o dê: a execução para com saída 2 antes de enviar qualquer coisa. Mantenha em ultraman/files/ os arquivos que suas requests enviam. Veja Segurança e consentimento.

Testes de carga no CI #

- uses: ultraman-app/run-action@v1
  with:
    load: checkout-peak
    env: staging
    allow: api_key=https://staging.example.com

Os limiares do teste decidem o código de saída: ele passa quando todos se mantiveram e o veredito é aguenta, enfileira ou limitado. Veja Carga para o que significam. Dois pontos para uma máquina de build:

  • Carregue só uma API sua, e dimensione o teste para o runner: um runner compartilhado é um computador pequeno, e um veredito limitado diz que os números descrevem o runner, não o servidor.
  • --baseline last compara com o último relatório salvo em ultraman/loads/, e um runner novo não tem nenhum, então não imprime nada. Guarde o relatório com o qual quer comparar (como artefato ou num cache), restaure-o antes da execução e passe o caminho dele: --baseline previous/load.json. --output load.json escreve o relatório para guardar.

Valores que vivem na máquina de quem desenvolve #

Alguns valores de ambiente não estão no git: em cada máquina eles vivem em ultraman/local/envs/<env>.yaml. Num runner a action escreve esse arquivo a partir de local-env, um name: value por linha, e antes mascara cada valor no log. Os valores são simples: sem aspas, comentários, valores de várias linhas nem outro YAML; a action para diante de um.

with:
  env: staging
  local-env: |
    tenant: acme
    user: ${{ vars.TEST_USER }}

Uma credencial pertence a uma variável ULTRAMAN_SECRET_* em vez disso: essas ficam escondidas também nos relatórios, enquanto os valores de local-env ficam escondidos só no log.

Outros sistemas de CI #

Fora do GitHub Actions não existe allow: --yes é tudo ou nada. Execute só em branches que o seu time controla.

Tudo o que a action faz é o comando ultraman mais algumas regras. No GitLab, Jenkins, CircleCI ou no seu próprio runner:

  1. Instale só o comando. No Linux e no macOS: curl -fsSL https://ultraman-app.github.io/install.sh | sh -s -- --cli (acrescente --version 0.6.2 para fixar uma) e garanta que ~/.local/bin esteja no PATH. No Windows: $env:ULTRAMAN_CLI_ONLY = 1; irm https://ultraman-app.github.io/install.ps1 | iex. O instalador confere os checksums assinados da versão e traz o seu próprio Node.
  2. Dê a ele os segredos como variáveis mascaradas chamadas ULTRAMAN_SECRET_<NAME>.
  3. Execute. O código de saída barra o job:
ultraman run --all --env ci --yes --junit reports/ultraman.xml
  1. Escolha `--yes` sabendo o que faz. Um runner não tem terminal, então um segredo indo a uma origem, um arquivo de fora de ultraman/files/ ou uma pasta não confiável precisam todos de --yes. A linha de comando não tem equivalente do allow: --yes é tudo ou nada, com o mesmo risco do yes: true acima. Acrescente --local num runner compartilhado.
  2. Valores só da máquina (ultraman/local/envs/) não estão no git: forneça-os como variáveis do CI ou escreva o arquivo num script.
  3. O relatório. Aponte o seu sistema para o arquivo. Exemplos, que você deve conferir na documentação do seu sistema:
# GitLab CI (.gitlab-ci.yml)
ultraman:
  script:
    - curl -fsSL https://ultraman-app.github.io/install.sh | sh -s -- --cli
    - export PATH="$HOME/.local/bin:$PATH"
    - ultraman run --all --env ci --yes --junit reports/ultraman.xml
  artifacts:
    reports:
      junit: reports/ultraman.xml

No Jenkins o passo junit lê o arquivo (junit testResults: 'reports/ultraman.xml'), executado num bloco post { always { } } para que uma execução que falhou também seja reportada.

Os testes de carga funcionam do mesmo jeito: ultraman run --load checkout-peak --env staging --yes --junit load.xml --output load.json.
