CI #

O Ultraman funciona num pipeline de build com as mesmas pipelines que você usa na sua máquina, gera um relatório JUnit e faz o job falhar quando um passo ou um limiar falha. Para o GitHub Actions existe uma action que, além disso, impede que os segredos vão para onde ninguém aprovou. Nos outros sistemas, basta instalar o comando e chamá-lo.

A GitHub Action #

ultraman-app/run-action@v1 instala só o comando ultraman no runner (Linux, macOS ou Windows), executa suas pipelines ou um teste de carga e gera o relatório JUnit. Os códigos de saída são os do ultraman run: 1 quando um passo ou limiar falha, 2 quando não deu para executar (um input errado, um valor faltando, um segredo que ninguém autorizou a ir para onde uma pipeline o manda).

- uses: actions/checkout@v4
  with:
    persist-credentials: false
- uses: ultraman-app/run-action@v1
  env:
    ULTRAMAN_SECRET_API_KEY: ${{ secrets.API_KEY }}
  with:
    args: --tag smoke
    env: staging
    allow: api_key=https://staging.example.com

persist-credentials: false deixa o token do GitHub do job fora da pasta do projeto; a action se recusa a executar com ele ali.

O relatório JUnit #

O relatório é gerado mesmo quando a execução falha. Faça o upload dele para as falhas aparecerem no job:

- uses: ultraman-app/run-action@v1
  id: ultraman
  with:
    pipelines: create order
- uses: actions/upload-artifact@v4
  if: always()
  with:
    name: ultraman-junit
    path: ${{ steps.ultraman.outputs.junit }}
    retention-days: 7

Sem if: always(), o upload é pulado justamente quando você mais precisa dele.

Os inputs da action #

InputO que faz
pipelinesAs pipelines a executar, uma por linha. Deixe vazio e use args para --all, --tag X ou --collection ID.
argsFlags extras para o ultraman run: --parallel 4, --bail... Elas são separadas nos espaços, então um valor com espaço não cabe aqui.
loadUm teste de carga para executar no lugar das pipelines; os limiares dele decidem o código de saída.
envO ambiente (ultraman/envs/<env>.yaml).
local-envOs valores do ambiente que só existem na máquina. Veja valores locais.
allowQual segredo pode ir para qual origem. Veja allow.
yestrue passa --yes. O padrão é false. Veja yes.
working-directoryA pasta que contém ultraman/. O padrão é .
junitO caminho do relatório dentro dela. O padrão é ultraman-junit.xml.
versionA versão do Ultraman a instalar, ou latest (o padrão). Fixe uma para ter execuções reproduzíveis.

Saídas: junit (o caminho do relatório) e exit-code (0, 1 ou 2).

Cada segredo que uma pipeline usa como {{secrets.name}} vem de uma variável ULTRAMAN_SECRET_<NAME> (veja o terminal): mapeie os seus segredos do GitHub para elas no env: do passo, só os que as pipelines usam. O Ultraman escreve [secret:name] em tudo o que imprime e salva, e o GitHub também os mascara no log. A action sempre executa as pipelines no próprio processo, nunca através de um Ultraman que já esteja aberto no runner.

Para onde um segredo pode ir: allow #

Na sua máquina, o Ultraman pergunta antes de um segredo ir para uma origem pela primeira vez. No runner não há a quem perguntar, então o workflow diz isso de antemão: allow lista, um por linha, name=origin para cada segredo (esquema, host e a porta, se não for a padrão; sem path e sem barra no final).

allow: |
  api_key=https://staging.example.com
  admin_token=https://admin.staging.example.com

Uma pipeline que mandaria um segredo para qualquer outro lugar é recusada antes de qualquer envio (saída 2). Assim, um pull request que altera uma pipeline ou um ambiente para apontar um segredo para outro host não consegue enviá-lo para lá. Isso protege os segredos da sua equipe contra um arquivo alterado; não os protege contra um arquivo de workflow alterado, que executa o que estiver escrito nele. O GitHub não entrega segredos a workflows de forks em pull_request; nunca faça checkout do código de um pull request em pull_request_target ou workflow_run com os seus segredos por perto.

yes: o caminho arriscado #

yes: true deixa todo segredo ir para onde as pipelines mandarem, sem perguntar nada. Aí qualquer pessoa que consiga alterar uma pipeline ou um ambiente na branch testada pode mandar os seus segredos para um servidor dela. Use só em branches em que apenas a sua equipe pode fazer push, nunca em pull requests de forks, e prefira allow. Se você quer a proteção do allow, também não coloque --yes em args.

Arquivos que uma request envia #

Só os arquivos dentro de ultraman/files/ saem sem um sim (o app desktop copia para lá os arquivos que você escolhe). Um body, uma parte multipart, um certificado ou uma mensagem de stream lido de qualquer outro lugar do repositório precisa de um sim na primeira vez, e no runner não há quem o dê: a execução para com saída 2 antes de enviar qualquer coisa. Deixe em ultraman/files/ os arquivos que suas requests enviam. Veja Segurança e consentimento.

Testes de carga no CI #

- uses: ultraman-app/run-action@v1
  with:
    load: checkout-peak
    env: staging
    allow: api_key=https://staging.example.com

Os limiares do teste decidem o código de saída: ele passa quando todos se mantiveram e o veredito é aguenta, enfileira ou limitado. O que cada um significa está em Carga. Dois cuidados numa máquina de build:

  • Faça carga só contra uma API sua, e dimensione o teste para o runner: um runner compartilhado é um computador pequeno, e um veredito limitado diz que os números descrevem o runner, não o servidor.
  • --baseline last compara com o último relatório salvo em ultraman/loads/, e um runner novo não tem nenhum, então não aparece nada. Guarde o relatório que você quer usar na comparação (como artifact ou num cache), restaure-o antes da execução e passe o caminho dele: --baseline previous/load.json. --output load.json grava o relatório para guardar.

Valores que ficam na máquina de quem desenvolve #

Alguns valores de ambiente não vão para o git: em cada máquina, eles ficam em ultraman/local/envs/<env>.yaml. No runner, a action cria esse arquivo a partir de local-env, um name: value por linha, e antes mascara cada valor no log. Os valores são simples: nada de aspas, comentários, valores de várias linhas ou outros recursos de YAML; se aparecer um, a action para.

with:
  env: staging
  local-env: |
    tenant: acme
    user: ${{ vars.TEST_USER }}

Uma credencial deve ir numa variável ULTRAMAN_SECRET_*: essas ficam ocultas também nos relatórios, enquanto os valores de local-env ficam ocultos só no log.

Outros sistemas de CI #

Fora do GitHub Actions não existe allow: --yes é tudo ou nada. Use só em branches que a sua equipe controla.

Tudo o que a action faz se resume ao comando ultraman mais algumas regras. No GitLab, Jenkins, CircleCI ou no seu próprio runner:

  1. Instale só o comando. No Linux e no macOS: curl -fsSL https://ultraman-app.github.io/install.sh | sh -s -- --cli (acrescente --version 0.6.2 para fixar uma versão) e confira se ~/.local/bin está no PATH. No Windows: $env:ULTRAMAN_CLI_ONLY = 1; irm https://ultraman-app.github.io/install.ps1 | iex. O instalador confere os checksums assinados da versão e traz o próprio Node.
  2. Passe os segredos como variáveis mascaradas chamadas ULTRAMAN_SECRET_<NAME>.
  3. Execute. O código de saída decide se o job passa:
ultraman run --all --env ci --yes --junit reports/ultraman.xml
  1. Use `--yes` sabendo o que está fazendo. O runner não tem terminal, então um segredo indo para uma origem, um arquivo de fora de ultraman/files/ ou uma pasta não confiável, tudo isso precisa de --yes. A linha de comando não tem nada equivalente ao allow: --yes é tudo ou nada, com o mesmo risco do yes: true descrito acima. Num runner compartilhado, acrescente --local.
  2. Valores só da máquina (ultraman/local/envs/) não estão no git: passe-os como variáveis do CI ou crie o arquivo num script.
  3. O relatório. Aponte o seu sistema para o arquivo. Seguem exemplos, que você deve conferir na documentação do seu sistema:
# GitLab CI (.gitlab-ci.yml)
ultraman:
  script:
    - curl -fsSL https://ultraman-app.github.io/install.sh | sh -s -- --cli
    - export PATH="$HOME/.local/bin:$PATH"
    - ultraman run --all --env ci --yes --junit reports/ultraman.xml
  artifacts:
    reports:
      junit: reports/ultraman.xml

No Jenkins, quem lê o arquivo é o passo junit (junit testResults: 'reports/ultraman.xml'), dentro de um bloco post { always { } }, para que uma execução que falhou também apareça no relatório.

Os testes de carga funcionam do mesmo jeito: ultraman run --load checkout-peak --env staging --yes --junit load.xml --output load.json.
