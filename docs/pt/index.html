Documentação do Ultraman

Como o Ultraman funciona, o que cada recurso oferece e o que protege você e sua equipe.

  1. O que o Ultraman te dá

    O Ultraman testa APIs HTTP, incluindo WebSocket e SSE: um só app no seu computador para requests avulsas, testes de vários passos, carga e CI, tudo salvo como arquivos simples no seu próprio repositório git. O Ultraman nunca envia nada de forma insegura sem o seu consentimento explícito: um segredo vai só para um host que você aprovou, e uma pasta em que você ainda não confia não envia nada.

  2. Por que o Ultraman

    O Ultraman reúne requests de API, fluxos de teste, testes de carga e checks de CI num só app local, salvos como arquivos simples no seu próprio repositório git. Esta página diz como isso difere das ferramentas que você talvez já use, e quando uma delas é a melhor escolha.

  3. Primeiros passos

    Da instalação do Ultraman até a sua primeira request e a sua primeira pipeline, mais como ele se atualiza, por que o seu sistema pode avisar sobre ele e como removê-lo.

  4. Segurança e consentimento

    O que o Ultraman pergunta antes de enviar qualquer coisa, como ele mantém seus segredos fora de vista e o que deixa por sua conta: as promessas que você pode conferir, para você, sua equipe e seu CI. Não há telemetria, nem analytics, nem relatório de falhas, nem conta.

  5. Requests

    A área de Requests é onde você monta, envia e checa requests avulsas: coleções com pastas e requests, abertas em abas, como no Postman. A diferença é que cada request carrega seus checks, e tudo é um arquivo simples em ultraman/requests/ que a sua equipe compartilha pelo git.

  6. Pipelines

    Uma pipeline é um fluxo de requests e checks que você lê de cima para baixo, salvo em ultraman/pipelines/<nome>.yaml e executado pela janela ou pelo terminal. Ela tem um host, auth e headers opcionais para todas as suas requests, inputs (valores que a execução pede) e passos. Nada nela fica escondido: o que um passo faz é o que a linha dele diz.

  7. Carga

    Carga (ao lado de Executar) diz quantos usuários, ou quanto tráfego, sua API aguenta antes de ficar lenta ou falhar. Ela abre a tela de carga da pipeline que está na tela: cada usuário virtual roda a pipeline inteira em loop, e se um passo falha, aquela volta conta como erro e o usuário começa outra.

  8. Ambientes e segredos

    Os ambientes deixam as mesmas requests rodarem contra local, staging ou produção, e os segredos mantêm tokens e senhas no seu computador, criptografados, fora do git e de todo log.

  9. Importar

    Os botões ao lado de Nova coleção (área de Requests) trazem o que você já tem: uma exportação do Postman, uma especificação OpenAPI, um plano do JMeter, um script do Artillery ou uma gravação do navegador, para você não começar do zero. Nada no projeto é sobrescrito: um nome já usado ganha -2. No fim, um resumo diz o que entrou, o que foi adaptado, o que precisa de uma mão e quais arquivos foram pulados.

  10. Servidor mock

    O servidor mock responde às requests da sua API com respostas que você já gravou, para um front end (ou um teste) poder trabalhar enquanto a API real está fora do ar, lenta ou ainda não existe. Ele roda no seu computador e ninguém mais consegue alcançá-lo, a menos que você escolha.

  11. O terminal

    O comando ultraman executa suas pipelines e testes de carga num terminal, serve o projeto a outras ferramentas e guarda segredos no cofre. Execute-o na pasta do projeto (ou em qualquer pasta dentro dele). Para usá-lo numa máquina de build, veja CI.

  12. CI

    O Ultraman roda num pipeline de build com as mesmas pipelines que você usa na sua máquina, escreve um relatório JUnit e faz o job falhar quando um passo ou um limiar falha. Para o GitHub Actions existe uma action que também impede os segredos de irem a qualquer lugar que ninguém aprovou. Para outros sistemas você instala o comando e o chama.

  13. Trabalhando em time

    Tudo o que um time compartilha é um arquivo sob ultraman/, então seus testes viajam com o seu código e uma mudança num teste aparece num pull request como qualquer outra mudança.

  14. Agentes (MCP)

    Um agente de IA (Claude Code, ou qualquer outro cliente MCP) pode usar o Ultraman por meio de ultraman mcp. Ele pode fazer o que você faz na janela: ler e escrever requests, pipelines e testes de carga, enviá-los e executá-los, importar, iniciar o servidor mock, ler relatórios e compará-los. Você aprova cada chamada.

  15. Se você vem de outra ferramenta

    Algumas ideias têm o mesmo nome aqui, outras têm outro, e umas poucas não existem de propósito.

  16. Perguntas

    Respostas curtas ao que os times perguntam antes de adotar o Ultraman, os "nãos" honestos incluídos. Cada resposta leva à página que aprofunda.

  17. Format reference (YAML)

    Everything lives as YAML under ultraman/ in the user's project. Unknown keys are errors: write only what's listed. Variables: {{env.x}} (the environment), {{secrets.x}} (a secret: usable, never visible), {{x}} (an input, an extract or a collection variable).
