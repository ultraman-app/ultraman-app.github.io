Documentação do Ultraman

Como o Ultraman funciona, o que cada recurso oferece e o que protege você e sua equipe.

  1. O que o Ultraman oferece

    O Ultraman testa APIs HTTP, inclusive WebSocket e SSE: um único app no seu computador para requests avulsas, testes de vários passos, carga e CI, tudo salvo em arquivos simples no seu próprio repositório git. Ele nunca envia nada de forma insegura sem o seu consentimento explícito: um segredo só vai para um host que você aprovou, e uma pasta em que você ainda não confia não envia nada.

  2. Por que o Ultraman

    O Ultraman junta requests de API, fluxos de teste, testes de carga e checks de CI num só app local, salvos em arquivos simples no seu próprio repositório git. Esta página mostra em que ele difere das ferramentas que você talvez já use, e quando uma delas é a melhor escolha.

  3. Primeiros passos

    Da instalação do Ultraman até a sua primeira request e a sua primeira pipeline, além de como ele se atualiza, por que o seu sistema pode emitir um aviso sobre ele e como removê-lo.

  4. Segurança e consentimento

    O que o Ultraman pergunta antes de enviar qualquer coisa, como ele mantém os seus segredos longe dos olhos e o que fica por sua conta: promessas que você pode conferir, para você, a sua equipe e o seu CI. Não há telemetria, analytics, relatório de falhas nem conta.

  5. Requests

    Na área de Requests você monta, envia e confere requests avulsas: coleções com pastas e requests, abertas em abas, como no Postman. A diferença é que cada request leva os seus checks, e tudo é um arquivo simples em ultraman/requests/ que a sua equipe compartilha pelo git.

  6. Pipelines

    Uma pipeline é um fluxo de requests e checks que você lê de cima para baixo, salvo em ultraman/pipelines/<nome>.yaml e executado pela janela ou pelo terminal. Ela tem um host, auth e headers opcionais para todas as requests, inputs (valores que a execução pede) e passos. Nada fica escondido: o que um passo faz é o que a linha dele diz.

  7. Carga

    Carga (ao lado de Executar) mostra quantos usuários, ou quanto tráfego, a sua API aguenta antes de ficar lenta ou começar a falhar. Abre a tela de carga da pipeline que você está vendo: cada usuário virtual executa a pipeline inteira em loop e, se um passo falha, aquela iteração conta como erro e o usuário começa outra.

  8. Ambientes e segredos

    Com os ambientes, as mesmas requests executam contra local, staging ou produção; os segredos guardam tokens e senhas no seu computador, criptografados, fora do git e de qualquer log.

  9. Importar

    O menu Importar ao lado de Nova coleção (área de Requests) traz o que você já tem: uma exportação do Postman, uma spec OpenAPI, um plano do JMeter ou um script do Artillery; o que fica ao lado de Nova pipeline (área de Pipelines) traz uma gravação do navegador. Assim você não começa do zero. Nada no projeto é sobrescrito: um nome já usado ganha -2. No fim, um resumo mostra o que entrou, o que foi adaptado, o que precisa de ajuste manual e quais arquivos foram pulados.

  10. Servidor mock

    O servidor mock responde às requests da sua API com respostas que você já gravou. Assim, um front end (ou um teste) continua funcionando enquanto a API real está fora do ar, lenta ou ainda nem existe. Ele funciona no seu computador, e ninguém mais tem acesso a ele, a não ser que você queira.

  11. O terminal

    O comando ultraman executa suas pipelines e testes de carga pelo terminal, serve o projeto para outras ferramentas e guarda segredos no cofre. Execute-o na pasta do projeto (ou em qualquer pasta dentro dela). Para usá-lo numa máquina de build, veja CI.

  12. CI

    O Ultraman funciona num pipeline de build com as mesmas pipelines que você usa na sua máquina, gera um relatório JUnit e faz o job falhar quando um passo ou um limiar falha. Para o GitHub Actions existe uma action que, além disso, impede que os segredos vão para onde ninguém aprovou. Nos outros sistemas, basta instalar o comando e chamá-lo.

  13. Trabalho em equipe

    Tudo o que uma equipe compartilha é um arquivo dentro de ultraman/. Assim, os testes andam junto com o código, e uma mudança num teste aparece num pull request como qualquer outra.

  14. Agentes (MCP)

    Um agente de IA (o Claude Code ou qualquer outro cliente MCP) pode usar o Ultraman através de ultraman mcp. Ele faz o mesmo que você faz na janela: lê e escreve requests, pipelines e testes de carga, envia e executa, importa, inicia o servidor mock, lê relatórios e compara. Cada chamada passa pela sua aprovação.

  15. Vindo de outra ferramenta

    Algumas ideias têm o mesmo nome aqui, outras têm outro nome, e umas poucas não existem de propósito.

  16. Perguntas

    Respostas curtas para o que as equipes perguntam antes de adotar o Ultraman, inclusive os "nãos" sinceros. Cada resposta leva à página que entra em mais detalhes.

  17. Format reference (YAML)

    Everything lives as YAML under ultraman/ in the user's project. Unknown keys are errors: write only what's listed. Variables: {{env.x}} (the environment), {{secrets.x}} (a secret: usable, never visible), {{x}} (an input, an extract or a collection variable).
