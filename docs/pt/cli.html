O terminal #

O comando ultraman executa suas pipelines e testes de carga num terminal, serve o projeto a outras ferramentas e guarda segredos no cofre. Execute-o na pasta do projeto (ou em qualquer pasta dentro dele). Para usá-lo numa máquina de build, veja CI.

Os comandos #

ComandoO que faz
ultraman run <pipeline>Executa uma pipeline, encontrada pelo nome e depois pelo id.
ultraman run --all, --tag X, --collection IDExecuta várias pipelines de uma vez.
ultraman run --load <test>Toca um teste de carga; ultraman run <pipeline> --load usa o teste padrão dessa pipeline.
ultraman serve [--port 4100]Inicia o servidor local do projeto (a janela e os outros comandos falam com ele).
ultraman secret set <name>, list, rm <name>, passwordGerencia o cofre.
ultraman mock [--port 4300]Serve o seu histórico gravado como uma API mock. Veja Servidor mock.
ultraman mcp [--project <folder>]A ponte à qual um agente de IA se conecta. Veja Agentes.
ultraman --versionMostra a versão.

Um comando sem argumentos, ou um desconhecido, mostra o uso e sai com 2.

Executar pipelines #

ultraman run "create order" --env local --input user=ana
ultraman run --all --env ci --yes
ultraman run --tag smoke --env ci --parallel 4
ultraman run --collection shop --env staging

Dê exatamente um destes: uma pipeline, --all, --tag ou --collection; qualquer outra coisa é saída 2. Tudo é verificado para todas as pipelines selecionadas antes de a primeira request sair.

FlagO que faz
--allTodas as pipelines do projeto.
--tag XAs pipelines com essa tag. Repita e uma pipeline precisa ter todas as tags dadas.
--collection IDExecuta uma coleção; shop/orders executa só essa pasta.
--env XO ambiente. Com um único ambiente no projeto ele é usado sozinho; com vários você precisa passar --env.
--input k=vUm valor para um input; repita para mais. Um valor que começa com [ ou { é lido como JSON quando é válido; qualquer outro fica como texto (id=00123 continua 00123). Os nomes env.* e secrets.* são reservados.
--parallel NExecuta até N pipelines ao mesmo tempo (1 a 16). Cada uma imprime inteira quando termina.
--bailPara de iniciar novas pipelines depois da primeira que falhar. As que estão rodando terminam; as demais aparecem como puladas.
--watchExecuta de novo sempre que um arquivo sob ultraman/ muda.
--every DExecuta de novo num temporizador: 30s, 5m, 1h ou um número puro de segundos, no mínimo 5 segundos. Conta a partir do fim da execução anterior e combina com --watch.
--no-notifyCom --watch ou --every, sem notificação na área de trabalho quando uma execução falha e quando volta a passar.
--jsonUm evento JSON por linha na saída padrão, para outras ferramentas. Sem cores.
--junit FILEEscreve um relatório JUnit XML. Veja JUnit.
--localExecuta neste processo mesmo quando a janela tem o projeto aberto. Veja Um só motor.
--yesResponde sim a toda pergunta. Leia antes Consentimento no terminal.

Cada execução é salva em ultraman/runs/. As cores aparecem só num terminal; NO_COLOR as desliga. Ctrl+C cancela o passo em andamento, salva a execução e sai com 1.

Códigos de saída: 0 tudo passou, 1 um passo falhou (ou você apertou Ctrl+C), 2 nem chegou a executar: uma flag errada, uma pipeline, input, ambiente ou segredo faltando, uma pipeline inválida, ou nada foi enviado porque ninguém disse sim.

Consentimento no terminal #

O Ultraman pergunta antes de enviar qualquer coisa que você não aprovou. Num terminal ele pergunta quando:

  • a pasta ainda não é confiável;
  • um segredo iria para uma origem para a qual nunca foi;
  • um arquivo de fora de ultraman/files/ seria enviado.

A pergunta lista o que iria para onde, e você responde y (desta vez), a (sempre, para este projeto) ou N (o padrão: nada é enviado). O "sempre" fica em ~/.ultraman/trust.json na sua máquina, nunca no projeto, então o checkout de um colega não pode carregá-lo. O modelo inteiro está na página Segurança e consentimento.

Sem terminal e sem --yes não há ninguém para perguntar: o Ultraman lista o que enviaria e sai com 2, sem ter enviado nada.

`--yes` pula todas as perguntas. Tudo o que as pipelines e os ambientes dizem vai então para onde eles dizem, inclusive os seus segredos, e um valor tirado de uma resposta que carrega um segredo vai junto. Use onde só o seu time pode mudar esses arquivos; nunca em código de forks ou de pessoas que você não conhece. O CI explica o caminho mais seguro para o GitHub Actions.

Executar um teste de carga #

ultraman run --load checkout-peak --env staging --junit load.xml --html report.html --baseline last

O teste é ultraman/load-tests/<nome>.yaml, dado por nome ou id. Além de --env, --input, --junit, --json, --local e --yes (que funcionam como acima), uma carga aceita:

FlagO que faz
--target URLEnvia tudo a outra origem nesta execução (https://staging.example.com, com um path base opcional, sem usuário, senha, ? nem #).
--overrides JSONTroca chaves de nível superior do teste nesta execução, escritas como no YAML.
--workers NToca a carga com N threads (1 a 8). O padrão é uma, ou ULTRAMAN_LOAD_WORKERS.
--output FILEEscreve o relatório final como JSON.
--html FILEEscreve o relatório como uma página autocontida.
--csv DIREscreve as séries e os passos como arquivos CSV nessa pasta.
--baseline last ou um arquivoMostra como esta execução se compara com um relatório anterior: o último salvo para este teste, ou um arquivo JSON.

--all, --tag, --collection, --bail, --parallel, --watch e --every não se aplicam a uma carga.

Códigos de saída: 0 todos os limiares se mantiveram e o veredito é aguenta, enfileira ou limitado; 1 um limiar falhou, a API rejeitou ou quebrou, saíram poucas requests, ou foi interrompido (Ctrl+C ou os próprios freios do gerador); 2 nada foi enviado. Os limiares e vereditos estão explicados em Carga; para barreiras numa pipeline veja CI.

JUnit para o CI #

--junit FILE escreve um relatório JUnit XML depois das execuções, também depois de um Ctrl+C com o que rodou: uma suíte de testes por pipeline e um caso de teste por passo de nível superior, com o que foi enviado e recebido nos que falharam. Os segredos ficam escondidos nele como em todo lugar. As pastas que não existem são criadas.

ultraman run --all --env ci --yes --junit reports/ultraman.xml

Segredos #

Na sua máquina, ultraman secret set api-key salva um no cofre: pede a senha mestra e o valor, ambos sem eco. Um valor passado por pipe (echo "$VALUE" | ultraman secret set api-key) é lido da entrada padrão; a senha mestra ainda precisa de um terminal. Os nomes usam letras, dígitos, _, . e -. secret list mostra os nomes, secret rm <name> remove um (saída 1 se ele não existe) e secret password troca a senha mestra. Veja o cofre.

Numa máquina de build não há cofre. Passe um segredo como variável de ambiente chamada ULTRAMAN_SECRET_ mais o nome dele em maiúsculas, com todo caractere que não seja letra nem dígito virando _: api-key é ULTRAMAN_SECRET_API_KEY. Ela vence o cofre e não precisa de senha. Sem --yes, um segredo continua indo só para onde foi aprovado.

Variáveis de ambiente #

VariávelO que faz
ULTRAMAN_SECRET_<NAME>O valor de um segredo para este comando.
ULTRAMAN_HOMESubstitui ~/.ultraman, onde ficam o cofre, a lista de confiança e as chaves do servidor.
ULTRAMAN_LOAD_WORKERSO número padrão de threads de uma carga (--workers vence).
ULTRAMAN_NO_UPDATE_CHECK1 desliga a verificação diária de uma versão mais nova.
ULTRAMAN_PROJECTA pasta do projeto com a qual a janela do desktop abre.
NO_COLORSem cores na saída.
ULTRAMAN_VERSION, ULTRAMAN_CLI_ONLYPara os instaladores: a versão a instalar, e só o comando, sem a janela. Veja Instalar.

A janela e o terminal juntos #

Se a janela está aberta no projeto, ultraman run entrega a execução a ela: você a vê ao vivo na janela, e o terminal imprime o mesmo de sempre. --local executa no terminal, que é o que você quer numa máquina de build compartilhada. As execuções de CI sempre usam isso.
