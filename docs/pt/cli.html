O terminal #

O comando ultraman executa suas pipelines e testes de carga pelo terminal, serve o projeto para outras ferramentas e guarda segredos no cofre. Execute-o na pasta do projeto (ou em qualquer pasta dentro dela). Para usá-lo numa máquina de build, veja CI.

Os comandos #

ComandoO que faz
ultraman run <pipeline>Executa uma pipeline, procurada primeiro pelo nome e depois pelo id.
ultraman run --all, --tag X, --collection IDExecuta várias pipelines de uma vez.
ultraman run --load <test>Executa um teste de carga; ultraman run <pipeline> --load usa o teste padrão dessa pipeline.
ultraman serve [--port 4100]Inicia o servidor local do projeto (é com ele que a janela e os outros comandos conversam).
ultraman secret set <name>, list, rm <name>, passwordGerencia o cofre.
ultraman mock [--port 4300]Serve o histórico gravado como uma API mock. Veja Servidor mock.
ultraman mcp [--project <folder>]A ponte em que um agente de IA se conecta. Veja Agentes.
ultraman sampleDeixa o projeto de exemplo como novo na pasta do próprio Ultraman e mostra o caminho dele. Veja o projeto de exemplo.
ultraman --versionMostra a versão.

Um comando sem argumentos, ou desconhecido, mostra como usar e sai com 2.

Executar pipelines #

ultraman run "create order" --env local --input user=ana
ultraman run --all --env ci --yes
ultraman run --tag smoke --env ci --parallel 4
ultraman run --collection shop --env staging

Informe exatamente um destes: uma pipeline, --all, --tag ou --collection; qualquer outra combinação sai com 2. Tudo é verificado em todas as pipelines selecionadas antes de a primeira request sair.

FlagO que faz
--allTodas as pipelines do projeto.
--tag XAs pipelines com essa tag. Se repetir, a pipeline precisa ter todas as tags informadas.
--collection IDExecuta uma coleção; shop/orders executa só essa pasta.
--env XO ambiente. Se o projeto tem um só, ele é usado automaticamente; se tem vários, é preciso passar --env.
--input k=vO valor de um input; repita para passar mais. Um valor que começa com [ ou { é lido como JSON quando é válido; o resto fica como texto (id=00123 continua 00123). Os nomes env.* e secrets.* são reservados.
--parallel NExecuta até N pipelines ao mesmo tempo (de 1 a 16). Cada uma é impressa inteira quando termina.
--bailPara de iniciar pipelines novas depois da primeira que falhar. As que já estão em execução terminam; as outras aparecem como puladas.
--watchExecuta de novo sempre que um arquivo dentro de ultraman/ muda.
--every DExecuta de novo de tempos em tempos: 30s, 5m, 1h ou só um número de segundos, no mínimo 5 segundos. Conta a partir do fim da execução anterior e dá para combinar com --watch.
--no-notifyCom --watch ou --every, desliga a notificação na área de trabalho quando uma execução falha e quando volta a passar.
--jsonUm evento JSON por linha na saída padrão, para outras ferramentas. Sem cores.
--junit FILEGera um relatório JUnit XML. Veja JUnit.
--contract Mstrict, warn ou off: substitui o modo do contrato de cada coleção, para o CI falhar com o que a spec não documenta. Veja o contrato.
--localExecuta neste processo mesmo com o projeto aberto na janela. Veja Um só motor.
--yesResponde sim a todas as perguntas. Leia antes Consentimento no terminal.

Cada execução fica salva em ultraman/runs/. As cores só aparecem num terminal; NO_COLOR desliga as cores. Ctrl+C cancela o passo em andamento, salva a execução e sai com 1.

Códigos de saída: 0 tudo passou; 1 um passo falhou (ou você apertou Ctrl+C); 2 nem chegou a executar: uma flag errada, falta de pipeline, input, ambiente ou segredo, uma pipeline inválida, ou nada foi enviado porque ninguém disse sim.

Consentimento no terminal #

O Ultraman pergunta antes de enviar qualquer coisa que você ainda não aprovou. No terminal, ele pergunta quando:

  • a pasta ainda não é confiável;
  • um segredo iria para uma origem para onde nunca foi;
  • um arquivo de fora de ultraman/files/ seria enviado.

A pergunta mostra o que iria para onde, e você responde y (desta vez), a (sempre, neste projeto) ou N (o padrão: nada é enviado). O "sempre" fica guardado em ~/.ultraman/trust.json, na sua máquina, nunca no projeto; assim, o checkout de um colega não tem como trazê-lo junto. O modelo completo está na página Segurança e consentimento.

Sem terminal e sem --yes, não há a quem perguntar: o Ultraman lista o que enviaria e sai com 2, sem ter enviado nada.

`--yes` pula todas as perguntas. Aí tudo o que as pipelines e os ambientes mandarem vai para onde eles disserem, inclusive os seus segredos, e um valor tirado de uma resposta que carrega um segredo vai junto. Use só onde apenas a sua equipe pode alterar esses arquivos; nunca em código de forks ou de pessoas que você não conhece. Em CI está o caminho mais seguro para o GitHub Actions.

Executar um teste de carga #

ultraman run --load checkout-peak --env staging --junit load.xml --html report.html --baseline last

O teste é ultraman/load-tests/<nome>.yaml, informado pelo nome ou pelo id. Além de --env, --input, --junit, --json, --local e --yes (que funcionam como descrito acima), uma carga aceita:

FlagO que faz
--target URLManda tudo para outra origem nesta execução (https://staging.example.com, com um path base opcional, sem usuário, senha, ? nem #).
--overrides JSONSubstitui chaves de primeiro nível do teste nesta execução, escritas como no YAML.
--workers NExecuta a carga com N threads (de 1 a 8). O padrão é uma, ou o valor de ULTRAMAN_LOAD_WORKERS.
--output FILEGrava o relatório final em JSON.
--html FILEGrava o relatório como uma única página autocontida.
--csv DIRGrava as séries e os passos como arquivos CSV nessa pasta.
--baseline last ou um arquivoMostra como esta execução se compara com um relatório anterior: o último salvo para este teste, ou um arquivo JSON.

--all, --tag, --collection, --bail, --parallel, --watch e --every não valem para uma carga.

Códigos de saída: 0 todos os limiares se mantiveram e o veredito é aguenta, enfileira ou limitado; 1 um limiar falhou, a API rejeitou ou quebrou, saíram poucas requests, ou a carga foi interrompida (por Ctrl+C ou pelos freios do próprio gerador); 2 nada foi enviado. Os limiares e os vereditos estão explicados em Carga; para usar a carga como barreira numa pipeline de build, veja CI.

JUnit para o CI #

--junit FILE gera um relatório JUnit XML depois das execuções, inclusive depois de um Ctrl+C, com o que chegou a executar: uma suíte de testes por pipeline e um caso de teste por passo de primeiro nível, com o que foi enviado e recebido nos que falharam. Os segredos ficam ocultos nele, como em todo lugar. As pastas que faltam são criadas.

ultraman run --all --env ci --yes --junit reports/ultraman.xml

Segredos #

Na sua máquina, ultraman secret set api-key guarda um segredo no cofre: ele pede a senha mestra e o valor, os dois sem eco. Um valor passado por pipe (echo "$VALUE" | ultraman secret set api-key) é lido da entrada padrão; a senha mestra continua precisando de um terminal. Os nomes aceitam letras, dígitos, _, . e -. secret list mostra os nomes, secret rm <name> remove um (sai com 1 se ele não existir) e secret password troca a senha mestra. Veja o cofre.

Numa máquina de build não existe cofre. Passe o segredo numa variável de ambiente chamada ULTRAMAN_SECRET_ seguido do nome em maiúsculas, trocando por _ todo caractere que não for letra nem dígito: api-key vira ULTRAMAN_SECRET_API_KEY. Essa variável tem prioridade sobre o cofre e não pede senha. Sem --yes, o segredo continua indo só para onde foi aprovado.

Variáveis de ambiente #

VariávelO que faz
ULTRAMAN_SECRET_<NAME>O valor de um segredo para este comando.
ULTRAMAN_HOMESubstitui ~/.ultraman, onde ficam o cofre, a lista de confiança e as chaves do servidor.
ULTRAMAN_LOAD_WORKERSO número padrão de threads de uma carga (--workers tem prioridade).
ULTRAMAN_NO_UPDATE_CHECK1 desliga a verificação diária de versão nova.
ULTRAMAN_PROJECTA pasta do projeto que a janela do desktop abre ao iniciar.
NO_COLORSaída sem cores.
ULTRAMAN_VERSION, ULTRAMAN_CLI_ONLYPara os instaladores: a versão a instalar e, no segundo, só o comando, sem a janela. Veja Instalar.

A janela e o terminal juntos #

Se a janela está aberta no projeto, o ultraman run passa a execução para ela: você acompanha ao vivo na janela, e o terminal imprime o mesmo de sempre. Com --local, a execução acontece no próprio terminal, que é o que você quer numa máquina de build compartilhada. As execuções de CI usam sempre essa opção.
