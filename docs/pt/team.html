Trabalho em equipe #

Tudo o que uma equipe compartilha é um arquivo dentro de ultraman/. Assim, os testes andam junto com o código, e uma mudança num teste aparece num pull request como qualquer outra.

Sincronizar #

Se o projeto está num repositório git com um remoto, a barra superior mostra quantos arquivos faltam sincronizar ("2 alterações não sincronizadas") e oferece Sincronizar. Salvar (Ctrl+S) só grava no seu disco; nada chega ao remoto até você sincronizar.

A sincronização mexe em seis pastas, e só nelas: ultraman/pipelines/, ultraman/blocks/, ultraman/envs/, ultraman/requests/ (as coleções), ultraman/load-tests/ e ultraman/files/ (os arquivos que as requests enviam). Ela faz o commit dessas pastas (o painel lista os arquivos e uma mensagem que você pode editar), busca as mudanças do remoto, faz o merge, dá push e recarrega. O resto do repositório, as outras mudanças que você não commitou e o que está em stage continuam intactos. Ela usa o git do seu sistema e as suas próprias credenciais; o app nunca pede senha.

Conflitos #

Se uma pipeline mudou no seu disco e também no remoto, um diálogo mostra as duas versões lado a lado, como passos ou como YAML. Escolha Ficar com a minha, Usar a do remoto ou Ficar com as duas (a sua é salva ao lado como <nome>-mine, igual para pipelines, requests, ambientes, testes de carga e arquivos copiados; nunca grava por cima de outro arquivo). Esc cancela sem mudar nada. O que você escolher, a versão que ficou de fora continua no histórico do arquivo.

Quando a sincronização falha #

A sincronização mostra o motivo e o que o git respondeu. Os casos mais comuns:

MensagemO que fazer
The branch … has no remote configuredFaça o push dela uma vez: git push -u origin <branch>
You have unpushed commits that touch files outside ultraman/Os commits são seus e o Ultraman não dá push neles: execute git push e sincronize de novo
The remote rejected the pushA branch é protegida ou falta permissão. Suas mudanças continuam commitadas localmente: mande-as por uma branch e um pull request
Couldn't fetch the remote'sProblema de rede ou de credenciais: tente git fetch no terminal
Git doesn't know who you aregit config --global user.name "Seu nome" e git config --global user.email voce@email
There's an unfinished merge or rebaseTermine ou aborte o merge ou rebase no terminal

Mudou no disco #

Se você executa git pull num terminal, ou altera um YAML em outro editor, a janela percebe sozinha: ela confere os arquivos abertos ao ganhar o foco, ao trocar de aba, antes de cada salvamento e a cada 5 segundos. Um arquivo sem mudanças não salvas simplesmente mostra a versão nova. Se uma request, pipeline ou ambiente aberto tinha mudanças não salvas, aparece "Mudou no disco enquanto você editava." com quatro opções:

  • Ficar com a minha: a sua versão fica; ao salvar, ela grava por cima da do disco.
  • Ficar com a do disco: o editor mostra o arquivo como está agora. A sua versão não salva fica guardada à parte no histórico do arquivo.
  • Ficar com as duas: a sua é salva como um arquivo novo ao lado (<nome>-mine) e o editor mostra a do disco.
  • Comparar: as duas versões lado a lado, com as mesmas três opções.

Nenhuma opção perde uma versão: a outra fica no histórico do arquivo.

O trabalho não salvo volta #

Enquanto uma request, pipeline, ambiente ou teste de carga tem mudanças não salvas, o Ultraman guarda um rascunho neste computador. Se a janela fecha, trava ou recarrega, a aba volta com as suas mudanças e o aviso "Suas alterações não salvas foram recuperadas"; Descartá-las volta ao arquivo (o rascunho fica guardado à parte no histórico). O rascunho some quando você salva ou descarta. Se o arquivo mudou no disco enquanto isso, aparecem as quatro opções acima.

O histórico de um arquivo #

Antes de o Ultraman gravar por cima de um arquivo de uma pasta do projeto ou apagá-lo (ao salvar, no Sincronizar, pelo agente, numa importação ou numa restauração), ele guarda a versão que substitui; quando um arquivo muda fora do Ultraman, guarda a última versão que conhecia. Versões deste arquivo… no menu ⋯ dele (o de uma request na árvore, o de uma pipeline ou de um ambiente ao lado de Salvar) abre as versões do arquivo e os commits do git numa só lista: escolha uma para vê-la ao lado do arquivo como está agora, e Restaurar esta versão a grava de volta byte a byte. Apagados recentemente… (no menu ⋯ de uma coleção, ou ao lado de Este arquivo na mesma janela) lista os arquivos que o Ultraman ou o disco removeram, com Restaurar. Cada arquivo guarda até 20 versões, por 30 dias, na pasta do próprio Ultraman neste computador (~/.ultraman), nunca no projeto.

Se outro programa está com um arquivo aberto (um editor, um antivírus verificando), Salvar espera até dois segundos, depois avisa e oferece Tentar de novo; o arquivo fica como estava.

O que fica só com você #

Os seus segredos, os valores de ambiente desta máquina, o histórico, as execuções anteriores e os relatórios de carga nunca são sincronizados. Cada pessoa define os próprios segredos no próprio cofre.

Pastas confiáveis #

A confiança numa pasta é de cada pessoa, em cada máquina. Numa pasta em que você não confiou, o Ultraman não envia nada pela janela e não executa git, então só há sincronização depois que você confiar nela. Isso protege você quando abre um repositório que acabou de clonar de outra pessoa. Confiar é decisão sua e fica no seu computador: nunca é guardado no projeto.

Em pull requests #

Como as pipelines e os testes de carga são YAML, uma mudança num teste aparece como um diff legível: qual passo mudou, qual limiar foi alterado. Uma request vinculada numa pipeline diz de onde veio (from: shop/orders/create).

O que mantém você seguro #

  • Sua equipe: só essas seis pastas entram no commit e no push; segredos, valores locais, histórico e relatórios ficam em cada máquina (o que fica guardado).
  • Você: os rascunhos e as versões anteriores de um arquivo ficam na pasta do próprio Ultraman neste computador (~/.ultraman), fora do projeto: o git nunca os vê, um commit não consegue plantar um, e nem o agente nem a CLI os leem.
  • Você: uma pasta em que você não confiou não envia nada e não executa git (pastas confiáveis).
  • Sua equipe: uma mudança num teste é um diff legível, então um host ou header novo não entra sem ninguém ver.
  • CI: os mesmos arquivos executam no seu pipeline de CI, com os segredos próprios dele (CI).
