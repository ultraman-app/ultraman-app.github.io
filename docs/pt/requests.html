Requests #

Na área de Requests você monta, envia e confere requests avulsas: coleções com pastas e requests, abertas em abas, como no Postman. A diferença é que cada request leva os seus checks, e tudo é um arquivo simples em ultraman/requests/ que a sua equipe compartilha pelo git.

Coleções e pastas #

Uma coleção tem um host e, se você quiser, auth, headers e variáveis (valores iniciais para {{nome}}). Pelo menu dela você cria requests e pastas, executa tudo, cria uma pipeline ou abre as configurações. Dá para renomear, mover e duplicar requests, e também adicioná-las a uma pipeline.

Enviar #

Enviar (Ctrl/Cmd+Enter) envia a request no ambiente selecionado. A resposta mostra status, tempo, tamanho, headers e body; Tempos mostra para onde foi o tempo (DNS, conexão, TLS, primeiro byte, total).

  • As variáveis aparecem como chips: {{env.x}} vem do ambiente, {{secrets.x}} do cofre e {{x}} da sessão (o que uma request anterior extraiu) ou das variáveis da coleção. Ctrl+Space sugere as variáveis.
  • Se faltar um valor, um diálogo pede esse valor para esta sessão.
  • Se você colar um comando curl no path, ele vira a request.

O editor de requests #

A request abre na primeira aba que tem conteúdo. As abas são Params (parâmetros de path como :id, e a query), Headers, Body, Auth, Opções, Checks e Notas. Uma linha desligada continua no arquivo, mas não é enviada. Uma request GET ou HEAD não pode ter body.

Body #

A aba Body tem sete modos. Cada um define o header Content-Type sozinho, a não ser que você escreva um em Headers (o editor avisa que o seu prevalece e que um header multipart escrito à mão perde o boundary).

ModoO que é enviadoContent-Type
Nenhumnenhum bodynenhum
JSONo JSON que você escreve, com {{variáveis}} dentroapplication/json
Textoo texto tal como foi escrito (XML, CSV, o que for)text/plain
Formpares nome=valor, codificados como URL; um nome pode se repetirapplication/x-www-form-urlencoded
Multipartpartes de texto ou de arquivomultipart/form-data
Arquivoos bytes de um arquivodeduzido pela extensão do arquivo
GraphQLuma query, as variáveis e o nome da operação, em JSON (veja GraphQL)application/json

Uma request tem um body só por vez. O arquivo vem do projeto: se você escolher um de outro lugar, o Ultraman oferece Copiar para o projeto (ultraman/files/, onde ele vai junto com o git) ou Deixar fora (só nesta máquina). Um arquivo fora de ultraman/files/ pede o seu sim na primeira vez que for enviado: veja arquivos.

Auth #

A aba Auth oferece Herdada, Nenhum, Bearer, Basic e API key (num header ou num parâmetro de query, com o nome que você escolher). Uma coleção ou uma pipeline pode definir a auth uma vez só; a request herda essa auth, define a sua ou fica com Nenhum. Os valores podem ser variáveis, em geral {{secrets.x}}, para o token nunca ficar no arquivo.

Os tipos são só esses. Para uma API com token, faça login com uma request, extraia o token e use-o como bearer ({{token}}): isso resolve a maioria dos fluxos de login. Não há fluxos OAuth 2, certificados de cliente nem assinatura de requests.

Opções da request #

As Opções ajustam uma request: timeout (em milissegundos; 30 000 por padrão, 0 para sem limite), redirects (quantos seguir; 10 por padrão, no máximo 20), tamanho máximo da resposta (50 MB), HTTP/2, HTTP simples (permite http: para um host que não seja localhost) e CA própria (um arquivo .pem do projeto, aceito além das CAs de sempre, para um servidor com certificado próprio). HTTP simples e CA própria diminuem a proteção da conexão, por isso a janela avisa quando você liga uma delas.

Uma opção vazia é herdada, e o editor mostra em cinza de onde ela vem ("30000 ms, por padrão"). A ordem é: as opções de request do ambiente, depois as da pipeline ou da coleção, depois as da própria request. Vale a mais próxima.

A request também pode ser marcada como responde sempre o mesmo: isso só faz diferença num teste de carga.

Copiar como cURL #

Numa pipeline, o botão de terminal na linha de uma request copia essa request como comando curl, com os valores que estão na janela. Os segredos nunca são escritos: viram ${ULTRAMAN_SECRET_NAME}, então o comando funciona num shell onde essa variável estiver definida e pode ser colado num chat com segurança. O caminho inverso também funciona na área de Requests: cole um comando curl no path e ele vira a request.

Redirects e Tempos #

Uma resposta redirecionada ganha a aba Redirects: cada salto com o status, a URL que respondeu e os headers (o location para onde apontou, um set-cookie no caminho). Tempos mostra para onde foi o tempo. Os redirects são seguidos até o limite da opção redirects. Duas regras protegem você: quando um redirect vai para outra origem, os headers authorization, cookie e proxy-authorization são descartados; e um 307 ou 308 que mandaria para outra origem um body com um segredo não é seguido (a resposta mostrada é o próprio redirect, com o destino dele). Veja redirects.

Checks #

Um check é um assert (a request precisa responder algo) ou um extract (guarda um valor para depois). Eles executam a cada envio, e a aba Checks da resposta mostra quais passaram.

CheckPassa quando
statuso status HTTP é o informado
equals, notEqualsum valor é (ou não é) o informado
containsum valor ou o body contém o que foi informado
lessThan, greaterThanum número (ou o tempo em ms) fica abaixo ou acima
exists, notExistsum path JSON ou um header está presente
matchesum texto bate com uma expressão regular
typeum valor JSON é string, número, array…
schemaum valor segue um JSON Schema

O jeito mais rápido de criar um: no body da resposta, passe o mouse sobre um valor e use o menu dele.

Gerar checks #

Gerar checks analisa a resposta que está na tela e sugere checks para ela:

  • que o status seja o que veio;
  • para cada campo de primeiro nível do JSON (ou do primeiro item, se for uma lista), que ele exista e qual é o seu tipo.

Ele adiciona no máximo 30, pula os que a request já tem e não salva nada até você clicar em Salvar: confira os checks na aba Checks e apague os que não quiser. É um ponto de partida para um teste de contrato; valores que mudam a cada chamada (ids, datas, tokens) são checados pelo tipo, nunca pelo valor. Na área de Pipelines, o mesmo botão adiciona os checks como passos logo depois da request.

A sessão #

Existe uma sessão por ambiente. O que um check extrai (o token do login) fica lá para a próxima request (Authorization: Bearer {{token}}). As variáveis da coleção são os valores iniciais.

Histórico #

Todo envio vai para o Histórico (ao lado de Coleções): o que foi enviado, a resposta, o tempo e os checks. Cada envio mostra o tempo habitual daquela request ("212 ms · costuma levar 180 ms") e ganha uma marca quando está mais lento. Dá para reabrir uma entrada como foi enviada ou compará-la lado a lado com outra. O histórico é pessoal: nunca é sincronizado.

O histórico tem uma tela só dele: uma tabela, do mais novo para o mais antigo e agrupada por dia, onde você busca (por nome, URL ou status) e filtra por método, status e ambiente; a barra lateral restringe a tabela a uma coleção. O envio escolhido abre ao lado da tabela, com o que saiu em cima do que voltou (lado a lado numa tela larga). Abrir como foi enviada devolve o envio à aba dele; ⋯ limpa o histórico.

Mudanças de contrato #

Depois de um envio, se o envio anterior da mesma request também devolveu JSON, um aviso mostra quais campos sumiram ou mudaram de tipo ($.id: string → number). Comparar abre os dois; Gerar checks transforma o formato atual em checks.

Contrato OpenAPI #

Uma coleção pode indicar a spec OpenAPI que a API dela promete cumprir: em Contrato, nas configurações, ou no collection.yaml:

contract:
  openapi: files/shop-openapi.yaml   # um arquivo dentro de files/, ou /openapi.json (um caminho no host), ou uma URL inteira
  mode: warn                         # warn (o padrão) ou strict

A partir daí, toda resposta das requests dela é conferida contra a operação correspondente na spec atual: num envio, numa execução da coleção, num passo de pipeline vinculado a uma dessas requests, numa execução de um agente e na CLI. A operação é a que a importação guardou na request (operation:) ou, se não houver, a que bate com o método e o path. O que a spec não documenta aparece como aviso: status 500 isn't documented for GET /orders/{id}, $.total: expected number, got null, not in the spec: POST /orders/bulk. Um body que não é JSON, ou uma resposta sem schema JSON, não tem o que conferir.

  • Onde aparece: ao lado do status (Contrato: 2 avisos), na lista acima do body, na linha da execução e no histórico. O terminal imprime uma linha embaixo do passo.
  • strict faz o passo de uma execução falhar no primeiro aviso (o JUnit registra isso). Um envio continua mostrando os avisos: ele não tem passo para falhar. Na CLI, --contract strict|warn|off passa por cima do modo do arquivo, então o CI pode ligar o contrato sem editar nada.
  • Um arquivo é relido quando muda. Um caminho ou uma URL é buscado como uma das requests da coleção (com o host, a auth, os headers e os segredos dela, e os mesmos sins), uma vez por execução; os envios da janela guardam a spec até você clicar em Reler a spec. Se não der para ler, isso vira um aviso, nunca um passo com falha.
  • Sob carga, não: um teste de carga não confere o contrato.
  • Com um contrato, Atualizar a partir da spec não escreve checks de schema (o contrato já cobre isso) e, quando o contrato é um arquivo, grava ali a spec mais nova.

Cópias vinculadas #

Adicionar a uma pipeline… coloca uma request no fim de uma pipeline como cópia vinculada (ela lembra de onde veio). Quando você muda uma das cópias, o Ultraman pergunta se deve atualizar as outras. Uma request WebSocket ou SSE entra como o passo connect vinculado a ela (só o handshake: as mensagens e a escuta ficam na área de Requests) e acompanha as mudanças do mesmo jeito.

Streams: WebSocket e SSE #

Abra um stream WebSocket ou SSE numa aba, como uma request: veja cada mensagem assim que ela chega, envie mensagens pelo compositor, filtre e pause a lista e guarde a sessão inteira no Histórico.

O menu de uma coleção tem Novo WebSocket ou SSE. Uma request de stream é um arquivo como qualquer outro (com websocket: live ou sse: prices como primeira chave) e abre numa aba com o mesmo layout de uma request. O seletor de método vira uma escolha WebSocket | SSE, o path vem depois do host da coleção (https vira wss, http vira ws) e as abas são Params, Headers, Auth, Opções (incluindo as do próprio stream: tamanho de mensagem, ping, ociosidade), Mensagens, Checks e Notas.

Conectar (Ctrl/Cmd+Enter) abre o stream e vira Desconectar enquanto ele está aberto. Logo abaixo, o painel do stream mostra uma pílula de status (connecting…, open 101, closed 1000), um relógio, quantas mensagens foram em cada direção e três abas:

  • Mensagens: uma linha por mensagem, a mais nova embaixo, com a direção (↓ recebida, ↑ enviada), a hora, o tamanho e, no SSE, o nome do event e o id. Clique numa linha para abri-la no visualizador do body. Filtrar esconde linhas pelo texto (ou por event:price no SSE), Pausar congela a lista enquanto as mensagens continuam sendo contadas e Limpar esvazia a lista.
  • Handshake: os headers do servidor (e o protocolo que ele escolheu).
  • Checks: os checks da request, executados sobre o handshake (status, um header).

Num WebSocket, o compositor embaixo da lista envia uma mensagem (texto ou JSON, Ctrl+Enter). Ele pode usar uma das mensagens salvas da request, e Salvar como mensagem adiciona o texto do compositor à request. Uma mensagem com {{secrets.x}} sai com o valor e aparece como [secret:x]. Quando o cofre é bloqueado, um stream que usou um segredo também é fechado.

O painel guarda as 500 mensagens mais recentes, cada uma cortada em 64 KB. Quando o stream termina (por você, pelo servidor ou por um erro), a sessão inteira vira uma entrada no Histórico: o handshake, as mensagens e como terminou.

Numa execução de coleção, em ultraman run --collection e quando um agente a envia, uma request de stream conecta, confere o handshake, envia as mensagens salvas, escuta por listen ms (2 segundos, a não ser que o arquivo diga outra coisa) e fecha. Um stream em silêncio não é uma falha. Para esperar uma mensagem específica e conferi-la, coloque o stream numa pipeline.

O que não tem aqui: uma request de stream não tem mock, nem mudanças de contrato, nem reconexão (se o servidor derrubar você, clique em Conectar de novo), e Socket.IO e WebSockets comprimidos (deflate) não são suportados (Se você vem de outra ferramenta).

GraphQL #

Envie queries e mutations GraphQL com autocompletar a partir do schema da API, e pegue os erros que um servidor devolve junto com um 200.

O menu de uma coleção tem Nova request GraphQL, e o Body de qualquer request tem um modo GraphQL (sempre POST). Nele ficam a query, as Variáveis (JSON, com {{variáveis}} dentro das strings, como num body JSON), um seletor de operação quando a query define mais de uma e Uma resposta com erros passa.

O schema. Carregar schema pede o schema ao servidor enviando a própria request com a query de introspecção: mesma URL, headers, auth e segredos, e as mesmas perguntas de um envio. Com o schema, o editor completa campos e argumentos, mostra a descrição do campo na lista de sugestões e marca o que não existe no schema. Salvar no projeto guarda o schema como ultraman/files/<coleção>.graphql e o registra no collection.yaml: todas as requests GraphQL daquela coleção passam a usá-lo, e o git o compartilha com a sua equipe. Um schema só carregado dura até você fechar a janela. Sem schema, o editor ainda destaca a sintaxe da query.

Erros. Um servidor GraphQL muitas vezes responde 200 com uma lista errors. A resposta mostra 1 erro GraphQL (ou N erros GraphQL) ao lado do status e lista cada mensagem, com o path dela, acima do body. Numa execução, numa execução de coleção e sob carga, um passo cuja resposta tem errors falha com a primeira mensagem, seja qual for o status; sob carga, cada uma dessas respostas conta como uma request com falha. Uma resposta com erros passa (allowErrors: true) serve para uma API que devolve dados parciais de propósito.

A query é enviada como está escrita: {{...}} dentro dela não é substituído, então os valores vão nas variáveis. A aba Enviado e o Histórico mostram a query como você escreveu e as variáveis como saíram (um segredo como [secret:x]).

Subscriptions. Quando a operação é uma subscription, a request mostra Assinar no lugar de Enviar. O Ultraman abre um WebSocket que fala graphql-transport-ws na URL da request (https vira wss), ou no path graphql: { subscriptions: /graphql/ws } da coleção quando o servidor atende as subscriptions em outro lugar, e inicia a subscription. O painel do stream mostra cada next como uma linha, em vermelho se vier com erros. Cancelar assinatura encerra a subscription e mantém o socket aberto; Desconectar fecha o socket. A sessão vira uma entrada no Histórico. Numa execução de coleção e quando um agente a envia, uma subscription escuta por 2 segundos e fecha, e os checks dela leem o primeiro next. Para esperar eventos específicos e conferi-los, use passos subscribe.

Ainda não há: GraphQL sobre SSE (graphql-sse), o protocolo antigo subscriptions-transport-ws, requests GET e persisted queries, batching e upload de arquivos.

O que mantém você seguro #

A promessa vale aqui como em qualquer lugar. O que esta parte acrescenta:

  • Você e sua equipe: um body de arquivo só sai sem perguntar se vier de ultraman/files/; qualquer outro arquivo pede antes. Veja arquivos.
  • Você: um redirect para outra origem não leva as suas credenciais junto. Veja redirects.
  • Sua equipe: o histórico é pessoal e nunca é sincronizado, então respostas com dados reais ficam na sua máquina. Veja onde as coisas ficam guardadas.
  • Você: a URL de um contrato é buscada como as próprias requests da coleção: os segredos dela pedem o mesmo sim, ela é recusada numa pasta em que você não confiou, e os avisos só citam a resposta depois que os segredos foram ocultados. Um arquivo de contrato só é lido de ultraman/files/, nunca através de um link. Veja consentimento.
  • Você: as variáveis GraphQL são um body: um segredo nelas pede o mesmo sim de qualquer outro lugar e aparece como [secret:x], e Carregar schema é um envio, com as mesmas perguntas. Veja consentimento.
  • Sua equipe: um schema só é lido de ultraman/files/, nunca através de um link, e as descrições dele e as mensagens de erro de um servidor aparecem como texto simples. Veja arquivos.
  • Você: as variáveis e o payload de connection_init de uma subscription são mensagens: um segredo neles pede o mesmo sim de um header, aparece como [secret:x] e, se o servidor devolver esse segredo, ele vem ocultado. Veja consentimento.
