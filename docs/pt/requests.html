Requests #

A área de Requests é onde você monta, envia e checa requests avulsas: coleções com pastas e requests, abertas em abas, como no Postman. A diferença é que cada request carrega seus checks, e tudo é um arquivo simples em ultraman/requests/ que a sua equipe compartilha pelo git.

Coleções e pastas #

Uma coleção tem um host e, se você quiser, auth, headers e variáveis (valores iniciais para {{nome}}). O menu dela cria requests e pastas, executa tudo, cria uma pipeline ou abre suas configurações. As requests podem ser renomeadas, movidas, duplicadas e adicionadas a uma pipeline.

Enviar #

Enviar (Ctrl/Cmd+Enter) envia a request no ambiente escolhido. A resposta mostra o status, o tempo, o tamanho, os headers e o body; Tempos diz para onde foi o tempo (DNS, conexão, TLS, primeiro byte, total).

  • As variáveis aparecem como chips: {{env.x}} do ambiente, {{secrets.x}} do cofre, {{x}} da sessão (o que uma request anterior extraiu) ou das variáveis da coleção. Ctrl+Space sugere.
  • Se faltar um valor, um diálogo pede para esta sessão.
  • Colar um comando curl no path o transforma na request.

O editor de requests #

Uma request abre na primeira aba com conteúdo. As abas são Params (parâmetros de path como :id, e a query), Headers, Body, Auth, Opções, Checks e Notas. Uma linha que você desliga continua no arquivo mas não é enviada. Uma request GET ou HEAD não pode ter body.

Body #

A aba Body tem seis modos. Cada um define o header Content-Type por você, a menos que você escreva um em Headers (o editor avisa que o seu vence, e que um header multipart escrito à mão perde o boundary).

ModoO que é enviadoContent-Type
Nenhumnenhum bodynenhum
JSONo JSON que você escreve, com {{variáveis}} dentroapplication/json
Textoo texto como escrito (XML, CSV, qualquer coisa)text/plain
Formpares nome=valor, codificados em URL; um nome pode se repetirapplication/x-www-form-urlencoded
Multipartpartes que são texto ou um arquivomultipart/form-data
Arquivoos bytes de um arquivodeduzido da extensão do arquivo

Uma request tem um body de cada vez. Um arquivo vem do projeto: se você escolhe um de outro lugar, o Ultraman oferece copiá-lo para o projeto (ultraman/files/, onde ele viaja com o git) ou deixá-lo fora (só nesta máquina). Um arquivo fora de ultraman/files/ pede o seu sim na primeira vez que é enviado: veja arquivos.

Auth #

A aba Auth oferece Herdada, Nenhum, Bearer, Basic e API key (um header ou um parâmetro de query, com o nome que você escolher). Uma coleção ou uma pipeline pode definir a auth uma vez; uma request a herda, define a sua própria, ou diz Nenhum. Os valores podem ser variáveis, em geral {{secrets.x}}, para que o token nunca fique no arquivo.

Esses são os tipos que existem. Para uma API com token, faça login com uma request, extraia o token e use-o como bearer ({{token}}): isso cobre a maioria dos fluxos de login. Não há fluxos OAuth 2, certificados de cliente nem assinatura de requests.

Opções da request #

Opções ajustam uma request: timeout (milissegundos, 30 000 por padrão, 0 para nenhum), redirects (quantos seguir, 10 por padrão, no máximo 20), tamanho máximo da resposta (50 MB), HTTP/2, HTTP simples (permitir http: para um host que não seja localhost) e uma CA própria (um arquivo .pem no projeto, aceito além das habituais, para um servidor com certificado próprio). HTTP simples e uma CA própria reduzem a proteção da conexão, então a janela avisa quando você os liga.

Uma opção vazia herda, e o editor diz de onde, em cinza ("30000 ms, por padrão"). A ordem é: as opções de request do ambiente, depois as da pipeline ou da coleção, depois as da request. A mais próxima vence.

Uma request também pode ser marcada como responde sempre o mesmo: isso só importa num teste de carga.

Copiar como cURL #

Numa pipeline, o botão de terminal na linha de uma request a copia como um comando curl, com os valores que você tem na janela. Os segredos nunca são escritos: eles viram ${ULTRAMAN_SECRET_NAME}, então o comando funciona num shell em que você define essa variável e é seguro colar num chat. O caminho inverso também funciona na área de Requests: cole um comando curl no path e ele vira a request.

Redirects e Tempos #

Uma resposta que foi redirecionada ganha uma aba Redirects: cada salto com seu status, a URL que respondeu e seus headers (o location para onde apontou, um set-cookie no caminho). Tempos diz para onde foi o tempo. Os redirects são seguidos até a opção redirects. Duas regras protegem você: quando um redirect vai para outra origem, os headers authorization, cookie e proxy-authorization são descartados, e um 307 ou 308 que enviaria um body com um segredo para outra origem não é seguido (a resposta mostrada é esse redirect, com para onde ele apontava). Veja redirects.

Checks #

Um check é um assert (a request tem que responder algo) ou um extract (guardar um valor para depois). Eles rodam em cada envio, e a aba Checks da resposta diz quais passaram.

CheckPassa quando
statuso status HTTP é o indicado
equals, notEqualsum valor é (ou não é) o indicado
containsum valor ou o body o contém
lessThan, greaterThanum número (ou o tempo em ms) está abaixo ou acima
exists, notExistsum path JSON ou um header está presente
matchesum texto bate com uma expressão regular
typeum valor JSON é string, número, array…
schemaum valor segue um JSON Schema

O jeito mais rápido de adicionar um: no body da resposta, passe o mouse sobre um valor e use o menu dele.

Gerar checks #

Gerar checks olha a resposta que está na tela e propõe checks para ela:

  • que o status seja o que ela recebeu;
  • para cada campo de primeiro nível do JSON (ou do primeiro item, se for uma lista), que ele exista e o seu tipo.

Adiciona no máximo 30, pula os que a request já tem e não salva nada até você apertar Salvar: veja na aba Checks e apague os que não quiser. É um ponto de partida para um teste de contrato; valores que mudam a cada chamada (ids, datas, tokens) são checados pelo tipo, nunca pelo valor. Na área de Pipelines, o mesmo botão os adiciona como passos logo depois da request.

A sessão #

Há uma sessão por ambiente. O que um check extrai (o token do login) fica disponível para a próxima request (Authorization: Bearer {{token}}). As variáveis da coleção são os valores iniciais.

Histórico #

Cada envio fica no Histórico (ao lado de Coleções): o que foi enviado, a resposta, o tempo e os checks. Cada envio mostra o tempo habitual daquela request ("212 ms · costuma levar 180 ms") e é marcado quando está mais lento. Uma entrada pode ser reaberta como foi enviada, ou comparada com outra lado a lado. O histórico é pessoal: nunca é sincronizado.

Mudanças de contrato #

Depois de um envio, se o envio anterior da mesma request também devolveu JSON, um aviso diz quais campos sumiram ou mudaram de tipo ($.id: string → number). Comparar abre os dois; Gerar checks transforma a forma atual em checks.

Cópias vinculadas #

Adicionar a um pipeline… coloca uma request no fim de uma pipeline como cópia vinculada (ela lembra de onde veio). Quando você a muda num lugar, o Ultraman pergunta se deve atualizar as outras cópias. Uma request WebSocket ou SSE vai como seu passo connect vinculado (só o handshake: suas mensagens e sua escuta ficam na área de Requests) e a segue do mesmo jeito.

Streams: WebSocket e SSE #

Abra um stream WebSocket ou SSE numa aba como uma request: veja cada mensagem conforme chega, envie uma de um compositor, filtre e pause a lista, e guarde a sessão inteira no Histórico.

O menu de uma coleção tem Novo WebSocket ou SSE. Uma request de stream é um arquivo como qualquer outro (websocket: live ou sse: prices como primeira chave), aberto numa aba com o mesmo layout de uma request. O seletor de método é uma escolha WebSocket | SSE, o path vai depois do host da coleção (https vira wss, http vira ws), e as abas são Params, Headers, Auth, Opções (inclusive as do stream: tamanho de mensagem, ping, ociosidade), Mensagens, Checks e Notas.

Conectar (Ctrl/Cmd+Enter) abre o stream e vira Desconectar enquanto estiver aberto. Embaixo, o painel do stream mostra uma pílula de estado (connecting…, open 101, closed 1000), um relógio, quantas mensagens foram em cada sentido, e três abas:

  • Mensagens: uma linha por mensagem, a mais nova embaixo, com a direção (↓ recebida, ↑ enviada), hora, tamanho e, no SSE, o nome event e o id. Clique numa linha para abri-la no visualizador do body. Filtrar esconde linhas por texto (ou event:price no SSE), Pausar para a lista enquanto as mensagens continuam contando, Limpar esvazia.
  • Handshake: os headers do servidor (e o protocolo que ele escolheu).
  • Checks: os checks da request rodam sobre o handshake (status, um header).

Num WebSocket, o compositor embaixo da lista envia uma mensagem (texto ou JSON, Ctrl+Enter). Ele pode pegar uma das mensagens salvas da request, e Salvar como mensagem adiciona o texto do compositor à request. Uma mensagem com {{secrets.x}} é enviada com o valor e aparece como [secret:x]. Quando o cofre bloqueia, um stream que usou um segredo também fecha.

O painel guarda as 500 mensagens mais novas, cada uma cortada em 64 KB. Quando o stream termina (você, o servidor ou um erro), a sessão inteira vira uma entrada no Histórico: o handshake, as mensagens e como terminou.

Numa execução de coleção, em ultraman run --collection e quando um agente a envia, uma request de stream conecta, verifica o handshake, envia as mensagens salvas, escuta por listen ms (2 segundos, a menos que o arquivo diga outra coisa) e fecha. Um stream silencioso não é uma falha. Para esperar uma mensagem específica e checá-la, coloque o stream numa pipeline.

Não há aqui: uma request de stream não tem mock, nem mudanças de contrato, nem reconexão (se o servidor derrubar você, Conecte de novo), e Socket.IO e WebSockets comprimidos (deflate) não são suportados (Se você vem de outra ferramenta).

O que mantém você seguro #

A promessa vale aqui como em todo lugar. O que esta parte acrescenta:

  • Você e sua equipe: um body de arquivo sai sem perguntar só de ultraman/files/; qualquer outro arquivo pergunta antes. Veja arquivos.
  • Você: um redirect para outra origem não leva suas credenciais junto. Veja redirects.
  • Sua equipe: o histórico é pessoal e nunca é sincronizado, então respostas com dados reais ficam na sua máquina. Veja onde as coisas ficam guardadas.
