Requests #

Na área de Requests você monta, envia e confere requests avulsas: coleções com pastas e requests, abertas em abas, como no Postman. A diferença é que cada request leva os seus checks, e tudo é um arquivo simples em ultraman/requests/ que a sua equipe compartilha pelo git.

Coleções e pastas #

Uma coleção tem um host e, se você quiser, auth, headers e variáveis (valores iniciais para {{nome}}). Pelo menu dela você cria requests e pastas, executa tudo, cria uma pipeline ou abre as configurações. Dá para renomear, mover e duplicar requests, e também adicioná-las a uma pipeline. Todo lugar que nomeia uma request (a árvore, as abas, o Histórico, a abertura rápida, as linhas de uma execução de coleção) mostra o tipo dela onde vai o método: o método em HTTP, e GQL, MCP, WS ou SSE. Atualizar a partir de uma spec OpenAPI… aparece no menu só numa coleção que tem uma spec: um contrato OpenAPI, ou requests que vieram de uma operação.

Executar uma coleção #

Executar, no menu de uma coleção ou de uma pasta, envia todas as requests em ordem, cada uma com seus checks. Uma request que falha não interrompe as outras: a execução continua, e a faixa acima das linhas diz quantas passaram e quantas falharam, e quais. Sob uma linha que falhou ficam o erro dela e os checks que não passaram. Um check cuja request falhou não é lido: diz «não verificado: a request falhou». Uma request que precisa de um valor que uma anterior não produziu, como o token de um login que falhou, não é enviada: a linha dela diz «não enviada», e a faixa diz o motivo uma só vez. Interromper encerra a execução onde está: a request em andamento diz «interrompida» e as demais «não executado». A lista de Execuções sob as linhas diz «7 passaram», «1 de 7 falhou» ou «interrompida». Uma pipeline continua parando na primeira falha, porque os passos dela alimentam uns aos outros. O terminal (`ultraman run --collection`), o JUnit e o run_collection do agente relatam uma coleção da mesma forma.

Enviar #

Enviar (Ctrl/Cmd+Enter) envia a request no ambiente selecionado. A resposta mostra status, tempo, tamanho, headers e body; Tempos mostra para onde foi o tempo (DNS, conexão, TLS, primeiro byte, total).

  • As variáveis aparecem como chips: {{env.x}} vem do ambiente, {{secrets.x}} do cofre e {{x}} da sessão (o que uma request anterior extraiu) ou das variáveis da coleção. Ctrl+Space sugere as variáveis.
  • Se faltar um valor, um diálogo pede esse valor para esta sessão.
  • Se você colar um comando curl no path, ele vira a request.

O editor de requests #

A request abre na primeira aba que tem conteúdo. As abas são Params (parâmetros de path como :id, e a query), Headers, Body, Auth, Opções, Checks e Notas. Uma linha desligada continua no arquivo, mas não é enviada. Uma request GET ou HEAD não pode ter body.

O tipo. A primeira célula da caixa da URL é o tipo da request: HTTP, GraphQL, MCP, WebSocket ou SSE. No HTTP o método vem em seguida; GraphQL e MCP são sempre enviados como POST. O menu de uma coleção tem uma só Nova request: abre em HTTP com a célula do tipo em foco, ou em MCP quando a coleção declara o path do seu servidor MCP. Mudar o tipo mantém o nome, o path, os headers, a auth e as opções. Quando o novo tipo não tem lugar para algo (um body JSON que vai para GraphQL, uma query que vai para um stream), uma pergunta lista o que é removido antes que algo mude, e enquanto você não fechar a aba, voltar ao tipo anterior traz tudo de volta. Um stream aberto não pode mudar de tipo. No passo de request de uma pipeline o tipo é HTTP, GraphQL ou MCP, e o tipo de um passo vinculado se muda na sua coleção.

Body #

A aba Body tem seis modos. Cada um define o header Content-Type sozinho, a não ser que você escreva um em Headers (o editor avisa que o seu prevalece e que um header multipart escrito à mão perde o boundary).

ModoO que é enviadoContent-Type
Nenhumnenhum bodynenhum
JSONo JSON que você escreve, com {{variáveis}} dentroapplication/json
Textoo texto tal como foi escrito (XML, CSV, o que for)text/plain
Formpares nome=valor, codificados como URL; um nome pode se repetirapplication/x-www-form-urlencoded
Multipartpartes de texto ou de arquivomultipart/form-data
Arquivoos bytes de um arquivodeduzido pela extensão do arquivo

Uma request tem um body só por vez. Uma query GraphQL e uma chamada MCP têm uma aba própria no lugar de Body, Consulta e Chamada (veja GraphQL e Servidores MCP). O arquivo vem do projeto: se você escolher um de outro lugar, o Ultraman oferece Copiar para o projeto (ultraman/files/, onde ele vai junto com o git) ou Deixar fora (só nesta máquina). Um arquivo fora de ultraman/files/ pede o seu sim na primeira vez que for enviado: veja arquivos.

Auth #

A aba Auth oferece Herdada, Nenhum, Bearer, Basic e API key (num header ou num parâmetro de query, com o nome que você escolher). Uma coleção ou uma pipeline pode definir a auth uma vez só; a request herda essa auth, define a sua ou fica com Nenhum. Os valores podem ser variáveis, em geral {{secrets.x}}, para o token nunca ficar no arquivo.

Os tipos são esses, mais OAuth 2 para servidores MCP (abaixo). Para uma API com token, faça login com uma request, extraia o token e use-o como bearer ({{token}}): isso resolve a maioria dos fluxos de login. Não há certificados de cliente nem assinatura de requests.

De uma request #

Na janela, a aba Auth de uma request (ou as configurações de uma coleção) pode pegar um token bearer De uma request: escolha a request de login e a propriedade da resposta dela (da última resposta, ou digitada como JSONPath). O Ultraman escreve auth: { bearer: '{{token}}' } na request ou na coleção, e um check extract no login. Numa coleção, o login ganha Nenhum como auth própria se não tinha, para nunca enviar o bearer que ele mesmo gera. O arquivo do login só é escrito quando a aba dele não tem edições não salvas; caso contrário, diz "Salve o login primeiro".

Depois disso, quando você envia e falta o token, ou a resposta é um 401, a janela envia primeiro o login, no mesmo ambiente, e depois a sua request. Depois de um 401 o token é renovado uma única vez: uma request que só lê (GET, HEAD, OPTIONS, uma query GraphQL ou um recurso ou prompt MCP enviados ao endpoint da sua coleção) é enviada de novo sozinha, uma que escreve espera você enviá-la de novo ("Token renovado: envie de novo"), e um segundo 401 é mostrado como veio. Uma execução de coleção pela janela faz o mesmo com um token que falta, não com um 401 dentro da execução. Na primeira vez para cada coleção, ambiente e login, ela pergunta Enviar {login} e continuar, dizendo para onde o login vai; em um ambiente de produção ela pergunta sempre, com um aviso.

É só bearer. Um agente que envia uma request salva ou executa uma coleção também envia o login antes, sob o cartão que você aprova (agentes); a CLI e as pipelines continuam usando um passo de login como antes.

Login OAuth 2 #

Para um servidor MCP que pede login, escolha OAuth 2 na aba Auth. Ela tem três campos opcionais: Issuer URL, Client ID e Scopes. Podem levar um valor do ambiente, {{env.x}}, assim cada ambiente faz login no seu próprio servidor (os valores são preenchidos antes de qualquer outra coisa lê-los, e um valor do ambiente nunca é um segredo: um {{secrets.x}} aqui é recusado). Um servidor que segue o padrão MCP não precisa de nenhum. A auth de uma coleção ou de uma pipeline pode ser OAuth 2 e as requests dela a herdam; os passos WebSocket e SSE não a oferecem.

No topo do corpo de OAuth 2 um botão mostra em que ponto o login está, e a mesma marca aparece no rótulo da aba Auth (passe o cursor para ver o estado em palavras): um anel âmbar significa que você precisa fazer login ou ainda não pode (o centro dele pulsa enquanto o navegador está aberto), um círculo verde que você já fez login e um quadrado vermelho que o login falhou. O menu do botão diz o estado, com o host a conferir em negrito, e oferece uma ação: Entrar, Abrir o navegador, Cancelar, Sair, Entrar de novo ou, quando o estado pede, Revisar, Usar login OAuth 2, Abrir Segredos, Confiar nesta pasta ou Abrir a auth da coleção. Abrir o menu não envia nada. Entrar descobre onde fazer login e mostra o host antes de Abrir o navegador; então o navegador do sistema abre no servidor de login.

Se você faz Enviar sem ter feito login, o Ultraman pergunta: Cancelar, Enviar sem entrar ou Abrir o navegador. Se o servidor não consegue identificar o Ultraman ou não diz onde fazer login, a pergunta pede o client id ou a issuer URL; num Enviar, o que você digita vira uma mudança não salva na Auth da request. Uma execução, Carregar do servidor ou uma comparação fazem a mesma pergunta sem Enviar sem entrar.

Num ambiente de produção o Ultraman pergunta antes de cada abertura do navegador e nunca lembra esse sim. Um login feito em outro projeto só é usado aqui depois de um sim neste projeto (Revisar, depois Usar para o servidor). Esse sim vale para esse login: depois de sair ou de entrar como outra pessoa, este projeto pergunta de novo. Em produção nunca é lembrado: vale só para o seu próximo envio ou execução aqui, e um sim que você deu em outro ambiente não conta ali. Sair pergunta antes: o Ultraman pede ao servidor que encerre o login e o esquece neste computador, então os outros projetos que o usam precisarão fazer login de novo.

Máquina a máquina #

Para um serviço ou um job de CI não há uma pessoa para fazer login. No corpo de OAuth 2, coloque Flow em Client credentials (machine to machine). Ele tem quatro campos: Issuer URL, Client ID, Client secret e Scopes, mais um Token URL opcional para um emissor que não publica onde fica o seu endpoint de token. O client secret é uma referência a um segredo, {{secrets.x}}, nunca o valor. O Ultraman pede um token ao emissor por conta própria e o envia como bearer.

O token vai para qualquer caminho da origem própria da API (esquema, host e porta) e para nenhuma outra origem, e vive só na memória: nunca é salvo no projeto, no cofre nem no git, e uma nova execução o pede de novo quando ele venceu. Um Token URL precisa estar na origem do próprio emissor. Uma request que usa um token de máquina não precisa de login nem do cofre destravado; numa máquina de build o segredo vem de ULTRAMAN_SECRET_<NOME> (o terminal). Os passos WebSocket e SSE não podem usar OAuth 2 e dizem isso. Um teste de carga compartilha um token por ambiente entre todos os seus usuários e o renova por eles.

Antes vêm duas permissões, cada uma pedida uma vez por projeto: o client secret indo para a origem do emissor, e o token indo para a origem da API quando ela não é a do emissor. São separadas: permitir o token numa origem nunca deixa o próprio segredo ir para lá. No CI, allow diz as duas de antemão (OAuth 2 no CI).

Em Copy as cURL e na aba Code, o token de uma request com OAuth 2 é escrito como ${ULTRAMAN_OAUTH_TOKEN}: defina essa variável onde o código rodar.

Opções da request #

As Opções ajustam uma request: timeout (em milissegundos; 30 000 por padrão, 0 para sem limite), redirects (quantos seguir; 10 por padrão, no máximo 20), tamanho máximo da resposta (50 MB), HTTP/2, HTTP simples (permite http: para um host que não seja localhost) e CA própria (um arquivo .pem do projeto, aceito além das CAs de sempre, para um servidor com certificado próprio). HTTP simples e CA própria diminuem a proteção da conexão, por isso a janela avisa quando você liga uma delas.

Uma opção vazia é herdada, e o editor mostra em cinza de onde ela vem ("30000 ms, por padrão"). A ordem é: as opções de request do ambiente, depois as da pipeline ou da coleção, depois as da própria request. Vale a mais próxima.

A request também pode ser marcada como responde sempre o mesmo: isso só faz diferença num teste de carga.

Copiar como cURL #

O código de uma request, cURL incluído, agora fica na aba Code: veja Trechos de código. O botão </> (copiar como código) na linha de uma request numa pipeline abre essa aba no inspetor, na última linguagem usada. Os segredos nunca são escritos: viram ${ULTRAMAN_SECRET_NAME}, então o comando funciona num shell onde essa variável estiver definida e pode ser colado num chat com segurança. O caminho inverso também funciona na área de Requests: cole um comando curl no path e ele vira a request.

Trechos de código #

A aba Code de uma request (depois de Notes) mostra a request como código que você pode copiar. Escolha a linguagem: cURL (bash), cURL (PowerShell), JavaScript fetch, Python requests, HTTPie (bash), HTTPie (PowerShell), Go net/http, C# HttpClient ou HTTP, uma exibição da request crua (não um arquivo .http para executar). As versões bash são para bash ou zsh; as de PowerShell chamam curl.exe e leem os segredos de $env:. Só rodam no PowerShell 7.3 ou posterior (HTTPie só como http.exe): o Windows PowerShell 5.1 pode partir um valor em outras opções ao passá-lo a um programa, então ali o snippet para com um erro em vez de rodar. Nunca cole um snippet de cURL ou HTTPie no Prompt de Comando do Windows (cmd.exe): ele lê &, |, > e ^ dentro das aspas como comandos, então um valor poderia rodar um programa ou gravar um arquivo. Um header, campo de formulário ou autenticação básica que não pode ir com segurança numa linha de comando fica de fora com um comentário #; se a URL ou o body não puderem, ou o HTTPie não puder enviar o método, o snippet é só esse comentário. Linhas longas quebram, Copy põe o código na área de transferência e a aba lembra a última linguagem usada (na primeira vez é cURL; no Windows, a versão PowerShell).

Os valores do ambiente são escritos no código. Cada segredo é lido de uma variável de ambiente chamada ULTRAMAN_SECRET_<NAME> nessa linguagem (process.env, os.environ, os.Getenv, $ULTRAMAN_SECRET_NAME etc.), então você define a variável onde o código roda e o trecho pode ser colado com segurança. Numa pipeline, o botão </> na linha de uma request abre o inspetor na aba Code. O trecho de uma request MCP começa com um comentário dizendo que a chamada precisa antes de uma sessão ou server/discover. Uma request WebSocket ou SSE não tem código a mostrar: uma conexão ao vivo não tem código para copiar, e a aba diz isso. Os agentes têm get_snippet, que dá o mesmo texto.

Redirects e Tempos #

Uma resposta redirecionada ganha a aba Redirects: cada salto com o status, a URL que respondeu e os headers (o location para onde apontou, um set-cookie no caminho). Tempos mostra para onde foi o tempo. Os redirects são seguidos até o limite da opção redirects. Duas regras protegem você: quando um redirect vai para outra origem, os headers authorization, cookie e proxy-authorization são descartados; e um 307 ou 308 que mandaria um body para outra origem não é seguido (a resposta mostrada é o próprio redirect, com o destino dele). Veja redirects.

Checks #

Um check é um assert (a request precisa responder algo) ou um extract (guarda um valor para depois). Eles executam a cada envio, e a aba Checks da resposta mostra quais passaram.

CheckPassa quando
statuso status HTTP é o informado
equals, notEqualsum valor é (ou não é) o informado
containsum valor ou o body contém o que foi informado
lessThan, greaterThanum número (ou o tempo em ms) fica abaixo ou acima
exists, notExistsum path JSON ou um header está presente
matchesum texto bate com uma expressão regular
typeum valor JSON é string, número, array…
schemaum valor segue um JSON Schema

O jeito mais rápido de criar um: no body da resposta, passe o mouse sobre um valor e use o menu dele.

Gerar checks #

Gerar checks analisa a resposta que está na tela e sugere checks para ela:

  • que o status seja o que veio;
  • para cada campo de primeiro nível do JSON (ou do primeiro item, se for uma lista), que ele exista e qual é o seu tipo.

Ele adiciona no máximo 30, pula os que a request já tem e não salva nada até você clicar em Salvar: confira os checks na aba Checks e apague os que não quiser. É um ponto de partida para um teste de contrato; valores que mudam a cada chamada (ids, datas, tokens) são checados pelo tipo, nunca pelo valor. Na área de Pipelines, o mesmo botão adiciona os checks como passos logo depois da request.

Numa chamada MCP os checks descem um nível: leem os campos do Resultado estruturado ($.structuredContent.total), não os blocos de texto de content. Uma ferramenta que respondeu com erro recebe só o check de status.

A sessão #

Existe uma sessão por ambiente. O que um check extrai (o token do login) fica lá para a próxima request (Authorization: Bearer {{token}}). As variáveis da coleção são os valores iniciais.

Histórico #

Todo envio vai para o Histórico (ao lado de Coleções): o que foi enviado, a resposta, o tempo e os checks. Cada envio mostra o tempo habitual daquela request ("212 ms · costuma levar 180 ms") e ganha uma marca quando está mais lento. Dá para reabrir uma entrada como foi enviada ou compará-la lado a lado com outra. O histórico é pessoal: nunca é sincronizado.

O histórico tem uma tela só dele: uma tabela, do mais novo para o mais antigo e agrupada por dia, onde você busca (por nome, URL ou status) e filtra por método, status e ambiente; a barra lateral restringe a tabela a uma coleção. O envio escolhido abre ao lado da tabela, com o que saiu em cima do que voltou (lado a lado numa tela larga). Abrir como foi enviada devolve o envio à aba dele; ⋯ limpa o histórico.

Mudanças de contrato #

Depois de um envio, se o envio anterior da mesma request também devolveu JSON, um aviso mostra quais campos sumiram ou mudaram de tipo ($.id: string → number). Comparar abre os dois; Gerar checks transforma o formato atual em checks. Um campo que a resposta anterior não tinha não é uma mudança: não mostra o aviso, e na resposta a linha dele diz novo desde o último envio.

Contrato OpenAPI #

Uma coleção pode indicar a spec OpenAPI que a API dela promete cumprir: em Contrato, nas configurações, ou no collection.yaml:

contract:
  openapi: files/shop-openapi.yaml   # um arquivo dentro de files/, ou /openapi.json (um caminho no host), ou uma URL inteira
  mode: warn                         # warn (o padrão) ou strict

A partir daí, toda resposta das requests dela é conferida contra a operação correspondente na spec atual: num envio, numa execução da coleção, num passo de pipeline vinculado a uma dessas requests, numa execução de um agente e na CLI. A operação é a que a importação guardou na request (operation:) ou, se não houver, a que bate com o método e o path. O que a spec não documenta aparece como aviso: status 500 isn't documented for GET /orders/{id}, $.total: expected number, got null, not in the spec: POST /orders/bulk. Um body que não é JSON, ou uma resposta sem schema JSON, não tem o que conferir.

  • Onde aparece: ao lado do status (Contrato: 2 avisos), na lista acima do body, na linha da execução e no histórico. O terminal imprime uma linha embaixo do passo.
  • strict faz o passo de uma execução falhar no primeiro aviso (o JUnit registra isso). Um envio continua mostrando os avisos: ele não tem passo para falhar. Na CLI, --contract strict|warn|off passa por cima do modo do arquivo, então o CI pode ligar o contrato sem editar nada.
  • Um arquivo é relido quando muda. Um caminho ou uma URL é buscado como uma das requests da coleção (com o host, a auth, os headers e os segredos dela, e os mesmos sins), uma vez por execução; os envios da janela guardam a spec até você clicar em Reler a spec. Se não der para ler, isso vira um aviso, nunca um passo com falha.
  • Sob carga, não: um teste de carga não confere o contrato.
  • Com um contrato, Atualizar a partir de uma spec OpenAPI não escreve checks de schema (o contrato já cobre isso) e, quando o contrato é um arquivo, grava ali a spec mais nova.

Cópias vinculadas #

Adicionar a uma pipeline… coloca uma request no fim de uma pipeline como cópia vinculada (ela lembra de onde veio). Quando você muda uma das cópias, o Ultraman pergunta se deve atualizar as outras. Uma request WebSocket ou SSE entra como o passo connect vinculado a ela (só o handshake: as mensagens e a escuta ficam na área de Requests) e acompanha as mudanças do mesmo jeito.

Streams: WebSocket e SSE #

Abra um stream WebSocket ou SSE numa aba, como uma request: veja cada mensagem assim que ela chega, envie mensagens pelo compositor, filtre e pause a lista e guarde a sessão inteira no Histórico.

Escolha WebSocket ou SSE na célula do tipo da request. Uma request de stream é um arquivo como qualquer outro (com websocket: live ou sse: prices como primeira chave) e abre numa aba com o mesmo layout de uma request. A célula do tipo diz qual é (ocupa o lugar do método), o path vem depois do host da coleção (https vira wss, http vira ws) e as abas são Params, Headers, Auth, Opções (incluindo as do próprio stream: tamanho de mensagem, ping, ociosidade), Mensagens, Checks e Notas.

Conectar (Ctrl/Cmd+Enter) abre o stream e vira Desconectar enquanto ele está aberto. Logo abaixo, o painel do stream mostra uma pílula de status (connecting…, open 101, closed 1000), um relógio, quantas mensagens foram em cada direção e duas abas:

  • Mensagens: uma linha por mensagem, a mais nova embaixo, com a direção (↓ recebida, ↑ enviada), a hora, o tamanho e, no SSE, o nome do event e o id. Clique numa linha para abri-la no visualizador do body. Filtrar esconde linhas pelo texto (ou por event:price no SSE), Pausar congela a lista enquanto as mensagens continuam sendo contadas e Limpar esvazia a lista.
  • Handshake: os headers do servidor (e o protocolo que ele escolheu).

A aba Checks da própria request guarda os checks de um stream. Eles leem o handshake (status, um header), não as mensagens: a aba diz isso quando está vazia. Para conferir uma mensagem, ponha o stream numa pipeline: a aba tem um link para a ação abaixo.

Esperar isto em uma pipeline… fica na linha de uma mensagem recebida (e na mensagem next de uma assinatura GraphQL). Ela propõe uma pipeline: o connect do stream (vinculado a esta request), as mensagens salvas enviadas antes, uma espera por uma mensagem como esta com limite de 5 segundos, um check e o fechamento. Uma prévia lista os passos; você pode deixar um de fora ou movê-lo, e nada é salvo até Criar, que abre a nova pipeline. O texto da mensagem é escrito como texto, nunca como variável.

Num WebSocket, o compositor embaixo da lista envia uma mensagem (texto ou JSON, Ctrl+Enter). Ele pode usar uma das mensagens salvas da request, e Salvar como mensagem adiciona o texto do compositor à request. Uma mensagem com {{secrets.x}} sai com o valor e aparece como [secret:x]. Quando o cofre é bloqueado, um stream que usou um segredo também é fechado.

O painel guarda as 500 mensagens mais recentes, cada uma cortada em 64 KB. Quando o stream termina (por você, pelo servidor ou por um erro), a sessão inteira vira uma entrada no Histórico: o handshake, as mensagens e como terminou.

Numa execução de coleção, em ultraman run --collection e quando um agente a envia, uma request de stream conecta, confere o handshake, envia as mensagens salvas, escuta por listen ms (2 segundos, a não ser que o arquivo diga outra coisa) e fecha. Um stream em silêncio não é uma falha. Para esperar uma mensagem específica e conferi-la, coloque o stream numa pipeline.

O que não tem aqui: uma request de stream não tem mock, nem mudanças de contrato, nem reconexão (se o servidor derrubar você, clique em Conectar de novo), e Socket.IO e WebSockets comprimidos (deflate) não são suportados (Se você vem de outra ferramenta).

GraphQL #

Envie queries e mutations GraphQL com autocompletar a partir do schema da API, e pegue os erros que um servidor devolve junto com um 200.

Escolha GraphQL na célula do tipo da request (sempre POST). Sua aba Consulta tem a query. Nela ficam a query, as Variáveis (JSON, com {{variáveis}} dentro das strings, como num body JSON), um seletor de operação quando a query define mais de uma e Permitir erros.

O schema. Carregar schema pede o schema ao servidor enviando a própria request com a query de introspecção: mesma URL, headers, auth e segredos, e as mesmas perguntas de um envio. Com o schema, o editor completa campos e argumentos, mostra a descrição do campo na lista de sugestões e marca o que não existe no schema. Salvar no projeto guarda o schema como ultraman/files/<coleção>.graphql e o registra no collection.yaml: todas as requests GraphQL daquela coleção passam a usá-lo, e o git o compartilha com a sua equipe. Um schema só carregado dura até você fechar a janela. Sem schema, o editor ainda destaca a sintaxe da query.

Erros. Um servidor GraphQL muitas vezes responde 200 com uma lista errors. A resposta mostra 1 erro GraphQL (ou N erros GraphQL) ao lado do status e lista cada mensagem, com o path dela, acima do body. Numa execução, numa execução de coleção e sob carga, um passo cuja resposta tem errors falha com a primeira mensagem, seja qual for o status; sob carga, cada uma dessas respostas conta como uma request com falha. Uma nota sob a lista diz isso ("Uma resposta com erros falha a request. Permitir erros a deixa passar."). Permitir erros (allowErrors: true) serve para uma API que devolve dados parciais de propósito.

A query é enviada como está escrita: {{...}} dentro dela não é substituído, então os valores vão nas variáveis. A aba Enviado e o Histórico mostram a query como você escreveu e as variáveis como saíram (um segredo como [secret:x]).

Subscriptions. Quando a operação é uma subscription, a request mostra Assinar no lugar de Enviar. O Ultraman abre um WebSocket que fala graphql-transport-ws na URL da request (https vira wss), ou no path graphql: { subscriptions: /graphql/ws } da coleção quando o servidor atende as subscriptions em outro lugar, e inicia a subscription. O painel do stream mostra cada next como uma linha, em vermelho se vier com erros. Cancelar assinatura encerra a subscription e mantém o socket aberto; Desconectar fecha o socket. A sessão vira uma entrada no Histórico. Numa execução de coleção e quando um agente a envia, uma subscription escuta por 2 segundos e fecha, e os checks dela leem o primeiro next. Para esperar eventos específicos e conferi-los, use passos subscribe. Uma subscription não tem Comparar com…, porque um stream não é comparado; mude-a para uma query e o botão volta.

Ainda não há: GraphQL sobre SSE (graphql-sse), o protocolo antigo subscriptions-transport-ws, requests GET e persisted queries, batching e upload de arquivos.

Servidores MCP #

Chame uma ferramenta, leia um recurso ou obtenha um prompt de um servidor MCP que fala MCP sobre HTTP, e confira o que volta como qualquer outra resposta.

A request. Escolha MCP na célula do tipo da request (sempre POST; sua aba Chamada; o path é o endereço do servidor depois do host da coleção, como /mcp). Escolha Ferramenta, Recurso ou Prompt. O nome é completado a partir da lista do servidor (a que uma coleção importada do servidor guarda), e os Argumentos são JSON, com {{variáveis}} dentro das strings, como um body JSON. Permitir erros deixa passar o erro próprio de uma ferramenta (só ferramentas). Os argumentos de um prompt são texto.

Do servidor. Abaixo dos argumentos, o cartão Do servidor mostra o que o servidor diz sobre o argumento onde está o cursor: as palavras dele, o tipo, exemplos e o valor padrão, e um clique escreve um valor. Fora de um argumento, ele lista todos. No editor, a sugestão traz as mesmas palavras. Uma request escrita à mão ainda não tem lista: Carregar do servidor (↻ no canto do cartão Do servidor, onde está tudo o que o servidor diz da chamada) pede a lista ao servidor com o endereço e a auth desta request. É um envio, com as perguntas de um Send; lista o servidor e nunca chama uma ferramenta. Salvar no projeto guarda a lista na coleção (files/<coleção>.mcp.json), e Carregar de novo pede outra vez.

A resposta. A resposta é o resultado da ferramenta: o conteúdo (texto, imagens, recursos embutidos) e depois o Resultado estruturado (structuredContent), então você extrai e verifica em $.structuredContent… como em qualquer body JSON. Uma ferramenta que responde com erro mostra isso junto ao status e faz o passo falhar, a não ser que Permitir erros esteja ligado; um erro JSON-RPC também o faz falhar (MCP error -32602: …). O Histórico os lista como MCP com o nome da ferramenta, e o filtro de método dele tem MCP. Uma nota sob o erro de uma ferramenta diz que Permitir erros o deixa passar. Enviado mostra a mensagem JSON-RPC que saiu, nunca o id da sessão.

Blocos de texto. Um bloco de texto que traz JSON aparece no mesmo visor do resultado estruturado, então passar o mouse ou Enter extrai ou verifica um valor de dentro dele: o path lê dentro do texto ($.content[0].text.@json…, mais abaixo). Quando diz o mesmo que o resultado estruturado, ele se dobra em uma linha com Mostrar. Qualquer outro texto, também o de um recurso ou de um prompt, tem um menu ⋯: Verificar que contém…, Extrair com uma regex… (uma regex lê a resposta inteira) e Copiar path. Gerar checks lê structuredContent ou, quando uma ferramenta não manda, o primeiro texto JSON dela.

Uma ferramenta que responde JSON como texto. Muitas ferramentas põem o JSON dela em uma string, em content[0].text. Acrescente .@json ao caminho e o Ultraman lê dentro desse texto: $.content[0].text.@json.customers[0].id, em um extract, um assert ou no where de um stream. Ele pode se repetir e pode vir depois de [*] (os itens que não são JSON são pulados). Se o valor não é texto, o texto não é JSON ou passa de 1 MB, o caminho não encontra nada e a falha diz qual (the text at … isn't JSON). Uma chave que de fato se chama @json se escreve ['@json']. Os caminhos que escolhem campos para deixar de fora em um compare não o aceitam.

Versões do protocolo. O Ultraman fala MCP sobre HTTP (o transporte Streamable HTTP) em quatro versões: 2026-07-28, que não tem initialize nem sessão (cada chamada vai por conta própria), e 2025-11-25, 2025-06-18 e 2025-03-26, que abrem uma sessão com initialize. Por padrão o protocolo é Automático: na primeira vez que encontra um servidor, o Ultraman pergunta server/discover; se ele responde em 2026-07-28, fala assim, e se não, usa o cumprimento das versões anteriores e pede primeiro a mais nova. Ele lembra o que encontrou enquanto o app estiver aberto, então um teste de carga não pergunta de novo para cada usuário. Um servidor que muda de época no meio de uma execução faz essa chamada falhar, e a seguinte pergunta de novo.

Fixar o protocolo. Adicione protocol: ao mcp: de uma requisição (ou ao da coleção) com auto ou uma das quatro versões, e o Ultraman fala só essa e nunca pergunta ao servidor qual ele fala. O valor da requisição vale mais que o da sua coleção, auto inclusive. Na janela, a aba Chamada da requisição tem um seletor Protocolo ao lado de Permitir erros (um recurso o tem em uma linha própria), e a seção Servidor MCP da coleção guarda a escolha da coleção, que cada requisição usa a menos que escolha a sua; o seletor avisa quando um valor vem da coleção. Um servidor que não fala a versão fixada faz o passo falhar.

O que diz a linha de sessão. Sob a resposta, um servidor das versões anteriores diz "Sessão: shop 1.2 · MCP 2025-11-25 · aberta para este envio e encerrada depois dele", e um de 2026-07-28 diz "Servidor: shop 1.2 · MCP 2026-07-28 · sem sessão: cada chamada vai por conta própria". O passo de uma execução e o resultado de um pipeline nomeiam a versão do mesmo jeito, e o terminal a imprime sob o passo cuja primeira chamada a abriu. Em um teste de carga o relatório tem uma linha por servidor e método para o que abre uma sessão (server/discover e initialize à parte), e o tempo delas fica fora do p95 do veredito.

Uma ferramenta que fica fora de uma listagem. Em 2026-07-28 uma ferramenta pode marcar um argumento para viajar como cabeçalho (x-mcp-header). Quando o esquema de uma ferramenta faz isso de um jeito que o Ultraman não consegue enviar com segurança (um nome que não é um cabeçalho válido, dois argumentos com o mesmo cabeçalho ou um argumento que não é texto, inteiro nem booleano), a ferramenta fica fora da listagem e a importação diz por quê, em vez de falhar a listagem toda. Atualizar a partir do servidor mantém a requisição dessa ferramenta como estava, e as listas salvas dizem "left out", nunca "gone".

Sessões. Com 2025-11-25 e as versões anteriores, um Enviar abre a sua própria sessão, faz a chamada e a encerra. Uma execução abre uma sessão por servidor na primeira vez que o chama, a compartilha entre blocos, repetições e ramos, e a encerra quando termina (também com Stop). A aba Code dá o único POST, com um comentário de que o servidor pode precisar de uma sessão ou server/discover antes.

Servidores que não seguem o padrão. O Ultraman se comporta como o cliente mais rigoroso entre os comuns e diz por quê quando faz algo diferente do padrão. Quando só existe uma leitura possível da resposta e um cliente padrão funcionaria, ele se recupera e o passo continua verde com uma nota, em Enviado, na execução, no terminal e no JUnit, e no resultado de um agente; uma carga as conta por tipo. Ele se recupera de: uma versão de protocolo antiga (2024-11-05) sobre este transporte, uma sessão que o servidor esqueceu (abre uma nova, uma só vez), um serverInfo ou capabilities ausentes, uma resposta sem "jsonrpc", uma com result e error ao mesmo tempo, e um lote (lê o item que responde). Ele falha com palavras que nomeiam o problema quando um passo verde seria um resultado falso: um status HTTP sem resposta MCP (um 401 diz que o servidor pede autorização), um redirecionamento (diz para onde; nunca é seguido: ponha /mcp/ no endereço se for isso que o servidor quer), um 404 ou 405 na primeira chamada (provavelmente o transporte antigo HTTP+SSE, que não é suportado), uma resposta a outro id, JSON-RPC com o content type errado, um erro sem código numérico, um 400 onde o padrão responde 404, um pedido do servidor no meio do stream (sampling, roots, elicitation) ou um stream que fecha antes da resposta. Ele recusa um redirecionamento para outra origem, uma versão de protocolo mais nova do que a que ele fala (ou nenhuma) e um id de sessão que não seja ASCII visível.

O nome de uma ferramenta ou de um prompt é qualquer texto de até 128 caracteres sem caracteres de controle nem {{, então o ns/tool de um gateway funciona.

O que mantém você seguro #

A promessa vale aqui como em qualquer lugar. O que esta parte acrescenta:

  • Você e sua equipe: um body de arquivo só sai sem perguntar se vier de ultraman/files/; qualquer outro arquivo pede antes. Veja arquivos.
  • Você: um valor lido com .@json é um valor da resposta: ele é ocultado, e conta como o do segredo se um servidor o devolve como está ou escrito com escapes, até seis níveis de profundidade (texto JSON dentro de texto JSON). Uma verificação que lê um valor com esse eco é recusada, e também um exists ou notExists com .@json sobre uma resposta que devolve um.
  • Você: um token OAuth 2 fica no cofre de segredos deste computador, nunca no projeto nem no git, é guardado pelo endereço do servidor e vai só para esse servidor. Confira o host que o menu mostra antes de abrir o navegador; um ambiente de produção pergunta antes de cada abertura, e um login de outro projeto só é usado aqui depois do seu sim. Uma pasta sem confiança nunca faz login, e sem cofre de segredos a janela leva você a Segredos. Veja onde as coisas ficam guardadas.
  • Você: o client secret de um login máquina a máquina vai só para o endpoint de token do seu emissor e pergunta antes, como qualquer segredo indo para um host novo. Um token de máquina nunca é salvo, nunca é mostrado (é escondido como um segredo) e vai só para a origem da sua API, que também pergunta antes, uma vez por origem. Um valor do ambiente nos campos de OAuth 2 nunca é um segredo.
  • Você: um redirect para outra origem não leva as suas credenciais junto. Veja redirects.
  • Você: em 2026-07-28, um argumento que uma ferramenta pede para enviar como cabeçalho (Mcp-Param-…) vai ao mesmo servidor que já recebe esse valor no corpo; o que você vê dele (Enviado, o histórico, um erro que cite o cabeçalho) é montado com o valor oculto, então um segredo nunca aparece ali, nem mesmo codificado como texto. O esquema da ferramenta, que é do servidor, escolhe quais argumentos viajam como cabeçalhos, e gateways e logs de acesso costumam registrar cabeçalhos: não coloque um segredo num argumento marcado como cabeçalho de um servidor a quem você não confiaria esse segredo.
  • Sua equipe: o histórico é pessoal e nunca é sincronizado, então respostas com dados reais ficam na sua máquina. Veja onde as coisas ficam guardadas.
  • Você: a URL de um contrato é buscada como as próprias requests da coleção: os segredos dela pedem o mesmo sim, ela é recusada numa pasta em que você não confiou, e os avisos só citam a resposta depois que os segredos foram ocultados. Um arquivo de contrato só é lido de ultraman/files/, nunca através de um link. Veja consentimento.
  • Você: as variáveis GraphQL são um body: um segredo nelas pede o mesmo sim de qualquer outro lugar e aparece como [secret:x], e Carregar schema é um envio, com as mesmas perguntas. Veja consentimento.
  • Você: Carregar do servidor é um envio: pergunta o mesmo que um Send, nunca segue um redirecionamento e nunca chama uma ferramenta. O que o servidor diz aparece como texto e chega ao projeto só como texto literal: um {{ nele nunca é uma variável viva. Veja consentimento.
  • Sua equipe: um schema só é lido de ultraman/files/, nunca através de um link, e as descrições dele e as mensagens de erro de um servidor aparecem como texto simples. Veja arquivos.
  • Você: as variáveis e o payload de connection_init de uma subscription são mensagens: um segredo neles pede o mesmo sim de um header, aparece como [secret:x] e, se o servidor devolver esse segredo, ele vem ocultado. Veja consentimento.
  • Você: o único sim por trás de Enviar {login} e continuar fica guardado nesta máquina (~/.ultraman/trust.json), nunca no projeto. Qualquer mudança na request de login (método, caminho, body, headers, extracts ou o que ela herda da coleção), ou em para onde ela vai depois de preenchidos os valores do ambiente, pergunta de novo; um ambiente de produção pergunta sempre, e esse sim não é guardado. O login vai com os valores da própria coleção. Um token chega só à sessão do próprio ambiente, e a janela envia um login por você apenas para os nomes que uma auth lê: qualquer outro valor que faltar continua perguntando.
  • Você: um argumento MCP é um body: um segredo dentro dele pede o mesmo sim de qualquer lugar e aparece como [secret:x], e um resultado que o repita é censurado. O id de sessão do servidor nunca é mostrado nem guardado. Veja consentimento.
  • Você: as palavras de um servidor (nomes de ferramentas, descrições, resultados, erros) aparecem como texto puro, sem caracteres de controle, e são cortadas antes de serem guardadas. Um redirecionamento nunca é seguido, então o seu token e o id de sessão ficam com o endereço que você escolheu. Um servidor que foge do padrão só é recuperado quando há uma leitura segura, e isso é dito.
  • Você: um trecho nunca leva o valor de um segredo: cada segredo é uma referência a uma variável de ambiente chamada ULTRAMAN_SECRET_<NAME>, e qualquer outro valor é escrito como dado na linguagem escolhida, escapado para ela (para cURL e HTTPie, como bash, zsh ou PowerShell o leem; um segredo dentro de uma string JSON é escapado para JSON antes), então não consegue escapar da sua string ali. O que uma linguagem não consegue escrever com segurança fica de fora, e um comentário diz isso. Gerar um trecho não envia nada. Veja consentimento.
