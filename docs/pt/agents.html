Agentes (MCP) #

Um agente de IA (o Claude Code ou qualquer outro cliente MCP) pode usar o Ultraman através de ultraman mcp. Ele faz o mesmo que você faz na janela: lê e escreve requests, pipelines e testes de carga, envia e executa, importa, inicia o servidor mock, lê relatórios e compara. Cada chamada passa pela sua aprovação.

Conectar #

ultraman mcp é um servidor MCP via stdio. No Claude Code:

claude mcp add ultraman -- ultraman mcp --project <your project folder>

Em qualquer outro cliente MCP, a configuração é a mesma, nas opções do próprio cliente: um servidor stdio com o comando ultraman e os argumentos mcp --project <your project folder>. Sem --project, o projeto é a pasta de onde você o inicia (ou a mais próxima acima dela que tenha ultraman/).

Duas condições precisam valer; senão, toda ferramenta responde "open Ultraman on this project to approve the agent's requests":

  • a janela do Ultraman está aberta nesse projeto, porque é nela que você aprova;
  • a pasta é confiável na janela (pastas confiáveis).

Você aprova cada chamada #

Cada pedido do agente aparece como um cartão no canto inferior direito: quem pede, o quê e os detalhes (numa alteração, o diff). Escolha Aprovar ou Rejeitar (com um motivo, que o agente lê). Pedidos só de leitura podem ser aprovados para "sempre"; isso vale só para a sessão atual do agente, e só enquanto o Ultraman continuar aberto.

O que executa algo (uma pipeline, uma request, uma carga) tem dois cartões: um para iniciar e outro para entregar o resultado ao agente. O cartão de entrega avisa quando o resultado traz tokens, cookies ou headers de autenticação. Se você rejeitar uma entrega, não tem volta.

Uma chamada dura no máximo uns 50 segundos, porque a maioria dos clientes corta uma chamada de ferramenta aos 60: uma execução longa segue ativa, e o agente pede o resultado depois. Enquanto um cartão espera por você, o agente recebe um aviso de progresso a cada 5 segundos que diz se espera o seu cartão ou um resultado. Um cartão que ninguém responde a tempo se fecha, e o agente sabe qual foi: se era o de início, que nada executou; se era uma entrega, que o resultado fica guardado e ele pode pedir de novo. Todo pedido fica registrado em ultraman/mcp/, que o git ignora.

Um stream WebSocket ou SSE é enviado de uma vez só (send_stream, ou uma request de stream salva): ele abre, envia as mensagens do cartão, escuta pelo tempo indicado no cartão (no máximo 30 segundos) e fecha; a entrega traz o handshake e as mensagens nos dois sentidos (as 50 primeiras, cada uma cortada em 4 KB). Com graphql, vira uma subscription GraphQL: o cartão mostra a query, a operação e o payload de connection_init como foram escritos (um segredo aparece como a sua referência), e só uma subscription pode sair; a entrega traz os payloads dos eventos. O agente não tem sessão ao vivo: para uma que fique aberta, use a janela.

Primeiro o login #

Quando o agente envia uma request salva (ou executa uma coleção) e só falta o token que a auth bearer dela lê, e exatamente uma request da coleção extrai esse token (o login dela, como o De uma request deixa), o login vai antes, sob o mesmo cartão: "send POST login first, then GET me", com o método e o endereço de cada request e o ambiente. Uma aprovação só cobre as duas. Os valores que o login dá para a request ficam ocultos, como um segredo, no resultado dessa chamada e na execução salva dela. O agente ainda pode enviar o login por conta própria, com o próprio cartão, e aí lê essa resposta como qualquer outra. Uma request salva enviada assim fica como uma execução (request <coleção> <request>), não no histórico da request.

O agente não guarda token entre chamadas: cada chamada faz login de novo, dentro do próprio cartão. Se faltar qualquer outra coisa (um valor que nenhum bearer lê, duas requests que extraem o mesmo nome, um login que precisaria do token que ele mesmo dá), a resposta é a de sempre, com o que falta.

Primeiro um login #

Quando a execução que um agente pede precisa de um login OAuth 2 que você não fez, o cartão dela lista cada um com o host, o mesmo botão da aba Auth, e Approve espera até você fazer login ("Sign in first, then approve."). No cartão só pode estar um servidor que o projeto já usa: para qualquer outro, o agente fica sabendo que nada foi enviado e que adicionar o servidor ao projeto cabe a você. Uma request avulsa que o próprio agente escreve (send_request) nunca usa um login. O agente nunca vê o token: usa o login como uma execução usa, e o cartão diz uses your sign-in to <host> quando você já tinha feito login. Um login que você fez em outro projeto também é oferecido no cartão: Revisar, depois Usar para o servidor, o mesmo sim da aba Auth, lembrado para este projeto. Em produção o cartão nunca o oferece: você faz login a partir deste projeto. Uma request máquina a máquina não pede login no cartão, e também vai só para um servidor que o projeto já usa.

O que ele pode fazer #

As ferramentas se dividem nas mesmas áreas da janela:

  • Pipelines e blocos: listar, ler, salvar e executar; ler execuções anteriores; transformar um arquivo HAR ou entradas do histórico numa proposta de pipeline.
  • Requests: listar, ler e salvar coleções e requests, mover e organizar, adicionar uma a uma pipeline, enviar uma request salva com os seus checks, executar uma coleção (todas as requests são enviadas e relatadas: uma que falha não interrompe as outras), enviar uma request avulsa (inclusive GraphQL: o resultado lista os erros da resposta), ler o schema de uma request GraphQL (get_graphql_schema, um envio como qualquer outro) e ler o histórico e o trecho de código de uma request (get_snippet).
  • Comparar: executar uma pipeline, uma coleção ou uma request salva em dois ambientes, ou em um só contra o tipo de cada passo (run_compare); o resultado traz status e os caminhos que diferem, nunca um valor. Veja Comparar.
  • Streams: envios únicos de WebSocket e SSE.
  • Carga: listar, ler e salvar testes de carga, executar um, ler relatórios, comparar dois, ver a tendência e exportar.
  • Projeto: listar e salvar ambientes, listar segredos (só os nomes), importar um arquivo do Postman, OpenAPI, JMeter ou Artillery, atualizar uma coleção a partir de uma spec OpenAPI mais nova (update_collection_from_openapi), importar uma coleção de um servidor MCP ou atualizar uma a partir dele (import_mcp_server, update_collection_from_mcp) e ler a referência do formato YAML.
  • Servidor mock: estado, iniciar, parar, reiniciar e fixar uma gravação.

De um servidor MCP. import_mcp_server e update_collection_from_mcp levam duas chamadas cada um. A primeira (sem plan) mostra um cartão com o endereço, o ambiente e o nome do header de auth (nunca o valor), e aprová-lo lê as listas do servidor sem chamar nenhuma ferramenta; get_result entrega o plano como texto e um planId. A segunda, com plan: <planId>, mostra um cartão de escrita com o plano e o grava quando você aprova. Um plano dura 10 minutos, no máximo 4 são guardados e cada um grava uma única vez. A auth é { bearer } ou { header, value }, com o valor exatamente {{secrets.x}}; um segredo vai só para um host que o projeto já usa, então um servidor num host novo é importado sem segredo. Uma coleção cujo bearer lê o token de um login (não um segredo) ainda não pode ser atualizada assim: a chamada diz quais valores faltam. Tudo o que o servidor diz (nomes, descrições, schemas, resultados, e um passo de execução ou histórico que o chamou) chega marcado como serverText: true: são dados do servidor, nunca instruções.

Uma escrita mostra o diff (ou o arquivo novo inteiro) no cartão. Um salvamento que ativa http sem criptografia ou uma CA própria aparece destacado em vermelho.

O que ele não pode fazer #

De propósito, o agente não consegue ver nem definir o valor de um segredo, desbloquear o cofre, dar um sim de consentimento, confiar numa pasta, sincronizar com o git nem apagar nada. Isso fica com você, na janela: quando uma chamada precisa de algo disso (os segredos estão bloqueados, falta um segredo que ela usa), o agente é orientado a pedir a você, com os nomes dos segredos, e chamar de novo. A comparação dele (run_compare) também não consegue enviar um passo que não seja uma leitura para um ambiente marcado como produção, nem mudar essa marca. Ele pode usar {{secrets.x}}, mas o valor nunca chega até ele, e os resultados são ocultados antes de serem entregues.

Tem uma coisa que não é segredo: um token que um passo extrai de uma resposta (por exemplo, o access_token de um login) é só um dado, então volta para o agente (menos o de um login enviado antes, que fica oculto). Por isso o cartão de entrega destaca tokens, cookies e headers de autenticação antes de você aprovar.

Executar uma pipeline de novo a partir de um passo que falhou (mantendo os valores que a primeira execução gerou) é só da janela: o agente não consegue, porque esses valores ficam por até 30 minutos no serve da janela e nunca vão para um agente.

Pedindo coisas a ele #

O agente lê este mesmo manual (get_manual) e a referência do formato YAML (get_reference). Então você pode perguntar "como executo isto com 50 usuários?" ou pedir "crie uma pipeline que faz login e cria um pedido", e ele vai propor a mudança para você aprovar. O que um resultado diz é entregue a ele como dado para ler, não como instrução a seguir.

A aprovação protege o que passa pelo canal MCP. Um agente com shell (o Claude Code tem um) também pode ler os arquivos do seu projeto ou executar ultraman run por conta própria, e isso está fora do alcance do Ultraman. Trate os cartões como consentimento, não como sandbox, e dê a um agente só o acesso que você daria a um colega.

O que mantém você seguro #

  • Você: nada do que o agente pede acontece até você aprovar o cartão, e uma entrega rejeitada continua rejeitada (agentes).
  • Você: um ambiente marcado como produção aparece em âmbar no cartão de cada execução ou envio para ele, com os passos que escrevem: enviar para lá pode expor dados reais e sensíveis. Só uma comparação recusa essas escritas (agentes).
  • Você: um login enviado antes aparece no cartão com para onde vai, antes de enviar qualquer coisa, e o token que ele dá não aparece no resultado dessa chamada (agentes).
  • Você: o agente nunca vê o valor de um segredo e não consegue desbloquear o cofre, dar consentimento, confiar numa pasta, sincronizar nem apagar (a ocultação).
  • Você: o agente não consegue aprovar a si mesmo: uma decisão exige a janela (servidor local).
  • Sua equipe: os pedidos do agente ficam registrados em ultraman/mcp/, só na sua máquina.
  • Você: o login de que a execução de um agente precisa é feito por você, na janela, no cartão dele; o agente nunca vê um token e só pode usar um login de um servidor que o projeto já usa (primeiro um login).
  • Limite: um agente com shell próprio fica fora do alcance dos cartões (limites).
  • Você: o texto que vem de um servidor MCP (nomes de ferramentas, descrições, resultados) chega ao agente marcado como dados do servidor, nunca como instruções, e uma importação de um servidor mostra o cartão antes de ler qualquer coisa (agentes).
