Agentes (MCP) #

Um agente de IA (o Claude Code ou qualquer outro cliente MCP) pode usar o Ultraman através de ultraman mcp. Ele faz o mesmo que você faz na janela: lê e escreve requests, pipelines e testes de carga, envia e executa, importa, inicia o servidor mock, lê relatórios e compara. Cada chamada passa pela sua aprovação.

Conectar #

ultraman mcp é um servidor MCP via stdio. No Claude Code:

claude mcp add ultraman -- ultraman mcp --project <your project folder>

Em qualquer outro cliente MCP, a configuração é a mesma, nas opções do próprio cliente: um servidor stdio com o comando ultraman e os argumentos mcp --project <your project folder>. Sem --project, o projeto é a pasta de onde você o inicia (ou a mais próxima acima dela que tenha ultraman/).

Duas condições precisam valer; senão, toda ferramenta responde "open Ultraman on this project to approve the agent's requests":

  • a janela do Ultraman está aberta nesse projeto, porque é nela que você aprova;
  • a pasta é confiável na janela (pastas confiáveis).

Você aprova cada chamada #

Cada pedido do agente aparece como um cartão no canto inferior direito: quem pede, o quê e os detalhes (numa alteração, o diff). Escolha Aprovar ou Rejeitar (com um motivo, que o agente lê). Pedidos só de leitura podem ser aprovados para "sempre"; isso vale só para a sessão atual do agente, e só enquanto o Ultraman continuar aberto.

O que executa algo (uma pipeline, uma request, uma carga) tem dois cartões: um para iniciar e outro para entregar o resultado ao agente. O cartão de entrega avisa quando o resultado traz tokens, cookies ou headers de autenticação. Se você rejeitar uma entrega, não tem volta.

Uma chamada dura no máximo uns 50 segundos, porque a maioria dos clientes corta uma chamada de ferramenta aos 60: uma execução longa segue ativa, e o agente pede o resultado depois. Enquanto um cartão espera por você, o agente recebe um aviso de progresso a cada 5 segundos. Todo pedido fica registrado em ultraman/mcp/, que o git ignora.

Um stream WebSocket ou SSE é enviado de uma vez só (send_stream, ou uma request de stream salva): ele abre, envia as mensagens do cartão, escuta pelo tempo indicado no cartão (no máximo 30 segundos) e fecha; a entrega traz o handshake e as mensagens nos dois sentidos (as 50 primeiras, cada uma cortada em 4 KB). Com graphql, vira uma subscription GraphQL: o cartão mostra a query, a operação e o payload de connection_init como foram escritos (um segredo aparece como a sua referência), e só uma subscription pode sair; a entrega traz os payloads dos eventos. O agente não tem sessão ao vivo: para uma que fique aberta, use a janela.

O que ele pode fazer #

As ferramentas se dividem nas mesmas áreas da janela:

  • Pipelines e blocos: listar, ler, salvar e executar; ler execuções anteriores; transformar um arquivo HAR ou entradas do histórico numa proposta de pipeline.
  • Requests: listar, ler e salvar coleções e requests, mover e organizar, adicionar uma a uma pipeline, enviar uma request salva com os seus checks, executar uma coleção, enviar uma request avulsa (inclusive GraphQL: o resultado lista os erros da resposta), ler o schema de uma request GraphQL (get_graphql_schema, um envio como qualquer outro) e ler o histórico.
  • Streams: envios únicos de WebSocket e SSE.
  • Carga: listar, ler e salvar testes de carga, executar um, ler relatórios, comparar dois, ver a tendência e exportar.
  • Projeto: listar e salvar ambientes, listar segredos (só os nomes), importar um arquivo do Postman, OpenAPI, JMeter ou Artillery, atualizar uma coleção a partir de uma spec OpenAPI mais nova (update_collection_from_openapi) e ler a referência do formato YAML.
  • Servidor mock: estado, iniciar, parar, reiniciar e fixar uma gravação.

Uma escrita mostra o diff (ou o arquivo novo inteiro) no cartão. Um salvamento que ativa http sem criptografia ou uma CA própria aparece destacado em vermelho.

O que ele não pode fazer #

De propósito, o agente não consegue ver nem definir o valor de um segredo, desbloquear o cofre, dar um sim de consentimento, confiar numa pasta, sincronizar com o git nem apagar nada. Isso fica com você, na janela. Ele pode usar {{secrets.x}}, mas o valor nunca chega até ele, e os resultados são ocultados antes de serem entregues.

Tem uma coisa que não é segredo: um token que um passo extrai de uma resposta (por exemplo, o access_token de um login) é só um dado, então volta para o agente. Por isso o cartão de entrega destaca tokens, cookies e headers de autenticação antes de você aprovar.

Pedindo coisas a ele #

O agente lê este mesmo manual (get_manual) e a referência do formato YAML (get_reference). Então você pode perguntar "como executo isto com 50 usuários?" ou pedir "crie uma pipeline que faz login e cria um pedido", e ele vai propor a mudança para você aprovar. O que um resultado diz é entregue a ele como dado para ler, não como instrução a seguir.

A aprovação protege o que passa pelo canal MCP. Um agente com shell (o Claude Code tem um) também pode ler os arquivos do seu projeto ou executar ultraman run por conta própria, e isso está fora do alcance do Ultraman. Trate os cartões como consentimento, não como sandbox, e dê a um agente só o acesso que você daria a um colega.

O que mantém você seguro #

  • Você: nada do que o agente pede acontece até você aprovar o cartão, e uma entrega rejeitada continua rejeitada (agentes).
  • Você: o agente nunca vê o valor de um segredo e não consegue desbloquear o cofre, dar consentimento, confiar numa pasta, sincronizar nem apagar (a ocultação).
  • Você: o agente não consegue aprovar a si mesmo: uma decisão exige a janela (servidor local).
  • Sua equipe: os pedidos do agente ficam registrados em ultraman/mcp/, só na sua máquina.
  • Limite: um agente com shell próprio fica fora do alcance dos cartões (limites).
