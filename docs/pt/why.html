Por que o Ultraman #

O Ultraman junta requests de API, fluxos de teste, testes de carga e checks de CI num só app local, salvos em arquivos simples no seu próprio repositório git. Esta página mostra em que ele difere das ferramentas que você talvez já use, e quando uma delas é a melhor escolha.

A ideia em poucas palavras #

O Ultraman combina com uma equipe que mantém os testes de API junto do código, revisa esses testes em pull requests e quer que um único arquivo sirva de teste manual, de check no CI e de cenário de carga.

  • Um arquivo, três usos. Uma pipeline, uma lista de passos visíveis, é ao mesmo tempo um teste que você executa na janela, um check no CI e um cenário num teste de carga.
  • Nada escondido em código. Os passos são requests, extracts, checks, esperas, repetições e ramificações que você consegue ler. O que cada passo faz está sempre na tela e no diff.
  • O seu repositório git é o lugar em comum. Sem conta e sem workspace: Sincronizar faz commit só das pastas do Ultraman, e a mudança num teste é revisada como qualquer mudança de código.
  • Os segredos continuam seus. Um segredo fica num cofre criptografado no seu computador e só vai para os hosts a que você disse sim.

As comparações abaixo tratam da abordagem e foram conferidas na documentação de cada ferramenta em novembro de 2026. Ferramentas mudam: o que elas fazem hoje está na documentação delas.

Postman #

O Postman é uma plataforma de API ampla, construída em torno de workspaces de equipe. O Ultraman cobre a parte dele que envia e testa requests HTTP, e soma fluxos, carga e CI que ficam no seu repositório.

  • Onde os testes ficam. Coleções, pipelines, ambientes e testes de carga são arquivos YAML dentro de ultraman/, e o git é a única forma de compartilhá-los. Um pull request mostra exatamente o que mudou. Veja Trabalho em equipe.
  • Checks sem scripts. O Postman executa JavaScript antes e depois de uma request. No Ultraman, um check é um passo que você lê ("status é 201", "$.id existe"), e um valor passa de uma resposta para a request seguinte por um extract visível. Veja Checks.
  • Fluxos que você enxerga. Uma pipeline aparece como lista e como diagrama, com uma seta do passo que gera um valor até o passo que o usa. Veja Pipelines.
  • Carga a partir do mesmo arquivo. O Postman também consegue executar uma coleção com muitos usuários virtuais. No Ultraman, um teste de carga é um arquivo no repositório, com etapas, dados e cookies por usuário, um modelo de taxa de chegada, controles durante a execução e um veredito que avisa quando o limite foi o seu próprio computador. Veja Carga.

Onde o Postman se sai melhor: muito mais protocolos (gRPC, Socket.IO, MQTT e outros); scripts para qualquer lógica que dê para escrever em JavaScript; e colaboração hospedada, em que uma empresa inteira compartilha e discute o trabalho em workspaces.

Bruno, Insomnia e Hoppscotch #

Estes são clientes de requests: você monta, organiza e envia requests, e também pode executá-las pela linha de comando. O Bruno parte do mesmo ponto que o Ultraman: coleções em arquivos de texto que você guarda no git.

  • Um fluxo acima da request. No Ultraman, passar um valor de uma resposta para a request seguinte é um passo que dá para ler, não um script, e o fluxo inteiro vira um diagrama. Veja Pipelines.
  • Carga no mesmo app. A pipeline que você envia à mão também executa sob carga, com um veredito por extenso. Não há uma segunda ferramenta nem um segundo formato para manter em sincronia. Veja Carga.
  • Segredos com consentimento. Os segredos vêm de um cofre criptografado, aparecem como [secret:name] em toda resposta, entrada do histórico e exportação, e o primeiro envio para um host novo pede a sua confirmação. Veja Segurança e consentimento.
  • Mudanças de forma. O Ultraman avisa quando a forma de uma resposta muda em relação à última vez que você a enviou. Veja Mudanças de contrato.

Onde eles se saem melhor: requests gRPC (Bruno e Insomnia), Socket.IO e MQTT (Hoppscotch); scripts em JavaScript nos três; o Hoppscotch funciona no navegador sem instalar nada e pode ser hospedado nos seus próprios servidores; o Insomnia tem plugins.

k6 #

O k6 é uma ferramenta de teste de carga em que o teste é um programa em JavaScript ou TypeScript. As duas ferramentas oferecem modelos fechados (um número de usuários virtuais) e abertos (uma taxa de chegada), além de limiares que fazem um build de CI falhar.

  • Sem código. No Ultraman, um teste de carga é um arquivo YAML curto que indica uma pipeline e as etapas dela. Você monta a pipeline numa janela e a testa passo a passo antes de colocar carga nela. Veja O formato da carga.
  • Um arquivo para tudo. A pipeline que você põe sob carga é a mesma que você envia à mão e executa no CI, então uma mudança chega aos três de uma vez.
  • Um veredito por extenso. O relatório diz se a API aguentou, enfileirou, rejeitou ou quebrou, e diz limited quando o gargalo foi o seu próprio computador, em vez de pôr a culpa na API. Veja O relatório.
  • Comande durante a execução. Adicione ou remova usuários, pause e retome sem parar; depois, compare o relatório com um anterior ou veja a tendência das últimas execuções. Veja Durante a execução.

Onde o k6 se sai melhor: lógica de qualquer tipo, escrita em código; gRPC, e mais protocolos por meio de extensões; testes de performance com um navegador de verdade; e carga distribuída por muitas máquinas (no Kubernetes ou no Grafana Cloud).

JMeter #

O JMeter é uma ferramenta de teste de carga em Java, com um editor desktop para planos de teste e um modo de linha de comando para executá-los.

  • Arquivos legíveis. Um teste de carga do Ultraman tem poucas linhas de YAML, fáceis de revisar num pull request. Um plano do JMeter é um arquivo .jmx; o Ultraman o importa e lista o que não consegue converter. Veja Do JMeter.
  • O mesmo fluxo para teste funcional e de carga. A pipeline sob carga é a mesma que o seu CI executa a cada mudança.
  • Um relatório que se explica. Um veredito por extenso, onde o tempo foi gasto, erros por passo com uma request com falha guardada para cada um, limiares que aprovam ou reprovam a execução. Veja O relatório.
  • Segredos fora dos arquivos. Um segredo fica num cofre criptografado e nunca é gravado nos arquivos que você commita. Veja O cofre.

Onde o JMeter se sai melhor: muito mais protocolos (bancos de dados via JDBC, JMS, LDAP, FTP, e-mail, TCP); scripts em Groovy e outras linguagens da JVM; testes distribuídos, em que um controlador comanda muitas máquinas remotas; e plugins.

Artillery #

O Artillery descreve testes em YAML, com lógica própria em JavaScript. É o formato mais próximo do Ultraman: um script do Artillery pode ser importado, as fases viram etapas, capture vira um extract e ensure vira limiares. Veja Se você vem do Artillery.

  • Uma janela em volta do YAML. O diagrama, Enviar para um passo só, Gerar checks, o histórico, uma área de Requests para explorar a API e um servidor mock local, tudo sobre os mesmos arquivos. Veja Lista e diagrama.
  • Os relatórios ficam com você. Cada relatório de carga fica guardado na sua máquina; compare com um anterior, veja a tendência ou exporte em HTML ou CSV, sem precisar se cadastrar em nenhum serviço. Veja O relatório.
  • Segredos com consentimento. Os segredos vêm de um cofre criptografado e precisam do seu sim para cada host novo. Veja Segurança e consentimento.
  • Um arquivo, três usos. O cenário que você põe sob carga é uma pipeline que você também executa à mão e no CI.

Onde o Artillery se sai melhor: lógica própria em JavaScript com qualquer pacote npm; Socket.IO; carga com navegadores de verdade via Playwright; testes distribuídos em serviços de nuvem (AWS Lambda, AWS Fargate, Azure Container Instances); um painel hospedado para equipes; e plugins.

Quando escolher outra ferramenta #

O Ultraman não é a ferramenta certa se você precisa de:

  • lógica escrita em código: o Ultraman não tem scripts, de propósito (veja Por que não há scripts);
  • gRPC, Socket.IO, MQTT, bancos de dados ou outros protocolos: o Ultraman fala HTTP (inclusive GraphQL), WebSocket e SSE (veja Quais protocolos);
  • carga gerada de várias máquinas ou da nuvem: o Ultraman gera carga a partir de um só computador, em até 8 threads (veja Mais de uma thread);
  • carga com navegadores de verdade;
  • contas, papéis e permissões num workspace hospedado: no Ultraman, o controle de acesso é o seu repositório git (veja Permissões);
  • fluxos OAuth2, certificados de cliente, AWS SigV4 ou NTLM (veja Autenticação);
  • uma ferramenta no navegador, sem nada para instalar.
