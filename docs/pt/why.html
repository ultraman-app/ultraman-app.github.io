Por que o Ultraman #

O Ultraman reúne requests de API, fluxos de teste, testes de carga e checks de CI num só app local, salvos como arquivos simples no seu próprio repositório git. Esta página diz como isso difere das ferramentas que você talvez já use, e quando uma delas é a melhor escolha.

A ideia em resumo #

O Ultraman serve a uma equipe que guarda seus testes de API junto do código, os revisa em pull requests, e quer que um só arquivo sirva como teste manual, check de CI e cenário de carga.

  • Um arquivo, três usos. Uma pipeline, uma lista de passos visíveis, é um teste que você roda na janela, um check no CI e um cenário num teste de carga.
  • Nada escondido em código. Os passos são requests, extracts, checks, esperas, repetições e ramos que você consegue ler. O que um passo faz está sempre na tela e no diff.
  • O seu repositório git é o lugar compartilhado. Sem conta e sem workspace: Sincronizar faz commit só das pastas do Ultraman, e uma mudança num teste se revisa como qualquer mudança em código.
  • Os segredos continuam seus. Um segredo vive num cofre criptografado no seu computador e vai só para hosts a que você disse sim.

As comparações abaixo tratam de abordagem e foram conferidas na documentação de cada ferramenta em novembro de 2026. As ferramentas mudam: a documentação delas diz o que fazem hoje.

Postman #

O Postman é uma plataforma de API ampla, construída em torno de workspaces de equipe. O Ultraman cobre a parte dela que envia e testa requests HTTP, e acrescenta fluxos, carga e CI que vivem no seu repositório.

  • Onde os testes vivem. Coleções, pipelines, ambientes e testes de carga são arquivos YAML dentro de ultraman/, e o git é o único jeito de compartilhá-los. Um pull request mostra exatamente o que mudou. Veja Trabalho em equipe.
  • Checks sem scripts. O Postman roda JavaScript antes e depois de uma request. No Ultraman um check é um passo que você lê ("status é 201", "$.id existe"), e um valor vai de uma resposta para a request seguinte por um extract visível. Veja Checks.
  • Fluxos que você vê. Uma pipeline aparece como lista e como diagrama, com uma seta do passo que produz um valor até o passo que o usa. Veja Pipelines.
  • Carga a partir do mesmo arquivo. O Postman também consegue rodar uma coleção com muitos usuários virtuais. No Ultraman um teste de carga é um arquivo no repositório, com etapas, dados e cookies por usuário, um modelo de taxa de chegada, controles enquanto roda, e um veredito que avisa quando o limite foi o seu próprio computador. Veja Carga.

Onde o Postman é a melhor escolha: muito mais protocolos (GraphQL, gRPC, Socket.IO, MQTT, SOAP e outros); scripts para qualquer lógica que você consiga escrever em JavaScript; e colaboração hospedada, em que uma empresa inteira compartilha e discute o trabalho em workspaces.

Bruno, Insomnia e Hoppscotch #

Estes são clientes de requests: você monta, organiza e envia requests, e também as executa por linha de comando. O Bruno compartilha o ponto de partida do Ultraman, coleções como arquivos de texto que você guarda no git.

  • Um fluxo acima da request. No Ultraman, passar um valor de uma resposta para a request seguinte é um passo que você consegue ler, não um script, e o fluxo inteiro se desenha como diagrama. Veja Pipelines.
  • Carga no mesmo app. A pipeline que você envia à mão também roda sob carga, com um veredito em palavras. Não há uma segunda ferramenta nem um segundo formato para manter em sincronia. Veja Carga.
  • Segredos com consentimento. Os segredos vêm de um cofre criptografado, aparecem como [secret:name] em toda resposta, entrada de histórico e exportação, e o primeiro envio para um host novo pergunta a você. Veja Segurança e consentimento.
  • Mudanças de forma. O Ultraman avisa quando a forma de uma resposta muda em relação à última vez que você a enviou. Veja Mudanças de contrato.

Onde eles são a melhor escolha: requests GraphQL e gRPC (Bruno e Insomnia), Socket.IO e MQTT (Hoppscotch); scripts em JavaScript nos três; o Hoppscotch roda no navegador sem nada para instalar, e pode ser hospedado nos seus próprios servidores; o Insomnia tem plugins.

k6 #

O k6 é uma ferramenta de teste de carga em que um teste é um programa em JavaScript ou TypeScript. As duas ferramentas oferecem modelos fechados (um número de usuários virtuais) e abertos (uma taxa de chegada), e limiares que fazem um build de CI falhar.

  • Sem código. No Ultraman um teste de carga é um arquivo YAML curto que nomeia uma pipeline e suas etapas. Você monta a pipeline numa janela e a testa um passo por vez antes de pôr carga nela. Veja O formato da carga.
  • Um arquivo para todo uso. A pipeline que você carrega é a que você envia à mão e roda no CI, então uma mudança chega aos três de uma vez.
  • Um veredito em palavras. O relatório diz se a API aguentou, enfileirou, rejeitou ou quebrou, e diz limited quando o gargalo foi o seu próprio computador, em vez de culpar a API. Veja O relatório.
  • Conduza enquanto roda. Adicione ou remova usuários, pause e retome sem parar; depois compare o relatório com um anterior ou veja a tendência das últimas execuções. Veja Enquanto roda.

Onde o k6 é a melhor escolha: lógica de qualquer tipo, escrita como código; gRPC, e mais protocolos por extensões; testes de performance por um navegador de verdade; e carga distribuída em muitas máquinas (no Kubernetes, ou no Grafana Cloud).

JMeter #

O JMeter é uma ferramenta de teste de carga em Java, com um editor desktop para planos de teste e um modo de linha de comando para executá-los.

  • Arquivos legíveis. Um teste de carga do Ultraman são poucas linhas de YAML que se revisam num pull request. Um plano do JMeter é um arquivo .jmx; o Ultraman importa um e lista o que não consegue traduzir. Veja Do JMeter.
  • O mesmo fluxo para testes funcionais e de carga. A pipeline sob carga é a que o seu CI roda a cada mudança.
  • Um relatório que se explica. Um veredito em palavras, para onde foi o tempo, erros por passo com uma request falha guardada para cada um, limiares que aprovam ou reprovam a execução. Veja O relatório.
  • Segredos fora dos arquivos. Um segredo vive num cofre criptografado e nunca é escrito nos arquivos que você commita. Veja O cofre.

Onde o JMeter é a melhor escolha: muito mais protocolos (bancos de dados via JDBC, JMS, LDAP, FTP, e-mail, TCP); scripts em Groovy e outras linguagens da JVM; testes distribuídos, em que um controlador comanda muitas máquinas remotas; e plugins.

Artillery #

O Artillery descreve testes em YAML, com lógica própria em JavaScript. É o mais próximo do formato do Ultraman: um script do Artillery é importado, as fases viram etapas, capture vira um extract e ensure vira limiares. Veja Se você vem do Artillery.

  • Uma janela em volta do YAML. O diagrama, Enviar para um passo só, Gerar checks, o histórico, uma área de Requests para explorar a API e um servidor mock local, tudo sobre os mesmos arquivos. Veja Lista e diagrama.
  • Os relatórios ficam com você. Cada relatório de carga é guardado na sua máquina; compare-o com um anterior, veja a tendência ou exporte-o como HTML ou CSV, sem nenhum serviço para se cadastrar. Veja O relatório.
  • Segredos com consentimento. Os segredos vêm de um cofre criptografado e precisam do seu sim para cada host novo. Veja Segurança e consentimento.
  • Um arquivo, três usos. O cenário que você carrega é uma pipeline que você também roda à mão e no CI.

Onde o Artillery é a melhor escolha: lógica própria em JavaScript com qualquer pacote npm; Socket.IO; carga por navegadores de verdade com Playwright; testes distribuídos em serviços de nuvem (AWS Lambda, AWS Fargate, Azure Container Instances); um painel hospedado para equipes; e plugins.

Quando escolher outra coisa #

O Ultraman não é a ferramenta certa se você precisa de:

  • lógica escrita em código: o Ultraman não tem scripts, de propósito (veja Por que sem scripts);
  • gRPC, um cliente GraphQL dedicado, Socket.IO, MQTT, bancos de dados ou outros protocolos: o Ultraman fala HTTP, WebSocket e SSE (veja Quais protocolos);
  • carga a partir de várias máquinas ou da nuvem: o Ultraman gera carga a partir de um computador, em até 8 threads (veja Mais de uma thread);
  • carga por navegadores de verdade;
  • contas, papéis e permissões num workspace hospedado: o controle de acesso do Ultraman é o seu repositório git (veja Permissões);
  • fluxos OAuth2, certificados de cliente, AWS SigV4 ou NTLM (veja Autenticação);
  • uma ferramenta no navegador sem nada para instalar.
