Carga #

Carga (ao lado de Executar) diz quantos usuários, ou quanto tráfego, sua API aguenta antes de ficar lenta ou falhar. Ela abre a tela de carga da pipeline que está na tela: cada usuário virtual roda a pipeline inteira em loop, e se um passo falha, aquela volta conta como erro e o usuário começa outra.

Envie carga só para uma API sua, ou para uma que você tenha permissão de testar. A tela de carga mostra o alvo antes de você começar e diz o mesmo.

Um teste de carga é um arquivo #

A configuração vive em ultraman/load-tests/<nome>.yaml, compartilhada pelo git, assim o mesmo teste roda igual para todos. Na primeira vez, Carga cria um com 10 usuários durante 30 segundos.

A forma da carga #

Os presets desenham os usuários previstos enquanto você digita:

PresetForma
Constanteos mesmos usuários o tempo todo
Subida e sustentaçãocresce, se mantém, desce (o thread group do JMeter)
Rampacresce de 0 até os usuários
Picouma base e um pico repentino
Taxa de chegadaN iterações novas por segundo, demore o que a API demorar (o arrivalRate do Artillery)
Personalizadosuas próprias etapas

Usuários (modelo fechado) responde "aguenta essa quantidade de gente?". Taxa de chegada (modelo aberto) responde "aguenta esse tráfego?": se a API fica lenta, as chegadas continuam vindo, como em produção.

Com taxa de chegada, cada chegada é um usuário novo que roda uma iteração. Máximo de usuários (maxUsers, 100 se o teste não disser outra coisa, no máximo 1000) é quantos podem estar vivos ao mesmo tempo. Uma chegada que encontra todos ocupados é descartada, nunca enfileirada, e o relatório a conta. Se mais de 1% das chegadas é descartado, o veredito diz que a taxa não foi alcançada. O relatório então tem duas latências: o tempo de serviço (do envio até a resposta) e o tempo de resposta, contado desde quando a chegada estava prevista, de modo que uma largada lenta neste computador aparece nele.

Por usuário #

Em Mais:

  • Bloco de preparação: roda uma vez por usuário antes da primeira volta (fazer login uma vez por usuário).
  • Antes e depois: um bloco uma vez por teste (carregar dados, limpar).
  • Cookies: cada usuário tem o seu próprio pote de cookies.
  • Arquivo de dados: um CSV ou JSON dentro do projeto; cada linha são os valores de um usuário (ou de uma volta).
  • Pausa e ritmo: pausas entre voltas, e um tempo mínimo por volta.
  • Respostas: por padrão só ficam os bodies que um check ou extract lê, para economizar memória.

Enquanto roda #

Indicadores e gráficos ao vivo mostram requests por segundo, latência, erros e usuários. −N, +N, Manter e Retomar mudam a carga sem parar. A faixa Este computador vigia a sua própria máquina: se o gerador for o gargalo, o veredito diz limited em vez de culpar a API.

O veredito #

O relatório começa com um veredito em palavras. Eles são:

VereditoEm palavras simplesMais ou menos quando
Aguentaa API deu contamenos de 1% das iterações falhou e a latência não subiu conforme os usuários cresceram
Enfileiraa API ficou mais lenta em vez de falharo p95 do último quinto do teste é mais de cinco vezes o do primeiro quinto e pelo menos 50 ms maior, e as requests por segundo pararam de crescer com os usuários; num teste de taxa de chegada, também quando mais de 1% das chegadas foi descartado
Rejeitaa API respondeu errosmais de 1% das iterações falhou; diz quando os erros começaram e com quantos usuários
Quebradao problema é a pipeline ou o endereço, não a cargaas primeiras 20 iterações falharam todas; "O destino recusa conexões" quando o servidor não está acessível
Poucas iteraçõesnão há o bastante para concluirmenos de 20 iterações rodaram; aumente o tempo ou os usuários
Limitadoeste computador foi o limite, então os números dizem pouco sobre a APIa thread, a memória ou as conexões do próprio Ultraman estavam no limite
Protegidoo Ultraman parou o teste para proteger este computadora memória estava acabando; o que foi medido até ali está no relatório

Uma carga nunca diz "aguenta" num computador que estava no limite: diz Limitado. A faixa Este computador mostra o motivo.

O relatório #

No fim, um veredito em palavras (aguentou, enfileirou, quebrou…), as latências (p50, p95, p99, máx), o throughput, os erros por passo com uma request falha guardada para cada um, para onde foi o tempo e APDEX se o teste pedir.

  • Os limiares (p95: 500ms, errors: 1%) aprovam ou reprovam a execução; os níveis warn só avisam.
  • Comparar com coloca um relatório contra um anterior; Tendência mostra as últimas execuções do teste.
  • Exportar escreve uma página HTML autocontida ou arquivos CSV.

Respostas que não podem mudar #

Nas Opções de uma request, responde sempre o mesmo marca uma request que deve dar a mesma resposta toda vez (uma página de produto, uma consulta). Sob carga, cada resposta, status e body, é comparada com a primeira da mesma request. Uma diferente faz aquela iteração falhar, e o relatório mostra quantas vezes e as duas respostas. Ignorar campos ($.timestamp, $.meta.requestId) deixa de fora o que muda de propósito. No YAML é idempotent: true ou idempotent: { ignore: [$.timestamp] }. Quando um teste descarta os bodies das respostas, não há o que comparar, e o relatório diz "not compared".

Streams sob carga #

Uma pipeline com passos websocket ou sse é um cenário de carga como qualquer outro: cada iteração abre a sua própria conexão, roda send e receive nela e a fecha (ou o motor a fecha no fim da iteração). Dez usuários que seguram um socket por vinte segundos cada um esperando três atualizações são um repeat em volta de um receive; a demo tem esse teste como live orders.

Com streams no teste, o relatório ganha uma faixa Streams embaixo dos indicadores: conexões abertas, quantas estavam abertas ao mesmo tempo e quantas ainda abertas no fim (deveria ser 0), mensagens recebidas e enviadas, mensagens por segundo, quantos streams o servidor fechou (com o código de fechamento mais comum) e quantas mensagens um limite de tamanho deixou de fora. O gráfico de Usuários desenha as conexões abertas como uma linha pontilhada. Uma linha receive na tabela de passos informa o tempo até a mensagem, a latência do stream, com seu próprio p95 e taxa de erro.

  • streamErrors: 0% é um limiar sobre as conexões que o servidor fechou durante a execução e as mensagens que descartou; steps: { update: { p95: 3s } } limita um receive pelo nome.
  • Cada stream guarda no máximo 1 MB em buffer sob carga, e o leitor espera quando ele enche.
  • Exportar e --csv acrescentam -streams.csv com os números da faixa.
  • O veredito limited vale aqui também: uma contagem de conexões é um limite da máquina como qualquer outro.

Vários cenários #

Um teste pode misturar pipelines: três pessoas navegando para cada uma que fecha a compra. Cada cenário tem suas próprias etapas, ou compartilham as do teste divididas por peso. O relatório tem uma linha e um veredito por cenário.

Mais de uma thread #

Por padrão uma carga roda numa thread. Quando a faixa Este computador mostra a thread no limite e o veredito diz limited, espalhe os usuários por mais threads: --workers N (1 a 8) em ultraman run --load, ou a variável de ambiente ULTRAMAN_LOAD_WORKERS; os relatórios se juntam num só. Um teste com um bloco antes ou depois roda numa thread.

O que mantém você seguro #

A promessa vale aqui como em todo lugar. O que esta parte acrescenta:

  • Quem é dono da API: o alvo é mostrado antes de o teste começar, com um lembrete para testar só uma API sua.
  • Você: freios seguram ou param usuários quando o seu computador está sobrecarregado ou com pouca memória, em vez de travá-lo.
  • Seu time: um teste de carga nunca guarda um segredo; os inputs dele não podem levar valores secrets. ou env.. Os relatórios em ultraman/loads/ ficam na sua máquina. Veja onde as coisas ficam guardadas.
