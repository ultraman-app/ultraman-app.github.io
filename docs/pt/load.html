Carga #

Carga (ao lado de Executar) mostra quantos usuários, ou quanto tráfego, a sua API aguenta antes de ficar lenta ou começar a falhar. Abre a tela de carga da pipeline que você está vendo: cada usuário virtual executa a pipeline inteira em loop e, se um passo falha, aquela iteração conta como erro e o usuário começa outra.

Só mande carga para uma API sua ou para uma que você tenha permissão para testar. A tela de carga mostra o alvo antes de você começar e lembra a mesma coisa.

Um teste de carga é um arquivo #

As configurações ficam em ultraman/load-tests/<nome>.yaml, compartilhado pelo git, então o mesmo teste executa do mesmo jeito para todo mundo. Na primeira vez, Carga cria um com 10 usuários por 30 segundos.

Uma pipeline pode ter vários testes. Novo teste… salva o que está na tela com outro nome, e Apagar remove o teste selecionado. O teste da própria pipeline, que é o que Carga abre, não pode ser apagado pela janela. As alterações que você não salvou continuam lá quando você volta à tela de carga, e fechar a janela pergunta antes.

Os Limiares são linhas embaixo da forma da carga: um limite para o teste inteiro ou para uma request, como p95, erros ou requests/s, que reprova a execução ou só avisa. Um tempo precisa da unidade (500ms, 2s).

A forma da carga #

Os presets desenham os usuários previstos enquanto você digita:

PresetForma
Constanteos mesmos usuários do começo ao fim
Subida e sustentaçãosobe, se mantém, desce (o thread group do JMeter)
Rampasobe de 0 até o número de usuários
Picouma base e um pico repentino
Taxa de chegadaN iterações novas por segundo, demore o que a API demorar (o arrivalRate do Artillery)
Personalizadoas suas próprias etapas

Usuários (modelo fechado) responde "aguenta essa quantidade de pessoas?". Taxa de chegada (modelo aberto) responde "aguenta esse tráfego?": se a API fica lenta, as chegadas continuam vindo, como em produção.

Com taxa de chegada, cada chegada é um usuário novo que executa uma iteração. Máximo de usuários (maxUsers, 100 se o teste não disser outro valor, no máximo 1000) é quantos podem estar vivos ao mesmo tempo. A chegada que encontra todos ocupados é descartada, nunca entra numa fila, e o relatório conta isso. Se mais de 1% das chegadas for descartado, o veredito diz que a taxa não foi alcançada. O relatório traz então duas latências: o tempo de serviço (do envio até a resposta) e o tempo de resposta, contado a partir do momento em que a chegada estava prevista, então uma largada lenta neste computador aparece nele.

Por usuário #

Em Mais:

  • Bloco de preparação: executa uma vez por usuário, antes da primeira iteração (para fazer login uma vez por usuário).
  • Antes e depois: um bloco que executa uma vez por teste (carregar dados, limpar).
  • Cookies: cada usuário guarda os seus próprios cookies.
  • Arquivo de dados: um CSV ou JSON dentro do projeto; cada linha traz os valores de um usuário (ou de uma iteração).
  • Pausa, máximo e ritmo: uma pausa aleatória entre a pausa entre iterações (ao lado dos usuários) e este máximo, e um tempo mínimo por iteração.
  • Respostas: por padrão, só ficam guardados os bodies que um check ou extract lê, para economizar memória.

Durante a execução #

Indicadores e gráficos ao vivo mostram requests por segundo, latência, erros e usuários. −N, +N, Manter e Retomar mudam a carga sem parar o teste. A faixa Este computador acompanha a sua própria máquina: se o gargalo for o gerador, o veredito diz limited em vez de pôr a culpa na API.

O veredito #

O relatório começa com um veredito em palavras. São estes:

VereditoEm palavras simplesMais ou menos quando
Aguentaa API deu contamenos de 1% das iterações falhou e a latência não subiu conforme os usuários aumentaram
Enfileiraa API ficou mais lenta em vez de falharo p95 do último quinto do teste passa de cinco vezes o do primeiro quinto e é pelo menos 50 ms maior, e as requests por segundo pararam de crescer junto com os usuários; num teste de taxa de chegada, também quando mais de 1% das chegadas foi descartado
Rejeitaa API respondeu com errosmais de 1% das iterações falhou; ele diz quando os erros começaram e com quantos usuários
Quebradao problema é a pipeline ou o endereço, não a cargatodas as 20 primeiras iterações falharam; "O destino recusa conexões" quando o servidor não está acessível
Poucas iteraçõespouco para tirar conclusõesexecutaram menos de 20 iterações; aumente o tempo ou os usuários
Limitadoo limite foi este computador, então os números dizem pouco sobre a APIa thread, a memória ou as conexões do próprio Ultraman chegaram ao limite
Protegidoo Ultraman parou o teste para proteger este computadora memória estava acabando; o que ele mediu até ali está no relatório

Uma carga nunca diz "aguenta" num computador que estava no limite: diz Limitado. A faixa Este computador mostra o porquê.

O relatório #

No fim, vêm um veredito em palavras (aguentou, enfileirou, quebrou…), as latências (p50, p95, p99, máx.), o throughput, os erros por passo com uma request com falha guardada para cada um, para onde foi o tempo e o APDEX, se o teste pedir.

  • Os limiares (p95: 500ms, errors: 1%) aprovam ou reprovam a execução; os níveis warn só avisam.
  • Comparar com compara um relatório com um anterior; Cargas anteriores mostra as últimas execuções do teste em três linhas (p95, requests/s, erros).
  • Exportar (no cabeçalho do relatório) gera uma página HTML autocontida ou arquivos CSV.

GraphQL. Uma resposta com errors conta como request com falha, mesmo com um 200 e também com responses: discard (o body é lido para achar os erros e depois descartado). Todas as operações vão para a mesma URL, mas o relatório é por passo: dê a cada passo GraphQL o nome da operação dele, e cada um ganha a sua própria linha.

Respostas que não podem mudar #

Nas Opções de uma request, responde sempre o mesmo marca uma request que deve dar sempre a mesma resposta (uma página de produto, uma consulta). Sob carga, cada resposta, status e body, é comparada com a primeira da mesma request. Se vier diferente, aquela iteração falha, e o relatório mostra quantas vezes isso aconteceu e as duas respostas. Ignorar campos ($.timestamp, $.meta.requestId) deixa de fora o que muda de propósito. No YAML, fica idempotent: true ou idempotent: { ignore: [$.timestamp] }. Quando um teste descarta os bodies das respostas, não há o que comparar, e o relatório diz "sem comparar".

Streams sob carga #

Uma pipeline com passos websocket ou sse é um cenário de carga como qualquer outro: cada iteração abre a sua própria conexão, executa send e receive nela e fecha a conexão (ou o motor fecha no fim da iteração). Dez usuários que seguram um socket por vinte segundos, cada um esperando três atualizações, viram um repeat em volta de um receive; a demo tem esse teste como live orders.

Com streams no teste, o relatório ganha uma faixa Streams embaixo dos indicadores: conexões abertas, quantas ficaram abertas ao mesmo tempo e quantas ainda estavam abertas no fim (deveria ser 0), mensagens recebidas e enviadas, mensagens por segundo, quantos streams o servidor fechou (com o código de fechamento mais comum) e quantas mensagens ficaram de fora por um limite de tamanho. O gráfico de Usuários desenha as conexões abertas como uma linha pontilhada. Uma linha receive na tabela de passos mostra o tempo até a mensagem, a latência do stream, com p95 e taxa de erro próprios.

Quando a pipeline só abre streams (nenhuma request própria foi executada; um login no bloco de preparação não conta), o relatório começa por eles: os indicadores mostram o tempo até a mensagem do receive com mais correspondências (o handshake, quando não há receive), as mensagens por segundo e as mensagens; os dois primeiros gráficos são esse p95 e as mensagens por segundo; e o veredito vai na mesma linha. Ele diz Enfileira quando o tempo até uma mensagem cresce enquanto as mensagens por segundo não acompanham os usuários, e limited informa as mensagens por segundo que alcançou. Uma carga com requests mantém os indicadores de requests.

  • streamErrors: 0% é um limiar sobre as conexões que o servidor fechou no meio da execução, os handshakes que falharam e as mensagens descartadas, em relação às conexões tentadas; steps: { update: { p95: 3s } } limita um receive pelo nome.
  • Sob carga, cada stream guarda no máximo 1 MB em buffer (menos quando o limite por resposta da carga é menor; uma nota diz qual), e o leitor espera quando o buffer enche.
  • Com vários workers, o pico de conexões abertas é contado uma vez por segundo, por isso aparece como ≥ N: no mínimo N.
  • Exportar e --csv acrescentam -streams.csv com os números da faixa.
  • O veredito limited vale aqui também: o número de conexões é um limite da máquina como qualquer outro.
  • Um socket GraphQL é uma só conexão, não importa quantas subscriptions ele tenha: a faixa ganha Assinaturas GraphQL, uma linha subscribe mostra o tempo para enviá-la e o receive de uma subscription mostra o tempo até o próximo evento dela.

Vários cenários #

Um teste pode misturar pipelines: três pessoas navegando para cada uma que finaliza a compra. Cada cenário tem as próprias etapas, ou todos dividem as etapas do teste conforme o peso. O relatório tem uma linha e um veredito por cenário.

Mais de uma thread #

Por padrão, uma carga é executada numa thread só. Quando a faixa Este computador mostra a thread no limite e o veredito diz limited, distribua os usuários por mais threads: --workers N (de 1 a 8) em ultraman run --load, ou a variável de ambiente ULTRAMAN_LOAD_WORKERS; os relatórios se juntam num só. Um teste com bloco antes ou depois é executado numa thread só.

O que mantém você seguro #

A promessa vale aqui como em qualquer lugar. O que esta parte acrescenta:

  • Quem é dono da API: o alvo aparece antes de o teste começar, com um lembrete para testar só uma API sua.
  • Você: freios seguram ou param usuários quando o seu computador fica sobrecarregado ou com pouca memória, em vez de deixá-lo travar.
  • Sua equipe: um teste de carga nunca guarda um segredo; os inputs dele não podem levar valores secrets. nem env.. Os relatórios em ultraman/loads/ ficam na sua máquina. Veja onde as coisas ficam guardadas.
