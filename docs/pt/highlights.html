O que o Ultraman oferece #

O Ultraman testa APIs HTTP, inclusive WebSocket e SSE: um único app no seu computador para requests avulsas, testes de vários passos, carga e CI, tudo salvo em arquivos simples no seu próprio repositório git. Ele nunca envia nada de forma insegura sem o seu consentimento explícito: um segredo só vai para um host que você aprovou, e uma pasta em que você ainda não confia não envia nada.

Cada parte abaixo conta o que ela resolve para você e onde ler mais. Se preferir começar pela sua função, vá direto para Por onde começar.

Pipelines que você enxerga #

Uma pipeline é um teste escrito como uma lista de passos: fazer login, pegar o token da resposta, criar um pedido, conferir se ele aparece. O resultado é um teste que se lê como uma frase: cada passo é uma linha ("token ← $login $.token"), e a mesma pipeline aparece como diagrama, com uma seta da request que gera um valor até a que o usa. Ela fica salva em YAML no seu repositório, então qualquer mudança num teste é revisada num pull request, como o resto do código. → Pipelines

Requests como no Postman, com memória #

Para quando você só quer testar uma chamada: coleções, pastas, abas, Enviar. Cada request guarda os próprios checks, e cada envio vai para o histórico com o tempo que levou, então dá para ver o que um endpoint respondeu ontem. Se a forma de uma resposta muda em relação à anterior, o Ultraman avisa. Streams WebSocket e SSE abrem numa aba só para eles. → Requests

Teste de carga de verdade #

A pipeline que você já tem, executada por muitos usuários virtuais ou numa taxa de chegada fixa: você descobre como a sua API se comporta sob carga sem escrever um segundo teste. Rampas, platôs, tempo de pensar, dados e cookies por usuário, vários cenários combinados por peso, até 8 threads numa só máquina. O relatório dá um veredito por extenso (aguentou, enfileirou, rejeitou requests…) e avisa quando o limite foi o seu próprio computador, e não a API. → Carga

Traga o que você já tem #

Você não começa do zero: coleções e ambientes do Postman, documentos OpenAPI, planos do JMeter, scripts do Artillery e tráfego gravado no navegador viram coleções, pipelines, ambientes e testes de carga. O que não dá para converter aparece numa lista, em vez de se perder. A importação lê só o arquivo que você escolher e não envia nada. → Importar

Seus segredos só vão aonde você mandou #

O Ultraman nunca envia nada de forma insegura sem o seu consentimento explícito. Um segredo, escrito {{secrets.token}}, fica num cofre criptografado no seu computador, nunca no repositório. Na primeira vez que uma request for enviá-lo a um servidor que você não aprovou para ele, o Ultraman pergunta; o mesmo vale para um arquivo de fora da pasta ultraman/files/ do projeto. Onde o valor de um segredo apareceria (numa resposta, no histórico, num relatório de execução, numa exportação), você vê [secret:token] no lugar. Uma pasta em que você ainda não confia abre em modo restrito: não envia nada e não executa git. É isso que permite abrir uma pipeline escrita por um colega, ou baixada da internet, sem que ela mande o seu token para outro lugar às escondidas. O que isso não cobre está dito sem rodeios em os limites. → Segurança e consentimento, Ambientes e segredos

Uma equipe que compartilha pelo git #

A sua equipe compartilha testes do mesmo jeito que compartilha código, sem conta nem servidor no meio: pipelines, coleções, ambientes, testes de carga e os arquivos que as requests enviam são todos arquivos dentro de ultraman/. Sincronizar faz commit e push só deles e mostra os conflitos lado a lado. Os segredos, os valores desta máquina e o seu histórico ficam no seu computador. → Trabalho em equipe

Os mesmos testes no CI #

Os testes que você executa na janela podem barrar o seu build. ultraman run executa pipelines, uma coleção ou um teste de carga pelo terminal, gera um relatório JUnit e sai com erro quando um check ou um limiar falha. No GitHub Actions, ultraman-app/run-action instala e executa o Ultraman; você define para qual servidor cada segredo pode ir. → CI, O terminal

O seu agente pode comandá-lo #

Um agente de IA que fala MCP (o Claude Code, por exemplo) pode criar requests, escrever pipelines, executá-las, iniciar uma carga e ler os relatórios, enquanto quem decide continua sendo você: cada chamada mostra um cartão na janela e nada acontece até você aprovar (chamadas só de leitura podem ser liberadas pelo resto de uma sessão). O agente pode usar os seus segredos pelo nome, mas nunca vê os valores. → Agentes (MCP)

Uma API falsa feita do que você já enviou #

Quando a API de verdade está fora do ar, lenta ou ainda nem existe, o servidor mock responde com as respostas que você já gravou, para que um front end ou um teste continue funcionando. Ele só responde no seu computador, a menos que você o inicie pelo terminal e escolha outra coisa. → Servidor mock
