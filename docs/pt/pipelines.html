Pipelines #

Uma pipeline é um fluxo de requests e checks que você lê de cima para baixo, salvo em ultraman/pipelines/<nome>.yaml e executado pela janela ou pelo terminal. Ela tem um host, auth e headers opcionais para todas as requests, inputs (valores que a execução pede) e passos. Nada fica escondido: o que um passo faz é o que a linha dele diz.

Os passos #

PassoO que faz
requestenvia uma request HTTP; os outros passos se referem a ela como $nome
extracttira um valor de uma resposta (path JSON, header ou regex) e guarda em {{nome}}
assertconfere algo numa resposta (veja Checks)
waitpausa por alguns milissegundos
repeatexecuta os passos dele N vezes, ou uma vez para cada item de uma lista
ifexecuta os passos dele só quando uma condição é verdadeira
useexecuta um bloco (uma pipeline reutilizável) com os inputs dele
parallelexecuta ramos ao mesmo tempo; o passo seguinte espera todos terminarem
websocket, sseabre um stream; os outros passos se referem a ele como $nome (o handshake)
sendescreve uma mensagem num WebSocket
receiveespera a próxima mensagem de um stream que passe num filtro; os outros passos se referem a ela como $nome
closeencerra um stream (um stream que ficar aberto é fechado quando a execução termina)

Adicionar passo explica cada um. O + entre dois passos insere um ali mesmo. De uma coleção… adiciona uma request de uma coleção, com os checks dela, como cópia vinculada.

GraphQL. Um passo request pode levar um body GraphQL, editado do mesmo jeito que na área de Requests (veja GraphQL); um passo vinculado usa o schema da coleção dele. A lista mostra o nome da operação (POST /graphql · Order), e uma resposta com errors faz o passo falhar, mesmo com um 200.

Streams numa pipeline #

Um stream WebSocket ou SSE vira quatro tipos de passo à vista, nesta ordem: abrir, enviar, esperar uma mensagem e fechar. O host da pipeline também serve o stream (https vira wss).

steps:
  - websocket: live
    path: /live

  - send: live
    json: { subscribe: orders }

  - receive: update
    from: $live
    where: { path: $.type, equals: order.updated }
    timeout: 5000

  - assert: equals
    of: $update
    path: $.status
    equals: shipped

  - close: live
    code: 1000
    reason: done

$live é o handshake, então assert: status of: $live equals: 101 funciona. Uma mensagem recebida é uma resposta como qualquer outra: o texto dela é o body, e extract e assert leem esse texto com um path JSON. No SSE, o event e o id do evento são lidos como headers (header: event).

receive pega a próxima mensagem que atende ao where dele. As mensagens anteriores são puladas e contadas, e um segundo receive começa depois da mensagem que o primeiro pegou. Sem where, qualquer mensagem serve. Se nenhuma atender em timeout ms (o options.timeout do stream, se o passo não tiver um), o passo falha e mostra as três últimas mensagens que pulou. Um timeout de 0 espera sem limite, até uma mensagem atender, o stream terminar ou você parar a execução.

whereatende quando
{ path: $.type, equals: order.created }o body JSON tem esse valor no path
{ path: $.id, exists: true }o path encontra algo
{ contains: shipped }o texto contém isso
{ matches: /^ord_/ }o texto bate com uma regex
{ event: price }só no SSE: o nome do evento; pode ir junto com um dos anteriores

repeat: 10 em volta de um receive junta dez mensagens. Numa execução, a seção recolhível Mensagens embaixo da linha websocket ou sse lista tudo o que passou pelo stream, nos dois sentidos, então dá para ver o que chegou entre um passo e outro. Uma request de stream da área de Requests também pode entrar numa pipeline (De uma coleção…).

Um token no subprotocolo. Alguns servidores (Kubernetes exec, alguns gateways de GraphQL sobre WebSocket) só aceitam o token em Sec-WebSocket-Protocol. Para esses casos, protocols aceita um segredo, protocols: [v4.channel.k8s.io, "{{secrets.kube_token}}"], com o mesmo sim de um header, e ele aparece como [secret:kube_token] em todo lugar. Prefira um header Authorization quando o servidor aceitar: proxies costumam registrar os subprotocolos em log. Detalhes na referência do formato.

Subscriptions GraphQL #

Uma subscription GraphQL é um WebSocket com graphql: e passos subscribe visíveis sobre ele; os eventos dela são recebidos como mensagens.

steps:
  - websocket: live
    path: /graphql
    graphql:
      init: { authorization: "Bearer {{secrets.token}}" }

  - subscribe: orders
    on: $live
    graphql:
      query: |
        subscription { orderCreated { id total } }

  - receive: order
    from: $orders
    where: { path: $.data.orderCreated.total, exists: true }
    timeout: 5000

  - close: orders

  - close: live

graphql: num passo websocket transforma esse passo num socket GraphQL: o Ultraman define o subprotocolo (graphql-transport-ws), envia connection_init com init como payload e espera a confirmação do servidor (ackTimeout ms; se você não definir, vale o timeout do passo). Cada subscribe inicia uma subscription nesse socket, e dá para ter várias no mesmo socket se precisar, cada uma com o seu $nome. Um receive de uma subscription pega o próximo evento dela que atende ao filtro: o body é o payload do evento ({ data, errors }), então $.data.orderCreated.id lê o valor. Um evento com errors faz o receive falhar, a menos que a subscription tenha allowErrors: true. close: orders encerra uma subscription; close: live encerra todas e fecha o socket, e o fim da execução faz o mesmo.

As mensagens do próprio protocolo ficam por conta do Ultraman: um socket GraphQL não aceita send, e um receive aponta para uma subscription, não para o socket. A demo traz esta pipeline como live orders (graphql).

Inputs #

inputs: [user] declara valores de que a pipeline precisa e que ela não tem. Executar pede esses valores num diálogo; no terminal, você os passa com --input user=ana (veja o terminal), e um bloco recebe os inputs de use … with. Uma execução com um input faltando não começa. Dentro da pipeline, um input é uma variável: {{user}}.

Headers para todas as requests #

headers: numa pipeline (ou num bloco, ou numa coleção) é enviado por todas as requests dela. Um passo que define o mesmo header, com qualquer combinação de maiúsculas e minúsculas, fica com o dele. Os headers de um bloco são só do bloco: a pipeline que chama o bloco não repassa os headers dela para as requests do bloco. Um segredo num header compartilhado pede o sim do host dele, como um segredo num passo.

name: orders
host: "{{env.api}}"
headers: { x-tenant: acme }
steps:
  - request: list
    method: GET
    path: /orders

Ao mesmo tempo #

parallel executa dois ou mais ramos de uma vez, e o passo seguinte espera todos. Se um ramo falhar, os outros continuam: o parallel falha quando todos terminarem. Dois ramos não podem extrair a mesma variável.

- parallel: dashboard
  branches:
    - - request: me
        method: GET
        path: /me
    - - request: orders
        method: GET
        path: /orders

Para se achar #

Dê tags a uma pipeline em Auth e opções (Enter ou vírgula adiciona uma) e elas aparecem como chips embaixo do nome; clicar num chip filtra por ele. Toda barra lateral tem uma caixa Filtrar… (um nome, ou #tag). Ctrl+P (Cmd+P no macOS) abre uma caixa única para pipelines, blocos e requests: digite algumas letras do nome, ou #tag, e aperte Enter para abrir.

Lista e diagrama #

A Lista mostra cada passo numa linha, do jeito que os outros passos se referem a ele. O Diagrama desenha os mesmos passos com uma seta da request que produz um valor até a que o lê, e assim o fluxo de dados aparece num relance.

Executando #

Executar percorre a pipeline de cima para baixo no ambiente selecionado. Cada passo mostra o status e o tempo; um check que falhou mostra a resposta que o derrubou. Vigiar executa de novo quando algo muda, ou de tempos em tempos. As execuções anteriores ficam listadas embaixo da pipeline.

Blocos #

Um bloco é uma pipeline feita para ser reaproveitada: um login, uma preparação. Ele declara inputs e exports. Uma pipeline executa o bloco com use: login e recebe os exports dele como variáveis.

Ajudantes #

  • Funções dentro de {{ }}: random.uuid, random.email, random.int(1, 100), now.iso, counter, base64(x), hmac.sha256(secrets.key, body) e outras (veja a referência do formato).
  • Extract com regex: regex: name="csrf" value="([^"]+)" pega o grupo 1.
  • Extract opcional: quando nada é encontrado, a variável fica sem valor em vez de dar falha.
  • `if`: executa os passos dele só quando uma condição é verdadeira. Não existe else.

Juntos, eles cobrem os casos de sempre, do tipo "token na página, talvez um cupom":

- extract: csrf
  from: $page
  regex: 'name="csrf" value="([^"]+)"'

- extract: coupon
  from: $cart
  path: $.coupon
  optional: true

- if: { exists: coupon }
  steps:
    - request: apply
      method: POST
      path: /cart/coupon
      json: { code: "{{coupon}}" }

Não há scripts, de propósito: o que um passo faz está sempre à vista, e quem revisa consegue ler uma pipeline num pull request.

O que mantém você seguro #

A promessa vale aqui como em qualquer lugar. O que esta parte acrescenta:

  • Você: uma condição, um check ou uma regex nunca lê o conteúdo de um segredo, nem de um valor gerado a partir de um: uma pipeline que tentasse isso é recusada em vez de executada, então o ramo que for seguido não pode revelar um segredo. Veja a ocultação.
  • Sua equipe: uma pipeline de uma pasta em que você não confiou não envia nada pela janela. Veja pastas confiáveis.
