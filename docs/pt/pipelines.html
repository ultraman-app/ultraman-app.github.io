Pipelines #

Uma pipeline é um fluxo de requests e checks que você lê de cima para baixo, salvo em ultraman/pipelines/<nome>.yaml e executado pela janela ou pelo terminal. Ela tem um host, auth e headers opcionais para todas as suas requests, inputs (valores que a execução pede) e passos. Nada nela fica escondido: o que um passo faz é o que a linha dele diz.

Os passos #

PassoO que faz
requestenvia uma request HTTP; os outros se referem a ela como $nome
extractpega um valor de uma resposta (path JSON, header ou regex) e guarda em {{nome}}
assertcheca algo de uma resposta (veja Checks)
waitespera alguns milissegundos
repeatroda seus passos N vezes, ou uma vez por item de uma lista
ifroda seus passos só quando uma condição é verdadeira
useroda um bloco (uma pipeline reutilizável) com seus inputs
parallelroda ramos ao mesmo tempo; o passo seguinte espera todos
websocket, sseabre um stream; os outros se referem a ele como $nome (o handshake)
sendescreve uma mensagem num WebSocket
receiveespera a próxima mensagem de um stream que atende a um filtro; os outros se referem a ela como $nome
closeencerra um stream (um que ficar aberto é fechado quando a execução terminar)

Adicionar passo explica cada um. O + entre dois passos insere um exatamente ali. De uma coleção… adiciona uma request de uma coleção, com seus checks, como cópia vinculada.

Streams numa pipeline #

Um stream WebSocket ou SSE são quatro tipos de passo que você enxerga, em ordem: abrir, enviar, esperar uma mensagem, fechar. O host da pipeline também atende o stream (https vira wss).

steps:
  - websocket: live
    path: /live

  - send: live
    json: { subscribe: orders }

  - receive: update
    from: $live
    where: { path: $.type, equals: order.updated }
    timeout: 5000

  - assert: equals
    of: $update
    path: $.status
    equals: shipped

  - close: live
    code: 1000
    reason: done

$live é o handshake, então assert: status of: $live equals: 101 funciona. Uma mensagem recebida é uma resposta como qualquer outra: o texto dela é o body, e extract e assert o leem com um path JSON. No SSE, o event e o id do evento são lidos como headers (header: event).

receive pega a próxima mensagem que atende ao seu where. As anteriores são puladas e contadas, e um segundo receive começa depois da mensagem que o primeiro encontrou. Sem where, qualquer mensagem serve. Se nada atender em timeout ms (o options.timeout do stream, se o passo não tiver um), o passo falha e mostra as últimas três mensagens que pulou.

whereatende quando
{ path: $.type, equals: order.created }o body JSON tem esse valor no path
{ path: $.id, exists: true }o path encontra algo
{ contains: shipped }o texto contém isso
{ matches: /^ord_/ }o texto bate com uma regex
{ event: price }só SSE: o nome do evento; pode ir junto com um dos anteriores

repeat: 10 em volta de um receive junta dez mensagens. Numa execução, a dobra Mensagens sob a linha websocket ou sse lista tudo o que o stream carregou, nos dois sentidos, então o que chegou entre os passos fica visível. Uma request de stream da área de Requests também pode ser adicionada a uma pipeline (De uma coleção…).

Um token no subprotocolo. Alguns servidores (Kubernetes exec, alguns gateways de GraphQL sobre WebSocket) aceitam o token só em Sec-WebSocket-Protocol. Para eles protocols aceita um segredo, protocols: [v4.channel.k8s.io, "{{secrets.kube_token}}"], com o mesmo sim de um header, e ele aparece como [secret:kube_token] em todo lugar. Prefira um header Authorization quando o servidor aceitar um: proxies costumam registrar subprotocolos. Detalhes na referência do formato.

Inputs #

inputs: [user] declara valores de que a pipeline precisa e que ela não tem. Executar pede esses valores num diálogo; no terminal você os passa com --input user=ana (veja o terminal), e um bloco os recebe de use … with. Uma execução com um input faltando não começa. Dentro da pipeline um input é uma variável, {{user}}.

Headers para todas as requests #

headers: numa pipeline (ou num bloco, ou numa coleção) é enviado por todas as suas requests. Um passo que define o mesmo header, com qualquer capitalização, mantém o dele. Os headers de um bloco são só do bloco: a pipeline que o chama não repassa os seus headers para as requests do bloco. Um segredo num header compartilhado pede o sim do host dele como um segredo num passo.

name: orders
host: "{{env.api}}"
headers: { x-tenant: acme }
steps:
  - request: list
    method: GET
    path: /orders

Ao mesmo tempo #

parallel roda dois ou mais ramos de uma vez e o passo seguinte espera todos. Um ramo que falha não para os outros: o parallel falha quando todos terminam. Dois ramos não podem extrair a mesma variável.

- parallel: dashboard
  branches:
    - - request: me
        method: GET
        path: /me
    - - request: orders
        method: GET
        path: /orders

Para se achar #

Dê tags a uma pipeline em Auth e opções (Enter ou uma vírgula adiciona uma) e elas aparecem como chips embaixo do nome; um clique num chip filtra por ele. Toda barra lateral tem uma caixa Filtrar… (um nome, ou #tag). Ctrl+P (Cmd+P no macOS) abre uma caixa só sobre pipelines, blocos e requests: digite algumas letras do nome, ou #tag, e Enter abre.

Lista e diagrama #

A Lista mostra cada passo em uma linha, do jeito que os outros se referem a ele. O Diagrama desenha os mesmos passos com uma seta da request que produz um valor até a que o lê, assim o fluxo dos dados fica visível de relance.

Executando #

Executar roda a pipeline de cima para baixo no ambiente escolhido. Cada passo mostra seu status e seu tempo; um check que falhou mostra a resposta que o fez falhar. Vigiar executa de novo quando algo muda, ou num temporizador. As execuções passadas ficam listadas embaixo da pipeline.

Blocos #

Um bloco é uma pipeline feita para ser reutilizada: um login, uma preparação. Ele declara inputs e exports. Uma pipeline o roda com use: login e recebe os exports dele como variáveis.

Ajudantes #

  • Funções dentro de {{ }}: random.uuid, random.email, random.int(1, 100), now.iso, counter, base64(x), hmac.sha256(secrets.key, body) e mais (veja a referência do formato).
  • Extract com regex: regex: name="csrf" value="([^"]+)" pega o grupo 1.
  • Extract opcional: quando nada é encontrado, a variável fica sem valor em vez de falhar.
  • `if`: roda seus passos só quando uma condição é verdadeira. Não existe else.

Juntos, cobrem os casos de sempre, "token na página, cupom talvez":

- extract: csrf
  from: $page
  regex: 'name="csrf" value="([^"]+)"'

- extract: coupon
  from: $cart
  path: $.coupon
  optional: true

- if: { exists: coupon }
  steps:
    - request: apply
      method: POST
      path: /cart/coupon
      json: { code: "{{coupon}}" }

Não há scripts de propósito: o que um passo faz está sempre à vista, e quem revisa pode ler uma pipeline num pull request.

O que mantém você seguro #

A promessa vale aqui como em todo lugar. O que esta parte acrescenta:

  • Você: uma condição, um check ou uma regex nunca lê o conteúdo de um segredo, nem de um valor feito a partir de um: uma pipeline que leria é recusada em vez de executada, então um ramo que você toma não pode revelar um segredo. Veja a ocultação.
  • Seu time: uma pipeline de uma pasta em que você não confiou não envia nada pela janela. Veja pastas confiáveis.
