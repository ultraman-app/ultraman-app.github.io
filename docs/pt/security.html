Segurança e consentimento #

O que o Ultraman pergunta antes de enviar qualquer coisa, como ele mantém os seus segredos longe dos olhos e o que fica por sua conta: promessas que você pode conferir, para você, a sua equipe e o seu CI. Não há telemetria, analytics, relatório de falhas nem conta.

A promessa #

O Ultraman nunca envia nada de forma insegura sem o seu consentimento explícito. Na prática:

  • um segredo só vai para uma origem (esquema, host e porta) a que você disse sim para aquele segredo;
  • um arquivo só sai sem perguntar se estiver em ultraman/files/, a pasta que o seu projeto compartilha de propósito; qualquer outro arquivo precisa de um sim;
  • uma pasta em que você não confiou não envia nada e não executa git;
  • o valor de um segredo não aparece: em todo lugar onde daria para lê-lo, aparece [secret:name].

O sim é seu. Ele fica guardado no seu computador, nunca no projeto, então quem escreveu uma pipeline não pode dizer sim por você. Quando o Ultraman não tem como perguntar (um terminal sem ninguém na frente, um runner de CI), ele para em vez de enviar. A única forma de pular as perguntas é uma que você mesmo escolhe: --yes num terminal ou yes: true no CI, pensados para branches que só a sua equipe pode alterar.

Confira você mesmo, no seu próprio projeto:

  • Aponte uma request que usa {{secrets.x}} para um host que você não liberou para esse segredo e clique em Enviar: a pergunta aparece antes que qualquer coisa saia. Aperte Esc e nada é enviado.
  • Abra o ultraman/.gitignore: runs/, loads/, mcp/, history/, .serve, local/ e mock/ ficam fora do git. Procure secrets. no projeto: você só vai achar referências como {{secrets.token}}, nunca um valor guardado pelo Ultraman.
  • Dê uma olhada em ~/.ultraman: os valores dos segredos só são guardados criptografados, em secrets.enc (junto com vault.json); a mesma pasta também tem arquivos em texto simples, como o trust.json e a verificação de atualização. Nada disso está no projeto.

O resto desta página explica como cada parte funciona, quem ela protege e o que ela não cobre.

Quando o Ultraman pergunta #

O Ultraman pergunta antes de enviar um segredo para uma origem que você não liberou para esse segredo neste projeto, e antes de enviar um arquivo de fora de ultraman/files/. A pergunta diz o que vai para onde. A opção segura vem primeiro e já vem com o foco; Cancelar (ou Esc) não envia nada.

Um segredo para uma origem nova. A janela pergunta "Enviar o segredo token para https://api.example.com?" e lembra que, se a request foi escrita por outra pessoa, vale conferir se o host é seu. O valor em si nunca aparece.

OpçãoO que faz
Usar outro valor, só desta vez (o padrão)Você digita um valor só para este envio; o segredo salvo continua no seu computador.
Enviar, só desta vezEle vai desta vez; da próxima, o Ultraman pergunta de novo.
Permitir https://api.example.com para este segredoDaqui em diante, neste projeto, este segredo vai para essa origem sem perguntar.
CancelarNada é enviado.

Um sim vale para um segredo e uma origem: o mesmo segredo indo para outro host ou outra porta pergunta de novo, e outro segredo indo para o mesmo host também. Quando uma request define o próprio header host, a origem indicada nesse header também passa pela pergunta.

Um arquivo de fora de `ultraman/files/`. A janela pergunta "Enviar um arquivo de fora de ultraman/files?", mostrando o caminho e para onde ele vai, e avisa que quem escolheu o arquivo foi quem escreveu o caminho. Escolher o arquivo (janela desktop) deixa você mesmo escolher, dentro do projeto ou copiando o arquivo para ele; Enviar e lembrar deste arquivo libera o envio daqui em diante neste projeto; Cancelar não envia nada.

No terminal. O ultraman run lista o que a execução enviaria sem o seu sim, indica o arquivo a conferir e pergunta:

  y  yes, just this once
  a  always: allow these for this project
  N  no, send nothing (default)

Enter, Ctrl+C ou Ctrl+D valem como não. Numa pasta em que você não confiou, a também passa a confiar nela. Se não houver terminal para perguntar, a execução para com código de saída 2 antes de enviar qualquer coisa. --yes diz sim a tudo só naquela execução e não guarda nada; no CI, liste em vez disso o que pode ir para onde (No CI).

Quem isso protege: você, quando executa uma request que outra pessoa escreveu; a sua equipe, porque a mudança de um colega não consegue apontar o seu segredo para um host novo sem você ver; o CI, que recusa em vez de enviar.

Pastas confiáveis e modo restrito #

Na primeira vez que você abre uma pasta, o Ultraman pergunta "Você confia nesta pasta?": as pipelines e requests dela podem enviar seus segredos e arquivos para qualquer servidor, e as configurações de git dela podem executar comandos no seu computador.

  • Abrir em modo restrito (o padrão): você pode navegar e editar. O Ultraman não envia nada a partir dela, não executa nada (nem requests, pipelines, testes de carga, streams ou servidor mock) e não executa git, então não há sincronização. Um cadeado de Modo restrito na barra superior pergunta de novo quando você estiver pronto.
  • Confiar nesta pasta: só se você souber de onde ela veio. Você decide uma vez por pasta, neste computador.

Um agente não consegue salvar, enviar nem executar nada numa pasta em que você não confiou. A lista das suas pastas confiáveis fica na sua pasta do Ultraman (~/.ultraman/trust.json), nunca no projeto.

Confiar não é dar carta branca: numa pasta confiável, um segredo continua perguntando antes de ir para uma origem nova, e um arquivo de fora de ultraman/files/ continua perguntando antes de sair.

O projeto de exemplo é a única pasta confiável sem que o Ultraman pergunte, porque o conteúdo dele é do próprio Ultraman e é reconstruído limpo toda vez que você o abre.

Quem isso protege: você, quando abre um repositório escrito por outra pessoa. O git executa o que as configurações do próprio repositório mandam, por isso o Ultraman não executa git ali até você confiar na pasta.

O cofre #

Os valores dos segredos ficam num cofre no seu computador: vault.json e secrets.enc em ~/.ultraman/ (ou na pasta indicada por ULTRAMAN_HOME). Eles nunca estão no projeto, então o git nunca os leva junto: o projeto guarda só referências como {{secrets.token}}.

  • Criptografia. Uma chave aleatória criptografa os segredos (AES-256-GCM). Essa chave só é guardada embrulhada por outra chave, derivada da sua senha mestra (scrypt). A senha precisa ter pelo menos 8 caracteres; uma frase longa é melhor.
  • Bloqueio. A janela pede a senha na primeira vez que uma execução precisa de um segredo. O cofre volta a ser bloqueado depois de 30 minutos sem uso. O cadeado no topo (Segredos: bloqueio, senha) bloqueia o cofre na hora ou troca a senha. Bloquear também encerra as sessões WebSocket e SSE que leem um segredo do cofre.
  • Sem recuperação. Ninguém abre o cofre sem a senha, nem o próprio Ultraman. Se você esquecer a senha, Esqueceu? apaga todos os segredos salvos para você começar de novo.
  • Lembrar neste computador (só na janela desktop, desligado por padrão) guarda a chave do cofre no chaveiro do sistema, para que o cofre abra sem pedir a senha. No Windows e no Linux, outros apps que você executa podem ler essa entrada; no macOS, o Keychain pergunta antes. O terminal nunca usa isso: a CLI sempre pede a senha ou, no lugar dela, usa variáveis ULTRAMAN_SECRET_<NAME> (Segredos).

Quem isso protege: você, porque uma cópia da sua pasta do Ultraman, um backup ou um disco roubado não abrem os seus segredos sem a senha; a sua equipe, porque os segredos nunca passam pelo repositório.

Ocultação #

O valor de um segredo não aparece em nenhum lugar onde você possa lê-lo: respostas, histórico, execuções, relatórios de carga, exportações (cURL, HTML, CSV), erros, saída do terminal e o que um agente recebe. No lugar dele aparece [secret:name].

  • Valores gerados a partir de um segredo também contam: um header basic-auth montado com ele, o segredo codificado em URL ou em base64, um valor que o servidor devolve como eco e valores repassados por variáveis, blocos, exports e extracts. O Ultraman acompanha até 256 desses valores para cada pipeline e bloco numa execução; passando disso, trata a variável inteira como segredo.
  • Ocultado antes de cortar. Um body longo só é cortado para caber depois que os segredos são ocultados, então ele nunca mostra metade de um.
  • Checks não podem ler um segredo. Um assert, um if, o where de um stream ou um extract por regex sobre uma resposta que devolve um segredo como eco é recusado com erro em vez de executado: saber se ele passou já diria algo sobre o valor. Compare, em vez disso, um valor que a própria resposta fornece.

Arquivos que uma request envia #

Só os arquivos de ultraman/files/ saem sem perguntar. É a pasta que o seu projeto compartilha de propósito: quando você escolhe na janela um arquivo de outro lugar, o Ultraman oferece Copiar para o projeto, e a sincronização do git o compartilha com a sua equipe.

Qualquer outro arquivo que uma request leia (um body, uma parte multipart, uma mensagem de stream, uma CA própria) pergunta uma vez (Quando o Ultraman pergunta) e não é usado até você dizer sim. Isso inclui arquivos em outros lugares do repositório, arquivos e pastas ocultos como .env, .npmrc ou .git (mesmo dentro de ultraman/files/) e as pastas que são só deste computador dentro de ultraman/ (valores locais, histórico, execuções, relatórios).

O Ultraman também não segue links simbólicos (nem junctions do Windows) dentro de ultraman/. Se um arquivo ali for um link, uma janela mostra para onde ele aponta e nada é salvo através dele; Salvar como arquivo normal aqui substitui o link.

Quem isso protege: você, a sua equipe e o CI: uma pipeline compartilhada ou um pull request não consegue fazer uma request enviar as suas chaves SSH, um arquivo .env ou as credenciais de um checkout sem que alguém diga sim.

Redirects #

Quando um servidor redireciona uma request para outra origem, o Ultraman descarta os headers authorization, cookie e proxy-authorization. Se a request leva um segredo em outro header, os headers personalizados dela também ficam para trás. Um 307 ou 308 que reenviaria para outra origem um body com um segredo não é seguido: você recebe o próprio redirect como resposta. Um redirect de https para http é recusado, e o handshake de um WebSocket ou SSE nunca segue redirects.

Quem isso protege: você: o sim que você deu para um host não acompanha um redirect para outro.

O servidor local #

A janela, o comando ultraman e a ponte do agente conversam com um servidor local por projeto (ultraman serve). Ele só escuta em 127.0.0.1 e:

  • só responde a requests endereçadas a 127.0.0.1 ou localhost, para que uma página web não consiga alcançá-lo apontando o próprio nome de domínio para o seu computador;
  • recusa alterações vindas de qualquer página web que não seja a da própria janela, e só aceita JSON;
  • exige o token de sessão e a origem da janela para cada decisão: responder a uma pergunta de consentimento, confiar numa pasta, abrir o cofre, aprovar o cartão de um agente, abrir um stream;
  • pede a qualquer outro chamador que prove ser a CLI do Ultraman, com uma chave guardada na sua pasta do Ultraman; a CLI confere o servidor do mesmo jeito antes de passar uma execução para ele.

A página da janela só carrega os próprios arquivos e só se conecta a este computador.

O servidor mock também escuta em 127.0.0.1 e só responde a páginas e programas deste computador. ultraman mock --expose o abre para a sua rede, depois de um aviso que você confirma; a janela e o agente não podem fazer isso.

Quem isso protege: você: uma página web aberta no seu navegador é recusada pelo servidor local, então não consegue fazer o Ultraman enviar os seus segredos nem ler o seu projeto.

Agentes #

Um agente de IA conectado por ultraman mcp trabalha com a sua aprovação, cartão por cartão (Agentes):

  • cada chamada mostra um cartão na janela; executar algo exige dois, um para começar e outro para entregar o resultado ao agente; só chamadas de leitura podem ser aprovadas "sempre", e só durante aquela sessão;
  • o agente pode usar {{secrets.x}}, mas nunca vê nem define um valor; o que ele recebe chega com os segredos ocultados, e o cartão de entrega avisa quando um resultado traz tokens, cookies ou headers de autenticação;
  • ele só pode enviar um segredo para um host que o projeto já menciona (um valor de ambiente ou o host de uma pipeline), e o cartão de início lista cada segredo e origem que você ainda não liberou: aprovar o cartão deixa que eles saiam só daquela vez;
  • ele não pode desbloquear o cofre, responder a uma pergunta de consentimento, confiar numa pasta, sincronizar com o git nem apagar nada.

Quem isso protege: você, quando algo que o agente lê tenta manipulá-lo: nada é executado nem sai sem o seu clique.

No CI #

Um runner não tem cofre nem ninguém a quem perguntar. Os segredos vêm de variáveis ULTRAMAN_SECRET_<NAME> (No CI) e são ocultados como qualquer outro. Com a GitHub Action, a entrada allow lista qual segredo pode ir para qual origem; todo o resto é recusado antes de ser enviado. yes: true (ou --yes) desliga as perguntas: use só em branches em que apenas a sua equipe pode fazer push. Aqui também só ultraman/files/ sai sem um sim, e a action se recusa a executar junto com o token de checkout do job. Os detalhes estão em CI.

Quem isso protege: o CI e a sua equipe: um pull request que aponta um segredo para um host novo falha em vez de enviá-lo.

O que sai do seu computador #

As suas requests, para os hosts que elas indicam, dentro das regras acima. Além delas:

  • A verificação de atualização. Quando a janela abre, o servidor local pergunta ao GitHub qual é a versão mais recente do Ultraman, no máximo uma vez por dia. O GitHub vê o seu endereço IP; nada sobre você nem sobre os seus projetos é enviado. Só se houver uma versão mais nova a janela desktop lê no GitHub os detalhes da atualização. Nada é baixado até você clicar em Atualizar e reiniciar, e uma atualização só é instalada se tiver a assinatura do Ultraman. Para desligar as duas coisas, defina ULTRAMAN_NO_UPDATE_CHECK=1 no ambiente a partir do qual você inicia o Ultraman.
  • A sincronização do git, para o seu próprio remoto, quando você sincroniza (só em pastas confiáveis).
  • O `--proxy` do servidor mock, para a URL que você informar.

Não há telemetria, analytics, relatório de falhas nem conta.

Limites honestos #

O que o Ultraman não protege, e o que fazer a respeito:

  • Pasta confiável é pasta confiável. Confiar nela deixa as requests dela executarem e as configurações de git dela valerem. Só confie numa pasta se você também executaria o código dela.
  • O seu computador está fora do escopo. Um programa em execução com o seu usuário pode ler da memória um cofre desbloqueado ou capturar a senha que você digita. Com Lembrar neste computador no Windows ou no Linux, outros apps que você executa podem ler a chave: deixe essa opção desligada em computadores compartilhados ou não gerenciados.
  • Esqueceu a senha mestra, perdeu os segredos. É proposital: não há recuperação.
  • Só os segredos são ocultados. Um token digitado num header ou num valor de ambiente é texto simples: ele aparece, é salvo no histórico e é sincronizado se estiver num arquivo compartilhado. Os valores em ultraman/local/ ficam fora do git, mas não são ocultados. Transforme toda credencial em segredo.
  • A ocultação funciona por valor. O Ultraman reconhece um segredo nas formas que consegue prever (como está, codificado em URL, em base64, devolvido como eco); se um servidor o transformar de outro jeito, o que volta é algo que o Ultraman não consegue reconhecer. Segredos muito curtos são reconhecidos de menos formas: use segredos longos. E ele oculta valores, não nomes: um segredo que um servidor devolve como nome de um header aparece do jeito que está.
  • O CI executa o que o workflow manda. Um pull request que altera o próprio arquivo de workflow está fora do que o Ultraman consegue verificar, e yes: true ou --yes desliga as perguntas. Mantenha os seus segredos longe de pull requests vindos de forks (CI).
  • Um agente com acesso a um shell também pode executar comandos por conta própria: os cartões de aprovação só cobrem o que passa pelo Ultraman.
  • Os instaladores não são assinados pela Microsoft nem pela Apple, então o seu sistema avisa na primeira vez que você abre o Ultraman. O que é assinado: as atualizações (conferidas com uma chave embutida no app) e os checksums da versão, que os scripts de instalação verificam antes de instalar. O comando de instalação de uma linha executa um script baixado do site do Ultraman, então, para esse script, ele confia no site.
  • Sem auditoria independente. As revisões de segurança do Ultraman são feitas por quem o desenvolve, antes de cada versão; ninguém de fora o auditou. Se a sua política exige uma auditoria antes de guardar credenciais numa ferramenta, a resposta honesta hoje é essa.
