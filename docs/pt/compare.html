Comparar dois ambientes #

Comparar executa a mesma pipeline em dois ambientes e diz, passo a passo, se eles respondem igual: depois de um deploy, confira se o staging tem a estrutura e os dados replicados que o desenvolvimento tem. Também dá para conferir as respostas de um ambiente com o tipo delas, um JSON Schema ou a spec OpenAPI da coleção. Uma resposta que não é JSON (uma página de erro HTML) não combina com o tipo de um arquivo de schema.

O que ele responde #

Uma comparação executa a pipeline inteira no primeiro ambiente e depois no segundo, cada execução com os valores, o login e os segredos do próprio ambiente, e compara a resposta de cada request. Uma request com um bloco compare: é comparada pela regra dele; uma sem bloco, por Mesma estrutura, o padrão: os mesmos campos e tipos, os valores podem diferir. Para cada request, ele diz uma destas coisas:

  • igual: as duas respostas coincidem (com body: shape, mesmo formato);
  • N caminhos diferem: o status, um header que você nomeou ou o body diferem, e onde (o JSONPath de cada lugar);
  • sem comparar, e por quê: um lado não executou o passo, um lado falhou nele, ou a resposta não pode ser comparada.

Uma request sem bloco é comparada por estrutura sem que nada seja acrescentado ao arquivo dela, e a linha diz isso ("same (by structure, the default)"). Um passo que não é uma request (um extract, um assert, um wait) não tem nada a comparar. Isso vale para uma pipeline ou coleção que você nomeia; no terminal, uma seleção com --all ou --tag compara só os blocos escritos (veja pelo terminal). Uma request sem bloco que um lado nunca alcançou (um if que só um ambiente toma) aparece como sem comparar e por quê, mas não muda o veredito. Cada lado fica salvo como uma execução comum em ultraman/runs/. Nada mais é gravado: nenhum arquivo de diferenças, nenhuma linha de base.

O bloco compare #

Um passo request de uma pipeline, ou uma request de uma coleção, leva o bloco junto dos outros campos:

- request: get order
  method: GET
  path: /orders/{{order_id}}
  compare:
    body: value                      # value | shape | none; o status é sempre comparado
    only: [$.id, $.status, $.total, $.items]   # só estes campos; sem isso, tudo
    ignore: [$.updatedAt, $.meta.requestId]    # ficam de fora, também dentro de um caminho de only
    lists:
      $.items: { match: sku }        # emparelha os itens por este campo
      $.tags: { order: any }         # os mesmos itens, em qualquer ordem
    schema: files/order.schema.json  # o tipo da resposta, para --compare schema
    headers: [content-type]          # nenhum por padrão
    reuse: [order_id]                # veja "Pedindo o mesmo registro"

compare: {} compara o status e o body inteiro por valor. Toda chave é opcional:

ChaveO que faz
bodyvalue: os dados precisam ser os mesmos. shape: os mesmos campos com os mesmos tipos, quaisquer que sejam os valores. none: só o status e os headers que você nomear.
onlyJSONPaths. Só esses campos são comparados; um caminho para um objeto ou uma lista cobre o que há dentro dele.
shapeJSONPaths comparados só pelo tipo, dentro de uma comparação body: value: cada um precisa existir nos dois lados com o mesmo tipo, e o valor pode diferir. O resto do body é comparado por valor. Com only, um caminho de shape conta como incluído. Um caminho não pode estar em shape e em ignore ao mesmo tempo, e shape não combina com body: shape nem none.
ignoreJSONPaths deixados de fora, nos dois modos, também dentro de um caminho de only. Um timestamp ou um id de request que muda a cada chamada vai aqui.
listsNo modo value, uma lista é comparada em ordem, porque uma ordem diferente é uma diferença de verdade. match: <campo> emparelha os itens por esse campo; order: any compara como os mesmos itens em qualquer ordem. Dois itens com o mesmo valor de match se emparelham em ordem entre si, e o resultado avisa.
schemaUm arquivo JSON Schema em ultraman/files/: o tipo do passo quando você compara com tipos.
headersNomes de headers a comparar. authorization, cookie, set-cookie, proxy-authorization e www-authenticate são recusados.
reuseNomes de variáveis que o segundo ambiente pega do primeiro neste passo.

O caso clássico do shape é um id ou um timestamp: cada ambiente gera o seu, então os valores diferem, mas o campo precisa existir e manter o tipo:

compare:
  body: value
  shape: [$.id, $.createdAt]   # existem nos dois lados, mesmo tipo; os valores podem diferir
  ignore: [$.meta.requestId]   # não é comparado de jeito nenhum

Um passo de pipeline ligado a uma request de coleção leva o bloco dessa request, como os outros campos dela. O formato completo está na referência do formato.

Pelo terminal #

ultraman run "order compare" --compare local,staging
ultraman run "order compare" --env local --compare schema
ultraman run --tag smoke --compare dev,stg --junit reports/compare.xml

--compare a,b nomeia dois ambientes diferentes do projeto; o primeiro é a origem do reuse. Funciona com uma pipeline, --all, --tag ou --collection. Uma pipeline ou coleção que você nomeia compara cada request. --all e --tag ficam no que foi escrito: escolhem só as pipelines com um bloco compare: e comparam só esses passos, então uma pipeline que ninguém nomeou e que escreve sem bloco (um DELETE que apaga dados) nunca roda porque uma comparação a escolheu. As pipelines sem nada a comparar (contra um tipo, sem nenhuma com tipo) ficam de fora e são nomeadas. Uma comparação imprime uma tabela por pipeline quando os dois lados terminam:

order compare · local against staging
  login       POST /auth/login    200  200   same (by structure, the default)
  get order   GET  /orders/o-1    200  200   2 paths differ
      $.total       local 59.9 · staging 61.4
      $.items[1]    only in local
1 of 2 compared steps differs between local and staging.

No máximo 20 caminhos aparecem sob uma linha, depois "and N more". Os valores sob uma linha são ocultados e cortados como qualquer body impresso. As outras flags de ultraman run funcionam como sempre: --input vale para os dois lados, --parallel executa pipelines lado a lado (dentro de uma, os dois ambientes rodam um depois do outro), --bail, --watch, --every e --contract. --env não combina com --compare a,b (o par já nomeia os dois), e --load é recusado: nada é comparado sob carga. --json acrescenta side: 0 ou 1 a cada evento e termina cada pipeline com uma linha compare que tem caminhos e nenhum valor.

Quando a janela está com o projeto aberto, a comparação roda no motor dela e a janela mostra as duas execuções, como em um só motor.

Passos que escrevem #

Uma comparação envia cada passo duas vezes, uma para cada ambiente. Um passo comparado que não é uma leitura (um POST que cria um pedido) criaria dados nos dois, então o terminal pergunta sempre, nomeando o passo e os dois ambientes, mesmo que o resto da execução já esteja permitido. Uma leitura é um GET, HEAD ou OPTIONS, uma query GraphQL (a operação que sai) e um recurso ou um prompt MCP, quando vão ao endpoint da sua coleção (o caminho que as suas requests GraphQL usam, o servidor MCP de onde veio); para qualquer outro lugar, ou a partir de um passo de pipeline sem coleção, contam como escritas. Uma mutation ou subscription GraphQL, um documento que o Ultraman não consegue ler e uma ferramenta MCP contam como escritas: o readOnlyHint de uma ferramenta é a palavra do servidor, nunca a do Ultraman. a (sempre) nunca cobre essa pergunta, e --yes também não. Sem terminal (CI), diga o nome: --allow-write dev,stg.

Uma request sem bloco que escreve roda como numa execução comum da mesma pipeline: comparada por estrutura, é recusada só num ambiente de produção e não pergunta nada nos outros. A pergunta é para os passos que você marcou para comparar. O cartão de um agente ainda nomeia cada uma ("it writes in both").

Um ambiente com Isto é produção marcado (veja ambientes) é mais rígido: qualquer passo que não seja uma leitura, comparado ou só alimentando a comparação, é recusado antes de qualquer envio, a menos que --allow-write nomeie esse ambiente:

Not run. "create order" is a POST and prod is a production environment:
comparing it would create an order in stg and another in prod.

Compare only the steps that read, or allow it by name: --allow-write prod

Um ambiente sem marcação que aponta para o host de um ambiente de produção também conta como produção, no terminal, na janela e para um agente: uma cópia dos valores de prod salva com outro nome, um ambiente importado ou um host dado como input. A recusa o nomeia ("qa aponta para o host de prod, um ambiente de produção"), e --allow-write qa o permite por nome. O host é comparado inteiro, qualquer que seja o caminho, então um ambiente que compartilha o host de produção e difere só pelo caminho também conta como produção. Só decidem os hosts que suas pipelines e coleções leem: um host que todos os ambientes compartilham e que só o caminho de um passo nomeia (um provedor de login, uma API de pagamentos) não os torna de produção.

Códigos de saída #

CódigoQuando
0Todo passo comparado é igual, e as duas execuções passaram.
1Um passo comparado difere, ou um check da própria execução falhou. Os dois casos são informados.
2Nada foi enviado (uma flag errada, uma escrita recusada, um ambiente desconhecido), ou um passo comparado não pôde ser comparado e nenhum difere ("1 of 3 compared steps couldn't be compared"): um passo que um lado não alcançou, um body acima do limite. O terminal então diz o motivo de cada um desses passos. Uma request sem bloco que um lado não alcançou não conta, a menos que nada mais tenha sido comparado.

Um caminho que guardava um segredo fica "sem comparar" (veja abaixo) e nunca faz um passo diferir por si só: uma comparação cujos únicos pontos em aberto eram segredos ainda sai com 0 quando todo o resto é igual.

No CI: JUnit #

--junit FILE grava uma suíte de testes por pipeline, chamada order compare · local against staging, com compare nas propriedades e um caso de teste por passo comparado:

<testcase classname="order compare · local against staging" name="get order" time="0.000">
  <failure message="2 paths differ: $.total, $.items[1]"></failure>
</testcase>

Uma diferença é uma falha cuja mensagem traz a contagem e até 20 JSONPaths. Um passo que a execução de um lado falhou é uma falha que nomeia o lado; "sem comparar" é pulado; quando um passo não pôde ser comparado e nenhum difere, acrescenta-se um caso de erro, para o CI nunca ler isso como aprovação. O arquivo não traz nenhum valor nem body. Veja CI.

Contra um tipo #

--compare schema executa um ambiente (--env, ou o único do projeto) e confere cada resposta comparada com o tipo dela: o arquivo schema do bloco, ou então a operação OpenAPI do contrato da coleção.

order compare · local against each step's type
  login       POST /auth/login    200   not compared
  get order   GET  /orders/o-1    200   doesn't match the type Order at 2 paths
      $.currency    missing: the type requires it
      $.total       is a number, the type says string
      $.id          not named by the type (allowed)
1 of 1 compared step doesn't match its type in local.

O nome do tipo é o title do schema, ou então o nome do arquivo. Os campos que a resposta tem e o tipo não nomeia são uma nota, nunca uma diferença, a menos que o schema diga additionalProperties: false: uma API que acrescenta um campo não falha. O Ultraman lê um subconjunto do JSON Schema; as palavras-chave que ele não lê (patternProperties, prefixItems, if/then, um $ref para outro arquivo…) aparecem como "not checked" no passo, para que uma aprovação nunca afirme mais do que foi conferido. Com --compare schema, --contract off é recusado: ali o contrato é o tipo.

Pedindo o mesmo registro: reuse #

Por padrão, cada ambiente usa os próprios valores: o próprio login, os próprios ids. Isso serve para a estrutura. Para conferir que um registro foi replicado, o segundo ambiente precisa pedir o registro do primeiro:

compare:
  reuse: [order_id]   # no segundo ambiente, este passo é enviado com o order_id do primeiro

Só esse passo pega o valor; a execução do segundo lado segue com os próprios. --compare dev,stg pede ao stg o pedido do dev. Um valor feito a partir de um segredo nunca é levado, e um valor reutilizado não consegue mudar a request para outro host: o passo falha antes de enviar. A pergunta do terminal o nomeia ("in stg: send dev's order_id (reuse)").

O agente #

Um agente compara com run_compare, como numa execução: um cartão para iniciar e um cartão para entregar (veja agentes). Ele recebe o veredito, os status de cada passo e os JSONPaths que diferem, com o tipo de diferença e os tipos JSON, nunca um valor: você vê os valores na janela ou no terminal. O cartão de início nomeia o host de cada ambiente, as escritas comparadas, o reuse e um ambiente de produção ("prod is a production environment: this reads real data"). Uma query GraphQL e um recurso ou um prompt MCP são leituras ali, como um GET.

Um lado cuja própria verificação falhou é nomeado com o passo que o interrompeu, não com a mensagem da verificação, que pode citar a resposta. Um nome de campo que nenhum arquivo do projeto nomeia (um e-mail usado como chave, por exemplo) chega ao agente como o número dele no resultado, $.balances[field 2], porque as chaves de uma resposta podem ser os dados dela; a janela e o terminal mostram o nome.

A comparação de um agente nunca envia a um ambiente de produção um passo que não seja uma leitura, e nunca usa reuse com um ambiente de produção como fonte: não há como ele permitir nenhum dos dois, e uma comparação assim é recusada antes de qualquer cartão, dizendo para executá-la pela janela ou pelo terminal. Um ambiente que não está marcado mas aponta para o host de um ambiente de produção (uma cópia dos valores dele, a URL absoluta de um passo) conta aqui também como produção. Quando um agente salva um bloco compare:, o cartão diz o que o bloco deixa de fora ("compares only 2 fields", "ignores 3 fields: …").

Na janela #

Comparar com… à esquerda de Salvar envia o rascunho do editor, como Enviar, e compara a resposta dele:

  • Enviá-la também para outro ambiente: uma request para cada ambiente, cada uma com os próprios valores.
  • Contra um tipo: o arquivo de schema da request, ou a operação OpenAPI do contrato da coleção.
  • Meu último envio em um ambiente: nada é enviado; compara seus dois últimos envios ali. O histórico fica em cada computador, então um runner de CI novo não tem nenhum: ali, compare dois ambientes ou contra o tipo.

O menu diz o que cada ambiente precisa antes de você escolher, sem enviar nada: precisa de login quando uma request da coleção gera o valor que falta à comparação, precisa de order_id quando nada o gera, e nada quando está pronto. Vem antes do resto da linha (dados reais, pergunta antes de escrever).

O resultado abre sob a request: um cabeçalho com cada ambiente e a cor dele (um de produção em âmbar), uma frase ("The values differ at 2 paths."), e os caminhos que diferem, lidos como breadcrumbs (items › 2 › qty, cada JSONPath no tooltip; um passo dentro de um texto JSON aparece como (JSON)). Abrir as diferenças mostra as duas respostas Lado a lado ou Unificada.

Passe o mouse sobre um valor de uma resposta e abra Comparar… para Comparar este campo, Comparar só o tipo ou Ignorar este campo: cada um acrescenta o caminho ao bloco compare: da request, e a request fica não salva como em qualquer edição. Escolher o que comparar põe a resposta em um modo de seleção: marque os campos e Pronto grava only. Sem resposta ainda, os campos vêm do tipo; senão, envie-a uma vez antes. A aba Opções da request tem uma seção Comparar com as mesmas regras. Ela deixa três linhas à vista: Comparar do corpo (valores, forma ou nada), Campos a comparar e Campos a ignorar. O resto fica atrás de Mais: os campos comparados só por tipo, as regras de listas, o tipo da resposta, os headers e reuse (só aparece quando o arquivo o tem). Fechado, o Mais diz o que guarda numa linha de chips ("1 regra de lista", "tipo order"), então nada do que você definiu fica fora de vista; ele se abre sozinho enquanto algo dentro dele é inválido.

Uma pipeline (⋯ › Comparar em dois ambientes… no cabeçalho dela) ou uma coleção (o mesmo item no ⋯ dela na árvore) roda nos dois ambientes e mostra uma linha por request: toda request é comparada, pela própria regra ou, se não tiver, por Mesma estrutura. A linha termina com a regra que usou, como um chip, e com "o padrão" depois quando a request não tinha nenhuma. Em uma coleção, escolher outra regra no chip de uma linha abre essa request em uma aba com a regra não salva (nada é salvo nem reenviado); o chip de uma pipeline só nomeia a regra. Só o que difere mantém o resto recolhido.

Antes de enviar qualquer coisa, a janela pergunta o que o terminal pergunta: um segredo ou um arquivo indo pela primeira vez para o host do segundo ambiente, e um passo comparado que escreve, nomeado com os dois ambientes e as duas URLs, com Comparar as últimas respostas (nada é enviado) como primeira resposta. Um ambiente de produção diz isso na pergunta, e também um que aponta para o host de um ambiente de produção («qa aponta para o host de prod, um ambiente de produção»); o menu Comparar o marca ainda em âmbar. Contra um tipo, um passo que escreve em um ambiente de produção não é enviado pela janela: compare-o pelo terminal com --allow-write.

A primeira comparação: Mesma estrutura, o padrão #

Uma request sem bloco compare: é comparada por Mesma estrutura quando você escolhe um ambiente ou Meu último envio em: os mesmos campos e tipos, mesmo que os valores mudem, então os ids e as datas que cada ambiente cria não viram uma parede de diferenças. Nada é perguntado nem gravado: a request não fica com alterações não salvas.

A frase do resultado termina com a regra que usou: "local e staging respondem o mesmo. Comparado por Mesma estrutura, o padrão". A regra é um chip; clique para mudá-la:

  • Mesma estrutura: os mesmos campos e tipos; os valores podem mudar. Para conferir o que um deploy mudou. Grava compare: { body: shape }.
  • Dados replicados: os mesmos valores. Para conferir que os dados foram copiados. Grava compare: { body: value }.
  • Escolher o que comparar: marque o que deve ficar igual na resposta que a comparação mostra; Pronto grava only.

Escolher uma regra a grava na request (ela fica não salva, como em qualquer edição, e Salvar a mantém) e compara de novo por ela. Uma request com bloco próprio mostra a sua regra no chip sem "o padrão", e uma que escolhe ou ignora campos mostra Campos escolhidos. Ignorar este campo num resultado comparado pelo padrão mantém Mesma estrutura para o resto. As mesmas duas regras são cartões no topo de Opções enquanto a request não tem bloco. Uma verificação contra um tipo não tem chip: ela verifica o tipo.

Campos que mudam sozinhos #

Alguns campos mudam a cada chamada: um horário de criação, um id de request. Depois de uma comparação que difere, a janela os oferece para ignore com um clique, num aviso sob a frase:

  • Depois de Meu último envio em um ambiente, ela oferece todos os campos do corpo cujo valor mudou entre esses dois envios: "These 3 fields change by themselves: createdAt · requestId · meta › traceId."
  • Depois de uma comparação entre dois ambientes, ela oferece só as diferenças que também mudaram entre dois envios no primeiro ambiente, lidos do histórico dele (nada é enviado): "3 of the differences also change between two sends in dev: …". Uma diferença estável dentro de cada ambiente é a descoberta, então não é oferecida.

Ignorar estes 3 campos adiciona exatamente os campos que o aviso nomeia à lista ignore da request (a request fica não salva) e lê o resultado de novo a partir das duas respostas que o histórico já tem. Os limites:

  • Só um campo presente nos dois lados cujo valor mudou. Nunca um campo que existe de um lado só, um tipo que mudou, um header, o status, o corpo inteiro nem um item de lista em si (um campo dentro dos itens vale para esse campo de todos eles, items › each › seenAt).
  • Nunca um lugar que tinha um segredo (ficam "não comparados") nem um campo que você escolheu: um de only ou de shape, ou um objeto que o contém.
  • No máximo 8, todos nomeados. Com mais, diz "and N more change too" e o clique não os adiciona.
  • Nada com body: shape ou none, quando o status difere, nem contra um tipo.

Entrando no outro ambiente #

Cada ambiente usa os próprios valores: um token que o login de um ambiente gerou nunca vai para o outro. Quando um ambiente não tem um valor de que a request precisa e uma request da coleção o gera, escolher esse ambiente pergunta uma vez: Para comparar, primeiro envie login em staging. Ela lista cada request que será enviada com o método (até três, "POST login"), e quando os dois lados precisam de uma, elas vão na mesma pergunta.

  • Cancelar (primeiro e com o foco) não envia nada.
  • Enviar login e comparar envia cada request listada para o próprio ambiente, com os valores desse ambiente, e depois compara. O que elas geram fica só na sessão desse ambiente.
  • Digitar o valor em vez disso abre o diálogo de valores faltando, cujo título nomeia o ambiente quando ele não é o atual: "Falta 1 valor para enviar get order em staging".

Um ambiente de produção é nomeado num aviso dentro da pergunta ("prod é um ambiente de produção: isto envia POST login para lá."). Se uma request falha ou não dá o valor, nada mais é enviado e a aba dela abre com a resposta. Com mais de três requests, ou um valor que nada gera, aparece o diálogo de valores faltando de sempre. Um segredo indo pela primeira vez a um servidor continua pedindo o próprio sim.

O que mantém você seguro #

  • Você: os segredos de cada ambiente vão só para o host desse ambiente, com o consentimento de sempre; o segredo de um ambiente nunca chega ao outro.
  • Você: as duas respostas são ocultadas contra todo segredo do cofre que o projeto usa antes de serem comparadas ou mostradas, e um lugar que guardava um segredo fica "sem comparar", nunca "igual" nem "diferente" (ocultação). Os valores comuns em ultraman/local/envs/ são variáveis normais e não são ocultados: guarde um valor sensível no cofre.
  • Você: a pergunta antes de um login nomeia cada request, o método e o ambiente, produção incluída, e um sim cobre só o que ela listou. Cada ambiente guarda a própria sessão, e o "precisa de login" do menu é perguntado ao Ultraman sem enviar nada.
  • Você: a sugestão só nomeia campos das respostas que você já tem, nunca o lugar de um segredo nem um campo que você escolheu, e um clique adiciona exatamente os nomes que ela mostra.
  • Sua equipe: uma escrita comparada pergunta sempre, e um ambiente de produção recusa toda escrita a menos que você o nomeie com --allow-write; a comparação de um agente não consegue escrever lá de jeito nenhum (agentes).
  • CI: os resultados de uma comparação, no JUnit e na linha compare do --json, listam caminhos, tipos de diferença e tipos JSON, não os valores. O JUnit nomeia um lado cuja verificação falhou só pelo seu passo; as linhas do --json mantêm a mensagem da verificação, como em qualquer execução (no CI).
  • Limite: a caixa de produção vive num arquivo sob o git: ela protege contra uma escrita descuidada, não contra quem pode dar push no repositório (limites).
