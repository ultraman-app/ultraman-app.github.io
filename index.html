Ultraman

Build an API test the way you'd explain it: log in, create an order, check it shows up. Send single requests like in Postman, then watch every step run, put it under load, and let your agent use it.

In Terminal:

curl -fsSL https://ultraman-app.github.io/install.sh | sh

In a terminal:

curl -fsSL https://ultraman-app.github.io/install.sh | sh

In PowerShell:

irm https://ultraman-app.github.io/install.ps1 | iex

It installs the app and the ultraman command for your user, with everything they need inside, and checks each download against the release's signed checksums first. No account, no admin rights. Installing, updating and uninstalling

Ultraman never sends anything in an unsafe way without your explicit consent. A secret goes only to a host you approved, a file only from the folder you share, and nothing at all from a folder you haven't trusted. How it keeps you and your team safe

A pipeline is a file in your repo

name: create order
host: "{{env.api}}"
auth: { bearer: "{{token}}" }
steps:
  - request: login
    method: POST
    path: /auth/login
    auth: none
    json: { user: "{{env.test_user}}", password: "{{env.password}}" }
  - extract: token
    from: $login
    path: $.token
  - extract: user_id
    from: $login
    path: $.user_id
  - request: create
    method: POST
    path: /users/:userId/orders
    params: { userId: "{{user_id}}" }
    json: { sku: A-1, qty: 2 }
  - assert: status
    of: $create
    equals: 201
  - extract: order_id
    from: $create
    path: $.id
  - request: list
    method: GET
    path: /orders
  - assert: contains
    of: $list
    path: $[*].id
    value: "{{order_id}}"

Each step is a request, a value you take from a response, a check, a wait, a loop, a branch or a block you reuse, like logging in, and you build it in the window without writing YAML. The YAML lands in git next to your code, where the team reviews it in a pull request.

Run it and read what happened

From the window or a terminal, every step says what it did, and a failed check shows what it expected and what came back. Secret values show as [secret:name] in the output and in the history.

Checks that write themselves

Generate checks reads the response on screen and proposes its status and each field's type; you add a pattern or a JSON Schema where you need more. After every send, if a field went missing or changed type since the last time, a banner says so before your frontend finds out.

Read more about checks

# proposed by Generate checks
- assert: status
  equals: 200
- assert: type
  path: $.qty
  value: number
- assert: exists
  header: X-Request-Id
# added by hand
- assert: matches
  path: $.id
  value: /^ord_/
- assert: schema
  value: schemas/order.json

The response changed shape since the last send: $.qty removed, $.id: string → number

A fake API from what you already sent

Your frontend needs the API, and it's down, slow or not written yet: ultraman mock answers with the responses your sends got, and what it has no recording for can go on to the real API. Unless you say otherwise, it listens only on your machine and only pages on your machine can call it.

Read more about the mock server

Then see if it holds

The same pipeline, run by many users at once: steady, ramping up, in a spike or at a rate of new arrivals per second. The report starts with a verdict in plain words, then the numbers behind it.

Read more about load tests

Holds

p95 was 44.8 ms with up to 20 users and 602 requests per second, without errors.

One example run, against the demo API on a laptop: a 20-second ramp of create order, 4,040 runs, 12,120 requests. Your API and your machine give their own numbers.

Run it in CI

In GitHub Actions, ultraman-app/run-action runs your pipelines or a load test, writes a JUnit report and fails the job when a check or a threshold fails. Secrets come from your CI's secrets, and allow says which host each one may reach, so a changed pipeline can't send one anywhere else.

Read more about CI

- uses: actions/checkout@v4
  with:
    persist-credentials: false
- uses: ultraman-app/run-action@v1
  env:
    ULTRAMAN_SECRET_API_KEY: ${{ secrets.API_KEY }}
  with:
    args: --tag smoke
    env: staging
    allow: api_key=https://staging.example.com

Nothing unsafe goes out without your yes

Ultraman never sends anything in an unsafe way without your explicit consent. The first time a secret would go to a new host, or a file from outside ultraman/files would be sent, it stops and asks, and in a folder you haven't trusted it runs no git and sends nothing.

Read how it keeps you and your team safe

Your secrets stay locked

Saved secrets are encrypted on your machine under a master password only you know, and the vault locks again after 30 minutes without use. In an environment, shared values go to git, your own stay on this machine, and a secret leaves only a reference in the file.

Read more about the vault

$ ls ~/.ultraman
secrets.enc  vault.json
$ ultraman secret list
Master password:
api_token

Hand it to your agent

Point Claude Code or any MCP client at ultraman mcp: your agent finds your pipelines, reuses your blocks to build new ones and runs them. Each call waits for your OK in the window, and the agent can use a secret by name but never sees its value.

Read more about agents

{
  "mcpServers": {
    "ultraman": {
      "command": "ultraman",
      "args": ["mcp", "--project", "/path/to/your/repo"]
    }
  }
}

Why a download from the browser warns

The installers aren't signed by Apple or Microsoft, so one downloaded with a browser from the releases page makes macOS and Windows ask before it opens. The commands above don't mark the download as coming from the internet, and they check its signature themselves. What each system shows
